### 3. How Permissions Work (Fixing the `chmodPerm` Note)

Your image mentions `chmodPerm` twice. Here is exactly how permissions are applied:

1.  **Default creation permissions**:
    - When using `DirectoryOrCreate` or `FileOrCreate`, the kubelet creates the object with **default Linux permissions**:
      - Directory: `0755` (rwxr-xr-x) → Owner (root) can write, others can read/execute.
      - File: `0644` (rw-r--r--) → Owner (root) can write, others can only read.

2.  **The problem**: You cannot directly set custom permissions (e.g., `0777`) in the `hostPath` spec.
   ```yaml
   # ❌ This does NOT exist
   hostPath:
     path: /data
     type: DirectoryOrCreate
     perm: 0777
   ```

3.  **Solution to change permissions**:
   You can use an `initContainer` to adjust the permissions after the directory/file is created:
   ```yaml
   initContainers:
   - name: fix-permissions
     image: busybox
     command: ['sh', '-c', 'chmod 777 /host-data']
     volumeMounts:
     - name: host-storage
       mountPath: /host-data
   ```

### 💡 Summary Cheat Sheet

| Type | Existence Check | Creation Behavior |
| :--- | :--- | :--- |
| `""` (Empty) | Exists | None (legacy) |
| `DirectoryOrCreate` | Dir exists | **Creates** dir with `0755` |
| `Directory` | Dir exists | Fails if missing |
| `FileOrCreate` | File exists | **Creates** empty file with `0644` |
| `File` | File exists | Fails if missing |
| `Socket` | Socket exists | Fails if missing |

**The Golden Rule**: 
- Use **`DirectoryOrCreate`** when you want Kubernetes to "just make it work" (e.g., for logging agents).
- Use **`Directory`** or **`File`** when you are **certain** the host already has the resource (e.g., standard system paths like `/var/log`).
- If you need custom permissions (like `777`), **always use an `initContainer`** to run `chmod`, because the `hostPath` spec does not support it natively.
