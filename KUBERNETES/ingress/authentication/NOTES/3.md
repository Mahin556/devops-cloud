This is **not Basic Authentication**. It is **TLS Client Certificate Authentication (Mutual TLS or mTLS)** with the NGINX Ingress Controller.

In Basic Authentication:

* Client proves identity using **username/password**.

In mTLS:

* Client proves identity using a **client certificate** signed by a trusted Certificate Authority (CA).

---

# What is Mutual TLS (mTLS)?

In normal HTTPS:

```text
Client -----------------------> Server

Server sends its certificate
Client verifies the server
Encrypted communication begins
```

Only the **server** is authenticated.

---

In Mutual TLS:

```text
                    TLS Handshake

Client ------------------------------------> Server

            Server Certificate
<--------------------------------------------

Verify Server Certificate

            Client Certificate
-------------------------------------------->

Server verifies Client Certificate

Secure Connection Established
```

Now:

* Client verifies the server.
* Server verifies the client.

Both trust each other.

---

# Components

```text
                     CA
               (Certificate Authority)
                 /                 \
                /                   \
         signs server cert      signs client cert
               |                     |
        server.crt              client.crt

                     NGINX Ingress
                          |
                     verifies client
```

```

```

Private key of the CA.

Never share it.

server.crt

server.key

---

## Client Certificate

```
client.crt
```

Presented by the client.

---

## Client Key

```
client.key
```

Private key corresponding to `client.crt`.

# Step 1 — Create a Certificate Authority

```bash
openssl req \
-x509 \
-newkey rsa:4096 \
-sha256 \
-days 365 \
-nodes \
-keyout ca.key \
-out ca.crt \
-subj "/CN=Anvesh"
```

Meaning:

| Option      | Purpose                   |
| ----------- | ------------------------- |
| `-x509`     | Self-signed certificate   |
| `-newkey`   | Generate new key          |
| `rsa:4096`  | 4096-bit RSA key          |
| `-nodes`    | Don't encrypt private key |
| `-days 365` | Valid for one year        |
| `ca.key`    | Private CA key            |
| `ca.crt`    | Public CA certificate     |

Result:

```
ca.key
ca.crt
```

---

# Step 2 — Generate Server Certificate

Create key + CSR

```bash
openssl req \
-new \
-newkey rsa:4096 \
-keyout server.key \
-out server.csr \
-nodes \
-subj "/CN=ingress-domain.com"
```

Result

```
server.key
server.csr
```

---

# What is a CSR?

CSR means

```
Certificate Signing Request
```

Think of it as:

> "Please sign my certificate."

---

# Sign Server Certificate

```bash
openssl x509 \
-req \
-in server.csr \
-CA ca.crt \
-CAkey ca.key \
-set_serial 01 \
-out server.crt
```

Result

```
server.crt
```

Now

```
server.crt
```

is trusted by

```
ca.crt
```

---

# Step 3 — Generate Client Certificate

Generate CSR

```bash
openssl req \
-new \
-newkey rsa:4096 \
-keyout client.key \
-out client.csr \
-nodes \
-subj "/CN=Anvesh"
```

---

Sign it

```bash
openssl x509 \
-req \
-in client.csr \
-CA ca.crt \
-CAkey ca.key \
-set_serial 02 \
-out client.crt
```

Now

```
client.crt
```

is also trusted by

```
ca.crt
```

# Kubernetes Secret

Create Secret

```bash
kubectl create secret generic tls-secret \
--from-file=tls.crt=server.crt \
--from-file=tls.key=server.key \
--from-file=ca.crt=ca.crt
```

Contains

```
tls.crt
tls.key
ca.crt
```

Notice

```
client.crt
```

is **NOT** stored.

Clients keep their own certificate.

# Ingress

Typical configuration

```yaml
metadata:
  annotations:

    nginx.ingress.kubernetes.io/auth-tls-secret: default/tls-secret

    nginx.ingress.kubernetes.io/auth-tls-verify-client: "on"

    nginx.ingress.kubernetes.io/auth-tls-pass-certificate-to-upstream: "true"

spec:
  tls:
  - hosts:
    - ingress-domain.com

    secretName: tls-secret
```

# Difference between Basic Auth and mTLS

| Feature          | Basic Auth           | mTLS                                    |
| ---------------- | -------------------- | --------------------------------------- |
| Authentication   | Username + Password  | Client Certificate                      |
| Secret           | htpasswd             | CA Certificate                          |
| Credentials sent | Authorization header | TLS handshake                           |
| Encryption       | Requires HTTPS       | Built into TLS                          |
| Identity         | User                 | Certificate holder                      |
| Strong security  | Medium               | High                                    |
| Typical use      | Internal apps        | APIs, microservices, enterprise systems |

---

# Real-world use cases

mTLS is commonly used for:

* Service-to-service authentication (microservices)
* Banking APIs
* Healthcare systems
* Kubernetes admission webhooks
* Istio and Linkerd service meshes
* Enterprise B2B integrations
* Zero Trust networking

Unlike Basic Authentication, mTLS provides **cryptographic proof of identity**. Only clients that possess a certificate signed by the trusted CA can connect, making it much harder for unauthorized clients to access the protected application.
