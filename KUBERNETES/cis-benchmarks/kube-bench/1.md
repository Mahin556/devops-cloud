# Kubernetes CIS Benchmark & kube-bench — Complete CKS Notes

This scenario is about **checking the security posture of a Kubernetes cluster against the CIS Kubernetes Benchmark** using **kube-bench**, understanding failed checks, and remediating them.

The core CKS workflow is:

```text
CIS Benchmark
     ↓
kube-bench
     ↓
Scan Kubernetes cluster
     ↓
PASS / FAIL / WARN
     ↓
Find failed check
     ↓
Read remediation
     ↓
Fix Kubernetes configuration
     ↓
Run kube-bench again
     ↓
Verify PASS
```

---

# 1. What is CIS?

The transcript refers to **CIS** and its Kubernetes Benchmark.

> **CIS = Center for Internet Security**

CIS publishes security benchmarks that provide recommended security configurations for various technologies.

For Kubernetes, the **CIS Kubernetes Benchmark** provides recommendations for securely configuring Kubernetes components.

Think of it as:

```text
Kubernetes
     ↓
Security best practices
     ↓
CIS Kubernetes Benchmark
     ↓
Recommended secure configuration
```

The benchmark contains recommendations for areas such as:

* Control plane
* kube-apiserver
* kube-controller-manager
* kube-scheduler
* etcd
* Worker nodes
* kubelet
* Kubernetes configuration
* Authentication/authorization-related settings

The transcript describes the benchmark as a large document containing recommendations for Kubernetes control-plane and node components.

---

# 2. What is a Security Benchmark?

A benchmark is essentially a collection of security checks/recommendations.

For example:

```text
Check:
Is profiling disabled?

Expected:
profiling = false
```

Another check might ask:

```text
Is a particular service account being used appropriately?
```

Or:

```text
Is a security-sensitive API-server option configured correctly?
```

So instead of manually checking hundreds of Kubernetes security settings, you can use a tool that performs these checks automatically.

---

# 3. What is kube-bench?

**kube-bench** is an open-source tool from Aqua Security that checks Kubernetes against the **CIS Kubernetes Benchmark**.

The transcript describes it as a tool that checks whether Kubernetes has been deployed according to the security best practices defined by the CIS Kubernetes Benchmark.

Think:

```text
CIS Kubernetes Benchmark
          |
          v
     kube-bench
          |
          v
 Kubernetes cluster
          |
          v
 Security checks
```

---

# 4. What Does kube-bench Actually Do?

It examines the Kubernetes configuration and checks whether it satisfies various CIS recommendations.

For example:

```text
CIS Recommendation
       ↓
"Profiling should be disabled"
       ↓
kube-bench checks configuration
       ↓
Is profiling false?
       |
   +---+---+
   |       |
  Yes      No
   |       |
 PASS     FAIL
```

So kube-bench is essentially an **automated CIS compliance checker**.

# 7. Example CIS Check — Profiling

The transcript uses **profiling** as an example.

The recommendation is essentially:

```text
Profiling should be disabled
```

For example:

```yaml
--profiling=false
```

Why?

Profiling can expose information useful for performance analysis, but it can also expose sensitive program/system information.

The transcript explains that profiling generates program data that could potentially be exploited to uncover system and program information.

# 10. What Does FAIL Mean?

A failed check means:

> The current Kubernetes configuration does not satisfy the corresponding CIS recommendation.

For example:

```text
Check:
1.2.5

Recommendation:
profiling should be false

Current configuration:
profiling=true

Result:
FAIL
```

You then need to determine how to remediate it.

---

# 11. What Does WARN Mean?

A warning doesn't necessarily mean:

> "Your cluster is definitely insecure."

It means kube-bench couldn't simply classify the check as a straightforward pass/fail or the condition requires attention.

The important CKS workflow is:

```text
FAIL/WARN
    ↓
Read the check
    ↓
Understand what is being tested
    ↓
Check remediation
```

---

# 12. kube-bench Gives You Remediation

This is one of the most useful features for the CKS.

Suppose you have:

```text

```

kube-bench can provide a **remediation** describing what should be changed.

For example:

```text

Edit the kube-apiserver manifest and set:

--profiling=false
```

So you don't necessarily need to memorize every CIS check.

Instead:

```text

      ↓

      ↓
Read remediation
      ↓
Make the required change
```

# 14. Example: Fixing a Failed Check

Suppose kube-bench reports:

```text
1.2.5 FAIL
```

and tells you:

```text
--profiling should be false
```

First inspect:

```bash
vi /etc/kubernetes/manifests/kube-apiserver.yaml
```

Find the API-server command section:

```yaml
spec:
  containers:
  - command:
    - kube-apiserver
```

Then add/change:

```yaml
- --profiling=false
```

So you have:

```yaml
- command:
  - kube-apiserver
  - --profiling=false
```

---

# 15. Why Does the API Server Restart?

In kubeadm-style Kubernetes clusters, the API server is commonly managed as a **static Pod**.

Its manifest is:

```text
/etc/kubernetes/manifests/kube-apiserver.yaml
```

When you modify that file:

```text
kube-apiserver.yaml
       ↓
kubelet detects change
       ↓
API-server Pod recreated
       ↓
new configuration applied
```

Therefore, immediately after changing the manifest, Kubernetes may temporarily be unavailable.

You might see:

```text
connection refused
```

when running:

```bash
kubectl get nodes
```

Don't immediately assume you've destroyed the cluster.

Give the API server time to restart.

---

# 16. Verify the API Server

After making the change:

```bash
kubectl get nodes
```

or:

```bash
kubectl get pods -n kube-system
```

Wait until the API server is healthy again.

Then rerun kube-bench.

# 35. CKS Exam Trap — Component Restart

After editing a static Pod manifest:

```text
manifest changed
      ↓
kubelet detects it
      ↓
static Pod recreated
      ↓
component restarts
```

# 36. CKS Exam Trap — Backup

When making significant changes to a control-plane manifest, a backup is a useful safety measure:

```bash
cp /etc/kubernetes/manifests/kube-apiserver.yaml \
   /etc/kubernetes/manifests/kube-apiserver.yaml.bak
```

Then make your change.

This gives you a recovery path if you make a mistake.
