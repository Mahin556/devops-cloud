## What is RWX (ReadWriteMany)?

**ReadWriteMany (RWX)** is a Kubernetes access mode that allows **multiple pods on different nodes** to mount the same persistent volume and perform both read and write operations simultaneously.

Unlike RWO (ReadWriteOnce), which restricts access to a single node, RWX enables true shared storage across your entire cluster.

---

## Which Storage Solutions Support RWX?

**RWX is NOT supported by standard block storage** like AWS EBS, GCP Persistent Disk, or Azure Disk. You need **shared file storage** solutions:

| Storage Type | Examples |
| :--- | :--- |
| **Network File System** | NFS (self-managed or managed) |
| **Cloud Managed File Storage** | AWS EFS, GCP Filestore, Azure Files, Scaleway File Storage (SFS) |
| **Distributed File Systems** | CephFS, GlusterFS |
| **Kubernetes-Native Solutions** | Portworx, LINSTOR, OpenEBS (with NFS provisioner) |

## How to Use RWX: Step-by-Step

### Option 1: Dynamic Provisioning (Recommended)

With a RWX-capable StorageClass (e.g., `cephfs`, `sfs-standard`), you simply create a PVC that requests `ReadWriteMany`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-storage-pvc
spec:
  accessModes:
  - ReadWriteMany          # ← Key: Request RWX
  resources:
    requests:
      storage: 100Gi
  storageClassName: cephfs # ← Must be RWX-capable
```

Apply it:
```bash
kubectl apply -f pvc.yaml
```

Check the PVC status:
```bash
kubectl get pvc
# NAME                 STATUS   VOLUME     CAPACITY   ACCESS MODES
# shared-storage-pvc   Bound    pvc-xxx    100Gi      RWX
```



---

### Option 2: Static Provisioning (Manual PV Creation)

If you have an existing NFS share, create a PV and PVC manually:

**1. Create the PersistentVolume:**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-storage-pv
spec:
  capacity:
    storage: 250Gi
  accessModes:
  - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.168.1.100    # Your NFS server IP
    path: /exports/data      # NFS export path
  mountOptions:
  - vers=4.1
  - hard
  - noatime
```

**2. Create the PersistentVolumeClaim:**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nfs-storage-pvc
spec:
  accessModes:
  - ReadWriteMany
  resources:
    requests:
      storage: 250Gi
  volumeName: nfs-storage-pv
  storageClassName: ""       # Empty = static provisioning
```

## Deploying Multiple Pods with RWX

Here's a complete example with a Deployment that has 3 replicas all sharing the same RWX volume:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-logs-pvc
spec:
  accessModes:
  - ReadWriteMany
  resources:
    requests:
      storage: 50Gi
  storageClassName: cephfs
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: log-collector
spec:
  replicas: 3                    # All 3 pods share the same volume
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      containers:
      - name: collector
        image: my-log-collector:latest
        volumeMounts:
        - name: shared-storage
          mountPath: /var/logs   # All pods write logs here
      volumes:
      - name: shared-storage
        persistentVolumeClaim:
          claimName: shared-logs-pvc
```

**What happens:**
- Pod 1 (Node A) → Writes to `/var/logs/app.log` ✅
- Pod 2 (Node B) → Reads from `/var/logs/app.log` ✅ (sees Pod 1's writes)
- Pod 3 (Node C) → Appends to `/var/logs/app.log` ✅

All 3 pods can read and write to the same files simultaneously.

## Testing RWX Concurrent Access

You can test RWX with a simple busybox example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: rwx-test-pvc
spec:
  accessModes:
  - ReadWriteMany
  resources:
    requests:
      storage: 1Gi
  storageClassName: cephfs
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rwx-test
spec:
  replicas: 2
  selector:
    matchLabels:
      app: rwx-test
  template:
    metadata:
      labels:
        app: rwx-test
    spec:
      containers:
      - name: busybox
        image: busybox
        command: ["/bin/sh"]
        args: ["-c", "sleep 3600"]
        volumeMounts:
        - name: shared
          mountPath: /data
      volumes:
      - name: shared
        persistentVolumeClaim:
          claimName: rwx-test-pvc
```

After deployment, test shared access:
```bash
# Write from Pod 1
kubectl exec -it rwx-test-xxx-1 -- sh -c "echo 'Hello from Pod 1' > /data/test.txt"

# Read from Pod 2 (sees the same file!)
kubectl exec -it rwx-test-xxx-2 -- cat /data/test.txt
# Output: Hello from Pod 1
```

## Advanced: Using `subPath` with RWX

With `subPath`, multiple containers (or pods) can mount different subdirectories from the **same** RWX PVC:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: multi-service
spec:
  replicas: 1
  template:
    spec:
      containers:
      - name: web
        image: nginx
        volumeMounts:
        - name: shared-data
          mountPath: /var/www/html
          subPath: html          # Mounts PVC:/html → /var/www/html
      - name: logger
        image: fluentd
        volumeMounts:
        - name: shared-data
          mountPath: /var/log
          subPath: logs          # Mounts PVC:/logs → /var/log
      volumes:
      - name: shared-data
        persistentVolumeClaim:
          claimName: shared-fs-pvc
```

This allows logical partitioning of a single shared volume.

## ⚠️ Critical Considerations

### 1. **Application Must Handle Concurrent Writes**
Kubernetes does **not** provide file locking. If two pods write to the same file simultaneously, data corruption can occur. Your application must handle this (e.g., use `flock`, database-level locks, or append-only logging).

### 2. **Performance Overhead**
RWX storage (especially NFS) has higher latency than local block storage. It's not suitable for high-throughput databases.

### 3. **StorageClass Must Support RWX**
Not all StorageClasses support RWX. Check your cloud provider's documentation:
- **AWS**: Use EFS (not EBS)
- **GCP**: Use Filestore (not Persistent Disk)
- **Azure**: Use Azure Files (not Managed Disk)

### 4. **PVC Binding Issues**
If your PVC stays `Pending`:
```bash
kubectl describe pvc shared-storage-pvc
```
Common causes:
- No StorageClass supports RWX
- StorageClass name is incorrect
- Insufficient permissions or quota

### 5. **Cross-Namespace Sharing**
Some solutions (like Trident) allow sharing RWX volumes across namespaces.

## Troubleshooting RWX

| Issue | Likely Cause | Solution |
| :--- | :--- | :--- |
| PVC stuck `Pending` | StorageClass doesn't support RWX | Use a different StorageClass (NFS/EFS/CephFS) |
| Pods can't mount | NFS server unreachable | Check network connectivity and firewall rules |
| Permission denied | Wrong NFS export permissions | Adjust NFS export options (e.g., `no_root_squash`) |
| Slow performance | Network latency | Use local SSD caching or choose a faster storage tier |

## Summary

| Aspect | Details |
| :--- | :--- |
| **What it does** | Allows multiple pods on different nodes to read/write the same volume |
| **When to use** | Shared logs, static assets, collaborative workloads, shared configs |
| **Storage required** | NFS, EFS, CephFS, Filestore, or other shared file systems (NOT block storage) |
| **How to request** | `accessModes: - ReadWriteMany` in PVC |
| **Key risk** | Concurrent writes can corrupt data—application must handle locking |
| **Testing** | Use busybox pods to verify read/write across replicas |

**Bottom line:** RWX is powerful for sharing data across pods, but **choose the right storage backend** and **ensure your application can handle concurrent access**.
