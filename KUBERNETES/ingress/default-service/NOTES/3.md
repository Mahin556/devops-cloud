This section is describing **two different uses of a default backend**, which can be confusing. Let's break it down.

---

## 1. Ingress with **no rules**

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo
spec:
  ingressClassName: nginx
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
```

There are **no `rules`**.

This means:

> **Every request** goes to `default-service`, regardless of host or path.

Examples:

| Host              | Path     | Backend           |
| ----------------- | -------- | ----------------- |
| `app.example.com` | `/`      | `default-service` |
| `google.com`      | `/abc`   | `default-service` |
| `anything`        | `/login` | `default-service` |

This is what the documentation means by:

> "An Ingress with no rules sends all traffic to a single default backend."

---

## 2. Ingress with rules

Example:

```yaml
spec:
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80

  rules:
  - host: app.example.com
    http:
      paths:
      - path: /login
        backend:
          service:
            name: login-service

      - path: /payment
        backend:
          service:
            name: payment-service
```

Routing works like this:

```text
Request
   │
   ▼
Match host?
   │
   ├── No ─────────────► defaultBackend
   │
   ▼
Match path?
   │
   ├── Yes ───────────► Matching Service
   │
   └── No ────────────► defaultBackend (if the controller implements this behavior)
```

Examples:

| Host              | Path       | Result            |
| ----------------- | ---------- | ----------------- |
| `app.example.com` | `/login`   | `login-service`   |
| `app.example.com` | `/payment` | `payment-service` |
| `unknown.com`     | `/`        | `default-service` |
| `unknown.com`     | `/abc`     | `default-service` |

For unmatched paths on a **matched host**, the exact behavior depends on the Ingress controller implementation.

---

## 3. "The defaultBackend is conventionally a configuration option of the Ingress controller"

This refers to the controller itself.

For example, the ingress-nginx controller has a built-in default backend. If you don't specify one in your Ingress, the controller typically returns its own default response (often a 404 page).

```text
               Ingress Controller
                     │
        ┌────────────┴────────────┐
        │                         │
  Your Ingress rules         Built-in default backend
```

---

## 4. "If none of the hosts or paths match..."

Imagine you have:

```yaml
rules:
- host: app.example.com
  paths:
  - /login
```

Requests behave like this:

| Request                   | Matches? | Backend                                                                                           |
| ------------------------- | -------- | ------------------------------------------------------------------------------------------------- |
| `app.example.com/login`   | ✅        | `login-service`                                                                                   |
| `app.example.com/payment` | ❌ path   | Depends on the controller; may use the configured default backend or return its default response. |
| `test.example.com/login`  | ❌ host   | `defaultBackend` (if configured) or the controller's default backend                              |

---

## Visual summary

```text
                     Request
                        │
                        ▼
               Any rule matches?
                /              \
             Yes                No
             │                  │
             ▼                  ▼
      Matching Service     defaultBackend
```

---

### One important note

The sentence:

> "If none of the hosts or paths match the HTTP request in the Ingress objects, the traffic is routed to your default backend."

describes the **intended fallback behavior**. However, the Kubernetes Ingress API leaves some matching details to the **Ingress controller implementation**. Different controllers (or even different versions of the same controller) may handle unmatched paths slightly differently.

For **ingress-nginx**, it's useful to think of `spec.defaultBackend` as the **global fallback** for requests that don't match the configured Ingress rules handled by that controller.
