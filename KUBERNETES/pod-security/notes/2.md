### 1. The Core Philosophy: Prevention vs. Mitigation

| Approach | Goal | Action |
| :--- | :--- | :--- |
| **Prevention** | Stop vulnerabilities from entering the system. | Use minimal base images, scan dependencies, and write secure code. |
| **Mitigation** | Limit the damage if a vulnerability is exploited. | Restrict permissions, make the filesystem read-only, and drop capabilities. |

vulnerability are guarantee they will arise so we need to limit the damage if a vulnerability is exploited(limit the attack surface)--> To do it we need to run a secure pods.

### 2. Weakness #1: Running as `root` (Privileged User)

**The Problem:**
By default, containers run as the `root` user (UID 0) inside the container. If an attacker exploits your web server, they inherit `root` privileges. They can:
- Run `apt-get update` and install crypto-miners, `curl`, or backdoors.
- Set up SSH daemons (`sshd`) to maintain persistent access.
- Modify system files.

**The Solutions:**

**Option A: Kubernetes Security Context (`runAsUser`)**
Add a `securityContext` to the Pod spec to force a specific non-root UID. The video sets `runAsUser: 1000`.
```yaml
apiVersion: v1
kind: Pod
spec:
  securityContext:
    runAsNonRoot: true   # Ensures the container won't run as root(enforce container run as non-root user, either non-root user specified in dockerfile or used a runAsUser: 1000 flag)
    runAsUser: 1000      # Forces the user ID
```
*Impact*: The attacker now gets `Permission denied` errors when trying to `apt-get update`.

**Option B: Dockerfile `USER` Instruction (Recommended)**
Build the user directly into the image so you can test locally.
```dockerfile
FROM python:3.14-alpine
RUN adduser -D worker   # Alpine Linux command
USER worker             # Switch to non-root user
WORKDIR /app
COPY . .
```
*Benefit*: You test exactly how it runs in production, right on your local machine.

### 3. Weakness #2: Pre-installed Tools in Base Images

**The Problem:**
Even if you run as non-root, images like `python:3.14` (based on Debian/Ubuntu) come pre-packaged with `bash`, `curl`, `wget`, and `ping`. An attacker *doesn't need to install* anything—they can use these built-in tools to download malware, exfiltrate data, or scan your internal network.

**The Solutions:**

- **Use `-slim` variants**: `python:3.14-slim` (removes many unnecessary packages).
- **Use `-alpine` variants**: `python:3.14-alpine` (uses a minimal musl libc base, significantly smaller).
- **Result**: When you `kubectl exec` into the pod, you get `error: exec: "bash": executable file not found`. `curl` is also absent, forcing the attacker to write raw sockets (much harder).

### 4. Weakness #3: Privilege Escalation (SUID/`sudo`)

**The Problem:**
Even as a non-root user, processes can use `setuid` binaries (like `sudo`) or Unix capabilities to elevate back to root. The `sudo` command might not be installed, but other SUID binaries could exist.

**The Solution:**
Set `allowPrivilegeEscalation: false` in the container's security context. This prevents any process inside the container from gaining more privileges than its parent process (which is non-root).
```yaml
spec:
  containers:
  - name: my-app
    securityContext:
      allowPrivilegeEscalation: false
```

---

### 5. Weakness #4: Writable Filesystem (Malware/Backdoors)

**The Problem:**
If an attacker achieves Remote Code Execution (RCE), they can write malicious scripts, crypto-miner binaries, or backdoor SSH keys to the container's filesystem. Most microservices are stateless—they only need to read configs and environment variables.

**The Solution:**
Set `readOnlyRootFilesystem: true`. This makes the entire container root filesystem immutable.
```yaml
spec:
  containers:
  - name: my-app
    securityContext:
      readOnlyRootFilesystem: true
```
*Impact*: The attacker cannot write files to the disk. They get `Read-only file system` errors.

*Note*: If your app needs to write to `/tmp`, mount a writable `emptyDir` volume there.
```yaml
volumeMounts:
- name: tmp-vol
  mountPath: /tmp
volumes:
- name: tmp-vol
  emptyDir: {}
```

### 6. Weakness #5: Unnecessary Linux Capabilities

**The Problem:**
Linux splits "root" privileges into discrete chunks called **Capabilities** (e.g., `CAP_NET_BIND_SERVICE` to bind to ports <1024, `CAP_SYS_TIME` to change the system clock). Microservices rarely need any of these, but Docker grants a default set (roughly 14 capabilities) unless dropped.

**The Solution:**
Drop **all** capabilities. The syntax `drop: ["ALL"]` removes every capability.
```yaml
spec:
  containers:
  - name: my-app
    securityContext:
      capabilities:
        drop: ["ALL"]
```
*Impact*: The attacker cannot perform privileged system calls, change network interfaces, mount filesystems, or alter system time. This cripples most privilege escalation attempts.

### 7. The Ultimate Hardening: Scratch/Distroless Images

**The Problem:**
Even Alpine Linux has a shell (`/bin/sh`) and an APK package manager. An attacker could potentially leverage these.

**The Solution (For Compiled Languages like Go/Rust):**
Use `FROM scratch`. Scratch is an **empty image**. It contains absolutely nothing—no shell, no package manager, no CA certificates, no filesystem.
Container basically a filesystem that container all thing that req to run application.
But most of the binaries are not req to run application, so we can choose more lightweight base image.
```dockerfile
FROM scratch
COPY my-go-app /my-go-app
CMD ["/my-go-app"]
```
*Impact*:
- No `kubectl exec` shell (you can't run `sh` or `bash`).
- No curl/wget.
- No way to install tools.
- **Massively reduced attack surface**.

*Limitation*: This only works for statically compiled binaries (Go, Rust, Zig, etc.). Interpreted languages (Python, Node.js, Java) require a runtime filesystem.

### Consolidated "Secure Pod" YAML Example

Here is the full manifest combining all the hardening techniques discussed in the video:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-beast
spec:
  # Pod-level security context
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 1000   # Allows writing to specific mounted volumes if needed

  containers:
  - name: app
    image: myapp:alpine    # Use Alpine or Scratch for minimal tools

    # Container-level security context
    securityContext:
      allowPrivilegeEscalation: false  # Prevents sudo/setuid
      readOnlyRootFilesystem: true     # No writing malware to disk
      capabilities:
        drop: ["ALL"]                  # Removes all Linux capabilities

    ports:
    - containerPort: 8080

    # If you need a writable temp directory
    volumeMounts:
    - name: tmp-storage
      mountPath: /tmp

  volumes:
  - name: tmp-storage
    emptyDir: {}
```

### Summary of the Transformation

| Feature | Innocent Pod (Insecure) | Secure Beast (Hardened) |
| :--- | :--- | :--- |
| **User** | `root` (UID 0) | Non-root (UID 1000) |
| **Base Image** | Debian/Ubuntu (giant) | Alpine or Scratch (minimal) |
| **Pre-installed Tools** | `bash`, `curl`, `apt-get` | None (or only `sh`) |
| **Privilege Escalation** | Allowed (via `sudo`/setuid) | Disabled |
| **Root Filesystem** | Writable | Read-Only |
| **Linux Capabilities** | 14 default capabilities | **No capabilities** |

By applying these settings, you **don't** guarantee that your pod will never be hacked—but you ensure that if it is, the attacker's options are severely limited. They can't install tools, can't write files, can't escalate privileges, and can't exploit the kernel. This is the essence of **Zero Trust security** applied to Kubernetes workloads.
