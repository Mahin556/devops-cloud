---

### 🎯 What Topology Spread Constraints Do

They force the Kubernetes scheduler to **spread your Pods evenly** across failure domains (like nodes, zones, or regions) based on a **mathematical rule**.

---

### 🧮 The Core Rule (How Kubernetes "Decides")

The scheduler follows this exact logic:

1. **Define a Domain**: You pick a label key (e.g., `topology.kubernetes.io/zone`). Each unique value of that label is a "domain" (e.g., `us-east-1a`, `us-east-1b`).
2. **Count Existing Pods**: The scheduler counts how many Pods (matching your `labelSelector`) already exist in each domain.
3. **Calculate the "Skew"**: The `skew` is the difference between the **most populated** domain and the **least populated** domain.
4. **Enforce `maxSkew`**: The scheduler will **only** place the new Pod on a domain if doing so does **not** make the new skew exceed your `maxSkew` value.

---

### 🔑 The Two Decision Modes (`whenUnsatisfiable`)

| Setting | What Kubernetes Decides |
| :--- | :--- |
| **`DoNotSchedule`** | **Hard rule**. If placing the Pod would break the `maxSkew` rule, the scheduler **refuses** to schedule the Pod. It stays `Pending`. |
| **`ScheduleAnyway`** | **Soft rule**. If placing the Pod would break the `maxSkew` rule, the scheduler **still schedules it**, but it prioritizes domains that would minimize the skew the most. |

---

### 📝 A Simple Example

**Scenario**: 3 Nodes in 1 Zone. `maxSkew: 1`, `topologyKey: kubernetes.io/hostname`.

| Node A | Node B | Node C | New Pod Decision |
| :--- | :--- | :--- | :--- |
| 0 Pods | 0 Pods | 0 Pods | **Any Node** (skew stays 1). |
| 2 Pods | 1 Pod | 0 Pods | **Node C** (2-0 = 2; placing there makes skew 2 > 1? Wait. Let's do math: If I put on Node C, counts become 2,1,1. Max=2, Min=1, Skew=1. Allowed!). |
| 2 Pods | 2 Pods | 0 Pods | **Node C** (2-1=1? Actually 2-0=2. If put on Node C: 2,2,1 -> Skew=1. Allowed). |
| 2 Pods | 2 Pods | 1 Pod | **Nowhere** (If put on any, counts become 3,2,1 -> Skew=2 > 1. Rejected if `DoNotSchedule`). |

---

### 🆚 Why it's better than `podAntiAffinity`

| Feature | Topology Spread Constraints | podAntiAffinity |
| :--- | :--- | :--- |
| **Precision** | Controls **how many** Pods can be in a domain (via `maxSkew`). | Only says "don't be on the same node" (all-or-nothing). |
| **Flexibility** | Allows a specific number of Pods per domain (e.g., max 2 per zone). | Hard stop (0 or 1 per domain). |

---

### 🛠️ Minimal Working YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone   # Spread across zones
    whenUnsatisfiable: DoNotSchedule           # Strict rule
    labelSelector:
      matchLabels:
        app: my-app                           # Only count Pods with this label
  containers:
  - name: nginx
    image: nginx
```

---

### 💡 The Golden Rule to Remember
**Topology Spread Constraints** = **Count the Pods, calculate the difference (skew), and only schedule if the difference stays within your limit.** This ensures your application survives a zone or node failure while using cluster capacity efficiently.
