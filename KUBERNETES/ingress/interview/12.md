**This document is incorrect** — and directly contradicts what we established in our previous conversation about NGINX Ingress. The document describes the flow as `Ingress → Service ClusterIP → kube-proxy → Pod`, but that is **NOT how NGINX Ingress Controller actually works**.

## What the Document Gets Wrong

The document claims NGINX generates this config:
```nginx
# Document says NGINX does this:
upstream api_service_backend {
    server api-service.default.svc.cluster.local:80;  # ← Service DNS name
}
```

**This is factually wrong.** The actual NGINX config generated looks like this:

```nginx
# What NGINX Ingress ACTUALLY generates:
upstream api_service {
    server 10.244.1.10:8080;   # ← real Pod IP
    server 10.244.1.11:8080;   # ← real Pod IP
    server 10.244.1.12:8080;   # ← real Pod IP
    # Pod IPs sourced from EndpointSlice API directly
}
```

This is confirmed directly by the official NGINX Ingress documentation: The Ingress-Nginx Controller does not use Services to route traffic to the pods. Instead it uses the Endpoints API in order to bypass kube-proxy to allow NGINX features like session affinity and custom load balancing algorithms.

And from internal implementation analysis: ingress-nginx refers to the Service resource to find backends, but in the actual routing configuration, it writes the raw Pod IPs obtained from EndpointSlice, not the Service ClusterIP. This avoids iptables DNAT overhead and allows it to control L7 features like Session Affinity itself.

## The Correct Flow

```
Document says:
Client → Ingress → DNS lookup → Service ClusterIP → kube-proxy iptables → Pod

Reality (NGINX Ingress):
Client → Ingress controller
              │
              │ watches EndpointSlice API directly
              │ builds upstream pool with real pod IPs
              │
              ▼
            Pod IP (directly)
              ↑ kube-proxy NOT in this path at all
```

## Why the Document's "Problems with Direct Pod Routing" Section is Also Wrong

The document argues NGINX can't route to pods directly because pod IPs change. This logic is exactly wrong — NGINX Ingress handles this by **subscribing to the EndpointSlice API**, so when a pod restarts with a new IP:

```
Pod restarts → new IP assigned
     ↓
EndpointSlice controller updates the EndpointSlice object
     ↓
NGINX Ingress controller's informer detects the change (within 1-2 seconds)
     ↓
NGINX upstream pool is updated with the new pod IP
     ↓
NGINX regenerates its config and reloads
```

This is **exactly why** NGINX bypasses kube-proxy — it handles pod lifecycle tracking itself, which lets it implement features kube-proxy can't: session affinity, least-connections, custom load balancing algorithms, canary weights. kube-proxy only does random/round-robin via iptables probability rules.

## The One Thing the Document Gets Right

The Service resource IS still needed — but not for traffic routing: The Ingress controller looks at the Service resource to check the label selector, and from there traces the EndpointSlice to find Pod IPs.

Service is used for **discovery** (which pods belong to this backend), not for actual packet forwarding.
