A **multi-target Dockerfile** is a single Dockerfile that defines multiple named build stages, allowing you to build different variations of an image from the same file using the `--target` flag. 

This is often confused with **multi-stage builds**, but they serve different purposes:

| Feature | Multi-Stage Build | Multi-Target Build |
| :--- | :--- | :--- |
| **Purpose** | Optimize final image size by discarding build tools | Produce multiple distinct images from one Dockerfile |
| **Mechanism** | `COPY --from=previous_stage` to copy only artifacts | `--target` flag selects which stage to build |
| **Output** | One final slim image | Multiple possible images (dev, prod, test, etc.) |

A multi-target Dockerfile **is** a multi-stage Dockerfile, but not all multi-stage Dockerfiles are multi-target. The key difference is that multi-target explicitly defines stages meant to be **built and shipped** as separate images, not just intermediate layers.

## All Use Cases of Multi-Target Dockerfiles

### 1. Development vs. Production Images

**The Problem:** Development needs debug tools, hot-reload, and extra dependencies. Production needs a slim, secure image without any of that.

**The Solution:** One Dockerfile with a `dev` target and a `prod` target.

```dockerfile
# ========== BASE ==========
FROM python:3.14-slim AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

# ========== DEVELOPMENT ==========
FROM base AS dev
RUN pip install debugpy pytest  # dev-only dependencies
ENV FLASK_ENV=development
CMD ["python", "-m", "debugpy", "--listen", "0.0.0.0:5678", "-m", "flask", "run", "--host=0.0.0.0", "--port=5000"]

# ========== PRODUCTION ==========
FROM base AS prod
RUN pip install gunicorn
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

**Build Commands:**
```bash
docker build --target dev -t myapp:dev .
docker build --target prod -t myapp:latest .
```

### 2. Testing / CI Images

**The Problem:** You want to run tests inside a container with the exact same code that will go to production, plus test frameworks and coverage tools.

**The Solution:** A `test` target that extends production with test dependencies.

```dockerfile
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .

FROM base AS test
RUN npm install --save-dev jest @testing-library/react
CMD ["npm", "test", "--", "--coverage"]

FROM base AS prod
RUN npm run build
CMD ["npm", "start"]
```

**Build & Run:**
```bash
docker build --target test -t myapp:test .
docker run --rm myapp:test   # Runs tests in CI
```

**Why this is powerful:** You test **exactly what you ship** – no divergence between test and production environments.

### 3. Multiple Runtime Variants

**The Problem:** You need to build the same application for different environments (e.g., `runtime-root` for privileged containers, `runtime-user` for security-hardened non-root containers).

**The Solution:** Different targets with different user configurations.

```dockerfile
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp .

FROM alpine:latest AS runtime-root
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]

FROM runtime-root AS runtime-user
RUN adduser -D appuser
USER appuser
CMD ["myapp"]
```

**Build:**
```bash
docker build --target runtime-root -t myapp:root .
docker build --target runtime-user -t myapp:nonroot .
```

### 4. Multi-Architecture Builds (ARM64 / AMD64)

**The Problem:** You need to support both x86_64 (AMD64) and ARM64 architectures without maintaining separate Dockerfiles.

**The Solution:** Use Docker's `TARGETARCH` build argument with a single multi-target Dockerfile.

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.21 AS builder
ARG TARGETARCH
WORKDIR /app
COPY . .
RUN GOOS=linux GOARCH=$TARGETARCH go build -o myapp .

FROM alpine:latest AS runtime-${TARGETARCH}
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]
```

**Build with Buildx:**
```bash
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:latest --push .
```

### 5. Microservices in a Monorepo

**The Problem:** You have multiple services in one repository and want to build each from the same Dockerfile.

**The Solution:** Each service is a separate target.

```dockerfile
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .

FROM base AS auth-service
WORKDIR /app/services/auth
CMD ["node", "index.js"]

FROM base AS payment-service
WORKDIR /app/services/payment
CMD ["node", "index.js"]

FROM base AS notification-service
WORKDIR /app/services/notification
CMD ["node", "index.js"]
```

**Build:**
```bash
docker build --target auth-service -t auth:latest .
docker build --target payment-service -t payment:latest .
```

### 6. Build-Time Optimisation (Buildkit Caching)

**The Problem:** CI builds are slow because they rebuild everything from scratch.

**The Solution:** Multi-target allows you to build and cache intermediate stages separately.

```dockerfile
FROM ubuntu:22.04 AS deps
RUN apt-get update && apt-get install -y build-essential cmake

FROM deps AS build
COPY . /src
RUN cd /src && make

FROM alpine:latest AS runtime
COPY --from=build /src/bin/myapp /usr/local/bin/
CMD ["myapp"]
```

**In CI, you can pre-build the `deps` stage to cache it:**
```bash
docker build --target deps -t myapp:deps .
docker build --target runtime -t myapp:latest .
```

### 7. Debugging Production Issues with Debug Containers

**The Problem:** Production containers are stripped of debugging tools, making it hard to diagnose issues in live environments.

**The Solution:** A `debug` target that adds diagnostic tools.

```dockerfile
FROM alpine:latest AS prod
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]

FROM prod AS debug
RUN apk add --no-cache curl strace tcpdump vim
CMD ["/usr/local/bin/myapp"]
```

**Deploy the debug version temporarily to investigate:**
```bash
docker build --target debug -t myapp:debug .
kubectl set image deployment/myapp myapp=myapp:debug
```

---

### 8. Splitting a Large Application into Smaller Images

**The Problem:** Your application has multiple components (frontend, backend, worker) that are currently in one giant image.

**The Solution:** Each component as a separate target.

```dockerfile
FROM python:3.14 AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

FROM base AS api
CMD ["gunicorn", "api:app"]

FROM base AS worker
CMD ["celery", "-A", "tasks", "worker"]

FROM base AS frontend
RUN npm install && npm run build
CMD ["serve", "-s", "dist"]
```

---

### 9. Migration / Canary / A/B Testing Variants

**The Problem:** You want to test a new version of your app alongside the old one.

**The Solution:** Build both `stable` and `canary` targets from the same Dockerfile.

```dockerfile
FROM base AS stable
COPY . /app
RUN npm run build:stable

FROM base AS canary
COPY . /app
RUN npm run build:canary
```

---

### 10. Documentation / Static Site Generation

**The Problem:** You want to build documentation (e.g., with MkDocs, Sphinx) as a separate image for hosting on a docs site.

**The Solution:** A `docs` target.

```dockerfile
FROM python:3.14 AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

FROM base AS app
CMD ["gunicorn", "app:app"]

FROM base AS docs
RUN pip install mkdocs
RUN mkdocs build
CMD ["mkdocs", "serve", "--dev-addr=0.0.0.0:8000"]
```

## Advanced: Docker Bake for Multi-Target Orchestration

For complex scenarios, Docker **Bake** (`docker-bake.hcl`) lets you define build matrices, multiple registries, and target groups.

```hcl
# docker-bake.hcl
group "default" {
  targets = ["app", "worker"]
}

target "app" {
  dockerfile = "Dockerfile"
  target = "app"
  tags = ["myapp:latest"]
}

target "worker" {
  dockerfile = "Dockerfile"
  target = "worker"
  tags = ["myapp-worker:latest"]
}

target "multiarch" {
  platforms = ["linux/amd64", "linux/arm64"]
}
```

**Build all targets at once:**
```bash
docker buildx bake
```

## Key Takeaway

Multi-target Dockerfiles let you **maintain a single source of truth** for all your build variations. Instead of managing separate `Dockerfile.dev`, `Dockerfile.prod`, `Dockerfile.test`, and `Dockerfile.arm64`, you have **one file** that produces all of them. This reduces duplication, ensures consistency, and simplifies your CI/CD pipelines.
