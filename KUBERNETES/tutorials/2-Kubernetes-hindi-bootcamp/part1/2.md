Container layering is the architectural magic that makes Docker/OCI containers lightweight, portable, and storage-efficient. 

To understand it, you have to know three things: **Union File Systems (UnionFS)**, the **Copy-on-Write (CoW)** mechanism, and how **image layers** interact with the **container layer**. 

Your provided snippet perfectly captures these three core concepts—so let's break down container layering in detail using them.

---

### 1. The "Shared Store" (Read-Only Image Layers)
Container images are built as a **stack of read-only layers**. Every instruction in a `Dockerfile` (e.g., `FROM`, `RUN`, `COPY`, `ADD`) creates a new layer. 

- For example: `Layer 1` (Ubuntu 22.04 base) → `Layer 2` (Install Nginx) → `Layer 3` (Copy your `index.html`).
- These layers are stored in a **"shared store"** (usually under `/var/lib/docker/overlay2/`). 
- **Key benefit**: If you run 10 containers all based on Ubuntu 22.04, the host machine stores that base layer **only once** on disk. All 10 containers share it, saving massive amounts of storage space and memory.

---

### 2. The "Unified View" (The Union Mount)
This is where the **Union File System** (like OverlayFS, AUFS, or Btrfs) comes in. The kernel takes all those individual, read-only layers from the "shared store" and **stack-straddles them** into a single, cohesive directory structure. 

To the process running inside the container, it doesn't see `Layer 1`, `Layer 2`, and `Layer 3` as separate folders. It sees a **"unified view"**—one single root filesystem (`/`) where `/bin`, `/etc`, `/usr`, and `/var` appear seamlessly merged together, as if they were installed on a normal Linux OS.

---

### 3. "Each Container Has a White Layer" (The Writable Container Layer)
This is the most critical part for runtime behavior. 

- When you run `docker run`, the engine does **not** modify the underlying read-only image layers. Instead, it creates a **thin, writable layer** right on top of the unified stack—this is the **"white layer"** (often called the *Container Layer*).
- Every change made during the container's lifetime (creating a new log file, modifying a config, installing a temporary package) is written exclusively to this top-most writable layer.

#### What exactly is a "Whiteout" (`.wh.`) file?
Because the lower layers are **read-only**, the container cannot physically delete a file from them. So, to handle deletions, OverlayFS uses **"whiteout" files** (usually named `foo.wh.`). 
If a file named `config.json` exists in a lower read-only layer, and you delete it inside the container, the system creates a special "whiteout" marker called `config.json.wh` inside the writable "white layer". When the UnionFS creates the "unified view", it sees this whiteout marker and *hides* the underlying `config.json`, making it appear as if the file is completely gone.

---

### 4. The Copy-on-Write (CoW) Strategy
This is the engine that makes the "white layer" so efficient.

- **Reading**: If you read a file that exists in a lower layer, the container reads it directly from the shared store (fast and memory-efficient).
- **Writing (Modifying)**: If you need to *modify* a file that exists in a lower layer, the system performs a **"Copy-Up"**. It copies the specific file from the read-only layer up into the writable "white layer". The container then modifies this newly copied version. The original file in the shared store remains untouched.
- **Writing (New files)**: New files are created directly in the writable "white layer".

---

### A Visual Example
Imagine an image with **3 read-only layers** (Base OS → Python → App Code). When you start **Container A** and **Container B**:

| Component | Container A | Container B |
| :--- | :--- | :--- |
| **Shared Store** | Reuses Layers 1, 2, 3 (Shared) | Reuses Layers 1, 2, 3 (Shared) |
| **Writable Layer** | Creates its own "White Layer" | Creates its own separate "White Layer" |
| **Unified View** | Sees all layers merged as one OS | Sees all layers merged as one OS |
| **Runtime Change** | Edits `/app/config.ini` (CoW copies it up to its white layer) | Deletes `/app/logs.txt` (creates a whiteout marker in its white layer) |

Because each container has its **own dedicated "white layer"**, multiple containers can run from the exact same image simultaneously without interfering with each other or corrupting the base image.

---

### Why This Design is Revolutionary

1. **Instant Startup**: No need to copy gigabytes of data when starting a container—just stack the layers virtually.
2. **Disk Efficiency**: Storing 100 containers might take only the size of their unique "white layers" plus one copy of the base image.
3. **Immutable Infrastructure**: The image layers never change. If a container crashes and corrupts its "white layer", you just throw it away and start a new container from the pristine shared image layers. 
4. **Caching for CI/CD**: If you rebuild an image, Docker reuses cached layers that haven't changed. If you only changed your app code, it doesn't rebuild the entire Ubuntu OS layer—it only rebuilds the top app layer and reuses the "shared store" for the rest.

In summary: The **shared store** holds the immutable blueprint. The **unified view** is what the container "sees." The **white layer** is the container's personal scratchpad, capturing all runtime differences and deletions via whiteout markers, while the Copy-on-Write strategy ensures this entire system remains incredibly fast and lightweight.
