To truly understand containerization, you have to move past the `docker` command and look at the lower-level components that actually do the work. The diagram in your image shows the modern, standardized container stack.

Here is a detailed breakdown of every component and a practical guide to exploring them on a Linux system.

---

### Component Deep Dive

#### 1. OCI (Open Container Initiative)
The OCI is a set of open standards, not a piece of software. It was created to ensure that containers built by one tool (e.g., Docker) could be run by any other compliant tool (e.g., Kubernetes), preventing vendor lock-in.

The OCI defines **two core specifications**:
*   **Image Specification**: Defines how a container image should be built, packaged, and stored. This ensures `docker build` images work with `podman` or `containerd`.
*   **Runtime Specification**: Defines the exact steps a runtime must take to *run* a container from that image, including configuration, execution environment, and lifecycle. This is what `runc` implements.

#### 2. runc (The Low-Level Runtime)
`runc` is the **reference implementation** of the OCI Runtime Specification. It's a lightweight, command-line tool written in Go.

*   **Its Job**: `runc` takes an OCI-compliant "bundle" (a filesystem root and a `config.json` file) and uses the Linux kernel (`clone()`, `unshare()`) to spawn the container process. It sets up the namespaces, cgroups, and seccomp profiles.
*   **Its Lifespan**: `runc` is **short-lived**. Once it creates the container process, it exits, handing off responsibility.

#### 3. containerd (The High-Level Runtime)
`containerd` is a **long-running daemon** that provides the higher-level management logic for containers.

*   **Its Job**: It manages the entire lifecycle of a container: pulling images from registries, managing storage (snapshots), handling networking, and supervising the container's execution. It acts as the bridge between the user (or orchestrator like Kubernetes) and the low-level runtime (`runc`).

#### 4. containerd-shim (The Process Parent)
The `containerd-shim` is a **critical intermediary process**. For every running container, `containerd` launches a separate shim process.

*   **Its Job**:
    1.  **Parent Process**: Becomes the direct parent of the container's main process (PID 1).
    2.  **Daemonless Containers**: Keeps the container's stdio and file descriptors open, even if the main `containerd` daemon crashes or restarts.
    3.  **Reaping Zombies**: Cleans up any orphaned child processes inside the container when they exit, preventing zombie processes.

---

### The Complete Workflow
1.  You run `docker run` or `kubectl apply`.
2.  The orchestrator sends an API request to **`containerd`**.
3.  **`containerd`** pulls the image, unpacks it, and creates an OCI bundle.
4.  **`containerd`** starts a **`containerd-shim`** for the new container.
5.  The **shim** calls **`runc`** to create and start the container.
6.  **`runc`** uses the kernel to create the container process and then exits.
7.  The **shim** becomes the parent of the container process and monitors it until it stops.

### 🛠 Practical Exploration Lab
Now, let's get hands-on. **These commands must be run as root (`sudo -i`)** because they interact with low-level system components.

#### Step 1: Verify the Architecture
First, confirm the stack in use on your system.
```bash
docker info | grep "Runtime"
```
This will likely show `runc` as the default runtime.
```bash
ps aux | grep -E "containerd|runc|docker"
```
This shows the running processes. You should see the `containerd` daemon and a `dockerd` daemon, but you won't see `runc` running unless a container is in the middle of being created.

#### Step 2: Explore Containers with `ctr` (containerd's CLI)
`ctr` is the native CLI client for `containerd`. It bypasses Docker and talks directly to containerd.

```bash
# List all containers managed by containerd in the default namespace
ctr container ls

# List all containers in the Kubernetes namespace (if you're on a k8s node)
ctr -n k8s.io container ls

# Pull an image directly with containerd
ctr image pull docker.io/library/nginx:alpine

# List pulled images
ctr image ls

# Run a container directly with containerd
ctr run -d docker.io/library/nginx:alpine my-nginx

# List running containers again
ctr container ls
ctr task ls   # Tasks are the running processes within containers
```

#### Step 3: Find and Inspect the `containerd-shim`
Now, find the shim process for the container you just created.
```bash
ps aux | grep containerd-shim
```
You'll see a process like `containerd-shim-runc-v2`. Note its PID.

Now, find the container's main process (nginx).
```bash
# Get the PID of the nginx process (replace <shim-pid> with the actual PID)
pstree -p <shim-pid>
```
You'll see the shim as the parent of the nginx process. This proves the shim is the direct parent.

Now, check the process tree from a different angle:
```bash
# Find the PID of your container's main process (e.g., from 'ctr task ls')
CONTAINER_PID=$(ctr task ls | grep my-nginx | awk '{print $2}')
# Show the parent of that process
ps -o pid,ppid,cmd -p $CONTAINER_PID
```
The `PPID` (Parent PID) will be the PID of the `containerd-shim`, not `containerd`.

#### Step 4: Explore the Low-Level Runtime (`runc`)
`runc` stores its state in a specific directory (by default, `/run/runc` for rootless, or `/run/containerd/runc` for system containers).

Find the runc state directory for your container:
```bash
# Find the container's ID from the previous step
ctr container ls | grep my-nginx
# List runc containers in the default runc root
runc --root /run/containerd/runc/default list
```
This `runc list` command shows containers `runc` is aware of. You should see your `my-nginx` container with a status of `running`.

You can even execute a command inside the container directly using `runc`:
```bash
# Use the container ID from the list above
runc --root /run/containerd/runc/default exec <container-id> whoami
```
This bypasses containerd and Docker entirely, talking directly to the low-level runtime. The output will be `root` (or whatever user the container runs as).

#### Step 5: The OCI Bundle (The Container's Blueprint)
When `containerd` creates a container, it writes an OCI bundle to disk. This bundle contains the `config.json` that defines the container's spec.

Find the bundle directory:
```bash
# Find the directory for your container
ctr container info my-nginx | grep -i rootfs
```
This will show the path to the container's root filesystem (e.g., `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/.../fs`).

Look inside this directory to see the container's filesystem:
```bash
ls -la /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/.../fs/
```

Now, find the OCI `config.json` file. It's usually in a subdirectory under `/var/lib/containerd/io.containerd.runtime.v2.task/`.
```bash
find /var/lib/containerd -name "config.json" | grep my-nginx
```
View this file (`cat <path-to-config>/config.json`). You'll see the OCI specification in action—it defines the process to run, environment variables, mount points, and Linux capabilities. This is the exact blueprint `runc` uses to create the container.

#### Step 6: Clean Up
Finally, clean up the container you created with `ctr`.
```bash
ctr task kill my-nginx
ctr task rm my-nginx
ctr container rm my-nginx
ctr image rm docker.io/library/nginx:alpine
```

| Your Action | What It Proved |
| :--- | :--- |

| `ps aux | grep containerd-shim` | The shim is a separate, long-lived process for each container. |
| `ps -o ppid` on container process | The shim is the **direct parent** of the container process. |
| `runc list` | `runc` is the low-level runtime that ultimately creates the container. |
| `cat config.json` | The OCI specification is a real, readable file that defines the entire container. |
