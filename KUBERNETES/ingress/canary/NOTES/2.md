Below is a **complete working example** of a canary deployment using the **NGINX Ingress Controller**. It includes:

1. Stable Deployment (v1)
2. Stable Service
3. Stable Ingress
4. Canary Deployment (v2)
5. Canary Service
6. Canary Ingress (30% traffic)
7. Test commands
8. How to increase traffic
9. Rollback
10. Promote v2 to stable

# 1. Stable Deployment (v1)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: blogging-v1
  labels:
    app: blogging
    version: v1
spec:
  replicas: 3

  selector:
    matchLabels:
      app: blogging
      version: v1

  template:
    metadata:
      labels:
        app: blogging
        version: v1

    spec:
      containers:
      - name: nginx

        image: nginx:1.27

        ports:
        - containerPort: 80

        command:
        - /bin/sh
        - -c

        args:
        - |
          echo "<h1>VERSION 1</h1>" > /usr/share/nginx/html/index.html
          nginx -g 'daemon off;'
```

# 3. Stable Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: blogging-ingress

spec:
  ingressClassName: nginx

  rules:

  - host: blog.example.com

    http:

      paths:

      - path: /

        pathType: Prefix

        backend:

          service:

            name: blogging-v1-svc

            port:

              number: 80
```

↓

# 6. Canary Ingress

This is where the magic happens.

```yaml
apiVersion: networking.k8s.io/v1

kind: Ingress

metadata:

  name: blogging-canary

  annotations:

    nginx.ingress.kubernetes.io/canary: "true"

    nginx.ingress.kubernetes.io/canary-weight: "30"

spec:

  ingressClassName: nginx

  rules:

  - host: blog.example.com

    http:

      paths:

      - path: /

        pathType: Prefix

        backend:

          service:

            name: blogging-v2-svc

            port:

              number: 80
```

Deploy

```bash
kubectl apply -f 04-v2-deployment.yaml
kubectl apply -f 05-v2-service.yaml
kubectl apply -f 06-v2-canary-ingress.yaml
```

# Increase Canary Traffic

Change only the annotation.

## 10%

```yaml
nginx.ingress.kubernetes.io/canary-weight: "10"
```

## 30%

```yaml
nginx.ingress.kubernetes.io/canary-weight: "30"
```

## 50%

```yaml
nginx.ingress.kubernetes.io/canary-weight: "50"
```

## 80%

```yaml
nginx.ingress.kubernetes.io/canary-weight: "80"
```

Apply the updated Ingress:

```bash
kubectl apply -f 06-v2-canary-ingress.yaml
```

---

# Rollback

If VERSION 2 has issues, either delete the canary Ingress:

```bash
kubectl delete ingress blogging-canary
```

or set:

```yaml
nginx.ingress.kubernetes.io/canary-weight: "0"
```

Now all traffic goes back to v1.

---

# Promote VERSION 2 to Stable

Once you're confident in v2:

1. Edit the stable Ingress (`blogging-ingress`) so its backend points to `blogging-v2-svc`.
2. Remove the canary Ingress:

```bash
kubectl delete ingress blogging-canary
```

3. Optionally remove the old deployment and service:

```bash
kubectl delete deployment blogging-v1
kubectl delete service blogging-v1-svc
```

Now **100% of traffic** goes to VERSION 2.

# Useful Canary Annotations

| Annotation                                                     | Description                                                                |
| -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `nginx.ingress.kubernetes.io/canary: "true"`                   | Marks the Ingress as a canary Ingress.                                     |
| `nginx.ingress.kubernetes.io/canary-weight: "30"`              | Sends a percentage of traffic to the canary backend.                       |
| `nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"`     | Routes requests based on a request header.                                 |
| `nginx.ingress.kubernetes.io/canary-by-header-value: "always"` | Sends requests to the canary only when the header has the specified value. |
| `nginx.ingress.kubernetes.io/canary-by-cookie: "canary"`       | Routes requests based on a cookie value.                                   |

This example demonstrates the standard canary deployment pattern supported by the NGINX Ingress Controller without requiring a service mesh like Istio or Linkerd.
