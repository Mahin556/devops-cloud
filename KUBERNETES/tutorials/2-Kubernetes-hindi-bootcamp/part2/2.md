In Kubernetes, **GVK** and **GVR** are two fundamental concepts used to uniquely identify resources. Think of them as the "name" and "address" of a resource in the Kubernetes API.

### 🧠 GVK: The "What" (Type Identifier)

**GVK** stands for **Group, Version, Kind**. It's used to uniquely identify the **type** of a Kubernetes resource. You can think of it as the resource's "name" or "blueprint".

- **Group**: The API group the resource belongs to (e.g., `apps`, `batch`). Core resources like `Pod` and `Service` have an empty group (`""`).
- **Version**: The API version of the resource (e.g., `v1`, `v1beta1`). Versions can be `Alpha`, `Beta`, or `Stable`.
- **Kind**: The resource type, in singular form (e.g., `Pod`, `Deployment`, `Service`).

> **Example**: The GVK for a Deployment is `apps/v1, Kind: Deployment`.

**💡 When to use GVK**:
GVK is used when you need to **describe** or **define** a resource.
- **In Code**: When you create a resource object (like a Go struct), it has a GVK.
- **In Controllers/Operators**: When you need to handle different resource types, you switch on their `Kind`.

### 🗺️ GVR: The "Where" (API Path Identifier)

**GVR** stands for **Group, Version, Resource**. It's used to identify the **endpoint** for a resource in the Kubernetes API. Think of it as the resource's "address" or "URL path".

- **Group**: Same as GVK.
- **Version**: Same as GVK.
- **Resource**: The resource name, in **plural** form (e.g., `pods`, `deployments`, `services`).

> **Example**: The GVR for a Deployment is `apps/v1, Resource: deployments`.

> **💡 Key Insight**: A GVR directly corresponds to an HTTP path in the Kubernetes API. For instance, `GET /api/v1/namespaces/{namespace}/pods` is the GVR for Pods.

**💡 When to use GVR**:
GVR is used when you need to **operate** on a resource.
- **With `kubectl`**: When you run `kubectl get deployments`, you're using the `deployments` GVR.
- **With Dynamic Clients**: When you need to perform CRUD operations on resources whose types you don't know at compile time (like Custom Resources), you use a GVR.

### 🔄 The Connection: GVK ↔ GVR

GVK and GVR are two sides of the same coin. The Kubernetes API Server uses a **RESTMapper** to convert between them. When you make an API request using a GVR (the path), the API Server uses the RESTMapper to find the corresponding GVK (the type) to know how to decode and handle the object.

### 📊 Summary Table

| Feature | GVK (Group, Version, Kind) | GVR (Group, Version, Resource) |
| :--- | :--- | :--- |
| **Purpose** | Identifies the **type** of a resource | Identifies the **API endpoint** for a resource |
| **Form** | Singular (e.g., `Deployment`) | Plural (e.g., `deployments`) |
| **Used For** | Defining, describing, and handling resources | Performing operations (CRUD) on resources |
| **In Code** | `schema.GroupVersionKind` | `schema.GroupVersionResource` |

In essence, **GVK** is the *type* of a resource (its identity), and **GVR** is the *API path* to access it (its address). They work together to allow Kubernetes to understand and manage the vast ecosystem of built-in and custom resources.
