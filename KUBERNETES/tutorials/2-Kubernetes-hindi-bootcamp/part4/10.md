In Kubernetes, **Requests** and **Limits** are the primary mechanisms for managing compute resources (CPU and Memory) for your Pods. They work together with the **Scheduler** to determine *where* a Pod runs, and with the **Kubelet** to determine *how* it runs.

Here is exactly how they work, why the Scheduler only cares about one of them, and the critical difference between CPU and Memory.

---

### 1. The Definitions: Requests vs. Limits

| Concept | What it Means | Analogy |
| :--- | :--- | :--- |
| **Request** | The **guaranteed** minimum amount of resources the container is reserved. The Scheduler uses this to find a node. | Renting a hotel room. You are *guaranteed* a bed (the request), even if the hotel is full. |
| **Limit** | The **maximum** amount of resources the container is allowed to use. If it exceeds this, it gets throttled (CPU) or killed (Memory). | The maximum size of the hotel room. You cannot expand into the hallway (the limit). |

---

### 2. The Scheduler's Role (The "Node Selector")

The Scheduler's job is to find the **best node** for your Pod. 

**Crucially**: The Scheduler **only looks at `Requests`**, completely ignoring `Limits` for its initial placement decision.

**How it works**:
For every node, the Scheduler calculates the **Node Allocatable** (total node capacity minus system overhead). It subtracts the sum of `Requests` of all existing Pods on that node. If there is enough remaining capacity to fit the new Pod's `Requests`, the node is a candidate; if not, it is filtered out.

**Why ignore Limits?** This allows for **overcommitment**. If you set a high `Limit` but a low `Request`, the node can schedule many Pods (based on low Requests), assuming they won't all max out their Limits at the same time.

**Example**:
- Node has **4 CPU**.
- Pod A Requests **1 CPU**, Limits **2 CPU**.
- The Scheduler sees: "4 - 1 = 3 CPU left." It schedules the Pod, *optimistically* assuming it will only use 1 CPU most of the time.

---

### 3. CPU vs. Memory: The Critical Difference (Runtime Behavior)

Once the Pod is running on the node, the **Kubelet** enforces the `Limits`. The behavior here is **completely different** for CPU and Memory.

| Resource | Type | What happens when it exceeds the **Limit**? | Is it compressible? |
| :--- | :--- | :--- | :--- |
| **CPU** | Compressible | The container is **throttled** (slowed down). The OS gives it less CPU time. It does **not** get killed. | **Yes** (you can slow it down safely). |
| **Memory** | In-compressible | The container is **killed** (terminated) by the Out-Of-Memory (OOM) Killer. It is restarted, but data in memory is lost. | **No** (you cannot "slow down" memory usage; it must be freed instantly). |

**The Golden Rule**: **Never set a Memory Limit** without leaving room for the application's garbage collection or caching. If your app has a memory leak and hits the Limit, the OOM Killer will terminate it. If it hits the CPU Limit, it just runs a little slower.

---

### 4. The Result: Quality of Service (QoS) Classes

Based on how you set Requests and Limits, Kubernetes assigns the Pod a **QoS Class**. This is crucial because when the node is running out of resources (e.g., low memory), Kubernetes **evicts Pods based on their QoS Class**.

| QoS Class | Request & Limit Settings | Eviction Priority (Lowest to Highest) |
| :--- | :--- | :--- |
| **Guaranteed** | Requests == Limits for **all** containers. | **Highest priority** (last to be evicted). |
| **Burstable** | Requests < Limits (or at least one container has a Request). | Medium priority. |
| **BestEffort** | No Requests or Limits set for any container. | **Lowest priority** (killed first when node runs out of resources). |

---

### 5. Complete YAML Example

Here is a Pod specifying both CPU and Memory Requests and Limits:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        memory: "128Mi"   # Guarantees 128 MB of RAM
        cpu: "250m"       # Guarantees 1/4 of a vCPU core
      limits:
        memory: "256Mi"   # Max RAM allowed. If it uses >256Mi, OOM Kill!
        cpu: "500m"       # Max CPU allowed. If it exceeds, it is throttled.
```

*(**Note**: `250m` means 250 millicores, which is 0.25 of a CPU core.)*

---

### 6. Summary Cheat Sheet

| Concept | Actor | Watches? | Action on Exceedance |
| :--- | :--- | :--- | :--- |
| **Request** | **Scheduler** | Yes (to decide where to place the Pod). | If not available on a node, the Pod stays **Pending**. |
| **Limit (CPU)** | **Kubelet / Kernel** | Yes (to enforce max usage). | **Throttles** (slows down) the container. |
| **Limit (Memory)** | **Kubelet / Kernel** | Yes (to enforce max usage). | **Terminates** (OOM Kills) the container. |

**Pro-Tip for Production**:
- Always set **Requests** so the Scheduler can make intelligent decisions.
- Always set **Memory Limits** to prevent a runaway container from crashing the entire Node.
- Be cautious with **CPU Limits**; setting them too low can cause unnecessary throttling, slowing your app down. Sometimes, only setting CPU Requests (without Limits) is acceptable to allow bursting when CPU is available.
