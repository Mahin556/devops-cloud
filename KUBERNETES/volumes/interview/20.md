## Important Gotcha: ReadWriteOnce vs ReadWriteMany (Fully Corrected)

### ❌ The Misconception (Your original text)
> *"Deployment with RWO: Pod 2 & 3 are ALWAYS PENDING."*

### ✅ The Technical Truth (Corrected)
**RWO restricts access to a single NODE, not a single Pod.** 

Therefore, your Deployment fails **ONLY IF** Kubernetes schedules the Pods onto **different nodes**. If you force all 3 Pods onto the *same* node, they will all mount successfully—but you risk data corruption!

```yaml
# This FAILS (Standard behavior - Pods spread across nodes):
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3
  # ...
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc  # Single PVC, RWO access mode

# Result (assuming 3 different nodes):
# Pod 1 (Node A): ✅ Mounted
# Pod 2 (Node B): ❌ PENDING (multi-attach error)
# Pod 3 (Node C): ❌ PENDING (multi-attach error)
```

### ⚠️ The Dangerous Edge Case (SAME NODE)
If you add a `nodeSelector` to force all pods onto the same physical machine:

```yaml
spec:
  replicas: 3
  template:
    spec:
      nodeSelector:
        kubernetes.io/hostname: "node-1"  # Force all 3 to Node-1
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: my-pvc  # Still RWO
```
**What happens:**
```
Pod 1 (Node-1): ✅ Attaches disk to Node-1.
Pod 2 (Node-1): ✅ Mounts the LOCAL filesystem (disk already attached).
Pod 3 (Node-1): ✅ Mounts the LOCAL filesystem.

RESULT: All 3 Pods RUN! 
⚠️  BUT: If they write to the same file, CORRUPTION occurs!
```

```yaml
apiVersion: apps/v1

# Result (Guaranteed):

```

## ➕ Additional "Remaining" Gotchas You Must Know

### Gotcha 2: RWX is NOT Supported by Cloud Block Storage
Many beginners assume "RWX works everywhere." **It does not.**

| Storage Type | Supports RWX? | 
| :--- | :--- |
| AWS EBS, GCP PD, Azure Disk | ❌ **NO** (Block storage) |
| NFS, AWS EFS, Azure Files, CephFS | ✅ **YES** (Shared file storage) |

If you request `ReadWriteMany` on an EBS disk, your PVC will stay **Pending forever**.

---

### Gotcha 3: The Scheduler's "WaitForFirstConsumer" (Crucial for RWO)
When using RWO with cloud disks, the disk must be created in the **same Availability Zone (AZ)** as the Pod's Node.

- If you use `volumeBindingMode: Immediate` (old default), the disk is created in a random AZ (e.g., us-east-1a). If your Pod schedules to us-east-1b, it **fails**.
- **Fix:** Always use `volumeBindingMode: WaitForFirstConsumer` (default in modern Kubernetes). This makes the scheduler pick the Node *first*, then creates the disk in that exact AZ.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer  # <-- CRUCIAL for RWO!
```

### Gotcha 4: ReadWriteOncePod (RWOP) - The "True Exclusive" Mode
Since you asked for *remaining* access modes, note that **RWO does NOT guarantee single-pod access** (as shown in the edge case above). 

If you need **absolute guarantee** that only ONE specific pod touches the data (even if they are recreated on the same node), use `ReadWriteOncePod` (Kubernetes v1.27+ stable).

```yaml
# THIS guarantees only 1 Pod in the entire cluster can mount it.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: critical-db
spec:
  accessModes:
  - ReadWriteOncePod  # <-- NOT RWO! This is Pod-level, not Node-level.
  resources:
    requests:
      storage: 50Gi
```
With RWOP, even if Pod A dies and Pod B starts on the exact same Node 1 minute later, Pod B **cannot** mount it until the CSI driver releases the volume from Pod A's identity.

---

### Gotcha 5: VolumeMode (Filesystem vs. Block)
Access modes don't care *how* you access the data, only *who*.
- **Filesystem** (default): Kubernetes mounts it to a directory (`/var/data`).
- **Block**: Exposes the raw disk (`/dev/xvda`) inside the Pod. No filesystem overhead. 
You cannot use `mountPath` with Block mode; you must use `volumeDevices`. 
*(This is a "remaining" nuance often missed in beginner guides).*

**The Golden Rule:** 
- Use **RWO** only with **StatefulSet** (for separate disks) or **single-replica Deployments**.
- Use **RWX** only with **shared storage** (NFS/EFS).
- If you ever need to run multiple replicas of a Deployment sharing a *single* RWO disk, **don't**—unless your app handles distributed file-locking (like GFS or ZooKeeper).
