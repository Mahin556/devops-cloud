They can both perform **misconfiguration scanning**, but they are designed for different purposes.

## Short answer

```bash
trivy config .
```

means:

> **"Treat this directory as an IaC/configuration project and scan it for misconfigurations."**

Whereas:

```bash
trivy fs --scanners misconfig .
```

means:

> **"Scan this filesystem as a filesystem target, and additionally enable the misconfiguration scanner."**

Trivy's documentation explicitly says that `config` is the dedicated misconfiguration command, while `fs` can enable misconfiguration scanning with `--scanners misconfig`. ([Trivy][1])

---

# 1. `trivy config`

```bash
trivy config .
```

This is specifically designed for **configuration/IaC scanning**.

Trivy automatically detects supported configuration types, such as:

```text
Terraform
Kubernetes
Helm
Dockerfile
CloudFormation
Azure ARM
Terraform plan
```

and applies the appropriate misconfiguration checks. ([Trivy][1])

Example:

```bash
trivy config terraform/
```

or:

```bash
trivy config k8s/
```

or:

```bash
trivy config helm-chart/
```

Think:

```text
trivy config
      ↓
"I am scanning IaC/configuration"
```

---

# 2. `trivy fs --scanners misconfig`

```bash
trivy fs --scanners misconfig .
```

Here, `fs` is the **filesystem scanner**, and you're telling it:

```text
Use the misconfiguration scanner too.
```

The important advantage is that `fs` can combine multiple scanner types.

For example:

```bash
trivy fs \
  --scanners vuln,secret,misconfig \
  .
```

Now the same project can be scanned for:

```text
vuln
  ↓
Dependency vulnerabilities

secret
  ↓
Exposed secrets

misconfig
  ↓
IaC/configuration issues
```

This combined scanning capability is one of the documented differences between `config` and `fs`. ([Trivy][1])

---

# 3. The biggest difference

Consider this project:

```text
my-project/
├── package.json
├── package-lock.json
├── Dockerfile
├── terraform/
│   └── main.tf
├── k8s/
│   └── deployment.yaml
└── .env
```

### Option 1 — Dedicated config scan

```bash
trivy config .
```

Focus:

```text
Dockerfile
Terraform
Kubernetes
Helm
CloudFormation
etc.
       ↓
MISCONFIGURATION
```

---

### Option 2 — Filesystem scan

```bash
trivy fs .
```

Depending on the enabled/default scanners in your Trivy version, this can inspect the project for things such as vulnerabilities and secrets.

And:

```bash
trivy fs --scanners vuln,secret,misconfig .
```

explicitly asks for:

```text
              Project
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
     vuln      secret    misconfig
       │         │         │
      CVEs     Secrets    IaC
```

That's why `fs` is particularly convenient in a **single CI security stage**. ([Trivy][1])

---

# 4. So are the misconfiguration results the same?

**They can overlap heavily**, because both ultimately use Trivy's misconfiguration checks.

For example:

```bash
trivy config terraform/
```

and:

```bash
trivy fs --scanners misconfig terraform/
```

can both detect Terraform misconfigurations.

But `config` is the **purpose-built interface for configuration scanning**, whereas `fs` is a broader filesystem scan where you explicitly add misconfiguration scanning.

So don't think:

```text
config = different misconfiguration engine
fs + misconfig = completely different engine
```

Instead think:

```text
             Trivy
               │
        Misconfiguration
           scanner
               │
       ┌───────┴────────┐
       │                │
trivy config      trivy fs --scanners misconfig
       │                │
dedicated config    filesystem + misconfig
scan
```

---

# 5. Another important difference: scanner selection

`trivy config` is inherently a **misconfiguration scan**.

Its CLI has options specifically for selecting the types of misconfiguration checks, for example:

```bash
trivy config \
  --misconfig-scanners terraform,dockerfile \
  .
```

The current Trivy documentation lists supported configuration scanner types including Terraform, Dockerfile, Helm, Kubernetes, CloudFormation, Azure ARM and Terraform plan formats. ([Trivy][2])

With `fs`, you select the broader scanner categories:

```bash
trivy fs \
  --scanners vuln,secret,misconfig \
  .
```

So:

```text
config
 └── --misconfig-scanners

fs
 └── --scanners
       ├── vuln
       ├── secret
       └── misconfig
```

---

# 6. Which one should I use?

### If your goal is specifically IaC security:

Use:

```bash
trivy config .
```

For example:

```bash
trivy config terraform/
```

This is clearer and more semantically appropriate.

---

### If you're scanning an entire source repository in CI:

Use:

```bash
trivy fs \
  --scanners vuln,secret,misconfig \
  .
```

Because you want one stage to inspect:

```text
Dependencies
Secrets
IaC
```

### In one sentence:

> **`trivy config` is the dedicated command for IaC/configuration misconfiguration scanning, while `trivy fs --scanners misconfig` adds the same type of misconfiguration scanning to a broader filesystem scan, allowing you to combine it with vulnerability and secret scanning.** ([Trivy][1])

One small correction to your earlier notes: **`trivy config` should be your default command when your explicit goal is IaC misconfiguration scanning; `trivy fs --scanners misconfig` is most useful when you deliberately want a combined filesystem scan.**
