When multiple Ingress rules could match the same request, Kubernetes (and the Ingress controller) needs a way to decide **which backend should receive the request**.

There are three important rules.

---

# Rule 1: Longer paths win

The **most specific** (longest) matching path is chosen.

Example:

```yaml
paths:
- path: /
  pathType: Prefix
  backend: frontend

- path: /api
  pathType: Prefix
  backend: api

- path: /api/v1
  pathType: Prefix
  backend: api-v1
```

Request:

```text
GET /api/v1/users
```

Matches all three:

| Path      | Match |
| --------- | :---: |
| `/`       |   ✅   |
| `/api`    |   ✅   |
| `/api/v1` |   ✅   |

The longest path is:

```text
/api/v1
```

So the request goes to:

```text
api-v1
```

---

### More examples

| Request         | Matching Paths         | Selected  |
| --------------- | ---------------------- | --------- |
| `/`             | `/`                    | `/`       |
| `/api`          | `/`, `/api`            | `/api`    |
| `/api/users`    | `/`, `/api`            | `/api`    |
| `/api/v1/users` | `/`, `/api`, `/api/v1` | `/api/v1` |

# Rule 2: Exact beats Prefix

Suppose you have:

```yaml
paths:
- path: /login
  pathType: Prefix
  backend: login-prefix

- path: /login
  pathType: Exact
  backend: login-exact
```

Request:

```text
GET /login
```

Both rules match.

| Rule   | Match |
| ------ | :---: |
| Prefix |   ✅   |
| Exact  |   ✅   |

The **Exact** rule wins.

Result:

```text
login-exact
```

---

### Another request

```text
GET /login/admin
```

Now:

| Rule   | Match |
| ------ | :---: |
| Exact  |   ❌   |
| Prefix |   ✅   |

Result:

```text
login-prefix
```

# Rule 3: Oldest Ingress wins (ingress-nginx)

Suppose you accidentally create two Ingress resources with the **same host and same path**.

Ingress A:

```yaml
host: app.example.com
path: /api
backend: service-a
```

Created at:

```text
10:00 AM
```

---

Ingress B:

```yaml
host: app.example.com
path: /api
backend: service-b
```

Created at:

```text
10:05 AM
```

Now a request arrives:

```text
GET /api/users
```

Both rules are identical.

Ingress-NGINX chooses the **oldest** one.

Result:

```text
service-a
```

# Priority Order

Imagine these rules:

```text
/
├── /api
│   ├── /api/v1
│   │   └── /api/v1/admin
│   └── /api/v2
└── /login
```

Request:

```text
/api/v1/admin/users
```

The request matches:

* `/`
* `/api`
* `/api/v1`
* `/api/v1/admin`

The most specific (longest) path is:

```text
/api/v1/admin
```

So that backend is selected.

# Summary Table

| Rule                                    | Example                               | Winner                |
| --------------------------------------- | ------------------------------------- | --------------------- |
| **Longest path wins**                   | `/api` vs `/api/v1`                   | `/api/v1`             |
| **Exact beats Prefix**                  | Exact `/login` vs Prefix `/login`     | Exact                 |
| **Oldest Ingress wins** (ingress-nginx) | Two Ingresses with same host and path | First created Ingress |

### Overall matching order

When a request arrives, ingress-nginx effectively resolves conflicts in this order:

1. **Find all rules that match** the host and path.
2. **Choose the longest matching path** (most specific).
3. If two rules have the **same path**, **`Exact`** takes precedence over **`Prefix`**.
4. If there are still identical rules (same host, same path, same path type) across multiple Ingress resources, **the oldest Ingress resource wins**.
