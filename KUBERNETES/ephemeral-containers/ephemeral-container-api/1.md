This challenge is about sending a signal to a process inside a hardened, non-root container that has no shell. The solution involves using ephemeral containers, but you'll have to navigate some specific security constraints. Here is a detailed, step-by-step walkthrough.

### 🧐 Understanding the Challenge

The Pod `non-root` runs a single container from a `FROM scratch` base image. This means there is no shell, no package manager, and no standard command-line tools. Additionally, the Pod's security context is set to `runAsNonRoot`, which enforces that no container in the Pod—including any debug containers you add—can run as the root user.

Your goal is to send a signal (like `SIGHUP` or `SIGUSR1`) to the main application process (PID 1). Because the container is non-root and lacks a shell, a simple `kubectl exec` will not work. You need a different approach.

### 🛠️ The Solution: Ephemeral Containers

The correct approach is to attach an **ephemeral container** to the running Pod. This container can include a shell and tools like `kill`. However, due to the `runAsNonRoot` constraint, you cannot simply use the default `kubectl debug` command, which tries to run the debug container as root.

You need to create an ephemeral container that also runs as a non-root user, and critically, with the **same UID** as the target container. This allows the process in your debug container to send signals to the target process, as they share the same user ID.

### 📝 Step-by-Step Guide

Here is the complete workflow to create a suitable ephemeral container and send the signal.

#### Step 1: Identify the Target Container's UID

First, you need to find out which user ID the target container is running as. You can do this by inspecting the Pod's spec.

```bash
kubectl get pod non-root -o jsonpath='{.spec.containers[0].securityContext.runAsUser}'
```

This will output a number, for example, `1000`. Note this value, as you will need it in the next step.

#### Step 2: Create a Non-Root Ephemeral Container

The `kubectl debug` command does not offer a direct flag to set the `runAsUser` field for the ephemeral container. Therefore, you must create the container by directly patching the Pod's `ephemeralcontainers` subresource. This gives you full control over its specification.

The following command uses `kubectl proxy` and `curl` to send a `PATCH` request to the Kubernetes API. It creates an ephemeral container named `debug-non-root` that runs as the same UID as your target container.

**Start the proxy in a separate terminal:**
```bash
kubectl proxy
```

**In your main terminal, send the PATCH request:**
```bash
# Replace <TARGET_UID> with the value you found in Step 1.
# For example, if the UID is 1000, use "runAsUser": 1000.
curl -Lvk localhost:8001/api/v1/namespaces/default/pods/non-root/ephemeralcontainers \
  -XPATCH \
  -H 'Content-Type: application/strategic-merge-patch+json' \
  -d '
{
    "spec":
    {
        "ephemeralContainers":
        [
            {
                "name": "debug-non-root",
                "command": ["sh"],
                "targetContainerName": "app",
                "image": "alpine",
                "stdin": true,
                "tty": true,
                "securityContext": {"runAsUser": 1000}
            }
        ]
    }
}'
```
**Note:** You must replace `<TARGET_UID>` in the `securityContext` with the actual UID from Step 1. Also, ensure the `targetContainerName` matches the name of your application container (e.g., `app`). The `image` can be any image that contains a shell, like `alpine`.

#### Step 3: Attach to the Ephemeral Container

Once the PATCH request is successful, an ephemeral container is created. You can now attach to it interactively.

```bash
kubectl attach -it non-root -c debug-non-root
```

#### Step 4: Send the Signal

You should now be inside the `alpine` container's shell, running as the same UID as the target application.

1.  **Find the target process:** The main application process in the target container will be **PID 1**. You can confirm this by listing processes:
    ```bash
    ps aux
    ```
    You should see the application process running as PID 1.

2.  **Send the signal:** Use the `kill` command to send the desired signal to PID 1. For example, to send `SIGUSR1`:
    ```bash
    kill -USR1 1
    ```
    You can replace `-USR1` with any other signal, such as `-HUP` or `-TERM`.

### ⚠️ Troubleshooting Common Issues

You might encounter specific errors during this process. Here’s what they mean and how to resolve them.

*   **Error: `violates PodSecurity "baseline:latest": non-default capabilities ... "SYS_PTRACE"`**
    This occurs because `kubectl debug` tries to add the `SYS_PTRACE` capability to the ephemeral container, which is forbidden by the `baseline` Pod Security Standard. To get past this, you can use the `--profile` flag with a value that is compatible with the security policy. For example:
    ```bash
    kubectl debug -it non-root --image=alpine --target=app --profile=baseline
    ```
    This instructs `kubectl debug` to create a container without the forbidden capabilities.

*   **Warning: `container has runAsNonRoot and image will run as root` and the command hangs**
    This happens when the Pod enforces `runAsNonRoot: true` but the debug image you specified (like `alpine`) defaults to running as root. The kubelet refuses to start it. The solution is to use a debugging image that is designed to run as a non-root user, or to create the ephemeral container manually with a specific `runAsUser` in its security context, as shown in Step 2.

*   **Error: `can't kill pid 1: Operation not permitted`**
    This error appears even after you successfully attach a non-root ephemeral container. It indicates a UID mismatch. Your debug container is running as a different non-root UID than the target container. To send a signal to another process, you must have the same UID as that process. The fix is to ensure the `runAsUser` value in your ephemeral container's security context **exactly matches** the UID of the target container. This is why Step 1 is so important.

### 💡 Alternative: Using `cdebug`

The `cdebug` tool is a user-friendly alternative to `kubectl debug`. It is aware of these common issues and handles them automatically.

*   It can **auto-detect** targets with `runAsNonRoot` and adjust the debugger's security context accordingly, so you don't need to manually find and set the UID.
*   It provides a `--privileged` flag if you need elevated permissions, although that is not required for this specific challenge.

To use it for this task, you would simply run:
```bash
cdebug exec -it non-root
```
`cdebug` will create an ephemeral container with the correct non-root UID and drop you into a shell, allowing you to send the signal.
