If you do not specify **Requests** and **Limits** for a container, Kubernetes treats it as a **"BestEffort"** Pod. 

Here is exactly what happens, broken down by the scheduler, the runtime, and the stability of your node.

---

### 1. Effect on the Scheduler (Placement)
- **`Requests` default to `0`**: The Scheduler sees the Pod as requiring **zero** CPU and **zero** Memory to run.
- **Result**: The Scheduler will place this Pod on any node that has *any* remaining free capacity. However, because it takes up zero "reserved" space, it's essentially fitting into the leftover gaps of the node.
- **Risk**: If the node is heavily packed with other Pods that *do* have Requests, your BestEffort Pod might have to wait for scraps of CPU time, leading to severe performance degradation.

---

### 2. Effect on the Runtime (CPU & Memory Behavior)

| Resource | What Happens Without a Limit | Result |
| :--- | :--- | :--- |
| **CPU** | No upper bound. The container can consume **all available CPU cycles** on the node if they are free. | If a CPU-intensive BestEffort Pod runs wild, it can **starve** other Pods (including critical system components) of CPU. The Linux kernel will try to share fairly, but your app will likely be throttled heavily if the node is busy. |
| **Memory** | No upper bound. The container can consume **all available RAM** on the node until the node runs out. | This is **the most dangerous scenario**. If a BestEffort container has a memory leak, it will eat up all node memory. When the node runs out of RAM, the kernel triggers the **OOM Killer**. |

---

### 3. Effect on QoS Class & Eviction (The `BestEffort` Danger)

When you omit both requests and limits, your Pod is assigned the **`BestEffort`** Quality of Service (QoS) class. 

**Here is the critical consequence**:
- When the node is under memory pressure (e.g., other pods are using RAM), the kubelet starts evicting Pods to free up memory.
- The eviction order is strict: **`BestEffort` Pods are killed FIRST**, before `Burstable` or `Guaranteed` Pods.
- This means your Pods are the **first to be sacrificed** if the node gets even slightly busy.

---

### 4. What if you set *only* a Request, but no Limit?

This is a very common scenario and is often considered a best practice for CPU.

- You get a **`Burstable`** QoS class (Medium priority).
- **Scheduler**: Reserves the `Request` amount for you. Good!
- **CPU**: No Limit means it can burst up to 100% of the node's CPU if it's free. This is usually desirable for batch jobs or APIs.
- **Memory**: Since you didn't set a Memory Limit, the container could still eat all the node's memory and cause an OOM kill. 
- **Rule of thumb**: **Always set Memory Limits**. Setting CPU Limits is optional (many cloud providers recommend only setting CPU Requests to avoid throttling issues).

---

### 5. What if you set *only* a Limit, but no Request?

- You get a **`Burstable`** QoS class.
- **Scheduler**: The Scheduler uses **the Limit value as the Request** (they are implicitly the same). So it reserves that amount on the node.
- **Result**: This is generally safe, but wasteful. You are telling the scheduler to reserve the maximum possible RAM/CPU on the node, which reduces the number of other Pods you can fit onto that node.

---

### 📊 Summary Table: The 3 QoS Classes

| Configuration | QoS Class | Scheduler Uses | OOM/Eviction Priority | CPU Behavior |
| :--- | :--- | :--- | :--- | :--- |
| **No Requests, No Limits** | **BestEffort** | 0 | **Killed First** | Unbounded (can starve others). |
| **Request < Limit** (or Request missing) | **Burstable** | Request (or Limit if Request missing) | Killed Second | Can burst up to Limit. |
| **Request == Limit** (Exact match) | **Guaranteed** | Request | **Killed Last** (Highest priority) | Capped exactly at Limit. |

---

### 💎 Conclusion: Why you MUST set them

1.  **Stability**: Without Memory Limits, a single rogue container can crash your entire Node (`NodeNotReady` state).
2.  **Fairness**: Without CPU Requests, the scheduler can't guarantee your app gets enough CPU to respond to requests in time (leading to timeouts).
3.  **Avoid "Noisy Neighbors"**: In a multi-tenant cluster, BestEffort pods can hog resources and ruin the performance of critical apps.

**Production Standard Recommendation**:
```yaml
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"   # ALWAYS set Memory Limit
    # cpu: "500m"     # Optional: Set CPU Limit if you don't want CPU bursts
```
