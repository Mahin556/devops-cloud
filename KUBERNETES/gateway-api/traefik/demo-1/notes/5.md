These are excellent questions. Let's answer them one by one.

---

# 1. Can we configure TLS at the Gateway level or the Route level?

**Yes, but they have different responsibilities.**

## Gateway Level (Most Common)

The **Gateway** owns the listener and the TLS certificate.

Example:

```yaml
listeners:
- name: https
  protocol: HTTPS
  port: 443

  tls:
    mode: Terminate
    certificateRefs:
    - name: my-cert
```

Here the Gateway:

* Listens on port 443
* Performs the TLS handshake
* Uses the certificate
* Decrypts HTTPS traffic

The `HTTPRoute` only defines routing rules.

---

## Route Level

An `HTTPRoute` **does not configure TLS certificates**.

Instead, it can:

* Match on hostnames
* Define routing rules
* Apply filters

For example:

```yaml
spec:
  hostnames:
  - app.example.com
```

The route does **not** reference a TLS certificate.

Some implementations support advanced features like backend TLS policies, but **TLS termination itself belongs to the Gateway**.

---

# 2. Is `hostname` mandatory on the Gateway?

**No.**

It is **optional**.

Example without a hostname:

```yaml
listeners:
- name: https
  protocol: HTTPS
  port: 443

  tls:
    mode: Terminate
    certificateRefs:
    - name: my-cert
```

This listener accepts requests for **any hostname** (subject to the Gateway implementation and certificate).

---

# 3. When should you specify a hostname?

Suppose you have:

```text
app.example.com

api.example.com

admin.example.com
```

You can restrict a listener:

```yaml
hostname: app.example.com
```

Now only requests for:

```text
https://app.example.com
```

match this listener.

Requests for:

```text
https://api.example.com
```

will not match it.

---

# 4. What if the Gateway has no hostname?

Example:

```yaml
listeners:
- name: https
  protocol: HTTPS
  port: 443
```

This means:

```text
Accept all hostnames
```

The `HTTPRoute` decides which hostnames it serves.

---

# 5. Can the Route specify a hostname if the Gateway doesn't?

Yes.

Gateway:

```yaml
listeners:
- port: 443
```

HTTPRoute:

```yaml
hostnames:
- app.example.com
```

This is perfectly valid.

---

# 6. What if both specify hostnames?

Suppose:

Gateway:

```yaml
hostname: "*.example.com"
```

Route:

```yaml
hostnames:
- api.example.com
```

This works because:

```text
api.example.com
```

matches:

```text
*.example.com
```

However, if the Gateway is:

```yaml
hostname: app.example.com
```

and the Route is:

```yaml
hostnames:
- api.example.com
```

then the Route **will not attach** because the hostnames are incompatible.

---

# Hostname Matching

```text
Gateway Listener
hostname: *.example.com
        |
        |
--------------------------
|           |            |
app.example.com
api.example.com
dev.example.com
```

All three match.

---

# Best Practice

For most production clusters:

Gateway:

```yaml
listeners:
- hostname: "*.example.com"
```

Routes:

```yaml
hostnames:
- app.example.com
```

```yaml
hostnames:
- api.example.com
```

This allows one Gateway to securely serve multiple applications while each route handles its own hostname.

---

# Interview Answer

**Q: Is the hostname required on a Gateway?**

> No. The `hostname` field on a Gateway listener is optional. If it is omitted, the listener can accept requests for any hostname. When specified, it restricts the listener to matching only that hostname or wildcard domain. An `HTTPRoute` can also specify hostnames, and for the route to attach successfully, its hostname must be compatible with the Gateway listener's hostname.
