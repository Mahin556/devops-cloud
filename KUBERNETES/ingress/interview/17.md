## Understanding URL Rewriting: Complete Breakdown

### The Problem

Your legacy application expects URLs in the format `/v1/users`, but modern clients call `/api/users`. You can't change the application code, so the Ingress controller rewrites the path transparently.

---

## How the Regex Pattern Works

### Pattern: `/api(/|$)(.*)`

Let me break this down character by character:

```
Pattern: /api(/|$)(.*)

/api         = Literal string - must match "/api" exactly
(            = Start capture group #1 ($1)
  /|$        = Either "/" OR end-of-string ($)
)            = End capture group #1
(.*)         = Capture group #2 ($2) - matches anything after the first group
             = * means zero or more characters
```

### Real Examples with Capture Groups

```
Request: /api/users
├─ Matches /api
├─ Captures $1 = "/" (from /|$)
└─ Captures $2 = "users" (from .*)

Request: /api/products/123
├─ Matches /api
├─ Captures $1 = "/" (from /|$)
└─ Captures $2 = "products/123" (from .*)

Request: /api
├─ Matches /api
├─ Captures $1 = "" (from /|$ - the $ means end-of-string)
└─ Captures $2 = "" (nothing left)
```

---

## The Rewrite-Target Annotation

```yaml
annotations:
  nginx.ingress.kubernetes.io/rewrite-target: /v1/$2
```

**Translation:**
- Take the original path
- Discard `/api/$1` part
- Replace with `/v1/`
- Append `$2` (the captured remainder)

### Step-by-Step Transformation

```
Original:     /api/users
              /api  /
                    $1

Remaining:    /users
              users
              $2

Rewrite:      /v1/$2
              /v1/users

Forward to backend: /v1/users ✅
```

---

## Why `/api(/|$)(.*)` Instead of `/api/(.*)`?

The pattern `/api(/|$)(.*)` is more complex than `/api/(.*)`. Why?

**To handle edge cases:**

```yaml
# Pattern: /api(/|$)(.*)
Request: /api/users
Result: $1="/" $2="users"
Rewrite: /v1/users ✅

Request: /api
Result: $1="" $2=""
Rewrite: /v1/ or /v1 ✅

---

# Simpler pattern: /api/(.*)
Request: /api/users
Result: $1="users"
Rewrite: /v1/users ✅

Request: /api  ← PROBLEM
Result: No match! (pattern requires /)
Response: 404 Not Found ❌
```

The `(/|$)` allows matching `/api` without a trailing path or with one.

---

## Simpler Alternative Pattern

The YAML in your example also shows a simpler approach:

```yaml
path: /api/(.*)
rewrite-target: /v1/$1
```

**This is cleaner but more restrictive:**

```
Request: /api/users
├─ Matches /api/
└─ Captures $1 = "users"
└─ Rewrites to /v1/users ✅

Request: /api (no trailing slash)
└─ NO MATCH ❌
└─ 404 Not Found
```

**Use this simpler pattern if:**
- All clients always include a path after `/api`
- You want to reject bare `/api` calls
- Your API never uses `/api` as a standalone endpoint

**Use the complex pattern if:**
- Some clients might call `/api` without a path
- You want to support both `/api` and `/api/something`
- You need maximum compatibility

## Complete Request Flow

```
1️⃣  Client Sends Request
    Browser/App: GET http://example.com/api/users
    Headers: Host, User-Agent, etc.

2️⃣  DNS Resolution
    Browser resolves example.com → 192.168.1.100

3️⃣  Request Hits Ingress Controller
    192.168.1.100:80 → Ingress NGINX on Kubernetes node

4️⃣  Ingress Reads Request
    Path: /api/users
    Host: example.com
    Method: GET

5️⃣  Match Against Rules
    Does it match the Ingress rule?
    ├─ Host: example.com ✅
    └─ Path: /api/users matches /api/(.*) ✅

6️⃣  Regex Capture
    Pattern: /api/(.*)
    Request: /api/users
    Captures: $1 = "users"

7️⃣  Apply Rewrite-Target
    Original path: /api/users
    Rewrite rule: /v1/$1
    New path: /v1/users

8️⃣  Forward to Service
    Ingress forwards with NEW path
    Service: legacy-service:80
    Path: /v1/users ← Changed!

9️⃣  Service Routes to Pod
    Selects pod running legacy app
    Forwards: GET /v1/users

🔟 Pod Receives Request
    Legacy app sees: GET /v1/users
    Matches its route handler
    Returns 200 OK with user data

1️⃣1️⃣ Response Sent Back
    Through Ingress
    Through Service
    To Client
    Client receives: {"users": [...]}
```

## YAML Annotation Explained

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite-ingress
  annotations:
    # Most important - rewrite the path
    nginx.ingress.kubernetes.io/rewrite-target: /v1/$2
    
    # Enable regex pattern matching
    nginx.ingress.kubernetes.io/use-regex: "true"
```

**`nginx.ingress.kubernetes.io/rewrite-target`**
- NGINX-specific annotation (won't work with other ingress controllers)
- Tells NGINX to change the path before forwarding
- Uses `$1`, `$2`, `$3`, etc. to reference capture groups

**`nginx.ingress.kubernetes.io/use-regex: "true"`**
- Enables regex support for the path
- Without this, `/api(/|$)(.*)` is treated as literal string (won't match)
- With this, special regex characters like `(`, `|`, `*` are recognized

## Complete Working Example

```yaml
apiVersion: v1
kind: Service
metadata:
  name: legacy-service
spec:
  type: ClusterIP
  selector:
    app: legacy-backend
  ports:
  - port: 80
    targetPort: 80

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: legacy-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: legacy-backend
  template:
    metadata:
      labels:
        app: legacy-backend
    spec:
      containers:
      - name: app
        image: legacy-app:1.0
        ports:
        - containerPort: 80

---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /v1/$2
    nginx.ingress.kubernetes.io/use-regex: "true"
spec:
  ingressClassName: nginx
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: legacy-service
            port:
              number: 80
```

## Why This Works Without Code Changes

The rewrite happens **at the network layer**, before the request reaches your application:

```
Network/Transport Layer (Ingress)
└─ Path rewriting happens HERE
   └─ /api/users → /v1/users

Application Layer (Your legacy app)
└─ Only sees /v1/users
└─ Doesn't know rewriting occurred
└─ No code changes needed ✅
```

## Summary Table

| Concept | What It Does |
|---------|---|
| **Pattern `/api(/|$)(.*)`** | Matches `/api` optionally followed by more path |
| **Capture group `$1`** | The `/` or empty string after `/api` |
| **Capture group `$2`** | Everything after the first group (users, products/123, etc.) |
| **Rewrite-target** | Reconstructs path using `$1`, `$2`, etc. |
| **`use-regex: true`** | Enables special regex characters in pattern |
| **No app changes** | Rewrite is transparent to your legacy code |
