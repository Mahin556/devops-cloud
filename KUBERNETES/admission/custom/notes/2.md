## 1. The Admission Request Lifecycle (Image 4)

When you run `kubectl apply`, the request does **not** go straight to the database. It passes through four stages in order:

```
kubectl → Authentication → Authorization → Admission Control → etcd
```

- **Authentication** – confirms *who* you are
- **Authorization** – confirms you're *allowed* to make this request (RBAC)
- **Admission Control** – confirms the request is *valid and safe* — this is the final gate before anything touches etcd
- If admission fails, the request is rejected before storage

## 2. What an Admission Controller Is (Images 1, 5)

It's a gatekeeper that intercepts every create/update/delete request and falls into one of two buckets:

| Type | Behavior | Example |
|---|---|---|
| **Mutating** | Changes the request | Injects a sidecar container, adds labels/annotations |
| **Validating** | Only allows/blocks — never modifies | Rejects a pod for missing `runAsNonRoot` |

## 3. Why Ordering Matters (Images 2, 6)

```
API Request → Mutating Webhooks → (temp save) → Validating Webhooks → ✅ etcd
                                                                     → ❌ Request Rejected
```

**Mutating always runs before validating.** Reasoning from the transcript: since mutating webhooks can change the object, the API server needs to validate the **final, fully-modified** version — otherwise someone could sneak a policy-violating change in after validation passed, bypassing security entirely.

## 4. Configuring the Webhook — YAML structure

- **Lines 4–5**: the webhook's `name`
- **Lines 6–10**: the `rules` block — scoped to only the `CREATE` operation on `pods` (updates/deletes are ignored by this webhook)
- **Lines 11–15**: `clientConfig` — where the API server sends the request, pointing to a `service` named `webhook-server` in the `default` namespace

A `ValidatingWebhookConfiguration` matching that description looks like this:

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: pod-policy-webhook          # lines 4-5: webhook name
webhooks:
  - name: pod-policy-webhook.default.svc
    rules:                          # lines 6-10: scope
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]      # only CREATE — not UPDATE/DELETE
        resources: ["pods"]
    clientConfig:                   # lines 11-15: where to send the request
      service:
        name: webhook-server
        namespace: default
        path: "/validate"
      caBundle: <base64-encoded-CA-cert>
    admissionReviewVersions: ["v1"]
    sideEffects: None
    failurePolicy: Fail
```

A couple of fields the instructor didn't cover but that you'll need in practice:
- **`caBundle`** — the API server talks to your webhook over TLS, so it needs your webhook service's CA cert to trust the connection
- **`failurePolicy`** — `Fail` blocks the request if the webhook is unreachable; `Ignore` lets it through. For security-critical webhooks, `Fail` is safer (though it can cause outages if your webhook goes down)
- **`sideEffects: None`** — required field since Kubernetes 1.20+; tells the API server your webhook doesn't cause side effects outside the admission review itself

## 5. The Webhook Server Logic (Images 7, 12)

The backend receiving these calls follows this pattern (Go example from the slide):

```go
func handleValidatePods(w http.ResponseWriter, r *http.Request) {
    var review admissionv1.AdmissionReview
    if err := json.NewDecoder(r.Body).Decode(&review); err != nil {
        http.Error(w, "invalid request", http.StatusBadRequest)
        return
    }

    pod := corev1.Pod{}
    json.Unmarshal(review.Request.Object.Raw, &pod)

    allowed := true
    if pod.Spec.Containers[0].Image == "nginx:latest" {
        allowed = false
    }

    response := admissionv1.AdmissionResponse{Allowed: allowed}
    // Send response back to API server
}
```

Flow:
1. API server sends an `AdmissionReview` JSON object
2. Your server decodes it and pulls out the actual pod spec
3. You run your check (here: reject the `latest` tag on nginx — a real anti-pattern since `latest` isn't pinned/reproducible)
4. You set `allowed: true/false` on the `AdmissionResponse`
5. The API server reads that boolean and accepts or rejects the original request

## 6. Debugging Common Failures (Image 8)

**"Connection refused"** is the most common error — it means the API server tried to reach your webhook service and couldn't. Root causes and checks, in order:

```bash
# 1. Does the service exist at all?
kubectl get svc webhook-server -n default

# 2. Are the backing pods actually running?
kubectl get pods -n default -l app=webhook-server

# 3. Check logs for crash loops
kubectl logs -l app=webhook-server -n default
```

Common underlying causes the instructor flags: a missing environment variable or misconfigured port causing the server to crash immediately on startup, or a NetworkPolicy silently blocking traffic between the API server and your webhook pod.

## 7. Real-World Case Study (Images 9, 12)

A logistics company had developers routinely running containers as root (a major security risk) with no practical way to audit every deployment by hand. They built a **validating webhook** that:
- Checks every pod spec for a non-root security context
- Rejects the pod if `runAsNonRoot` is missing

Result: a 98% drop in unauthorized container escapes within a month — illustrating that policy-as-code beats manual review at scale.

## 8. When to Use / Not Use Webhooks (Image 10)

| Do use for | Don't use for |
|---|---|
| Security policy enforcement (block root containers, require resource limits) | Heavy compute tasks — every webhook call adds latency to *every* API request |
| Injecting default labels/sidecars | Cross-resource dependencies — checking another resource's state invites hard-to-debug race conditions |

## Best-practice recap
- Mutating runs before validating, always
- Keep webhook latency low — a slow webhook slows your entire API server
- Use in-cluster service endpoints (not external URLs) to keep traffic local and fast
- Prefer `failurePolicy: Fail` for security-critical checks, `Ignore` only where availability trumps strict enforcement
