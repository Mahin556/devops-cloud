### Database username and password must not appear in Git repositories or be visible in plain text in pod specifications.

**Solution:**

**Step 1 - Create Secret directly in cluster (NEVER in Git):**
```bash
# Create secret directly from CLI - no YAML file needed
kubectl create secret generic db-credentials \
  --from-literal=username=myapp-user \
  --from-literal=password='S3cur3P@ssw0rd!' \
  -n production

# Or from CI/CD pipeline
kubectl create secret generic db-credentials \
  --from-literal=username=$DB_USER \
  --from-literal=password=$DB_PASSWORD \
  -n production
```

**Step 2 - Reference Secret in Deployment YAML (Safe to store in Git):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: myapp:latest
        env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: db-credentials      # Reference only - no credentials visible
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
        # Alternative: Mount entire secret as files
        volumeMounts:
        - name: secret-volume
          mountPath: /etc/secrets
          readOnly: true
      volumes:
      - name: secret-volume
        secret:
          secretName: db-credentials
```

**Verification:**
```bash
# View secret (base64 encoded)
kubectl get secret db-credentials -o yaml

# Decode to verify
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
```

**Key Points:**
- Secrets are created directly in cluster via CLI or CI/CD - never in Git
- Deployment YAML only references secret name and key - no sensitive data
- `kubectl create secret` automatically base64 encodes values
- Secrets are stored in etcd (can be encrypted at rest)
- RBAC controls who can access secrets
- Alternative: External Secret Management (HashiCorp Vault, AWS Secrets Manager)
- Never use `stringData` in YAML files that go to Git



### Custom `nginx.conf` needs occasional routing and timeout updates. Must be updated without rebuilding the container image.

**Solution:**

**Step 1 - Create ConfigMap from existing nginx.conf file:**
```bash
# Read existing nginx.conf into ConfigMap
kubectl create configmap nginx-config \
  --from-file=nginx.conf \
  -n production
```

**ConfigMap YAML equivalent:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  nginx.conf: |
    events {
        worker_connections 1024;
    }
    http {
        server {
            listen 80;
            location / {
                proxy_pass http://backend-service;
                proxy_read_timeout 60s;
                proxy_connect_timeout 30s;
            }
            location /api {
                proxy_pass http://api-service;
                proxy_read_timeout 120s;
            }
        }
    }
```

**Step 2 - Mount ConfigMap in NGINX Deployment:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-proxy
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx-proxy
  template:
    metadata:
      labels:
        app: nginx-proxy
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80
        volumeMounts:
        - name: nginx-config-volume
          mountPath: /etc/nginx/nginx.conf
          subPath: nginx.conf          # KEY: Mount only the file, not entire directory
      volumes:
      - name: nginx-config-volume
        configMap:
          name: nginx-config
```

**Update Configuration:**
```bash
# Edit ConfigMap
kubectl edit configmap nginx-config

# Update proxy_read_timeout to 90s

# Reload NGINX or restart pods
kubectl rollout restart deployment/nginx-proxy

# Or reload NGINX without restart (if container supports it)
kubectl exec -it <nginx-pod> -- nginx -s reload
```

**Key Points:**
- ConfigMap stores the complete `nginx.conf` content
- `subPath: nginx.conf` is critical - mounts only that file
- Without `subPath`, the entire `/etc/nginx/` directory would be replaced
- NGINX reads configuration from mounted path
- ConfigMap updates propagate to the file inside the container
- NGINX requires reload (`nginx -s reload`) or pod restart to apply changes
- No image rebuild needed when configuration changes
