# Monitoring — Starting Theory

Before touching Prometheus, Grafana, Loki, or any configuration, first understand **what monitoring is, why we need it, and what exactly we monitor**.

The source starts with the idea of building a **central monitoring system** for services, microservices, and containers so that their metrics and logs can be collected centrally and visualized/tracked. 

---

# 1. What is Monitoring?

**Monitoring is the process of continuously observing the health, performance, and behavior of systems and applications.**

For example, suppose we have:

```text
Server
 ├── CPU
 ├── Memory
 ├── Disk
 ├── Network
 └── Applications
       ├── API
       ├── Database
       └── Microservices
```

We want to know:

* Is the server running?
* Is CPU utilization increasing?
* Is memory getting full?
* Is disk space running out?
* Are applications responding?
* Are requests becoming slow?
* Are applications returning errors?
* Are services available?
* What happened when an error occurred?

The source gives examples such as monitoring CPU, memory, available storage, request-response time, and database connection time. 

---

# 2. Why Do We Need Monitoring?

Imagine we have an application:

```text
Client
   ↓
Express Application
   ↓
Database
```

Everything appears to be working.

Then a customer reports:

> "The application was very slow at 2 PM."

Without monitoring, we may have no idea what happened.

Maybe:

```text
CPU       → 95%
Memory    → 98%
Database  → slow
Network   → high latency
API       → 3 seconds response time
```

If we had monitoring, we could go back to the historical data and investigate.

So monitoring helps us answer:

```text
WHAT happened?
WHEN did it happen?
HOW severe was it?
WHICH service was affected?
WHY did it happen?
```

---

# 3. Centralized Monitoring

In a real production environment, we don't have only one server.

We might have:

```text
Server 1
Server 2
Server 3
Server 4
Server 5

Microservice A
Microservice B
Microservice C

Database
Redis
Kafka
Kubernetes
Containers
```

If every server has its own monitoring system:

```text
Server 1 → Monitoring 1
Server 2 → Monitoring 2
Server 3 → Monitoring 3
Server 4 → Monitoring 4
```

This becomes difficult to manage.

Instead, we create:

```text
                    CENTRAL
                   MONITORING
                     SYSTEM
                        ▲
          ┌─────────────┼─────────────┐
          │             │             │
       Server 1      Server 2      Server 3
          │             │             │
       Service A     Service B     Service C
```

All important metrics and logs are sent/collected into one central system.

That is the central-monitoring concept emphasized in the source. 

---

# 4. Two Major Things We Monitor

The source divides monitoring into two important areas:

```text
Monitoring
    │
    ├── Metrics
    │
    └── Logs
```



These are **not the same thing**.

---

# 5. What Are Metrics?

A **metric is a numerical measurement of something happening in your system.**

Examples:

```text
CPU utilization        = 72%
Memory utilization     = 65%
Disk available         = 120 GB
Request latency        = 250 ms
Requests per second    = 120
Error count            = 15
Active connections     = 40
```

So metrics are basically:

> **Numbers that describe the current or historical state of a system.**

The source describes metrics as numbers used to observe things such as latency and resource utilization. 

---

# 6. Examples of Metrics

## Infrastructure metrics

```text
CPU
Memory
Disk
Network
Load average
Processes
```

For example:

```text
CPU = 82%
Memory = 70%
Disk = 45%
```

---

## Application metrics

```text
HTTP requests
HTTP errors
Request latency
Active requests
Database latency
Database connections
```

For example:

```text
HTTP requests/sec = 250
HTTP 500 errors = 12
Average latency = 180ms
```

The source specifically gives request-response time and database connection time as examples of application-level metrics. 

---

# 7. What Are Logs?

A **log is a record of an event that happened inside a system or application.**

Example:

```text
2026-08-21 12:10:22 INFO Server started
2026-08-21 12:11:03 INFO User request received
2026-08-21 12:11:08 ERROR Database connection failed
```

Unlike metrics, logs contain **contextual information**.

A metric might tell us:

```text
HTTP 500 errors = 20
```

A log might tell us:

```text
ERROR
Database connection failed
host=db01
timeout=5000ms
```

So:

```text
Metric → WHAT is happening?
Log    → WHAT exactly happened / context?
```

---

# 8. Metrics vs Logs

| Metrics             | Logs                         |
| ------------------- | ---------------------------- |
| Numerical data      | Event records                |
| Good for trends     | Good for investigation       |
| CPU = 80%           | "Database connection failed" |
| Latency = 500ms     | Stack trace                  |
| Error count = 100   | Error message                |
| Usually time-series | Timestamped events           |

Think of it like:

```text
METRIC

CPU
80%
70%
65%
90%
95%
```

versus:

```text
LOG

12:01 INFO Request received
12:02 INFO Request received
12:03 ERROR Database timeout
12:03 ERROR Connection refused
```

---

# 9. Why We Need Both

Suppose Grafana shows:

```text
HTTP Error Rate
       ↑
       │
       │       █
       │      ███
       │    █████
       └──────────────→ time
```

We know:

> Something went wrong.

But we still don't know why.

So we check logs:

```text
ERROR Database connection timeout
ERROR Database connection timeout
ERROR Database connection timeout
```

Now we have a direction for troubleshooting.

Therefore:

```text
Metrics
   ↓
Detect problem
   ↓
Logs
   ↓
Investigate problem
```

This is one of the most important concepts to understand.

---

# 10. What Is Prometheus?

**Prometheus is a monitoring and time-series database system used primarily for collecting and querying metrics.**

In our architecture:

```text
Application
     │
     │ metrics
     ▼
Prometheus
     │
     ▼
Grafana
```

The source describes Prometheus as the monitoring tool responsible for collecting metrics. 

---

# 11. What Does Prometheus Collect?

For an application, Prometheus can collect:

```text
CPU
Memory
Process information
Request count
Request latency
Error count
Active requests
Custom business/application metrics
```

For example:

```text
process_resident_memory_bytes
process_cpu_user_seconds_total
http_requests_total
http_request_duration_seconds
```

---

# 12. What Is Prometheus Client?

This is an important distinction.

```text
Prometheus
```

and

```text
Prometheus Client
```

are different.

### Prometheus

The central monitoring server.

```text
Prometheus Server
     ↓
collects/stores metrics
```

### Prometheus Client

A library installed **inside your application**.

For Node.js:

```bash
npm install prom-client
```

The source follows this exact approach: install the Prometheus client inside the server/application and use it to generate metrics. 

---

# 13. Architecture

```text
                  Application Server
                ┌─────────────────────┐
                │                     │
                │   Express App       │
                │                     │
                │   prom-client       │
                │        │            │
                │        ▼            │
                │    /metrics         │
                │                     │
                └─────────┬───────────┘
                          │
                          │ scrape
                          ▼
                    ┌─────────────┐
                    │ Prometheus  │
                    └─────────────┘
```

This is the fundamental Prometheus model.

---

# 14. Pull Model

One very important Prometheus concept is that Prometheus normally **pulls/scrapes** metrics.

It doesn't mean:

```text
Application
   ↓
push metrics
   ↓
Prometheus
```

Instead:

```text
Prometheus
     │
     │ HTTP GET /metrics
     ▼
Application
     │
     │ metrics response
     ▼
Prometheus
```

For example:

```text
Prometheus
    |
    | GET http://app:8000/metrics
    |
    ▼
Express
    |
    | returns metrics
    ▼
Prometheus
```

---

# 15. What Is `/metrics`?

`/metrics` is an HTTP endpoint exposed by your application containing metrics in a format Prometheus understands.

Example:

```text
http://localhost:8000/metrics
```

You might see:

```text
process_cpu_user_seconds_total 12.34

process_resident_memory_bytes 12345678
```

The source explains that after collecting the metrics, they need to be **exposed**, which is why the `/metrics` endpoint is used. 

---

# 16. What Is Scraping?

**Scraping means Prometheus periodically requests the `/metrics` endpoint and collects the returned metrics.**

For example:

```text
12:00:00 → scrape
12:00:04 → scrape
12:00:08 → scrape
12:00:12 → scrape
```

If:

```yaml
scrape_interval: 4s
```

then Prometheus attempts to collect metrics every four seconds.

The source uses a four-second scrape interval in its demonstration. 

---

# 17. What Is Scrape Interval?

```yaml
global:
  scrape_interval: 15s
```

means:

> Scrape configured targets every 15 seconds.

Example:

```text
Prometheus
    │
    ├── 12:00:00 → scrape
    ├── 12:00:15 → scrape
    ├── 12:00:30 → scrape
    ├── 12:00:45 → scrape
    └── 12:01:00 → scrape
```

For a lab you might use:

```yaml
scrape_interval: 4s
```

For production, the interval depends on your monitoring requirements and scale.

---

# 18. What Is Grafana?

**Grafana is a visualization and dashboard platform.**

Think:

```text
Prometheus
    ↓
raw metrics
    ↓
Grafana
    ↓
beautiful graphs
```

Prometheus is responsible for storing/querying metrics.

Grafana is responsible for making those metrics easy for humans to understand.

The source demonstrates connecting Grafana to Prometheus and creating visualizations from Prometheus metrics. 

---

# 19. Prometheus vs Grafana

Very important interview question.

| Prometheus              | Grafana              |
| ----------------------- | -------------------- |
| Collects metrics        | Visualizes metrics   |
| Stores time-series data | Creates dashboards   |
| Provides PromQL         | Uses PromQL queries  |
| Scrapes targets         | Queries data sources |
| Monitoring backend      | Visualization layer  |

Architecture:

```text
Application
     ↓
Prometheus
     ↓
   metrics
     ↓
Grafana
     ↓
Dashboard
```

---

# 20. What Is Loki?

For logs, we can use:

```text
Loki
```

Loki is a log aggregation system designed to store and query logs.

Architecture:

```text
Application
     ↓
Logs
     ↓
Loki
     ↓
Grafana
```

And with a log collector:

```text
Application
     ↓
Promtail
     ↓
Loki
     ↓
Grafana
```

The source demonstrates moving from metrics to centralized log collection and then using Grafana with Loki to visualize/filter application logs. 

---

# 21. What Is Promtail?

Promtail is a log collection agent.

Its basic job:

```text
Read logs
    ↓
Attach labels/metadata
    ↓
Send logs
    ↓
Loki
```

So:

```text
Winston
   ↓
application logs
   ↓
Promtail
   ↓
Loki
```

---

# 22. What Is Winston?

Winston is a Node.js logging library.

Instead of:

```javascript
console.log("something happened");
```

you can use:

```javascript
logger.info("something happened");
```

or:

```javascript
logger.error("database connection failed");
```

This lets us create structured application logs that can later be collected centrally.
