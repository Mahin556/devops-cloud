The Kubernetes Pod lifecycle is a **journey from birth (creation) to death (termination)**. It is a complex state machine governed by the **kubelet**, the **scheduler**, and **container runtimes** (like containerd).

To truly understand it, you must look at two distinct things together: **Phases** (the high-level status) and **Conditions** (the fine-grained milestones). 

Here is the complete, step-by-step lifecycle.

---

### 1. The High-Level Phases (The Big Picture)
These are the `status.phase` fields you see when you run `kubectl get pod`. There are exactly 5 phases:

| Phase | What It Means |
| :--- | :--- |
| **Pending** | The Pod has been accepted by the cluster, but the main containers aren't running yet. (Either the scheduler is looking for a node, images are pulling, or volumes are mounting). |
| **Running** | The Pod has been bound to a node, and **all** containers have been created. At least one container is still running, or is in the process of starting/restarting. |
| **Succeeded** | **All** containers in the Pod have **successfully terminated** (exit code 0) and will not restart. (Used for Jobs/CronJobs). |
| **Failed** | **All** containers in the Pod have **terminated** (exit code non-zero), and at least one container has failed. |
| **Unknown** | The Pod's state cannot be determined, usually because the kubelet on the node is down and stopped reporting heartbeats. |

---

### 2. The Step-by-Step Timeline (From YAML to Running)
Here is exactly what happens inside the Kubernetes control plane from the moment you run `kubectl apply`:

#### Step 1: API Admission & Object Creation
- Your YAML is validated and stored in `etcd`.
- **Admission Controllers** (like PodSecurity or MutatingAdmissionWebhooks) might modify the Pod spec (e.g., automatically inject a Service Mesh sidecar).
- The Pod enters the **`Pending`** phase.

#### Step 2: Scheduling (`PodScheduled`)
- The **Scheduler** watches for unscheduled Pods. It filters nodes based on resources, `nodeSelector`, taints/tolerations, and affinity.
- Once it finds a suitable node, it binds the Pod to that node.
- **Condition Check**: `PodScheduled` becomes `True`.

#### Step 3: Volume Mounting & Sandbox Creation (`PodReadyToStartContainers`)
- The **kubelet** on the target node takes over.
- It mounts all volumes (PVCs, ConfigMaps, Secrets, `emptyDir`).
- It tells the container runtime (`containerd`) to create the **Pod Sandbox** (which sets up the network namespace and starts the `pause` container, giving the Pod its IP address).
- **Condition Check**: `PodReadyToStartContainers` becomes `True` (as discussed in your previous question).

#### Step 4: Init Containers Run (`Initialized`)
- If `spec.initContainers` are defined, the kubelet runs them **sequentially** (one by one). 
- Each init container must run to completion with `exit code 0` before the next starts.
- If one fails, the kubelet restarts it (depending on `restartPolicy`) or marks the Pod as `Failed`.
- **Condition Check**: `Initialized` becomes `True` once all init containers succeed.

#### Step 5: Main Containers Start (`ContainersReady`)
- The kubelet starts the main containers (specified in `spec.containers`) in the order they are listed.
- **`PostStart` Hook**: If defined, this lifecycle hook runs immediately after the container is created. If it fails, the container is terminated.

#### Step 6: Running & Health Checks
- The containers are now running. The kubelet continuously monitors their health using **Probes**:
  - **Startup Probe**: For slow-starting apps. Disables Liveness/Readiness until it succeeds. 
  - **Liveness Probe**: If this fails, the kubelet **restarts** the container.
  - **Readiness Probe**: If this fails, the kubelet removes the Pod's IP from Service endpoints (so it receives **no traffic**), but the container keeps running.
- **Condition Check**: `ContainersReady` becomes `True` *only* when all main containers are running and their Readiness Probes are passing.
- **Condition Check**: `Ready` becomes `True` (the aggregate of all other conditions).

---

### 3. The Termination Lifecycle (Graceful Shutdown)
When you delete a Pod (`kubectl delete pod`), it doesn't just get killed instantly. It goes through a **graceful termination** process:

1.  **`TERMINATING` Phase**: The Pod is marked for deletion. It stops receiving new traffic (Endpoints controller removes its IP).
2.  **`PreStop` Hook**: If defined, the kubelet executes the `PreStop` lifecycle hook (e.g., `/shutdown` endpoint). 
3.  **`SIGTERM`**: The kubelet sends a `SIGTERM` signal to the main process (PID 1) in each container.
4.  **Grace Period (`terminationGracePeriodSeconds`)**: The kubelet waits for the containers to exit. Default is **30 seconds**. 
5.  **`SIGKILL`**: If the containers haven't exited after the grace period, the kubelet sends `SIGKILL` (force kill).
6.  **Resource Cleanup**: Kubelet releases all resources (volumes, IP address, sandbox). The Pod is removed from the API server.

---

### 4. Restart Policies (How the Kubelet Reacts to Failure)
The kubelet's behavior depends on `spec.restartPolicy`:

| Policy | Behavior |
| :--- | :--- |
| **`Always`** (Default) | Restart containers regardless of exit code. (Used for long-running services). |
| **`OnFailure`** | Restart only if the container exits with a non-zero code. (Used for Jobs). |
| **`Never`** | Never restart. If it exits, it stays exited. |

### 5. Complete Visual Flow Summary

```text
[ YAML Applied ]
      ↓
[ Pending ] ← (Waiting for scheduler)
      ↓
[ PodScheduled=True ] ← (Bound to a node)
      ↓
[ Volumes Mounting, Sandbox Creation ] 
      ↓
[ PodReadyToStartContainers=True ] ← (Infrastructure ready!)
      ↓
[ Init Containers Running... ] 
      ↓
[ Initialized=True ] ← (All init containers done)
      ↓
[ Main Containers Starting... ]
      ↓
[ ContainersReady=True ] ← (All apps running, probes passing)
      ↓
[ Ready=True ] ← (Pod is healthy & serving traffic!)
      ↓
[ ⏳ Running Continuously... ] ← (Liveness/Readiness probes cycle)
      ↓
[ kubectl delete / Crash / OOM ]
      ↓
[ PreStop Hook → SIGTERM → Grace Period → SIGKILL ]
      ↓
[ TERMINATING ] → [ Removed from etcd ]
```

### 6. The Golden Command to Debug Lifecycle Issues
If a Pod is stuck, this single command tells you exactly where it is in the lifecycle:

```bash
kubectl describe pod <pod-name>
```
Look at the **Events** section. You will see sequential events like:
- `Scheduled`
- `SuccessfulAttachVolume` / `MountVolume`
- `Started container` (for sandbox)
- `Pulled image` / `Created container`
- `Started container` (for main app)
- `Readiness probe failed` (if unhealthy)
