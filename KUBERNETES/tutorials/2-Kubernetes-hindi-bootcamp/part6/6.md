Here are the default values for all probe configuration fields, based on the official Kubernetes documentation:

### ⏱️ Timing & Threshold Fields

| Field | Default Value | Notes |
| :--- | :--- | :--- |
| **`initialDelaySeconds`** | `0` | Number of seconds to wait after the container starts before the first probe is run. |
| **`periodSeconds`** | `10` | How often (in seconds) to perform the probe. |
| **`timeoutSeconds`** | `1` | Number of seconds after which the probe times out and is considered a failure. |
| **`successThreshold`** | `1` | Minimum consecutive successes needed for the probe to be considered successful after a failure. **Must be `1` for liveness and startup probes**. |
| **`failureThreshold`** | `3` | Number of consecutive probe failures after which the probe is considered to have failed. |

### 🌐 HTTP Probe Specific Fields

| Field | Default Value |
| :--- | :--- |
| **`host`** | Pod's IP address |
| **`scheme`** | `HTTP` |
| **`path`** | `/` |
| **`httpHeaders`** | No custom headers by default. The `User-Agent` defaults to `kube-probe/<version>` and `Accept` defaults to `*/*` |

### ⚠️ Important Caveats

*   **Startup Probe**: If a startup probe is configured, liveness and readiness probes are **disabled** until the startup probe succeeds.
*   **Readiness Probe**: Before the `initialDelaySeconds` elapses, a readiness probe is considered to have **failed** by default. This prevents traffic from being sent to a container that hasn't had time to initialize.
*   **Liveness Probe**: Liveness probes do **not** wait for readiness probes to succeed. If you need to delay a liveness probe, use `initialDelaySeconds` or a startup probe.
