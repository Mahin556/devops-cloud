This is a classic example of **canary deployment using the NGINX Ingress Controller**. The key idea is that **you do not modify the existing (stable) Ingress**. Instead, you create **another Ingress** with the **same host and path**, mark it as a **canary**, and let the NGINX Ingress Controller split traffic.

Let's walk through it step by step.

---

# What is a Canary Deployment?

A canary deployment gradually exposes a **new version (v2)** of your application to a small percentage of users while the majority continue using the **stable version (v1)**.

Instead of this:

```
100% → v1

↓

100% → v2
```

you do this:

```
100% → v1

↓

90% → v1
10% → v2

↓

70% → v1
30% → v2

↓

50% → v1
50% → v2

↓

100% → v2
```

If something goes wrong, you simply stop sending traffic to v2.

---

# Architecture

```
                  Client
                     |
                     |
             Ingress NGINX
                     |
        -------------------------
        |                       |
   Stable Ingress         Canary Ingress
        |                       |
   Service v1              Service v2
        |                       |
 Deployment v1           Deployment v2
```

Notice there are:

* 2 Deployments
* 2 Services
* 2 Ingresses

# Step 1 – Deploy Version 1

Create

```
Deployment v1
```

↓

```
Service v1
```

↓

```
Ingress
```

The ingress looks like

```yaml
host: canary-app.com

path: /

backend:
    service: canary-test-v1
```

All traffic goes here.

```
Client
   |
NGINX
   |
Service v1
```

100%

---

# Step 2 – Deploy Version 2

Now deploy

```
Deployment v2
```

and

```
Service v2
```

**Do not touch v1.**

Nothing changes yet.

---

# Step 3 – Create Another Ingress

This surprises many people.

Instead of editing the existing ingress, create another one.

Stable ingress

```yaml
host: canary-app.com

path: /

backend:
    service: canary-test-v1
```

Canary ingress

```yaml
host: canary-app.com

path: /

backend:
    service: canary-test-v2
```

Notice:

Same host

Same path

Different backend

Normally Kubernetes rejects this because two ingresses cannot define the same host/path combination.

You would get:

```
host "canary-app.com"
path "/"

already defined
```

---

# Why doesn't Kubernetes reject it?

Because of

```yaml
nginx.ingress.kubernetes.io/canary: "true"
```

This annotation tells the NGINX admission webhook:

> This is **not** another normal ingress.
>
> It is a canary ingress.

Therefore duplicate host/path is allowed.

---

# Step 4 – Traffic Splitting

Add

```yaml
nginx.ingress.kubernetes.io/canary-weight: "30"
```

Now NGINX generates routing logic similar to:

```
If random < 30%

↓

Go to v2

Else

↓

Go to v1
```

Result

```
30%

↓

v2

70%

↓

v1
```

# Canary by Header

Instead of percentage

```
30%
```

you can test only your QA team.

Example

```yaml
nginx.ingress.kubernetes.io/canary-by-header: X-Canary
```

If request

```
GET /

X-Canary: always
```

↓

Go to

```
v2
```

Otherwise

```
v1
```

Useful for internal testing.

# Rollback

Suppose logs show

```
500 errors

Memory leak

CrashLoopBackOff

Latency increase
```

Just delete

```
Canary Ingress
```

or set

```yaml
canary-weight: "0"
```

Immediately

```
100%

↓

v1
```

No Deployment rollback is required.

---

# Promotion to v2

Once v2 is proven stable:

1. Update the **stable Ingress** so its backend points to `canary-test-v2` (or rename/relabel the Services so the stable Service targets the v2 Pods).
2. Remove the **canary Ingress**.
3. Optionally delete the old **v1 Deployment** after you're confident it's no longer needed.

Now all traffic flows to v2.

---

# Advantages

* **No downtime** during rollout.
* **Fast rollback** by disabling or removing the canary Ingress.
* **Gradual exposure** reduces risk.
* **No service mesh required**—the NGINX Ingress Controller handles the routing.
* **Flexible targeting** using percentages, headers, or cookies.

## Traffic Flow Summary

```
Client
   |
   | 100 Requests
   |
NGINX Ingress Controller
   |
   +-------------------------+
   |                         |
70% (Stable Ingress)     30% (Canary Ingress)
   |                         |
Service v1               Service v2
   |                         |
Pods v1                  Pods v2
```

This approach is one of the simplest ways to implement canary releases in Kubernetes because it leverages the routing capabilities already built into the NGINX Ingress Controller, without introducing the additional complexity of a service mesh.
