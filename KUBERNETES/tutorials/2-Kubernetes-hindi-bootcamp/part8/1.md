In Kubernetes, a **flat network** is the default networking model. It means every Pod in the cluster gets its own unique, routable IP address and can communicate directly with every other Pod, regardless of which node they're on, without using Network Address Translation (NAT).

This is a fundamental principle of Kubernetes networking, making it different from older container networking models where containers on different hosts couldn't talk to each other directly.

### 🔑 How Does a Flat Network Work?

The flat network model is implemented by a **Container Network Interface (CNI) plugin**, which is responsible for assigning IP addresses to Pods and managing network connectivity.

The core principle is that the IP addresses for Pods come from the **same address space** as the rest of your network infrastructure (like your VPC, Virtual Network, or physical network).

**Example from Azure (AKS)**:
- **Flat Network**: Pods receive IP addresses directly from the Azure Virtual Network (VNet). This means they are directly routable from other Azure resources. Traffic leaving the cluster is **not** SNAT'd (Source Network Address Translated), meaning the Pod's original IP address is preserved.

### ✅ Benefits of a Flat Network

- **Simplicity**: The network is straightforward to understand and troubleshoot. Every Pod has a unique, directly accessible IP.
- **Performance**: It's faster than other models, like the "island" model, which requires address translation that adds a performance overhead.
- **Direct Routing**: Pods can be reached directly from other services within the same network (e.g., from a VM or another cloud service) using their IP.

### ⚠️ Trade-offs and Considerations

- **IP Address Consumption**: This is the biggest drawback. Because every Pod gets an IP from your main network's address space, you need a large IP address space to support a significant number of Pods. This requires careful planning of your subnet sizes.
- **Scalability Limits**: The number of Pods you can run is directly limited by the number of available IP addresses in your network.
- **Security**: In a flat network, any Pod can reach any other Pod by default. You must use **Network Policies** to enforce segmentation and isolation.

### 🆚 Flat Network vs. Overlay Network

To make the decision clearer, here's how the flat network model compares to the more common **overlay network** model.

| Feature | Flat Network | Overlay Network |
| :--- | :--- | :--- |
| **IP Address Source** | Pods get IPs directly from the **same** network as the nodes (e.g., your VPC). | Pods get IPs from a **separate, private** CIDR range that is *overlaid* on top of the node network. |
| **IP Address Management** | Requires a **large** address space for all Pods. | Conserves the main network's IP address space. |
| **Performance** | **Faster**, as no NAT or encapsulation is needed. | **Slower**, due to the overhead of encapsulating packets (e.g., using VXLAN). |
| **Complexity** | **Simpler** to understand and troubleshoot. | **More complex**, as it introduces an additional layer of networking. |

### 💡 A Quick Historical Note

It's worth mentioning that the flat network model is sometimes contrasted with an **"island mode"** network model, where each node is an isolated network island and Pods communicate through gateways that perform NAT. The flat network model is essentially the evolution of that concept.

### ⚙️ CNI Plugins for Flat Networking

Many CNI plugins support a flat network model. Some popular ones include:

- **Flannel**: A simple, popular CNI that can be configured for a flat network.
- **Calico**: Offers both flat networking and advanced network policy enforcement.
- **Cilium**: Provides a simple flat Layer 3 network with eBPF-based data plane for high performance and security.

In summary, Kubernetes mandates a flat network model by design, where every Pod can communicate directly with every other Pod using its own unique IP address. This model provides a simple and high-performance foundation for all Kubernetes networking.
