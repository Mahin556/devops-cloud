Yes. **`seccompProfile` is one of the most important Kubernetes Linux security concepts**, especially if you're studying **PSA/PSS, Kubernetes security, and DevOps interviews**.

The key idea:

> **Seccomp restricts which Linux system calls a containerized process is allowed to make.**

Kubernetes exposes this through `securityContext.seccompProfile`. ([Kubernetes][1])

---

# 1. First: What is seccomp?

**seccomp** stands for **secure computing mode**.

Linux processes communicate with the Linux kernel through **system calls (syscalls)**.

For example, an application might need to:

```text
open()      → open a file
read()      → read data
write()     → write data
socket()    → create network socket
connect()   → connect to network
execve()    → execute a program
clone()     → create a process/thread
mount()     → mount filesystem
ptrace()    → inspect/control another process
```

The application:

```text id="q0rx1w"
Application
     │
     │ system call
     ▼
Linux Kernel
```

Seccomp puts a filter between the application and the kernel:

```text id="q8x9vb"
Application
     │
     │ syscall
     ▼
   seccomp
   filter
     │
 ┌───┴────┐
 ▼        ▼
ALLOW    DENY
 │        │
 ▼        ▼
Kernel   Error / action
```

So instead of allowing a container to freely invoke every syscall available to it, we can restrict the syscall surface.

---

# 2. Why is seccomp important for containers?

Containers share the **host kernel**.

This is extremely important.

A container does **not** have its own separate Linux kernel.

```text id="6v4hnb"
                 Linux Host
                     │
              Linux Kernel
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
    Container A  Container B  Container C
```

If a malicious application compromises a container, access to dangerous kernel functionality can increase the attack surface.

Seccomp helps reduce that attack surface by restricting syscalls.

Think:

```text id="d0v2q7"
Container
    │
    ├── syscall 1 → ALLOW
    ├── syscall 2 → ALLOW
    ├── syscall 3 → ALLOW
    ├── syscall 4 → DENY
    └── syscall 5 → DENY
```

---

# 3. Where does `seccompProfile` appear?

Kubernetes exposes it through:

```yaml id="6kquxq"
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

You can specify it at the:

### Pod level

```yaml id="q4m8f3"
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
```

### Container level

```yaml id="pihg8w"
containers:
- name: app
  securityContext:
    seccompProfile:
      type: RuntimeDefault
```

Kubernetes supports the field at Pod/container security-context levels, including init and ephemeral containers. ([Kubernetes][1])

# 4. The three seccomp profile types

This is the most important part.

```text id="k2xw1p"
seccompProfile.type

├── Unconfined
├── RuntimeDefault
└── Localhost
```

---

# 5. `Unconfined`

```yaml id="j2nhk3"
securityContext:
  seccompProfile:
    type: Unconfined
```

Means:

> **No seccomp restrictions are applied.**

The container can use syscalls without a seccomp filter.

Conceptually:

```text id="jv4tcy"
Application
     │
     │ all syscalls
     ▼
Linux Kernel
```

This provides the **least syscall restriction**.

### Security implication

An unconfined workload has a larger kernel attack surface.

Therefore, for security-sensitive workloads, you generally don't want:

```yaml id="bf73yv"
type: Unconfined
```

especially when using the **Restricted Pod Security Standard**.

The Restricted PSS explicitly disallows `Unconfined` and requires `RuntimeDefault` or `Localhost` when seccomp is explicitly specified. ([Kubernetes][2])

---

# 6. `RuntimeDefault`

This is the most important option for normal Kubernetes workloads.

```yaml id="3o3b7j"
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

It means:

> **Use the default seccomp profile provided by the container runtime.**

For example, your runtime might be:

```text id="q5nyjy"
Kubernetes
    │
    ▼
containerd / CRI-O
    │
    ▼
RuntimeDefault seccomp profile
```

The exact default profile can vary between container runtimes and runtime versions. ([Kubernetes][1])

The purpose is to provide useful security restrictions while maintaining compatibility with normal applications.

### Recommended starting point

For most applications:

```yaml id="6azx9h"
seccompProfile:
  type: RuntimeDefault
```

is the appropriate choice.

---

# 7. `Localhost`

This allows you to specify your **own custom seccomp profile** stored on the Kubernetes node.

Example:

```yaml id="x34f5h"
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: my-profile.json
```

The profile must exist on the node in the kubelet's seccomp profile location. Kubernetes documents the Linux default location as:

```text id="9jtp0e"
/var/lib/kubelet/seccomp
```

The `localhostProfile` is a path relative to the kubelet's configured seccomp profile directory. If the profile doesn't exist, container creation fails. ([Kubernetes][1])

---

# 8. How Localhost works

Suppose your node has:

```text id="6drn8x"
/var/lib/kubelet/seccomp/profiles/my-profile.json
```

Your Pod specifies:

```yaml id="2cx3v8"
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/my-profile.json
```

The flow becomes:

```text id="x2z7m8"
Pod
 │
 ▼
Kubelet
 │
 ▼
/var/lib/kubelet/seccomp/
 │
 ▼
my-profile.json
 │
 ▼
Container runtime
 │
 ▼
Linux kernel
```

# 9. What is inside a seccomp profile?

A custom seccomp profile is a JSON document.

A simplified example:

```json id="0mlg7n"
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": [
        "read",
        "write",
        "openat",
        "close"
      ],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
```

The important pieces are:

```text id="f0u0ur"
defaultAction
     ↓
What happens when syscall isn't explicitly allowed?

syscalls
     ↓
Which syscalls are being filtered?

names
     ↓
Which syscalls?

action
     ↓
What should happen?
```

Kubernetes uses the OCI runtime seccomp profile format for `Localhost` profiles. ([Kubernetes][1])

---

# 10. `defaultAction`

Consider:

```json id="9h92ty"
"defaultAction": "SCMP_ACT_ERRNO"
```

This means:

> If a syscall doesn't match an allowed rule, return an error.

Then:

```json id="r0l2oz"
{
  "names": ["read", "write"],
  "action": "SCMP_ACT_ALLOW"
}
```

means:

```text id="d4w7kz"
read   → ALLOW
write  → ALLOW
others → defaultAction
```

So:

```text id="b5ukjz"
Application
     │
     ├── read()  ──→ ALLOW
     ├── write() ──→ ALLOW
     ├── mount() ──→ DENY
     └── ptrace()─→ DENY
```

---

# 11. Common seccomp actions

You don't necessarily need to memorize every action for a DevOps interview, but know the major ones.

### `SCMP_ACT_ALLOW`

Allow the syscall.

```text
syscall → ALLOW
```

### `SCMP_ACT_ERRNO`

Return an error.

```text
syscall
   ↓
error
```

### `SCMP_ACT_KILL_PROCESS`

Kill the process.

```text
syscall
   ↓
process terminated
```

### `SCMP_ACT_KILL_THREAD`

Terminate the calling thread.

### `SCMP_ACT_LOG`

Allow the syscall but log it, depending on kernel/runtime behavior.

For interviews, remember:

```text id="j3b0tq"
ALLOW
ERRNO
KILL_PROCESS
LOG
```

# 12. Pod-level vs container-level seccomp

This is important.

You can configure:

```yaml id="0u1b0p"
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
```

This provides a Pod-level default.

Containers that don't specify their own seccomp profile inherit the Pod-level value. A container-level setting takes precedence over the Pod-level setting. ([Kubernetes][1])

For example:

```yaml id="l6yq7f"
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault

  containers:
  - name: app
    image: nginx

  - name: sidecar
    image: busybox
```

Both inherit:

```text id="bof7y9"
RuntimeDefault
```

But:

```yaml id="2j4e2m"
containers:
- name: app
  securityContext:
    seccompProfile:
      type: Unconfined
```

would override the Pod-level setting for that container.

---

# 13. Important exception: privileged containers

This is a very important security detail.

If:

```yaml id="w4j8yq"
securityContext:
  privileged: true
```

the container runs **Unconfined** for seccomp.

A seccomp profile cannot be applied to a privileged container. ([Kubernetes][1])

So don't think:

```yaml id="8x2q4p"
privileged: true

seccompProfile:
  type: RuntimeDefault
```

means:

> "The privileged container is still protected by RuntimeDefault."

It isn't.

Conceptually:

```text id="3kgm0s"
privileged: true
       │
       ▼
seccomp = Unconfined
```

---

# 14. How seccomp relates to PSS

This is particularly important given what you've just studied.

For the **Restricted** PSS profile, seccomp must not be explicitly set to `Unconfined`.

The allowed explicit types are:

```text id="l9q4pn"
RuntimeDefault
Localhost
```

The current Kubernetes documentation also describes the Restricted policy as requiring seccomp to be explicitly configured at Pod or container level, rather than left absent. ([Kubernetes][2])

So:

```yaml id="t3m5so"
seccompProfile:
  type: RuntimeDefault
```

is the common choice.

---

# 15. Why does Restricted care about seccomp?

Because a container normally interacts with the host kernel through syscalls.

Without syscall filtering:

```text id="6i5y9j"
Container
   │
   │ potentially broad syscall access
   ▼
Host Kernel
```

With seccomp:

```text id="g5h7ui"
Container
   │
   ▼
Seccomp Filter
   │
 ┌─┴──────┐
 ▼        ▼
Allowed  Blocked
 │
 ▼
Kernel
```

This reduces the potential attack surface.

---

# 16. Seccomp is NOT container isolation

This is an important conceptual distinction.

Seccomp doesn't create a VM.

It doesn't give every container its own kernel.

Instead:

```text id="2s9n4n"
Container
    │
    ▼
Shared Host Kernel
    │
    ▼
Seccomp limits syscalls
```

So Kubernetes security uses multiple layers:

```text id="s6z4h3"
Container Security
       │
       ├── Namespaces
       ├── cgroups
       ├── Linux capabilities
       ├── seccomp
       ├── AppArmor
       ├── SELinux
       └── Pod Security Admission
```

Each solves a different problem.

---

# 17. Seccomp vs capabilities

These are often confused.

### Capabilities

Control **privileged kernel operations** exposed through Linux capabilities.

Example:

```yaml id="r2oj1r"
securityContext:
  capabilities:
    drop:
    - ALL
```

### Seccomp

Controls **system calls**.

```yaml id="6s2n0g"
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

Think:

```text id="o4g5tk"
Capabilities
     ↓
"What privileged powers does the process have?"

Seccomp
     ↓
"Which kernel system calls can the process make?"
```

They complement each other.

---

# 18. Seccomp vs AppArmor

Another common interview question.

### Seccomp

Filters **system calls**.

```text id="44q8e4"
Application
   ↓
syscall
   ↓
seccomp
```

### AppArmor

Controls access based on **security profiles**, including filesystem/network/process-related behavior.

```text id="e0e7i9"
Application
   ↓
AppArmor profile
   ↓
Allowed/denied operations
```

### SELinux

Uses **labels and mandatory access control** to control what processes and objects can access.

So:

```text id="fyab6n"
seccomp
 → syscalls

AppArmor
 → application behavior/profile

SELinux
 → labels/MAC
```

# 19. RuntimeDefault vs Localhost

This is a common interview comparison.

| Feature       | RuntimeDefault    | Localhost             |
| ------------- | ----------------- | --------------------- |
| Profile       | Runtime-provided  | User-provided         |
| Customization | Limited           | High                  |
| Stored        | Container runtime | Node filesystem       |
| Management    | Easier            | More operational work |
| Portability   | Better            | Node-dependent        |
| Typical use   | Normal workloads  | Specialized workloads |

### Interview answer

> **I would normally use `RuntimeDefault` because it provides the container runtime's default seccomp restrictions without requiring us to manage profiles on every node. I'd use `Localhost` when an application requires a custom syscall policy and I'd ensure that the profile is distributed consistently to all nodes where the workload can run.**

---

# 20. Why Localhost can be dangerous operationally

Imagine:

```text id="m29hcg"
Node01 → profile exists
Node02 → profile exists
Node03 → profile missing
```

Your Pod gets scheduled on:

```text id="h3oh9a"
Node03
```

Then the container can fail to start because Kubernetes/container runtime can't find the requested profile. Kubernetes documents this behavior as a `CreateContainerError`. ([Kubernetes][1])

So with Localhost profiles, you need to ensure:

```text id="r9e4fj"
Every eligible node
       │
       └── has profile
```

This is why DaemonSets, image/node provisioning, configuration management, or other node-management mechanisms may be used to distribute profiles.

# 21. RuntimeDefault does NOT mean "no security"

This is a common misconception.

```yaml id="g2xj86"
type: RuntimeDefault
```

doesn't mean:

> "Use no restrictions."

It means:

> **Use the container runtime's default seccomp profile.**

The default profile aims to provide useful syscall restrictions while preserving compatibility. The exact profile can vary between runtimes and versions. ([Kubernetes][1])

# 22. What if `seccompProfile` is not specified?

This is where Kubernetes versions/configuration matter.

Historically, if no profile was specified, workloads could run **Unconfined** by default.

Kubernetes provides the **SeccompDefault** kubelet setting, which makes `RuntimeDefault` the default for workloads that don't explicitly specify another profile. This feature is stable from Kubernetes v1.27. ([Kubernetes][3])

Conceptually:

Without seccomp defaulting:

```text id="d3x48f"
Pod
 │
 └── no profile
        ↓
    potentially Unconfined
```

With kubelet `seccompDefault`:

```text id="4w5x4h"
Pod
 │
 └── no profile
        ↓
RuntimeDefault
```

For a production cluster, this is an important hardening consideration.

---

# 23. How to configure SeccompDefault

At the kubelet level, Kubernetes supports:

```text id="j3ksr2"
--seccomp-default
```

or the corresponding kubelet configuration.

This makes the runtime's default seccomp profile the default for workloads that don't specify a profile. ([Kubernetes][3])

**Important:** don't blindly enable this on every existing production node. Some workloads may depend on syscalls that the runtime default blocks. Kubernetes recommends testing workloads on a subset of nodes before rolling this out broadly. ([Kubernetes][3])

# 28. What happens when a syscall is blocked?

Suppose:

```text id="b49pjm"
defaultAction = SCMP_ACT_ERRNO
```

and the application executes:

```text id="d8y7tq"
mount()
```

but `mount` isn't allowed.

Then:

```text id="t6s7u2"
Application
    │
    ▼
mount()
    │
    ▼
seccomp
    │
    ▼
SCMP_ACT_ERRNO
    │
    ▼
system call fails
```

The application may then:

* Handle the error
* Fail to initialize
* Crash
* Become unhealthy

That's why overly restrictive custom seccomp profiles can break applications.

# 31. Seccomp + capabilities + non-root

These three are frequently discussed together.

A strong container security configuration might look conceptually like:

```yaml id="d8h7b1"
securityContext:
  runAsNonRoot: true

  seccompProfile:
    type: RuntimeDefault

containers:
- name: app
  securityContext:
    allowPrivilegeEscalation: false

    capabilities:
      drop:
      - ALL
```

These controls address different attack surfaces:

```text id="g6m5j9"
runAsNonRoot
      ↓
Don't run process as UID 0

allowPrivilegeEscalation=false
      ↓
Don't gain additional privileges

capabilities.drop=ALL
      ↓
Remove Linux capabilities

seccomp RuntimeDefault
      ↓
Restrict kernel syscalls
```

This is much stronger than relying on one control.

# 32. Very important interview distinction

If the interviewer asks:

> **"Does seccomp prevent a container from accessing the host filesystem?"**

Don't answer simply "yes."

Seccomp controls **system calls**. It isn't directly a filesystem access-control mechanism.

For filesystem access, other mechanisms are relevant, including:

* Linux namespaces
* Mount configuration
* AppArmor
* SELinux
* Container security context
* Volume configuration
* Privileges/capabilities

Seccomp may indirectly prevent operations because a required syscall is blocked, but its primary purpose is **syscall filtering**.

# 33. Another interview question: Does seccomp encrypt anything?

**No.**

Seccomp has nothing to do with encryption.

# 34. Another common question: Is RuntimeDefault the same on every node?

**Not necessarily.**

The RuntimeDefault profile comes from the container runtime, and Kubernetes documents that profiles can differ between runtimes and runtime versions. ([Kubernetes][1])

For example:

```text id="l0m0pg"
Node 1
containerd version X
        ↓
RuntimeDefault A

Node 2
containerd version Y
        ↓
RuntimeDefault B
```

This is one reason custom profiles and runtime standardization need careful testing.

# 35. Interview-ready answer

If asked:

### "What is seccompProfile in Kubernetes?"

Say:

> **`seccompProfile` controls the seccomp policy applied to a Pod or container. Seccomp is a Linux kernel security mechanism that filters system calls, reducing the kernel attack surface available to a container. Kubernetes supports three profile types: `RuntimeDefault`, which uses the container runtime's default profile; `Localhost`, which uses a custom profile stored on the node; and `Unconfined`, which disables seccomp restrictions. For normal production workloads, I would generally use `RuntimeDefault`, while `Localhost` is appropriate when a workload needs a carefully managed custom syscall policy.**

---

# 36. If they ask about PSS Restricted

Answer:

> **The Restricted Pod Security Standard requires seccomp to be configured securely. `Unconfined` is not permitted; the accepted profile types are `RuntimeDefault` and `Localhost`. I would normally use `RuntimeDefault` unless the application has a specific requirement for a custom profile.** ([Kubernetes][2])
