## CORS Support in Kubernetes Gateway API

CORS (Cross-Origin Resource Sharing) is a **standard (GA) feature** of the Gateway API, available since **v1.5**. It allows you to declare CORS policies directly in your `HTTPRoute` resources, offloading cross-origin handling from your application code to the gateway.

### How It Works

When you attach a CORS filter to a rule, the gateway automatically:

1. **Responds to preflight `OPTIONS` requests** – the gateway handles the CORS preflight itself, never forwarding it to your backend.
2. **Injects the correct `Access-Control-*` headers** into actual responses, based on your policy.

This makes your backend services completely unaware of CORS – they just serve content as usual.

---

### Configuring CORS in an HTTPRoute

The CORS filter is placed inside the `filters` array of a rule.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
spec:
  parentRefs:
  - name: my-gateway
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: my-service
      port: 8080
    filters:
    - type: CORS
      cors:
        allowOrigins:
        - "https://app.example.com"
        allowMethods: ["GET", "POST"]
        allowHeaders: ["Authorization", "Content-Type"]
        exposeHeaders: ["X-Custom-Header"]
        allowCredentials: false
        maxAge: 3600
```

---

### Available Fields

| Field | Corresponding Header | Description | Constraints |
| :--- | :--- | :--- | :--- |
| `allowOrigins` | `Access-Control-Allow-Origin` | Allowed origins. Use `*` or patterns like `https://*.example.com`. | Cannot be `*` if `allowCredentials` is `true`. |
| `allowMethods` | `Access-Control-Allow-Methods` | Allowed HTTP methods (e.g., `GET`, `POST`). | Cannot be `*` if `allowCredentials` is `true`. |
| `allowHeaders` | `Access-Control-Allow-Headers` | Allowed request headers. | Cannot be `*` if `allowCredentials` is `true`. |
| `exposeHeaders` | `Access-Control-Expose-Headers` | Headers that client scripts can access. | No special restrictions. |
| `allowCredentials` | `Access-Control-Allow-Credentials` | Boolean – whether to allow credentials (cookies, auth). | If `true`, `allowOrigins` **must not** be `*`. |
| `maxAge` | `Access-Control-Max-Age` | Cache duration (in seconds) for preflight responses. Defaults to 5s. | Must be a positive integer. |

### Practical Examples

#### 1. Allow a single specific origin (no credentials)
```yaml
cors:
  allowOrigins:
  - "https://app.example.com"
```

#### 2. Allow multiple origins (no credentials)
```yaml
cors:
  allowOrigins:
  - "https://app.example.com"
  - "https://dashboard.example.com"
```

#### 3. Allow any origin with credentials – **not allowed**
```yaml
# This is invalid – will be rejected by the API server
cors:
  allowOrigins: ["*"]
  allowCredentials: true
```

#### 4. Allow any origin **without** credentials (common for public APIs)
```yaml
cors:
  allowOrigins: ["*"]
  allowCredentials: false
```

#### 5. Full control with caching
```yaml
cors:
  allowOrigins:
  - "https://app.example.com"
  allowMethods: ["GET", "POST", "PUT", "DELETE"]
  allowHeaders: ["Authorization", "Content-Type", "X-Requested-With"]
  exposeHeaders: ["X-Total-Count", "X-RateLimit-Remaining"]
  allowCredentials: true          # careful: origin must be specific
  maxAge: 86400                   # cache preflight for 24 hours
```

### Important Considerations

1. **Implementation support**  
   CORS filtering is an **extension** feature. Your chosen gateway controller (e.g., Envoy Gateway, Traefik, Cilium, NGINX Gateway Fabric) **must** support the `HTTPRouteCORS` feature. Check your controller’s documentation.

2. **Gateway API version**  
   You need the **v1.5.0** (or later) CRDs installed. The experimental channel had it earlier, but the standard channel includes it as GA from v1.5 onward.

3. **Wildcard and credentials rule**  
   If you set `allowCredentials: true`, you **cannot** use `*` in `allowOrigins`, `allowMethods`, or `allowHeaders`. This is a security requirement of the CORS specification.

4. **Preflight handling**  
   The gateway responds to `OPTIONS` requests with the configured CORS headers and a `204 No Content` status. It never forwards these to your backend, which can reduce backend load.

5. **Overriding behaviour**  
   If your backend also sends CORS headers, the gateway’s policy will **override** them. It is recommended to remove CORS logic from your application code and rely solely on the gateway for consistency.

### Debugging Tips

- Check the `HTTPRoute` status:  
  `kubectl describe httproute my-route` – look for conditions indicating if the CORS filter was accepted.
- Verify the gateway controller logs for any CORS-related warnings.
- Use browser dev tools to inspect the `Access-Control-*` headers in the response.
- Test with `curl -I -X OPTIONS -H "Origin: https://test.example.com" https://your-gateway/` to see the actual preflight response.

---

### Summary

Gateway API’s native CORS support gives you a **declarative, centralised way** to manage cross-origin policies. It simplifies application development, improves security by enforcing consistent policies, and is now a production‑ready feature. Make sure your gateway implementation and CRD version are up to date to take full advantage of it.
