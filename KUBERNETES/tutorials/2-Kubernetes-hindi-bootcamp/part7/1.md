### 1. What Are ConfigMaps and Secrets?

Both are Kubernetes objects used to store configuration data separately from your container images. They allow you to change application behavior without rebuilding your Docker image.

| Feature | ConfigMap | Secret |
| :--- | :--- | :--- |
| **Purpose** | Store **non-sensitive** configuration (e.g., app config, feature flags). | Store **sensitive** data (e.g., passwords, API keys, TLS certificates). |
| **Data Format** | Plain text (key-value pairs). | Base64-encoded (for transport) but plaintext in memory. |
| **Size Limit** | **1 MiB** (by default). | **1 MiB** (by default). |
| **Encryption** | Not encrypted (stored in plaintext in etcd). | Optionally encrypted at rest (using `EncryptionConfiguration`). |

### 2. Decoding Your Note: "Key: volume pairs → non-configdonal"

This is your way of saying **"Key-Value pairs for configuration"**. 
- A ConfigMap/Secret contains **keys** (like `app.properties`) and **values** (like `logging.level=DEBUG`).
- They are **non-confidential** (for ConfigMaps) or **confidential** (for Secrets).

**Example YAML (ConfigMap)**:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  # Key: "database_url" | Value: "postgres://..."
  database_url: "postgres://user:pass@db:5432/myapp"
  # Key: "log_level"   | Value: "DEBUG"
  log_level: "DEBUG"
```

### 3. The 1 MiB Limit (Why it exists)

As your note correctly states, the **limit is 1 MiB**. 

- **Why?** ConfigMaps and Secrets are stored in **`etcd`** (Kubernetes's key-value store). `etcd` has a default request size limit of **1.5 MiB**. Kubernetes sets a conservative 1 MiB cap to prevent `etcd` from getting overloaded with huge configuration blobs.
- **What if you need more?** You cannot exceed 1 MiB. For large files (e.g., `ca.crt`, large JSON configs), you should use:
  - **Persistent Volumes** (for extremely large data).
  - **External Configuration Stores** (like HashiCorp Vault, AWS Parameter Store, or ConfigMap Reloader with sidecars).
  - **Helm** charts with large values files (but the underlying ConfigMap still respects the 1 MiB limit per object).

### 4. The 4 Ways to Consume ConfigMaps/Secrets (From Your Notes)

Your notes list the exact 4 methods to inject configuration into a Pod:

#### 1. Inside a container command and args
Use `valueFrom` to inject a ConfigMap/Secret value directly into the startup command.

```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    image: myapp
    command: ["/bin/sh"]
    args: ["-c", "echo Database is $DB_URL"]
    env:
    - name: DB_URL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: database_url
```

#### 2. Environment variables for a container
Use `envFrom` to inject all keys from a ConfigMap/Secret as environment variables.

```yaml
spec:
  containers:
  - name: app
    image: myapp
    envFrom:
    - configMapRef:
        name: app-config   # Injects log_level, database_url as env vars
    - secretRef:
        name: db-secret    # Injects DB_PASSWORD as env var
```

#### 3. Add a file in a read-only volume, for the application to read
Mount the ConfigMap/Secret as a file. This is the most common pattern for applications that read `config.properties` or `.env` files.

```yaml
spec:
  containers:
  - name: app
    image: myapp
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config-volume
    configMap:
      name: app-config   # Each key becomes a file (e.g., /etc/config/log_level)
```

#### 4. Write code to run inside the Pod that uses the Kubernetes API to read a ConfigMap
This is the **programmatic approach** (your note: *"Interrupt with Kubernetes programmatically"*). Instead of injecting the data, your application queries the Kubernetes API server directly to fetch the ConfigMap/Secret at runtime.

- **How**: Use a Kubernetes client library (e.g., `client-go` for Go, `fabric8` for Java, or `kubernetes` for Python).
- **When to use**: When you need to **watch** for live updates (e.g., auto-reload the config without restarting the Pod). 

**Example (Go client-go)**:
```go
clientset.CoreV1().ConfigMaps("my-namespace").Get(context.TODO(), "app-config", metav1.GetOptions{})
```
*(Note: Your Pod needs a ServiceAccount with RBAC permissions to read ConfigMaps/Secrets.)*

### 💡 Best Practices (The Golden Rules)

1.  **Never store sensitive data in ConfigMaps** (use Secrets with encryption enabled).
2.  **Keep ConfigMaps small** (< 1 MiB). For larger files, use a PersistentVolume or external config store.
3.  **Use immutable ConfigMaps/Secrets** (set `immutable: true`) to prevent accidental changes and improve performance (kubelet caches them).
4.  **Prefer volume mounts over environment variables** for large configs, and for auto-reload capabilities.
5.  **Use RBAC** to restrict which Pods/ServiceAccounts can read Secrets (principle of least privilege).
