# CKA Practice: Recover a NotReady Node After a Kubelet Configuration Error

## Scenario

A worker node `node-02` has dropped to `NotReady`. The control plane and other nodes are healthy. The workload in the `web` namespace is degraded. Your job is to diagnose and repair `node-02` without deleting, draining, or replacing it.

**Constraints:**
- Repair `node-02` in place.
- Do not delete or edit deployments in the `web` namespace.
- Do not recreate the cluster.
- If you cordon the node, uncordon it before finishing.

---

## The Three States of a Node

A `NotReady` node is a symptom, not a diagnosis. The kubelet passes through three distinct states, and failure can occur at any of them:

| State | What It Means | How to Check |
|---|---|---|
| 1. Process runs | systemd reports `active` | `systemctl is-active kubelet` |
| 2. Process initialises | Kubelet parsed config, reached runtime, started control loops | `journalctl -u kubelet` for errors |
| 3. Node reports Ready | Kubelet posts node status to API server continuously | `kubectl get nodes` |

Troubleshooting means identifying which of these three states the node failed to reach.

The API server only knows what the node last told it. Once a node stops reporting, the evidence lives on the node itself.

---

## Pre-Flight: Read What the Control Plane Knows

From `cplane-01`:

```bash
kubectl get nodes -o wide
kubectl describe node node-02
kubectl get pods -n web -o wide
```

### What to Look For

In `kubectl describe node node-02`, examine the `Ready` condition:

```text
Conditions:
  Type             Status  Reason
  ----             ------  ------
  Ready            Unknown NodeStatusUnknown
```

If the message says `Kubelet stopped posting node status`, that is the control plane telling you:

> The node went quiet. The kubelet stopped renewing its node lease in `kube-node-lease`, so after 40 seconds the node controller marked it `Unknown`.

The control plane cannot tell you **why**. Nothing on the control plane can. The next evidence is on the node.

### The Pod List Can Look Healthier Than It Is

For the first five minutes after a node goes quiet:

- The `web-canary` pod on `node-02` still shows `Running`.
- The deployment reports `0/1 available`.

Both views are true. The API server is showing you the node's last report. The node controller marks the pod not ready immediately, but only evicts it after the default **300-second unreachable toleration** expires. Until then, the pod listing still shows `Running`, but the deployment correctly reports it as unavailable.

---

## Step 1: Get the Kubelet Process Running

SSH into the node:

```bash
ssh node-02
sudo -i
```

### Check the Kubelet Service

```bash
systemctl status kubelet
systemctl is-active kubelet
```

Read the state word carefully:

| State | Meaning |
|---|---|
| `active (running)` | Process is up. May still be failing to do its job. |
| `activating (auto-restart)` | Starts, exits, systemd restarts. Crash loop. |
| `failed` | Exited and systemd gave up restarting. |

`activating (auto-restart)` is the interesting one. Something makes the kubelet exit very early, every time.

### Read the Journal

```bash
journalctl -u kubelet -n 100 --no-pager
```

In a restart loop, the journal repeats the same short block. **Find one restart boundary and read the lines above it.** Those are the real error. Everything below is systemd starting the process again.

The kubelet loads its configuration file before contacting the runtime or the API server. A configuration failure appears at the very top of each attempt, and nothing else gets a chance to log.

### Find the Config File

The kubelet does not read a fixed path. systemd passes it one:

```bash
systemctl cat kubelet | grep -- --config
```

On a kubeadm node, this points at `/var/lib/kubelet/config.yaml`. That file is a `KubeletConfiguration` object, and it is **strictly decoded**. A value of the wrong type stops startup.

### Compare with a Healthy Node

`node-01` is healthy and has the same file. Comparing is the fastest way to see what changed:

```bash
ssh node-01 sudo cat /var/lib/kubelet/config.yaml > /tmp/node-01.yaml
diff /tmp/node-01.yaml /var/lib/kubelet/config.yaml
```

The diff will show the corrupted or mistyped field. Fix it, then restart the kubelet:

```bash
systemctl restart kubelet
systemctl is-active kubelet
```

---

## Step 2: Get the Node Reporting Ready

A running process is not a healthy node. Once the kubelet starts cleanly, it re-registers and begins posting status again, which takes a few seconds.

Watch it from `cplane-01`:

```bash
kubectl get nodes -w
```

You should not need to do anything else here. If the node stays `NotReady` after the kubelet has been `active` for a minute, the process is running but not initialising—this is the **second state**. Look at the journal again for runtime or API server connectivity errors.

---

## Step 3: Confirm the Workload Recovered

A Ready node does not by itself mean the workload recovered. Confirm:

```bash
kubectl get pods -n web -o wide
kubectl -n web get deployment web-backend web-canary
```

`web-canary` is pinned to `node-02`, so it can only become available once the node is both `Ready` and **schedulable**.

If you cordoned the node during your work, uncordon it:

```bash
kubectl uncordon node-02
```

## Theory: Why This Happens

### Node Leases and Heartbeats

Since Kubernetes 1.14, each node has a **Lease** object in the `kube-node-lease` namespace. The kubelet renews this lease every 10 seconds by default. The node controller watches these leases.

If the lease is not renewed within a grace period (default 40 seconds), the node controller marks the node's `Ready` condition as `Unknown`. This is a deliberate design: it detects node failures faster and with less load on the API server than the older method of watching full node status updates.

### Node Status Updates

Separately from the lease, the kubelet posts full node status (conditions, capacity, allocatable, addresses, etc.) via `PATCH` to `/api/v1/nodes/{name}/status`. The default interval is every 5 minutes, or immediately when something changes.

The `Ready` condition you see in `kubectl describe node` comes from this status update. If the kubelet stops posting, the condition goes stale—but the lease mechanism is what actually flips it to `Unknown` first.

### Kubelet Configuration Loading

The kubelet's startup sequence is roughly:

1. Parse command-line flags.
2. Load the `--config` file (KubeletConfiguration).
3. Strict-decode the config. Unknown fields or wrong types → fatal error.
4. Initialise the container runtime client (CRI).
5. Initialise the API server client.
6. Start control loops: pod sync, status manager, probe manager, etc.
7. Register the node and begin posting status.

A failure at step 2 or 3 means the kubelet exits **before** it can log anything about runtimes, API servers, or pods. The journal shows the config error at the top of each restart attempt.

### Why Strict Decoding Matters

Kubernetes uses strict decoding for `KubeletConfiguration`. This means:

- Unknown fields cause an error.
- Wrong types cause an error.
- Deprecated fields may be rejected.

This is intentional. It prevents typos from silently being ignored. But it also means a single character change—like `true` becoming `"true"`, or a field moving to the wrong indentation level—can prevent the kubelet from starting entirely.

### The `describe node` Output

```text
Ready   Unknown   NodeStatusUnknown   Kubelet stopped posting node status.
```

This is the literal truth. The API server is not saying the node is broken. It is saying the node went quiet. The reason `NodeStatusUnknown` is a signal that the problem is **on the node**, not in the control plane.

### Pod Eviction Timing

When a node goes `NotReady`:

- The node controller marks all pods on that node as `NotReady` in the endpoints/endpointslices.
- The pods remain in the API server's etcd, still showing `Running`.
- After the **unreachable toleration** (default `node.kubernetes.io/unreachable:NoExecute` with `tolerationSeconds: 300`) expires, the pods are evicted.
- Eviction triggers deletion, and the Deployment controller creates replacements on other nodes (if any are available and the pods are not pinned).

This is why `kubectl get pods -n web -o wide` can show a pod on `node-02` as `Running` while the deployment reports `0/1 available`. The API server is showing stale state. The deployment controller is reading the readiness condition, which is accurate.

### Why "Do Not Delete the Node" Matters

Deleting a node object does not fix the underlying problem. The kubelet on the node will re-register and the node will come back—but you have lost the opportunity to diagnose the real issue. Worse, if the node's kubelet is genuinely broken, it will re-register and go `NotReady` again, and you have learned nothing.

Repairing in place forces you to find the actual root cause.

## Complete Walkthrough

```bash
# From cplane-01
kubectl get nodes -o wide
kubectl describe node node-02 | grep -A5 Conditions
kubectl get pods -n web -o wide

# SSH to the node
ssh node-02
sudo -i

# Check kubelet
systemctl status kubelet
systemctl is-active kubelet
journalctl -u kubelet -n 100 --no-pager

# Find config path
systemctl cat kubelet | grep -- --config

# Compare with healthy node
ssh node-01 sudo cat /var/lib/kubelet/config.yaml > /tmp/node-01.yaml
diff /tmp/node-01.yaml /var/lib/kubelet/config.yaml

# Fix the config (example: correct a wrong type)
# Edit /var/lib/kubelet/config.yaml to match node-01

# Restart
systemctl restart kubelet
systemctl is-active kubelet

# Back on cplane-01
kubectl get nodes -w
kubectl get pods -n web -o wide
kubectl -n web get deployment web-backend web-canary

# If cordoned
kubectl uncordon node-02
```

## Common Configuration Errors That Cause This

| Error | Example |
|---|---|
| Wrong type | `readOnlyPort: "10255"` instead of `readOnlyPort: 10255` |
| Unknown field | A typo like `authenticationt` instead of `authentication` |
| Bad indentation | A field at the wrong YAML level |
| Invalid value | `cgroupDriver: systemd` vs `cgroupDriver: cgroupfs` mismatch |
| Missing required field | Removing a mandatory field |
| Deprecated field | Using a field removed in the current Kubernetes version |

## Key Takeaways

1. **A NotReady node is a symptom.** The control plane shows you the node stopped reporting. It cannot tell you why.
2. **The kubelet has three states:** process running, process initialised, node reporting. Diagnose which one failed.
3. **`activating (auto-restart)` means a crash loop.** The journal repeats the same block. Find the restart boundary and read above it.
4. **Kubelet config is strictly decoded.** A type error or unknown field stops startup before anything else logs.
5. **Compare with a healthy node.** `diff` against `node-01` is the fastest way to find what changed.
6. **Pods can look Running while the node is gone.** The 300-second unreachable toleration delays eviction.
7. **Repair in place.** Do not delete the node. The exercise is to find the root cause, not to paper over it.
