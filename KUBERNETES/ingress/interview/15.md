### Public API exposed through Ingress needs rate limiting to limit requests per client before traffic reaches the application.

**Solution:**

```yaml

              number: 80
```

**Key Points:**
- Rate limiting is applied at the Ingress level before traffic reaches backend
- `limit-rps`: Maximum requests per second from a single IP
- `limit-rpm`: Maximum requests per minute
- `limit-burst-multiplier`: Allows temporary bursts above the limit
- `limit-whitelist`: IP ranges exempt from rate limiting
- HTTP 429 (Too Many Requests) returned when limit exceeded
- No application code changes needed
- Protects backend from excessive traffic/DDoS
- Can be combined with authentication for per-user rate limiting

# Rate Limiting at Ingress Level - Complete Explanation

Let me break down how rate limiting works and why it's crucial for your API.Now let me explain the detailed mechanics of rate limiting:

---

## Understanding Rate Limiting

### What is Rate Limiting?

Rate limiting **controls how many requests a client can send within a specific time window**. It's like a bouncer at a nightclub:
- "You can enter 10 people per minute"
- After 10 people enter, the bouncer says "wait 60 seconds"
- Or a new minute starts, the counter resets, and more can enter

---

## Rate Limit Annotations Explained

### 1. **`limit-rps` - Requests Per Second**

```yaml
nginx.ingress.kubernetes.io/limit-rps: "10"
```

**What it does:**
- Each client IP can send maximum 10 requests per second
- Time window: 1 second (1000ms)

**Example:**
```
Time: 0.0s to 1.0s (1 second window)
Client sends requests:
├─ 0.1s: Request #1  ✅ Accepted (count: 1/10)
├─ 0.2s: Request #2  ✅ Accepted (count: 2/10)
├─ 0.3s: Request #3  ✅ Accepted (count: 3/10)
├─ 0.4s: Request #4  ✅ Accepted (count: 4/10)
├─ 0.5s: Request #5  ✅ Accepted (count: 5/10)
├─ 0.6s: Request #6  ✅ Accepted (count: 6/10)
├─ 0.7s: Request #7  ✅ Accepted (count: 7/10)
├─ 0.8s: Request #8  ✅ Accepted (count: 8/10)
├─ 0.9s: Request #9  ✅ Accepted (count: 9/10)
├─ 0.95s: Request #10 ✅ Accepted (count: 10/10) - LIMIT REACHED
├─ 0.96s: Request #11 ❌ Rejected (HTTP 429)
├─ 0.97s: Request #12 ❌ Rejected (HTTP 429)
└─ 1.0s: Window resets, counter = 0

Time: 1.0s to 2.0s (new window)
├─ 1.1s: Request #13 ✅ Accepted (count: 1/10)
└─ ...
```

### 2. **`limit-rpm` - Requests Per Minute**

```yaml
nginx.ingress.kubernetes.io/limit-rpm: "600"
```

**What it does:**
- Each client IP can send maximum 600 requests per minute
- Time window: 1 minute (60,000ms)

**Example:**
```
Time: 0:00 to 1:00 (60 second window)
├─ 0:05 → Request count: 100 ✅
├─ 0:15 → Request count: 200 ✅
├─ 0:30 → Request count: 400 ✅
├─ 0:45 → Request count: 600 ✅ (LIMIT REACHED)
├─ 0:46 → Request #601 ❌ Rejected (HTTP 429)
├─ 0:47 → Request #602 ❌ Rejected (HTTP 429)
└─ 1:00 → Window resets, counter = 0
```

---

### 3. **`limit-burst-multiplier` - Allow Temporary Bursts**

```yaml
nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"
```

**What it does:**
- Allows temporary spikes above the normal limit
- Multiplier applies to the base limit

**Example with limit-rps: 10 and burst-multiplier: 5:**
```
Normal limit: 10 requests/second
Burst limit: 10 × 5 = 50 requests allowed in burst

Scenario:
├─ Normal traffic arrives at 5 req/s: ✅ All accepted
├─ Sudden spike arrives at 50 req/s (burst): ✅ All 50 accepted
├─ Request #51 in the burst: ❌ Rejected (HTTP 429)
└─ Traffic normalizes: Back to accepting 10 req/s
```

**Why useful?**
- Legitimate traffic has spikes
- A user clicks a button multiple times quickly
- Multiple API calls fire simultaneously
- Without burst allowance: Normal user traffic gets rejected

---

### 4. **`limit-rate-after` - Grace Period Before Limiting**

```yaml
nginx.ingress.kubernetes.io/limit-rate-after: "5"
```

**What it does:**
- Allow first N requests without counting toward limit
- Only start limiting after N requests

**Example with limit-rps: 10 and limit-rate-after: 5:**
```
Window: 0 to 1 second

Requests:
├─ #1  ✅ Accepted (grace period - no counting)
├─ #2  ✅ Accepted (grace period - no counting)
├─ #3  ✅ Accepted (grace period - no counting)
├─ #4  ✅ Accepted (grace period - no counting)
├─ #5  ✅ Accepted (grace period - no counting)
├─ #6  ✅ Accepted (now counting: 1/10)
├─ #7  ✅ Accepted (now counting: 2/10)
├─ #8  ✅ Accepted (now counting: 3/10)
├─ #9  ✅ Accepted (now counting: 4/10)
├─ #10 ✅ Accepted (now counting: 5/10)
├─ #11 ✅ Accepted (now counting: 6/10)
├─ #12 ✅ Accepted (now counting: 7/10)
├─ #13 ✅ Accepted (now counting: 8/10)
├─ #14 ✅ Accepted (now counting: 9/10)
├─ #15 ✅ Accepted (now counting: 10/10 - LIMIT)
├─ #16 ❌ Rejected (exceeded limit)
└─ ...
```

---

### 5. **`limit-whitelist` - Exempt Certain IPs**

```yaml
nginx.ingress.kubernetes.io/limit-whitelist: "192.168.0.0/16,10.0.0.0/8"
```

**What it does:**
- Requests from these IP ranges are NOT rate limited
- Useful for internal services, monitoring, trusted partners

**Example:**
```
Limit: 10 req/s

Request from 192.168.1.100 (whitelisted):
├─ #1 ✅ Accepted
├─ #2 ✅ Accepted
├─ #3 ✅ Accepted
├─ #100 ✅ Still accepted! (no counting)
└─ No rate limiting applied

Request from 203.0.113.50 (NOT whitelisted):
├─ #1  ✅ Accepted (1/10)
├─ #2  ✅ Accepted (2/10)
├─ #10 ✅ Accepted (10/10)
├─ #11 ❌ Rejected (429)
└─ Normal rate limiting applies
```

## Where Rate Limiting Happens

### Network Stack

```
Internet
    ↓
Your ISP Router
    ↓
Your Server's NIC (Network Interface Card)
    ↓
Kubernetes Cluster Network
    ↓
Ingress Controller Pod (NGINX) ← RATE LIMITING HAPPENS HERE
    │
    ├─ Check request rate for client IP
    ├─ If over limit: Return 429 and DROP request
    ├─ If under limit: Forward to Service
    ↓
Service (Load Balancer)
    ↓
Pod (Your Application)
    ↓
Response sent back
```

**Key insight:** Rate limiting at Ingress means:
- ✅ Bad traffic never reaches your app
- ✅ Application resources not wasted on bad requests
- ✅ Backend stays healthy and responsive
- ✅ DDoS protection at the edge

## Real-World Scenario: API Under Attack

### Without Rate Limiting ❌

```
Attacker sends 10,000 req/s
    ↓
All 10,000 reach Ingress
    ↓
All 10,000 reach Service
    ↓
All 10,000 reach Pod
    ↓
Pod tries to process 10,000 requests simultaneously
    ├─ CPU at 100%
    ├─ Memory filling up
    ├─ Thread pool exhausted
    ├─ Database connections maxed out
    └─ All OTHER legitimate users get timeout errors ❌
    ↓
Your API is DOWN
    ↓
Revenue lost, users angry, alert at 3 AM 📱
```

### With Rate Limiting ✅

```
Attacker sends 10,000 req/s
    ↓
Ingress receives all 10,000
    ↓
Rate limiter checks each one:
├─ Request 1-10: Within limit ✅ Forward to service
├─ Request 11-10,000: Over limit ❌ Return 429 (drop)
    ↓
Only 10 requests reach Service
    ↓
Only 10 requests reach Pod
    ↓
Pod easily handles 10 req/s
    ├─ CPU: 5%
    ├─ Memory: Normal
    ├─ Thread pool: 1/100 used
    └─ All OTHER legitimate users unaffected ✅
    ↓
Your API stays healthy
    ↓
You sleep peacefully 😴
```

### Advanced Test with Verification

```bash
#!/bin/bash

API_URL="http://api.example.com/public"
LIMIT=10
REQUESTS=20

echo "Testing rate limiting (limit: $LIMIT req/s)"
echo ""

success=0
rejected=0

for i in $(seq 1 $REQUESTS); do
  response=$(curl -s -w "%{http_code}" -o /dev/null "$API_URL")
  
  if [ "$response" = "200" ]; then

    ((rejected++))
  else
    echo "Request $i: ⚠️  $response (unexpected)"
  fi
done

echo ""
echo "Results:"
echo "✅ Accepted: $success"
echo "❌ Rejected: $rejected"
echo "Expected: ~10 accepted, ~10 rejected (with burst allowance)"
```

## Comparison: Different Rate Limit Strategies

| Strategy | When to Use | Example |
|----------|---|---|
| **IP-based** | Public API, no auth | `limit-rps: 10` - each IP gets 10 req/s |
| **API Key-based** | Licensed API | 100 req/s for free tier, 1000 for premium |
| **User-based** | Authenticated API | 50 req/s per logged-in user |
| **Path-based** | Different endpoints have different limits | `/api/expensive` = 1 req/s, `/api/cheap` = 100 req/s |
| **Hybrid** | Complete protection | IP limit + API key limit + user limit |
