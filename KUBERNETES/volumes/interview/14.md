## Can we attach multiple volumes to a single deployment? How would you configure this?

**Answer:** **YES**, a single deployment can have multiple volumes attached.

### Why Multiple Volumes are Needed (Use Case):
- Just like in traditional Linux systems where you mount multiple disks to different mount points
- Different types of data need separate storage:
  - **Log data** → separate volume
  - **Application data** → separate volume
  - **Database data** → separate volume
- You don't want to club different data types on the same disk
- This practice existed even before container technology

### How to Configure:

**Step 1: Create two separate PVCs**
```yaml
# First PVC - for app data
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

# Second PVC - for logs
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: log-data-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

**Step 2: Reference both PVCs in Deployment**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: nginx
        volumeMounts:
        - name: app-data
          mountPath: /app/data
        - name: log-data
          mountPath: /var/log/app
      volumes:
      - name: app-data
        persistentVolumeClaim:
          claimName: app-data-pvc
      - name: log-data
        persistentVolumeClaim:
          claimName: log-data-pvc
```

**Key Point:** Two PVCs → Two PVs → Both mapped to same Deployment


## Where does data actually get written - in PVC or in PV?

**Answer:** **The data is written to the actual storage backend (disk).**

### The Complete Picture:

| Component | What It Is |
|-----------|------------|
| **Actual Disk/Storage** | Where data physically resides |
| **PV** | API object representing that storage in the cluster |
| **PVC** | A request/claim to use a PV in a namespace |

### Key Clarification:
- PVC is NOT a physical object - it doesn't exist anywhere on disk
- PVC is just a **request** saying "I want this type of PV"
- PV is the **representation** of the storage in the API
- Data is actually written to the **backend storage** (NFS, EBS, local disk, etc.)
- PV and PVC are **volume controllers** - API resources that present storage information to Kubernetes

### Analogy from Transcript:
"PVC is nothing but a request that says 'this PV is mine now'. Data is written on the actual storage. PV and PVC are just volume controllers that present storage information to the API server."

| # | Question | Answer |
|---|----------|--------|
| 1 | Can one deployment have multiple volumes? | YES - create multiple PVCs and reference in deployment |
| 2 | Can same PVC be mapped to two deployments? | Possible but NOT best practice (data mixing) |
| 3 | Can one PV be used in two namespaces? | NO - PV binds to one namespace at a time |
| 4 | Can a 100GB PV be split into two 50GB PVCs? | NO - PV cannot be logically broken |
| 5 | How does API decide which PV to allocate? | Matches access mode + size (≥ requested) + storage class |
| 6 | Where does data actually get written? | On the backend storage (disk), not in PVC or PV |

## Static vs Dynamic Provisioning - Key Difference

| Feature | Static Provisioning | Dynamic Provisioning |
|---------|---------------------|----------------------|
| **PV Creation** | Admin creates PVs beforehand | PV created on-demand |
| **Size Flexibility** | Fixed sizes (waste possible) | Exact size provisioned |
| **Storage Efficiency** | Can waste storage (100GB PV for 50GB request) | No waste |
| **Admin Involvement** | Manual | Automatic |
