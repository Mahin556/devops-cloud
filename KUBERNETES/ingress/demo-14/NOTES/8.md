Yes. You can generate a **Certificate Signing Request (CSR)** first, and then either:

* self-sign it (for labs), or
* send the CSR to a Certificate Authority (CA).

---

# Step 1: Generate a private key

```bash
openssl genrsa -out tls.key 2048
```

This creates:

```text
tls.key
```

---

# Step 2: Generate a CSR

```bash
openssl req -new -key tls.key -out tls.csr
```

It will ask:

```text
Country Name (2 letter code) [XX]: IN
State or Province Name: Rajasthan
Locality Name: Jaipur
Organization Name: My Company
Organizational Unit Name: IT
Common Name: myapp.example.com
Email Address: admin@example.com
```

The **Common Name (CN)** should be the hostname clients will use, for example:

```text
myapp.example.com
```

This creates:

```text
tls.csr
```

---

# Step 3: Self-sign the CSR

```bash
openssl x509 \
    -req \
    -days 365 \
    -in tls.csr \
    -signkey tls.key \
    -out tls.crt
```

Output:

```text
tls.crt
```

Now you have:

```text
tls.key
tls.csr
tls.crt
```

---

# Step 4: Create the Kubernetes TLS Secret

```bash
kubectl create secret tls myapp-tls \
    --cert=tls.crt \
    --key=tls.key
```

Verify:

```bash
kubectl get secret myapp-tls
```

---

# Better approach: Include Subject Alternative Names (SAN)

Modern browsers ignore the Common Name for hostname validation and instead use the **Subject Alternative Name (SAN)** extension. If your certificate has only a CN and no SAN, browsers will typically warn that it's invalid for the hostname.

Create a configuration file `csr.conf`:

```ini
[req]
default_bits = 2048
prompt = no
default_md = sha256
distinguished_name = dn
req_extensions = req_ext

[dn]
C = IN
ST = Rajasthan
L = Jaipur
O = Lab
OU = Kubernetes
CN = myapp.example.com

[req_ext]
subjectAltName = @alt_names

[alt_names]
DNS.1 = myapp.example.com
DNS.2 = *.example.com
```

Generate the key and CSR:

```bash
openssl genrsa -out tls.key 2048

openssl req \
  -new \
  -key tls.key \
  -out tls.csr \
  -config csr.conf
```

Self-sign it while preserving the SAN extension:

```bash
openssl x509 \
  -req \
  -days 365 \
  -in tls.csr \
  -signkey tls.key \
  -out tls.crt \
  -extensions req_ext \
  -extfile csr.conf
```

Verify the SANs:

```bash
openssl x509 -in tls.crt -text -noout
```

Look for:

```text
X509v3 Subject Alternative Name:
    DNS:myapp.example.com, DNS:*.example.com
```

For Kubernetes Ingress, this SAN-based certificate is the preferred approach because it works correctly with modern browsers and TLS clients.
