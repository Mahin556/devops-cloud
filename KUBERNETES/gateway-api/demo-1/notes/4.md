Great question. The answer is that **WSL2 itself implements localhost forwarding** between Windows and the Linux VM.

### Without WSL2 localhost forwarding

Normally, your setup looks like this:

```text
+----------------------+
| Windows Host         |
| 127.0.0.1            |
+----------+-----------+
           |
           | (Hyper-V NAT)
           |
+----------v-----------+
| WSL2 VM              |
| eth0: 172.29.x.x     |
| lo: 127.0.0.1        |
+----------------------+
```

Normally:

* `Windows localhost (127.0.0.1)` is **not** the same as
* `WSL localhost (127.0.0.1)`.

They're different network namespaces.

---

## What WSL2 does

Microsoft runs a **localhost forwarding service** on Windows.

When WSL detects a process listening inside Linux, it automatically creates a proxy on Windows.

For example, suppose your Go application listens on:

```text
WSL
0.0.0.0:5000
```

WSL automatically exposes it on Windows as:

```text
Windows
127.0.0.1:5000
```

So the flow is:

```text
Chrome (Windows)
        |
        | localhost:5000
        |
Windows localhost proxy
        |
Hyper-V virtual network
        |
WSL eth0 (172.29.109.206)
        |
Go Application
```

You don't configure this yourself—WSL handles it.

---

## It's similar to running `netsh portproxy`

WSL is effectively doing something conceptually similar to:

```text
Windows localhost:5000
        ↓
172.29.109.206:5000
```

but internally, using Windows networking components (it's not literally invoking `netsh`).

---

## Example

Suppose inside WSL:

```bash
python3 -m http.server 8080
```

The server is listening on:

```text
0.0.0.0:8080
```

Without any additional configuration, on Windows you can open:

```text
http://localhost:8080
```

and you'll reach the Python server in WSL.

---

## Why doesn't it always work?

WSL only forwards if the application is listening on all interfaces (or at least the WSL network interface).

Good:

```text
0.0.0.0:8080
```

or

```text
[::]:8080
```

Potentially problematic:

```text
127.0.0.1:8080
```

because that binds only to the loopback interface inside Linux.

---

## Why does Traefik fail?

Your earlier error was:

```text
listen tcp :80: bind: permission denied
```

Traefik never successfully started listening on port 80.

That means WSL has nothing to forward.

The chain is:

```text
Windows localhost:80
        |
WSL forwarding
        |
Nothing is listening
        |
Connection refused
```

---

## How does WSL know what to forward?

WSL monitors the Linux networking stack. When a process starts listening on a TCP port, WSL's networking integration exposes that port on the Windows host's `localhost` (assuming localhost forwarding is enabled).

---

## What if another Windows application already uses port 80?

Suppose IIS is running:

```text
Windows
IIS ---> Port 80
```

and inside WSL:

```text
Traefik ---> Port 80
```

WSL **cannot** forward Linux port 80 because Windows already owns that port. Only one process can bind to a given TCP port on the same IP address.

### Your case

Since you're using **Docker Desktop + WSL + Traefik**, let's first verify **what is actually listening**.

Run inside WSL:

```bash
sudo ss -lntp | grep -E ':80|:8000|:443|:8443'
```

and on Windows PowerShell:

```powershell
netstat -ano | findstr ":80"
```

These two commands will tell us:

1. whether Traefik is listening inside WSL,
2. whether Windows already has something bound to port 80,
3. and why the forwarding isn't working.
