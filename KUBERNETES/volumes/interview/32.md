**Yes — `ReclaimPolicy: Delete` deletes the actual cloud volume too, not just the Kubernetes object.**

For volume plugins that support the Delete reclaim policy, deletion removes both the PersistentVolume object from Kubernetes AND the associated storage asset in external infrastructure — such as an AWS EBS, GCE PD, Azure Disk, or Cinder volume.

Here's the full deletion chain so you can see exactly what happens:

```
kubectl delete pvc my-pvc
         │
         ▼
1. PVC object deleted from Kubernetes
         │
         ▼
2. PV status changes: Bound → Released
         │
         ▼
3. ReclaimPolicy: Delete kicks in
         │
         ▼
4. Kubernetes calls the CSI driver / volume plugin:
   "delete this volume"
         │
         ▼
5. CSI driver calls the cloud API:
   AWS:   ec2.DeleteVolume(vol-0abc123...)   ← real EBS volume gone
   GCP:   compute.Disks.Delete(...)          ← real GCE PD gone
   Azure: disk.Delete(...)                   ← real Azure Disk gone
         │
         ▼
6. PV object deleted from Kubernetes

Result: EVERYTHING is gone — PVC, PV, and cloud volume.
Data is unrecoverable unless you had a snapshot.
```

## One Critical Gotcha — Only Works for Dynamically Provisioned Volumes

If you manually created a PV (pre-provisioned) with `persistentVolumeReclaimPolicy: Delete` and then delete the PVC, the EBS volume does NOT automatically get deleted — the controller can't find the right plugin to handle it for manually-created PVs. You'd have to delete the cloud volume yourself via AWS CLI/console.

```
Dynamically provisioned (StorageClass creates PV automatically):
  Delete PVC → cloud volume deleted ✅ (automatic)

Statically provisioned (you wrote the PV yaml manually):
  Delete PVC → PV deleted, cloud volume STAYS ⚠️ (manual cleanup needed)
```

## The Three Policies Compared

| Policy | Delete PVC → PV? | Delete PVC → Cloud Volume? | Data safe? |
|---|---|---|---|
| **Delete** | ✅ Yes | ✅ Yes (dynamically provisioned) | ❌ Gone permanently |
| **Retain** | ❌ No (PV moves to Released) | ❌ No — survives | ✅ Safe, manual cleanup |
| **Recycle** | ❌ Deprecated | ❌ N/A | ❌ Data wiped (rm -rf) |

## Practical Rule

Use Delete policy for ephemeral or easily reproducible data like caches, temporary processing workloads, or development environments. Use Retain policy for production databases, user data, or any storage requiring backup verification before deletion.

```yaml
# Production DB — use Retain, never lose data accidentally
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: prod-db-storage
provisioner: ebs.csi.aws.com
reclaimPolicy: Retain     # ← cloud volume survives PVC deletion

# Dev/cache — Delete is fine, nothing worth keeping
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: dev-storage
provisioner: ebs.csi.aws.com
reclaimPolicy: Delete     # ← cloud volume deleted automatically = no orphaned cost
```

The default reclaim policy for dynamically provisioned PersistentVolumes is "Delete" — this automatic behavior might be inappropriate if the volume contains precious data. Always check what StorageClass your PVCs are using in production — if it's the default class with `Delete`, a mistyped `kubectl delete pvc` on a production database PVC means the data is gone with no way back.
