This article demonstrates a **canary deployment** using the **NGINX Ingress Controller**. Let's understand the entire process from start to finish.

---

# What is a Canary Deployment?

A canary deployment is a deployment strategy where a **new version of an application (v2)** is released to a **small percentage of users**, while the majority continue using the **stable version (v1)**.

Instead of immediately switching everyone to the new version, traffic is shifted gradually.

```
Initially

100%
 |
 v
Version 1
```

↓

```
Canary

70%
 |
 v
Version 1

30%
 |
 v
Version 2
```

↓

```
Eventually

100%
 |
 v
Version 2
```

This minimizes risk because if version 2 has problems, only a small percentage of users are affected.

---

# Why Use Canary Deployments?

Suppose you release version 2 and it contains:

* Memory leaks
* High CPU usage
* Database migration issues
* API failures
* Unexpected bugs

If you switch **100%** of users to v2 immediately, your entire application is affected.

With a canary deployment:

* Most users continue using the stable version.
* Only a small group uses the new version.
* If issues are found, you can roll back quickly by removing the canary configuration.

# Prerequisites

Before starting, ensure you have:

* A Kubernetes cluster (e.g., Minikube, Kind, GKE, EKS, AKS, kubeadm).
* Helm installed.
* The NGINX Ingress Controller deployed.

---

# Step 1: Install the NGINX Ingress Controller

Add the Helm repository:

```bash
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
```

Install the controller:

```bash
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace \
  --wait
```

This creates:

* Deployment
* Service
* Admission webhook
* ConfigMap
* RBAC resources

---

# Step 8: Create a Canary Ingress

This is the key part.

Create another Ingress using:

```yaml
annotations:

  nginx.ingress.kubernetes.io/canary: "true"

  nginx.ingress.kubernetes.io/canary-weight: "30"
```

Notice:

* Same host
* Same path
* Different backend

Stable Ingress:

```
Host

canary-app.com

↓

Service v1
```

Canary Ingress:

```
Host

canary-app.com

↓

Service v2
```

Normally Kubernetes would reject duplicate host/path combinations.

You would get:

```
host already defined
```

The annotation:

```yaml
nginx.ingress.kubernetes.io/canary: "true"
```

tells the NGINX admission webhook that this Ingress is a **canary**, so duplicate host/path rules are allowed.

---

# Step 9: Canary Weight

The annotation:

```yaml
nginx.ingress.kubernetes.io/canary-weight: "30"
```

means:

```
30%

↓

Version 2
```

```
70%

↓

Version 1
```

Example:

```
100 Requests
```

↓

```
70 Requests

↓

Version 1
```

```
30 Requests

↓

Version 2
```

NGINX chooses the backend probabilistically.

# Canary Routing Options

NGINX supports several canary strategies.

### 1. By Weight

```yaml
nginx.ingress.kubernetes.io/canary-weight: "30"
```

Routes approximately 30% of traffic to the canary.

---

### 2. By Header

```yaml
nginx.ingress.kubernetes.io/canary-by-header: X-Canary
```

If the request includes:

```
X-Canary: always
```

it is routed to v2; otherwise it goes to v1.

Useful for QA teams or internal testers.

---

### 3. By Cookie

```yaml
nginx.ingress.kubernetes.io/canary-by-cookie: canary
```

Requests with a specific cookie value are routed to v2.

Useful for beta programs.

# Rollback

If version 2 has issues, rollback is simple.

Option 1:

Delete the canary Ingress:

```bash
kubectl delete ingress canary-test-v2
```

Option 2:

Set:

```yaml
nginx.ingress.kubernetes.io/canary-weight: "0"
```

Now all traffic returns to version 1.

---

# Promote Version 2

Once version 2 is verified:

1. Update the **stable Ingress** so its backend points to the **v2 Service** (or update the stable Service selector to target the v2 Pods).
2. Delete the canary Ingress.
3. Optionally remove the v1 Deployment and Service.

Traffic becomes:

```
100%

↓

Version 2
```

# Advantages of Canary Deployments

* **Reduced risk:** Only a small percentage of users see the new version initially.
* **Fast rollback:** Removing the canary Ingress or setting its weight to `0` immediately sends all traffic back to the stable version.
* **Gradual rollout:** Increase traffic in controlled steps as confidence grows.
* **Flexible routing:** Traffic can be split by percentage, request headers, or cookies.
* **No service mesh required:** The NGINX Ingress Controller provides canary functionality without adding technologies like Istio or Linkerd.
