# Current Capabilities
```
cap_chown, cap_dac_override, cap_fowner, cap_fsetid,
cap_kill, cap_setgid, cap_setuid, cap_setpcap,
cap_net_bind_service, cap_net_raw, cap_sys_chroot,
cap_mknod, cap_audit_write, cap_setfcap = ep
```
• `=ep` means:
* **e = effective**
* **p = permitted**

That means these capabilities are **currently active and usable** by the process.

### What this means practically:

• `cap_chown` → Change file ownership
• `cap_dac_override` → Bypass file permission checks
• `cap_setuid` → Change user ID
• `cap_setgid` → Change group ID
• `cap_net_bind_service` → Bind to ports < 1024
• `cap_net_raw` → Create raw network packets (⚠️ important)
• `cap_sys_chroot` → Use chroot
• `cap_mknod` → Create device files

⚠️ Important:
Even if container is “root”, Linux limits power using capabilities instead of giving full root privileges.

---

# Bounding Set
```
Bounding set = cap_chown, cap_dac_override, ...
```
• This is the **maximum capabilities this process can ever gain**.
• Even if it tries to elevate privilege, it **cannot exceed this set**.

Think of it as:
> Upper limit of power inside container
If something is NOT in bounding set → it can NEVER be obtained.

# Current IAB (Inheritable / Ambient / Bounding Restrictions)
You see:
```
!cap_sys_admin
!cap_sys_module
!cap_sys_ptrace
!cap_sys_boot
!cap_net_admin
...
```
The `!` means:
These capabilities are **NOT available**.
Important ones missing:
• `cap_sys_admin` ❌ (VERY powerful capability)
• `cap_sys_module` ❌ (load kernel modules)
• `cap_sys_ptrace` ❌ (inspect other processes)
• `cap_net_admin` ❌ (modify network interfaces)

This is GOOD.
If `cap_sys_admin` was present → container escape risk increases significantly.

# UID and GID
```
uid=0(root)
gid=0(root)
```

Container is running as:
• root user
• root group

⚠️ This is risky in production.

Better practice:
```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
```

# What This Means Overall

Your container:
✅ Has limited root (capability-based)
❌ Is running as root
❌ Allows privilege escalation
⚠️ Has `cap_net_raw` (can craft packets — used in attacks)

It is **not fully hardened**.

---

# How to Harden It

Example secure pod config:
```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
```

If needed:
```yaml
  capabilities:
    add:
      - NET_BIND_SERVICE
```

Principle:
> Drop everything. Add only what is necessary.

# DevOps Interview Insight

They may ask:
• Why drop `cap_net_raw`?
* Prevent packet crafting, ARP spoofing
  • Why remove `cap_setuid`?
* Prevent user switching
  • Why disable privilege escalation?
* Stop SUID-based attacks
