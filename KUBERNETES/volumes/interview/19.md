# Volumes with Deployments - Are They Shared or Per-Pod?

Great question! This is a critical concept. Let me explain with examples.

---

## Short Answer

**It depends on the volume type:**
- ✅ **Shared volumes** (ConfigMap, Secret, NFS, etc.): **Same volume for all pods**
- ❌ **Per-pod volumes** (PersistentVolume, emptyDir, etc.): **Separate volume for each pod**

Let me show you with examples:

---

## Example 1: ConfigMap Volume (SHARED)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:latest
        volumeMounts:
        - name: config-volume
          mountPath: /etc/config
      volumes:
      - name: config-volume
        configMap:
          name: app-config
```

**Result:**
```
ConfigMap: app-config (one instance in cluster)
        ↓
All 3 Pods mount the SAME ConfigMap
        ↓
Pod 1: /etc/config → reads app-config
Pod 2: /etc/config → reads SAME app-config
Pod 3: /etc/config → reads SAME app-config

If config changes:
├─ ConfigMap updated once
└─ All 3 pods see the change ✅
```

**Visual:**
```
┌─────────────────────────────────────────┐
│        ConfigMap: app-config            │
│      (Single shared instance)           │
│                                         │
│  config.json = {"debug": true}          │
└──────────────┬──────────────────────────┘
               │
        ┌──────┼──────┬────────┐
        │      │      │        │
    ┌───▼──┐ ┌─▼──┐ ┌─▼──┐ ┌──▼──┐
    │Pod 1 │ │Pod2│ │Pod3│ │Pod 4│ (replicas: 3)
    │reads │ │read│ │read│ │     │
    │same  │ │same│ │same│ │     │
    └──────┘ └────┘ └────┘ └─────┘
```

## Example 2: emptyDir Volume (PER-POD)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cache-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cache
  template:
    metadata:
      labels:
        app: cache
    spec:
      containers:
      - name: cache-app
        image: cache-app:latest
        volumeMounts:
        - name: temp-volume
          mountPath: /tmp/cache
      volumes:
      - name: temp-volume
        emptyDir: {}
```

**Result:**
```
emptyDir: {} (ephemeral, per-pod)
        ↓
Each Pod gets its OWN separate emptyDir
        ↓
Pod 1: /tmp/cache → separate empty directory
Pod 2: /tmp/cache → different empty directory
Pod 3: /tmp/cache → another different empty directory

Data is NOT shared:
├─ Pod 1 writes to /tmp/cache/data.txt
├─ Pod 2 cannot see this file
└─ Pod 3 cannot see this file ❌
```

**Visual:**
```
Each Pod has its own emptyDir:

Pod 1                Pod 2                Pod 3
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ /tmp/cache  │     │ /tmp/cache  │     │ /tmp/cache  │
│             │     │             │     │             │
│ file.txt    │     │ file.txt    │     │ file.txt    │
│ (Pod 1 only)│     │ (Pod 2 only)│     │ (Pod 3 only)│
└─────────────┘     └─────────────┘     └─────────────┘

NOT shared! Each is independent.
```

## Example 3: PersistentVolume (PER-POD or SHARED)

### Scenario A: Each Pod Gets Its Own PersistentVolume

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: database-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      containers:
      - name: db
        image: postgres:latest
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: db-pvc
```

**What happens:**
```
Issue: You specified claimName: db-pvc (single PVC)

Kubernetes tries to mount this to:
├─ Pod 1 ✅ Mounted successfully
├─ Pod 2 ❌ CANNOT MOUNT - already mounted to Pod 1!
└─ Pod 3 ❌ CANNOT MOUNT - already mounted to Pod 1!

Result: Only Pod 1 runs, Pods 2 & 3 are PENDING
Error message: "Multi-Attach error for volume "db-pvc""
```

**Why?** Most PersistentVolumes support `ReadWriteOnce` access mode:
- Only ONE pod can read AND write simultaneously
- Prevents data corruption

---

### Scenario B: Each Pod Gets Its Own PVC (Correct Way)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: database-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      containers:
      - name: db
        image: postgres:latest
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
      
      # StatefulSet with VolumeClaimTemplate is better for this!
      # But here's how to do it with Deployment:
      volumes:
      - name: data
        persistentVolumeClaim:
          # Problem: This would try to share one PVC
          claimName: db-pvc
```

**Better approach: Use StatefulSet**

```yaml
apiVersion: apps/v1
kind: StatefulSet  # ← Better for per-pod PVCs!
metadata:
  name: database
spec:
  serviceName: database
  replicas: 3
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      containers:
      - name: db
        image: postgres:latest
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  
  # Each replica gets its own PVC!
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 10Gi
```

**Result:**
```
Kubernetes automatically creates:
├─ database-0: PVC "data-database-0" (10Gi)
├─ database-1: PVC "data-database-1" (10Gi)
└─ database-2: PVC "data-database-2" (10Gi)

Each pod has its own persistent storage ✅
```

## Real-World Example: Web App with Multiple Pod Types

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: app
        image: myapp:latest
        volumeMounts:
        # SHARED across all 3 pods
        - name: config
          mountPath: /etc/config
        - name: secrets
          mountPath: /etc/secrets
        - name: shared-logs
          mountPath: /var/log/shared
        
        # SEPARATE for each pod
        - name: cache
          mountPath: /tmp/cache
      
      volumes:
      # SHARED: ConfigMap (same for all pods)
      - name: config
        configMap:
          name: app-config
      
      # SHARED: Secret (same for all pods)
      - name: secrets
        secret:
          secretName: db-credentials
      
      # SHARED: NFS (all pods mount same NFS server)
      - name: shared-logs
        nfs:
          server: nfs-server.example.com
          path: /exports/logs
      
      # SEPARATE: emptyDir (each pod gets its own)
      - name: cache
        emptyDir: {}
```

**What actually happens:**

```
Deployment creates 3 Pods:

Pod 1 (web-app-xyz-abc):
├─ /etc/config → ConfigMap app-config (SHARED)
├─ /etc/secrets → Secret db-credentials (SHARED)
├─ /var/log/shared → NFS server (SHARED)
└─ /tmp/cache → emptyDir (SEPARATE, unique to Pod 1)

Pod 2 (web-app-xyz-def):
├─ /etc/config → ConfigMap app-config (SAME as Pod 1)
├─ /etc/secrets → Secret db-credentials (SAME as Pod 1)
├─ /var/log/shared → NFS server (SAME as Pod 1)
└─ /tmp/cache → emptyDir (DIFFERENT, unique to Pod 2)

Pod 3 (web-app-xyz-ghi):
├─ /etc/config → ConfigMap app-config (SAME as Pod 1 & 2)
├─ /etc/secrets → Secret db-credentials (SAME as Pod 1 & 2)
├─ /var/log/shared → NFS server (SAME as Pod 1 & 2)
└─ /tmp/cache → emptyDir (DIFFERENT, unique to Pod 3)
```

## Database Scenario: Correct Way with StatefulSet

If you need **each pod to have its own persistent volume**, use **StatefulSet**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql-service
spec:
  clusterIP: None  # Headless service for StatefulSet
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306

---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-service
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  
  # ← KEY DIFFERENCE: volumeClaimTemplates
  # Creates a separate PVC for each pod!
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 20Gi
```

**Result:**
```
Kubernetes automatically creates:
├─ mysql-0
│  └─ PVC "data-mysql-0" (20Gi) ← Separate for Pod 0
│
├─ mysql-1
│  └─ PVC "data-mysql-1" (20Gi) ← Separate for Pod 1
│
└─ mysql-2
   └─ PVC "data-mysql-2" (20Gi) ← Separate for Pod 2

Each pod has its own persistent storage!
```

## Quick Decision Guide

**Choose based on your use case:**

```
Do you want all pods to SHARE the same data?
├─ YES: Use ConfigMap, Secret, NFS, PV with RWX
│   └─ Data is shared and synchronized
│
└─ NO: Use emptyDir or StatefulSet with volumeClaimTemplate
    └─ Each pod has independent storage
```
