This diagram shows exactly **how containers work at the Linux kernel level**. Containers are not virtual machines — they are just Linux processes with namespace isolation and cgroup limits applied. Let me explain every piece.

## The Core Idea First

```
Without namespaces:
  All processes on a host share:
  - the same process tree (PID 1 = systemd/init)
  - the same filesystem
  - the same network interfaces
  - the same hostname
  - the same users

With namespaces:
  Each container gets its OWN isolated view of those resources
  The host still has ONE real kernel
  But each container THINKS it's alone on the machine
```

---

## 1. PID Namespace — `pid`

**What the diagram shows:** PID 1 inside the container

```
HOST VIEW:                    CONTAINER VIEW:
PID 1  → systemd              PID 1  → nginx   ← container thinks IT is init
PID 2  → kubelet              PID 2  → worker
PID 3  → containerd           PID 3  → logger
PID 847 → nginx (real PID)
PID 848 → worker
PID 849 → logger

The nginx process has PID 847 on the host
but sees itself as PID 1 inside the container
```

**Why this matters:**
```bash
# Inside container:
ps aux
# PID 1 = nginx   ← thinks it's the only process

# On the host:
ps aux | grep nginx
# PID 847 = nginx  ← real PID on host

# This is why the pause container exists in Kubernetes:
# It holds PID 1 in the pod's PID namespace
# so the app container doesn't have to

# If PID 1 dies inside the container → container stops
# Container runtimes use this: kill PID 1 = stop container
```

---

## 2. Mount Namespace — `mnt`

**What the diagram shows:** root filesystem, `eth0` network interface

```
HOST filesystem:              Container filesystem:
/                             /
├── bin                       ├── bin    (from container image)
├── etc                       ├── etc    (from container image)
├── home                      ├── app    (your application)
├── var                       └── tmp
│   ├── lib
│   └── log
└── proc

Container cannot see /home, /var/lib, /etc/shadow on the host
It sees its OWN root filesystem built from the Docker image
```

**How it works — layers:**
```
Container image = read-only layers stacked together:
Layer 3: your app code        ← top layer (writable)
Layer 2: npm packages
Layer 1: node:18 base image
Layer 0: ubuntu base

Mount namespace presents all these as ONE unified filesystem
Changes inside container → written to writable top layer only
Underlying layers NEVER change (this is image immutability)
```

**Volume mounts punch a hole through:**
```bash
docker run -v /host/data:/container/data nginx
#             ↑ host path  ↑ container path
# Mount namespace is modified to bind-mount this specific directory
# Everything else still isolated
```

## 3. Network Namespace — `net`

**What the diagram shows:** eth0 network interface

```
HOST network:                 CONTAINER network:
eth0 → 192.168.1.100          eth0 → 10.244.1.5  ← different IP entirely
lo   → 127.0.0.1              lo   → 127.0.0.1

The container gets its OWN:
- Network interfaces (eth0)
- IP address
- Routing table
- iptables rules
- Port space (container can use port 80 even if host uses port 80)
```

**This is how Kubernetes pod networking works:**
```
Each pod gets its own network namespace
The pause container holds that namespace open
All containers IN the pod SHARE that one network namespace
→ that's why containers in the same pod talk via localhost

Pod A network namespace:      Pod B network namespace:
eth0 → 10.244.1.5             eth0 → 10.244.1.6
lo   → 127.0.0.1              lo   → 127.0.0.1

# Container A and sidecar in Pod A share 10.244.1.5
# They talk to each other via localhost:PORT
# They talk to Pod B via 10.244.1.6:PORT
```

**How the virtual ethernet works:**
```
Container eth0 ←──── veth pair ────► host vethXXX ──► bridge/CNI ──► other pods
(virtual cable connecting container to host network)
```

## 4. IPC Namespace — `ipc`

**What the diagram shows:** "Process inside container to share memory"

IPC = Inter-Process Communication. Covers:
- Shared memory segments
- Semaphores
- Message queues

```
Without IPC namespace:
  Process A (container 1) could write to shared memory
  Process B (container 2) could READ that memory
  → complete data leak between containers

With IPC namespace:
  Container 1 has its OWN shared memory space
  Container 2 has its OWN shared memory space
  They cannot see each other's memory AT ALL

# Kubernetes example where you'd REMOVE this isolation:
# High-performance apps that need shared memory between containers in same pod:
spec:
  volumes:
    - name: shm
      emptyDir:
        medium: Memory    # RAM-backed shared memory volume

# Or for containers that specifically need to share IPC:
spec:
  hostIPC: true           # dangerous — shares host's IPC namespace
  shareProcessNamespace: true  # containers in pod share PID+IPC namespace
```

## 5. UTS Namespace — `utc` (Unix Timesharing System)

**What the diagram shows:** "own hostname"

UTS controls the hostname and domain name of a process.

```
HOST hostname: prod-node-1.company.com

Container 1 hostname: webapp-pod-abc123
Container 2 hostname: database-pod-xyz789

# Inside container 1:
hostname
# webapp-pod-abc123   ← its own hostname

# Inside container 2:
hostname
# database-pod-xyz789  ← completely different

# On the host:
hostname
# prod-node-1.company.com  ← host is unchanged

# In Kubernetes — the hostname is the pod name:
kubectl exec -it mypod -- hostname
# mypod-7d4f9c8b6-xkp2n   ← pod name becomes the container hostname
```

**Why this matters in practice:**
```bash
# Apps that use hostname for identity (like Kafka, Zookeeper, StatefulSets)
# need a stable, unique hostname
# UTS namespace gives each pod/container its own hostname
# StatefulSets give predictable hostnames:
# kafka-0, kafka-1, kafka-2 → each has its own UTS namespace
```

## 6. User Namespace — `user`

**What the diagram shows:** "own root user for container → Map to different user on host"

This is the most security-critical namespace:

```
INSIDE CONTAINER:          ON THE HOST:
UID 0 (root)      ────►    UID 100000 (nobody)
UID 1000 (app)    ────►    UID 101000 (nobody)

Container THINKS it's running as root
Host kernel sees it as an unprivileged user

If container escapes (vulnerability):
Attacker gets UID 100000 on host = basically nothing
NOT actual root on the host
```

**OpenShift enforces this strictly:**
```bash
# OpenShift assigns a random UID range to each project:
oc get namespace myproject -o yaml | grep uid-range
# openshift.io/sa.scc.uid-range: 1000680000/10000
# Pods in this project run as UID 1000680000-1000689999

# NEVER as real root (UID 0) on the host
# This is WHY OpenShift blocks containers that require root by default
# SCC restricted policy enforces non-root user
```

**Docker rootless mode uses user namespaces:**
```
containerd/runc creates user namespace mapping:
Container UID 0 → Host UID 1000 (your regular user)
No real root involved anywhere
```

## Cgroups — Control Groups (Resource LIMITS, not isolation)

**What the diagram shows:** `cgroup (isolation)` at the bottom

```
Namespaces = what you CAN SEE (isolation)
Cgroups    = how much you CAN USE (limits)

These are completely separate Linux mechanisms
working together to create containers
```

**What cgroups control:**
```
cgroup subsystem    What it limits
─────────────────────────────────────────────────
cpu                 CPU time percentage
cpuset              Which CPU cores can be used
memory              RAM usage, swap usage
blkio               Disk read/write bandwidth
net_cls             Network packet priority
pids                Number of processes/threads
devices             Which devices can be accessed
```

**How Kubernetes resource limits map to cgroups:**
```yaml
resources:
  limits:
    cpu: "500m"       # → cgroup cpu.shares = 512
    memory: "256Mi"   # → cgroup memory.limit_in_bytes = 268435456
```

```bash
# See the actual cgroup for a container on the host:
cat /sys/fs/cgroup/memory/kubepods/pod<pod-uid>/<container-id>/memory.limit_in_bytes
# 268435456  ← 256Mi in bytes — the REAL kernel-level limit

# If container exceeds this:
# kernel OOM killer fires → process killed → Exit Code 137 → OOMKilled
```

## Full Picture Together

```
Linux Kernel
    │
    ├── Namespaces (isolation — what you SEE)
    │   ├── PID  → own process tree, PID 1 = your app
    │   ├── mnt  → own filesystem from image layers
    │   ├── net  → own eth0, own IP address
    │   ├── ipc  → own shared memory
    │   ├── uts  → own hostname
    │   └── user → root inside ≠ root outside
    │
    └── Cgroups (limits — how much you GET)
        ├── cpu    → max CPU usage
        ├── memory → max RAM (OOMKill if exceeded)
        ├── blkio  → max disk I/O
        └── pids   → max process count

Container runtime (containerd/runc/crun):
  1. Creates these namespaces
  2. Sets up cgroup limits
  3. Unpacks image layers (overlayfs)
  4. Runs your process inside

Result: isolated, limited process that THINKS it's alone on a machine
        but is actually sharing ONE Linux kernel with everyone else
```

**One-line summary of each:**

| Namespace | Isolates | Without it |
|---|---|---|
| `pid` | Process tree | All containers see all processes |
| `mnt` | Filesystem | All containers share host filesystem |
| `net` | Network interfaces + IPs | All containers share eth0 |
| `ipc` | Shared memory | Containers can read each other's memory |
| `uts` | Hostname | All containers have same hostname as host |
| `user` | User/group IDs | Root in container = root on host |
| `cgroup` | Resource limits (NOT isolation) | Container can consume all host CPU/RAM |
