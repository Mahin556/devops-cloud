# Kubernetes AppArmor — Complete CKS Notes

This transcript covers **AppArmor**, how to create an AppArmor profile, load it into the Linux kernel, attach it to a Kubernetes Pod/container, and verify that the restrictions are actually enforced.

The main CKS idea is:

> **AppArmor provides an additional layer of mandatory access control for workloads by restricting what a process inside a container is allowed to do.**

---

# 1. What is AppArmor?

**AppArmor** is a Linux kernel security module that provides **Mandatory Access Control (MAC)**.

It allows you to define a security profile describing what a program/process is allowed or denied to do.

For example, you can create a profile that says:

```text
Application
   |
   +-- Read files     ✅
   +-- Execute files  ✅
   +-- Write files    ❌
```

So even if the application normally has permission to perform an operation, **AppArmor can restrict it according to the security profile**.

The transcript describes AppArmor as a Linux kernel module that provides mandatory access control for workloads.

---

# 2. Why AppArmor in Kubernetes?

Normally, a container's process has access to whatever Linux capabilities and filesystem permissions it has.

AppArmor adds another security layer:

```text
Kubernetes
    |
    v
Container
    |
    v
Linux process
    |
    v
AppArmor profile
    |
    v
Allowed / Denied operations
```

The objective is **least privilege**:

> Allow the workload to perform only the operations it actually needs.

The transcript emphasizes that AppArmor adds an extra security layer to Kubernetes workloads and helps applications run with the least privilege necessary.

---

# 3. Important Concept: AppArmor Is Node-Level

This is one of the most important things to understand for the CKS.

AppArmor is a **Linux kernel feature**.

Therefore, the profile must exist and be loaded on the **node where the Pod runs**.

For example:

```text
Node 1
 ├── AppArmor profile loaded
 └── Pod scheduled here
       ↓
    Works ✅
```

But:

```text
Node 2
 ├── AppArmor profile NOT loaded
 └── Pod scheduled here
       ↓
    Profile unavailable ❌
```

Therefore:

> **The AppArmor profile needs to be available on every node where Pods using that profile may be scheduled.**

The transcript specifically points this out: if the profile exists only on the control-plane node and the Pod gets scheduled on another node, the profile won't be available there.

# 6. Create an AppArmor Profile

The transcript creates a profile called:

```text
deny-write
```

The purpose is simple:

> **Deny file writes.**

A simplified profile is:

```text
#include <tunables/global>

profile deny-write {
    file,
    deny /** w,
}
```

The important part is:

```text
deny /** w,
```

Meaning:

```text
/**  → files/directories under the filesystem
w    → write
```

So the profile denies write access.

### Concept

```text
Application
     |
     | touch /tmp/test
     v
AppArmor
     |
     v
❌ DENIED
```

# 10. Create a Kubernetes Pod Using AppArmor

Once the profile is loaded on the node, you can attach it to a Pod.

The transcript emphasizes an important change in Kubernetes configuration:

> Previously AppArmor profiles were commonly specified through annotations; now the profile can be specified through the Pod/container `securityContext`.

The example uses:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-demo

spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: deny-write

  containers:
  - name: apparmor-demo
    image: busybox
    command:
    - sleep
    - "3600"
```

---

# 11. Understand `appArmorProfile`

The important section is:

```yaml
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: deny-write
```

There are two particularly important values here:

```yaml
type: Localhost
```

and:

```yaml
localhostProfile: deny-write
```

---

# 12. What Does `Localhost` Mean?

```yaml
type: Localhost
```

means the AppArmor profile is a profile that is already available on the **local node**.

So:

```text
Pod
 ↓
Localhost AppArmor profile
 ↓
Node's loaded profile
 ↓
deny-write
```

The profile is **not being downloaded from somewhere else**.

The node must already have the profile.

---

# 13. `localhostProfile`

```yaml
localhostProfile: deny-write
```

This tells Kubernetes:

> Use the AppArmor profile named `deny-write`.

Therefore these two pieces work together:

```yaml
type: Localhost
localhostProfile: deny-write
```

Meaning:

> Attach the locally available AppArmor profile named `deny-write`.

---

# 14. Complete Example

A simple Pod from the scenario can be represented as:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-demo

spec:
  nodeName: control-plane

  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: deny-write

  containers:
  - name: apparmor-demo
    image: busybox
    command:
    - sleep
    - "3600"
```

The transcript pins the Pod to the control-plane node because the profile was loaded there.

---

# 15. Why `nodeName` Was Used

The transcript uses:

```yaml
nodeName: control-plane
```

because the profile had only been loaded on that node.

Think:

```text
control-plane
   |
   +── deny-write loaded
   |
   +── Pod scheduled here
          ↓
       Works
```

If the Pod were scheduled on another node:

```text
worker
   |
   +── deny-write NOT loaded
   |
   +── Pod
          ↓
       Problem
```

### Production/real cluster approach

Instead of forcing:

```yaml
nodeName: control-plane
```

you should make sure the profile is installed/loaded on **all appropriate nodes**, so normal scheduling can work.

The transcript explicitly says that the profile should ultimately be applied to all nodes where workloads using it might run.

# 17. Verify the AppArmor Profile Inside the Pod

The transcript uses:

```bash
kubectl exec apparmor-demo -- cat /proc/1/attr/current
```

This is extremely useful.

The output should show the active AppArmor profile.

For example:

```text
deny-write (enforce)
```

This tells you:

> The process is currently running under the `deny-write` AppArmor profile.

---

# 18. Why `/proc/1/attr/current`?

Inside the container:

```text
/proc/1/
```

represents information about **PID 1**, usually the main process of the container.

And:

```text
/proc/1/attr/current
```

shows the current security profile/attributes associated with that process.

Therefore:

```bash
kubectl exec apparmor-demo -- cat /proc/1/attr/current
```

is effectively asking:

> **Which AppArmor profile is currently applied to the container's main process?**

---

# 19. Test the Restriction

Our profile denies writes:

```text
deny /** w
```

Therefore try:

```bash
kubectl exec apparmor-demo -- touch /tmp/test
```

Expected:

```text
touch: /tmp/test: Permission denied
```

This is exactly what we want.

---

# 20. What Happened?

The process requested:

```text
touch /tmp/test
```

which requires a file write/create operation.

The Linux permission system might normally allow it.

But AppArmor says:

```text
write → DENY
```

Therefore:

```text
Process
   |
   | touch /tmp/test
   v
Linux kernel
   |
   v
AppArmor
   |
   v
DENY
   |
   v
Permission denied
```

This proves the profile is not merely loaded — it is actually **being enforced**.

---

# 21. Loaded vs Enforced

This distinction is important.

### Loaded

```bash
aa-status | grep deny-write
```

tells you:

> The profile exists/is loaded.

### Applied to the process

```bash
cat /proc/1/attr/current
```

tells you:

> The process is associated with the profile.

### Actually working

```bash
touch /tmp/test
```

returning:

```text
Permission denied
```

demonstrates:

> The restriction is actually being enforced.

So your troubleshooting sequence can be:

```text
AppArmor enabled?
      ↓
Profile loaded?
      ↓
Profile attached?
      ↓
Restriction actually works?
```

# 22. AppArmor Modes

The transcript focuses on enforcement, but one important concept is the difference between **enforcing** and **complain** behavior.

For the CKS scenario, the important state is:

```text
enforce
```

because the profile must actually restrict the workload.

If a profile is only logging violations rather than blocking them, your `touch` test would not demonstrate the desired restriction.

# 23. AppArmor at Pod and Container Level

The transcript mentions that AppArmor profiles can be specified at:

* Pod level
* Container level

And importantly:

> **The container-level AppArmor profile takes precedence over the Pod-level AppArmor profile.**

Think:

```text
Pod
 |
 +── Pod-level profile
 |
 +── Container A → container-level profile
 |
 +── Container B → container-level profile
```

If a container has its own profile:

```text
Container-level
      ↓
takes precedence
```

over the Pod-level setting for that container.

# 24. Profile Does Not Exist

The transcript points out an important failure case.

Suppose your Pod says:

```yaml
localhostProfile: deny-write
```

but `deny-write` isn't available on the node.

Then the Pod won't be able to successfully use that profile.

Therefore:

```text
Pod asks for:
deny-write

Node:
deny-write ❌

Result:
Pod cannot use requested profile
```

### CKS lesson

If you see an error related to an AppArmor profile:

1. Check AppArmor is enabled.
2. Check the profile exists.
3. Check the profile is loaded.
4. Check the Pod is on the expected node.
5. Check the profile name exactly matches.

# 25. AppArmor Profile Must Be on the Right Nodes

This deserves special emphasis.

Suppose you have:

```text
3 Kubernetes nodes

node1 → profile loaded
node2 → profile loaded
node3 → profile NOT loaded
```

And a Deployment has:

```yaml
localhostProfile: deny-write
```

The scheduler could place a Pod on:

```text
node3
```

where the profile isn't available.

Therefore, a proper implementation needs the profile distributed to all nodes where that workload can run.

The transcript explicitly recommends applying the profile to all nodes and automating this process.

# 26. Automating Profile Distribution

The transcript mentions that in a real setup you would want to:

> automate the application of the AppArmor profiles onto the nodes.

A common Kubernetes approach would be to use something such as a **DaemonSet** or node provisioning/configuration process to ensure every relevant node has the required profile.

The key concept for CKS is not the automation implementation itself:

```text

       ↓
Profile installed
       ↓
Profile loaded
       ↓
Pod can be scheduled anywhere
```

# 29. AppArmor vs Kubernetes SecurityContext

Don't confuse these concepts.

Kubernetes:

```yaml
securityContext:
```

is the Kubernetes configuration mechanism.

Inside it, you can specify:

```yaml
appArmorProfile:
```

which tells Kubernetes which AppArmor profile should be applied.

So:

```text
Kubernetes YAML
      ↓
securityContext
      ↓
appArmorProfile
      ↓
Linux AppArmor
      ↓
Kernel enforcement
```

# 30. AppArmor vs Linux File Permissions

This is an important security concept.

Suppose:

```text
Linux permissions → allow write
```

but:

```text
AppArmor → deny write
```

The operation can still be denied.

Why?

Because AppArmor provides an additional **mandatory access control layer**.

Conceptually:

```text
Application
     |
     v
Linux permissions
     |
     v
AppArmor policy
     |
     v
Kernel
```

The final result must satisfy the applicable security restrictions.

---

# 31. AppArmor and Least Privilege

The ultimate security principle is:

```text
Give workload only what it needs.
```

For example, suppose an application only needs:

```text
Read configuration
Read certificates
Execute application
```

It doesn't necessarily need:

```text
Write arbitrary files
Modify system files
Execute arbitrary programs
```

An AppArmor profile can help enforce those restrictions.

Therefore:

```text
Less access
    ↓
Smaller attack surface
    ↓
Reduced impact if application is compromised
```
