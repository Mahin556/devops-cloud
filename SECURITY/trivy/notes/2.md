# Trivy Filesystem Scan — `trivy fs`

`trivy fs <path>` scans a **local filesystem target**, such as a project directory, for security issues.

Basic syntax:

```bash
trivy fs <path>
```

For example:

```bash
trivy fs .
```

This is particularly useful in the **CI source-code stage**, before building the container image.

---

# 1. What does `trivy fs .` scan?

Suppose your repository looks like:

```text
myapp/
├── Dockerfile
├── package.json
├── package-lock.json
├── src/
├── requirements.txt
├── terraform/
│   ├── main.tf
│   └── variables.tf
└── k8s/
    ├── deployment.yaml
    └── service.yaml
```

Running:

```bash
trivy fs .
```

can inspect the project for applicable security information such as:

```text
                trivy fs .
                     │
       ┌─────────────┼──────────────┐
       ▼             ▼              ▼
   Dependencies    Secrets       Configuration
       │             │              │
       ▼             ▼              ▼
      CVEs       API keys        Misconfigs
      etc.       passwords       IaC issues
```

The exact scanners enabled depend on your Trivy version/configuration.

---

# 2. Basic filesystem scan

```bash
trivy fs .
```

This is the simplest command.

You can also specify another directory:

```bash
trivy fs /home/mahin/project
```

or:

```bash
trivy fs ./my-project
```

---

# 3. Scan a specific file

You can target a particular file:

```bash
trivy fs ./package-lock.json
```

For example:

```text
package-lock.json
       │
       ▼
     Trivy
       │
       ▼
Dependency vulnerabilities
```

This is useful when troubleshooting a specific dependency file.

---

# 4. Filesystem vulnerability scanning

Suppose your project contains:

```text
package.json
package-lock.json
```

Trivy can identify vulnerable dependencies.

For example, conceptually:

```text
Package       Version       Severity
-------------------------------------
lodash        x.x.x         HIGH
express       x.x.x         CRITICAL
```

You can focus on vulnerabilities:

```bash
trivy fs --scanners vuln .
```

---

# 5. Secret scanning

You can specifically enable the secret scanner:

```bash
trivy fs --scanners secret .
```

This is extremely useful in CI/CD.

For example, suppose someone accidentally commits:

```text
AWS_SECRET_ACCESS_KEY=xxxx
```

or:

```text
github_token=xxxx
```

Trivy can identify potential secrets.

Pipeline:

```text
Developer
    │
    ▼
Git Push
    │
    ▼
Trivy Secret Scan
    │
    ├── No secret → Continue
    │
    └── Secret → Fail/Alert
```

This is a good **shift-left security** practice.

---

# 6. Multiple scanners

You can explicitly specify multiple scanners:

```bash
trivy fs \
  --scanners vuln,secret,misconfig \
  .
```

This tells Trivy to use:

```text
vuln
  ↓
Vulnerability scanning

secret
  ↓
Secret scanning

misconfig
  ↓
Misconfiguration scanning
```

Your notes also mention:

```text
license
```

which can be included when applicable:

```bash
trivy fs \
  --scanners vuln,secret,misconfig,license \
  .
```

# 7. What does `misconfig` mean?

`misconfig` is useful for configuration/IaC security.

For example, your repository may contain:

```text
Terraform
Kubernetes YAML
Dockerfile
CloudFormation
```

Trivy can identify certain insecure configurations.

For example:

```text
Security Group
     │
     └── 0.0.0.0/0

S3
     │
     └── Public access

Container
     │
     └── Privileged configuration
```

So:

```bash
trivy fs --scanners misconfig .
```

can be useful during your **IaC/security stage**.

---

# 8. Severity filtering

You don't always want to display every finding.

You can use:

```bash
--severity
```

For example:

```bash
trivy fs \
  --severity HIGH,CRITICAL \
  .
```

This focuses the output on:

```text
HIGH
CRITICAL
```

A CI pipeline might use this as a security gate.

---

# 9. `--exit-code`

This is **very important for CI/CD**.

By itself, a scanner can report a vulnerability without necessarily making your pipeline fail.

You can use:

```bash
--exit-code 1
```

For example:

```bash
trivy fs \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  .
```

Conceptually:

```text
             Trivy
               │
               ▼
       HIGH/CRITICAL found?
          │           │
         NO          YES
          │           │
          ▼           ▼
      exit 0       exit 1
          │           │
          ▼           ▼
     CI passes     CI fails
```

This turns Trivy from simply a **reporting tool** into a **CI security gate**.

```bash

  --format sarif \
  --output trivy-results.sarif \
```

So:

```text

json
 ↓
Automation/API/report processing

sarif
 ↓
Security/code-scanning integrations
```

# 13. `trivy fs` vs `trivy image`

This distinction is **very important**.

### `trivy fs`

Scans the **source/project filesystem**.

```bash
trivy fs .
```

Think:

```text
Source code
Dependencies
Secrets
IaC/configuration
```

### `trivy image`

Scans the **built container image**.

```bash
trivy image myapp:1.0
```

Think:

```text
Container image
      │
      ├── OS packages
      ├── Application dependencies
      └── Vulnerabilities
```

So a strong pipeline can use both:

```text
                 Git Repository
                       │
                       ▼
                  trivy fs .
                       │
                       ▼
                   Docker Build
                       │
                       ▼
                  myapp:1.0
                       │
                       ▼
               trivy image myapp:1.0
```

---

# 14. Why use both?

Because they answer different questions.

### Filesystem scan

> "Is there anything insecure in my project before I build it?"

### Image scan

> "Is the final container artifact I'm about to deploy vulnerable?"

For example:

```text
Source
 ↓
Trivy FS
 ↓
PASS
 ↓
Docker Build
 ↓
Base image + packages
 ↓
Trivy Image
 ↓
PASS
 ↓
ECR
```

This gives you **defense in depth**.

# 20. Interview answer

If they ask:

> **"How would you use `trivy fs` in a CI/CD pipeline?"**

You can answer:

> **I use `trivy fs` early in the CI pipeline to scan the source repository before building the container image. I can enable vulnerability, secret, and misconfiguration scanners depending on the repository contents. For example, I can scan application dependencies for known vulnerabilities, detect accidentally committed secrets, and scan IaC configurations. I normally configure severity thresholds and use `--exit-code 1` so that the pipeline fails when vulnerabilities above our defined risk threshold are detected. I can also generate JSON or SARIF reports as CI artifacts. Later in the pipeline, I use `trivy image` to scan the final container image because the filesystem scan and image scan serve different purposes.**

### The key mental model:

```text
trivy fs
   ↓
"Scan my PROJECT"

trivy config
   ↓
"Scan my CONFIGURATION / IaC"

trivy image
   ↓
"Scan my FINAL CONTAINER"

trivy k8s
   ↓
"Assess my KUBERNETES resources/cluster"
```

That's the distinction I'd focus on for a **DevOps/Kubernetes interview**.
