This article is describing **Mutual TLS (mTLS) authentication at the Kubernetes Ingress**. Let's go through it in detail.

---

# The Problem

Normally, when you access a website:

```text
Browser  ----------------------->  Ingress
```

The Ingress only asks one question:

> "Can I prove that **I am the real server**?"

The client verifies the server certificate.

Example:

```text
Client
   │
HTTPS
   ▼
Ingress

Server Certificate
```

After that, **any client** can connect.

---

# Why is this not enough?

Suppose you have an internal dashboard.

```
https://grafana.company.com
```

Anyone who knows the URL can reach the login page.

Even if they don't know the password:

* They can brute force
* Scan your application
* Attempt exploits

The application still receives their traffic.

---

# Certificate Authentication changes this

Instead of:

```
Username + Password
```

you require:

```
Client Certificate
```

Now the connection becomes

```text
                HTTPS

Client ---------------------> Ingress

Server Certificate
<----------------------------

Client Certificate
---------------------------->

Verify Client
```

Only clients with a trusted certificate are allowed.

---

# What is Mutual TLS?

Normal HTTPS

```text
Client verifies Server
```

Mutual TLS

```text
Client verifies Server

AND

Server verifies Client
```

Both authenticate each other.

---

# Complete Architecture

```text
                Certificate Authority
                      (CA)
                  /              \
                 /                \
                ▼                  ▼

        Server Certificate    Client Certificate

                │                  │
                ▼                  ▼

             Ingress         Browser/API Client
                  │
                  ▼
             Backend Service
```

# Components

## Certificate Authority (CA)

The CA is responsible for issuing certificates.

Think of it as

```text
Passport Office
```

It signs identities.

---

## Server Certificate

Used by the Ingress.

Example

```
CN = ingress.company.com
```

The browser verifies this certificate.

---

## Client Certificate

Installed on

* Browser
* Curl
* API Client
* Another Service

Example

```
CN = Alice
```

or

```
CN = Jenkins
```

# TLS Handshake

Without mTLS

```text
Client
   │
ClientHello
   ▼

Ingress

ServerHello

Certificate

Finished

Encrypted Traffic
```

---

With mTLS

```text
Client
    │
ClientHello
    ▼

Ingress

ServerHello

Server Certificate

CertificateRequest
<----------------------

Client Certificate
---------------------->

Verify Client Certificate

Finished

Encrypted Traffic
```

Notice the extra step

```
CertificateRequest
```

# Kubernetes Configuration

Ingress

```yaml
metadata:
  annotations:

    nginx.ingress.kubernetes.io/auth-tls-secret: default/ca-secret

    nginx.ingress.kubernetes.io/auth-tls-verify-client: "on"

    nginx.ingress.kubernetes.io/auth-tls-verify-depth: "1"
```

---

## auth-tls-secret

```
default/ca-secret
```

Points to a Secret containing

```
ca.crt
```

Ingress trusts certificates signed by this CA.

---

## auth-tls-verify-client

```
on
```

Means

```
Every client MUST present a certificate.
```

---

## auth-tls-verify-depth

```
1
```

Controls how deep the certificate chain can be.

Usually

```
1
```

is enough.

---

# Kubernetes Secret

```
kubectl create secret generic ca-secret \
--from-file=ca.crt
```

Contains

```
ca.crt
```

NOT

```
client.crt
```

Client certificates remain with the client.

# Curl

Without certificate

```
curl https://ingress.company.com
```

Result

```
403

or

400
```

---

With certificate

```
curl \
--cert client.crt \
--key client.key \
https://ingress.company.com
```

```
200 OK
```

Traditional authentication

# Why the article says "Stops unauthorized traffic at the edge"

The **edge** is the Ingress Controller—the first component that receives external traffic.

Instead of allowing every request to reach your application, the Ingress validates the client certificate during the TLS handshake. If the certificate isn't trusted, the connection is rejected immediately.

```text
Internet
    │
    ▼
NGINX Ingress (Edge)
    │
    ├── Valid client certificate? ── Yes ──► Backend Pods
    │
    └── No ──► Connection rejected
```

This means:

* Unauthorized clients never reach your Services or Pods.
* Your applications don't need to perform certificate validation themselves.
* It reduces unnecessary load and blocks many attacks before they enter your cluster.

---

# Basic Authentication vs mTLS

| Feature                                | Basic Authentication                   | mTLS Authentication                                                              |
| -------------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------- |
| Identity                               | Username & Password                    | Client Certificate                                                               |
| Credentials sent                       | `Authorization` header                 | During the TLS handshake                                                         |
| Requires password                      | Yes                                    | No                                                                               |
| Client identity verified               | After HTTP request starts              | Before any HTTP request is processed                                             |
| Protection against brute-force attacks | Limited                                | Strong (no password to guess)                                                    |
| Typical use                            | Internal dashboards, simple protection | Enterprise APIs, service-to-service communication, highly sensitive applications |

In short, **Basic Authentication protects an HTTP endpoint**, while **mTLS protects the connection itself** by ensuring only trusted clients can establish it in the first place.
