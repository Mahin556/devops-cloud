# Send a Signal to a Kubernetes App: a Non-Root Container Case

This is an advanced debugging challenge that combines three restrictions at once: a `FROM scratch` container with no shell, a Pod that forbids root, and a Pod you cannot modify or redeploy. Sending a signal into such a container requires understanding ephemeral containers, Pod Security Standards, and Unix UID semantics.

Below is a complete walkthrough covering every obstacle, every error, and every solution path mentioned in the challenge.

---

## 1. The Setup and Why It's Hard

The Pod `non-root` runs a single container built from a `FROM scratch` base image. That means:

- No shell (`sh`, `bash`)
- No package manager
- No standard CLI tools (`kill`, `ps`, `ls`)
- Only the application binary and its runtime dependencies exist in the image

Additional constraints from the challenge:

| Constraint | Consequence |
|---|---|
| Cluster access limited to basic app management | You cannot SSH to nodes or run privileged cluster-wide commands |
| The Pod is called `non-root` | That's your target |
| You cannot modify or redeploy the Pod | No changing the image, no deleting/recreating |
| Pod security context disallows root | Any container you add, including debug containers, must also run as non-root |
| No shell in the target container | You cannot `kubectl exec` into it |

Your goal: send a signal (e.g., `SIGHUP`, `SIGUSR1`, `SIGTERM`) to the application process running as PID 1 inside the target container.

---

## 2. Why `kubectl exec` Fails

The naive approach is:

```bash
kubectl exec -it non-root -- sh
```

This fails immediately because there is no `sh` binary in the container. You get an error like:

```
OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH: unknown
```

So you need a way to run a command **from outside** the container, but **inside** the Pod's namespaces, so you can see and signal the target process.

---

## 3. The First Attempt: `kubectl debug`

The natural next step is `kubectl debug`, which attaches an **ephemeral container** to the running Pod. It can use any image you like (e.g., `alpine`, which has a shell), and with `--target` it shares the target container's process namespace.

```bash
kubectl debug -it non-root --image=alpine --target=app
```

However, this may fail with one of three distinct errors, each requiring a different fix.

---

## 4. Error #1: `SYS_PTRACE` Forbidden by Pod Security

### The error

```
Error from server (Forbidden): pods "non-root" is forbidden:
violates PodSecurity "baseline:latest":
non-default capabilities (container "debugger-r4d4s" must not
include "SYS_PTRACE" in securityContext.capabilities.add)
```

### Why it happens

When `kubectl debug` targets another container with `--target`, it tries to add the `SYS_PTRACE` Linux capability to the ephemeral container. `SYS_PTRACE` allows a process to trace and inspect other processes (via `ptrace`), which is useful for debugging.

However, the namespace enforces the **`baseline` Pod Security Standard**, which forbids adding capabilities beyond the default set. `SYS_PTRACE` is explicitly disallowed because it can be used to escape isolation. The API server therefore rejects the ephemeral container before it is even created.

### The fix: use a compatible `--profile`

`kubectl debug` has a `--profile` flag that selects a pre-defined security context for the ephemeral container. The default profile is too permissive for the `baseline` standard, but other profiles are compatible.

```bash
kubectl debug -it non-root --image=alpine --target=app --profile=baseline
```

Profile options include:

| Profile | Description |
|---|---|
| `legacy` | The default, which adds `SYS_PTRACE` — rejected by `baseline` |
| `baseline` | Compatible with the `baseline` Pod Security Standard; no extra capabilities |
| `restricted` | Compatible with the stricter `restricted` standard |
| `netadmin` | Adds network admin capabilities |
| `sysadmin` | Adds system admin capabilities (may still be rejected by `baseline`) |

For this challenge, `--profile=baseline` is the one that gets past the `SYS_PTRACE` rejection.

---

## 5. Error #2: `runAsNonRoot` and the Root Image Hang

### The error

After fixing the profile, the next attempt may produce:

```
container has runAsNonRoot and image will run as root
```

...and then the command hangs indefinitely.

### Why it happens

The Pod's security context includes `runAsNonRoot: true`. This is enforced at the **Pod level**, so it applies to every container in the Pod, including ephemeral debug containers.

The image you asked `kubectl debug` to use — `alpine` — defaults to running as **root** (UID 0). The kubelet sees the conflict:

- The Pod says: no container may run as root.
- The image says: this container runs as root by default.
- The kubelet cannot reconcile these, so it refuses to start the container.

The "hangs indefinitely" symptom is the client waiting for a container that will never become ready.

### The fix: use an image that runs as non-root by default

You need a debugging image whose default user is **not** UID 0. The challenge suggests building your own:

```bash
docker build -t registry.iximiuz.com/my-debugging-image:v1.0.0 -<<'EOD'
FROM alpine:3
USER 1002
EOD

docker push registry.iximiuz.com/my-debugging-image:v1.0.0
```

What this does:

- Starts from a minimal `alpine` base (which includes `sh` and `kill`).
- Sets the default user to UID `1002` via the `USER` directive.
- Tags and pushes the image so the cluster can pull it.

Then:

```bash
kubectl debug -it non-root --image=registry.iximiuz.com/my-debugging-image:v1.0.0 --target=app --profile=baseline
```

Now the image declares a non-root default, so `runAsNonRoot: true` is satisfied.

### Why this doesn't fully solve the problem yet

Even with a non-root image, you may hit Error #3, because the UID of your debug container may not match the UID of the target container.

---

## 6. Error #3: `can't kill pid 1: Operation not permitted`

### The error

You are now inside the ephemeral container's shell, sharing the target's PID namespace. You can see the process:

```bash
ps aux
# PID 1 ... /app
```

But when you try to signal it:

```bash
kill -USR1 1
# kill: can't kill pid 1: Operation not permitted
```

### Why it happens

This is a **Unix UID mismatch**. On Linux, a process can only send a signal to another process if:

- The sender has the same **real or effective UID** as the target, **or**
- The sender has `CAP_KILL` (which root has, but non-root does not).

Your ephemeral container is running as UID `1002` (from the image you built). The target container is running as some other UID — say `1000`. Different UIDs, no `CAP_KILL`, no permission to signal. The kernel returns `EPERM` ("Operation not permitted").

This is the same rule that applies outside Kubernetes: `alice` cannot `kill` `bob`'s process without root.

### The fix: match the UID exactly

You must run the debug container as the **same UID** as the target container. To do that, you first need to find the target's UID.

```bash
kubectl get pod non-root -o jsonpath='{.spec.containers[0].securityContext.runAsUser}'
```

Suppose that prints `1000`. Then your debug container must also run as UID `1000`.

With `kubectl debug`, you cannot set `runAsUser` directly — it does not expose that field as a flag. So you have two options:

1. Build a custom image with `USER 1000` baked in (matching the target).
2. Use the **Ephemeral Containers API** directly, which lets you set the full `securityContext`.

The challenge recommends the second approach, which is the next section.

---

## 7. The Manual Ephemeral Container PATCH

The `kubectl debug` command hides most of the Ephemeral Containers API behind a simplified interface. To get full control, you can `PATCH` the Pod's `ephemeralcontainers` subresource directly.

### Step 1: Start `kubectl proxy`

```bash
kubectl proxy &
```

This runs a local authenticated proxy to the Kubernetes API server on `localhost:8001`. It lets you send plain `curl` requests without dealing with tokens or certificates.

### Step 2: Find the target UID

```bash
kubectl get pod non-root -o jsonpath='{.spec.containers[0].securityContext.runAsUser}'
# e.g. 1000
```

### Step 3: PATCH the Pod to add an ephemeral container

```bash
curl -Lvk localhost:8001/api/v1/namespaces/default/pods/non-root/ephemeralcontainers \
  -XPATCH \
  -H 'Content-Type: application/strategic-merge-patch+json' \
  -d '
{
    "spec":
    {
        "ephemeralContainers":
        [
            {
                "name": "debug-123",
                "command": ["sh"],
                "targetContainerName": "app",
                "image": "alpine",
                "stdin": true,
                "tty": true,
                "securityContext": {"runAsUser": 1000}
            }
        ]
    }
}'
```

Let's break down every field:

| Field | Purpose |
|---|---|
| `name: debug-123` | A unique name for the ephemeral container. You will use this with `kubectl attach`. |
| `command: ["sh"]` | The process to run. `alpine` has `sh` and `kill`. |
| `targetContainerName: app` | The container whose PID namespace you want to join. Must match the actual container name in the Pod. |
| `image: alpine` | Any image with a shell and `kill`. `alpine` is small and fast to pull. |
| `stdin: true` | Needed for interactive input. |
| `tty: true` | Allocates a TTY for the shell. |
| `securityContext.runAsUser: 1000` | **The critical field.** Must match the target container's UID exactly. |

### Step 4: Attach to the ephemeral container

The PATCH creates the container but does not attach to it. To get a shell:

```bash
kubectl attach -it non-root -c debug-123
```

### Step 5: Send the signal

Inside the shell:

```bash
ps aux
# PID 1 ... /app

kill -USR1 1
```

Because your UID now matches PID 1's UID, the kernel permits the signal. The application receives `SIGUSR1` and acts on it.

## 8. The `cdebug` Alternative

If you don't want to build images or hand-craft `curl` PATCH requests, `cdebug` is a tool that wraps the Ephemeral Containers API with a friendlier interface. Most playgrounds have it preinstalled.

Check it:

```bash
cdebug exec --help
```

For this challenge, the typical invocation would be:

```bash
cdebug exec -it non-root
```

What `cdebug` does behind the scenes:

- It reads the target Pod's security context.
- It auto-detects the `runAsNonRoot` constraint and the target's UID.
- It creates an ephemeral container with a **matching UID** in its security context.
- It targets the correct container by default.
- It attaches you to a shell.

This eliminates the manual steps of finding the UID, building an image, or crafting the PATCH. It is the most direct path if the tool is available.

## 9. Summary of All Errors and Fixes

| Error | Cause | Fix |
|---|---|---|
| `violates PodSecurity "baseline:latest": ... SYS_PTRACE` | `kubectl debug` adds `SYS_PTRACE`, forbidden by `baseline` | Add `--profile=baseline` |
| `container has runAsNonRoot and image will run as root` + hang | `alpine` defaults to root; Pod forbids root | Build a non-root image (`USER 1002`) or PATCH with `runAsUser` |
| `can't kill pid 1: Operation not permitted` | Debug container's UID ≠ target container's UID | Set `runAsUser` in the ephemeral container's `securityContext` to match the target's UID |
| `exec: "sh": executable file not found` | Target container has no shell | Use an ephemeral container with a shell instead of `kubectl exec` |

---

## 10. Why the UID Match Is the Whole Point

The final error — `Operation not permitted` — is the deepest lesson in this challenge.

In Unix, **signals are a permission-gated operation**. The kernel checks, for every `kill()` call, whether the sender has the right to signal the target. The rule is:

> A process may send a signal to another process if the sender's real or effective UID matches the target's real or saved-set UID, or if the sender has `CAP_KILL`.

- Root has `CAP_KILL` and can signal anything.
- A non-root process can only signal processes with the **same UID**.

The Pod forbids root, so the debug container cannot be root. That leaves only one option: the debug container must run as the **same UID** as the target. Anything else — UID 1002, UID 0, UID 65534 — is rejected by the kernel.

This is why:

- A random non-root image (`USER 1002`) is not enough.
- You must read the target's UID from the Pod spec.
- You must set that exact UID in the ephemeral container's `securityContext`.

That single field, `runAsUser`, is what turns a debug shell into a process that can actually signal PID 1.

---

## 11. Final Checklist

1. Identify the target container's UID:
   ```bash
   kubectl get pod non-root -o jsonpath='{.spec.containers[0].securityContext.runAsUser}'
   ```
2. Choose a path:
   - `kubectl debug --profile=baseline` with a matching non-root image, or
   - Manual `PATCH` with `securityContext.runAsUser` set to the target UID, or
   - `cdebug exec -it non-root`.
3. Attach to the ephemeral container.
4. Verify PID 1 is the target:
   ```bash
   ps aux
   ```
5. Send the signal:
   ```bash
   kill -USR1 1
   ```
6. Confirm the application reacted (check its logs):
   ```bash
   kubectl logs non-root -c app --tail=20
   ```

---

## 12. One-Line Summary

To signal a non-root, shell-less container: attach an ephemeral container with a shell, run it as the **same UID** as the target (found via `runAsUser` in the Pod spec), use `--profile=baseline` if Pod Security is strict, and then `kill` PID 1 from inside the ephemeral shell — or let `cdebug` handle the UID matching for you.
