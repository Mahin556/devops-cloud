The **Ingress Default Backend** is the backend service that receives requests when **no Ingress rule matches** the incoming request.

Think of it as the **fallback service**.

---

# How it works

Suppose you have this Ingress:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /login
        pathType: Prefix
        backend:
          service:
            name: login-service
            port:
              number: 80

      - path: /payment
        pathType: Prefix
        backend:
          service:
            name: payment-service
            port:
              number: 80
```

Requests:

| Request                       | Result              |
| ----------------------------- | ------------------- |
| `app.example.com/login`       | login-service       |
| `app.example.com/payment`     | payment-service     |
| `app.example.com/payment/api` | payment-service     |
| `app.example.com/abc`         | **Default Backend** |

# Default Backend in Ingress-NGINX

Ingress-NGINX includes a built-in default backend.

If nothing matches, you'll usually get:

```text
404 Not Found
```

This is why you saw:

```html
<html>
<head><title>404 Not Found</title></head>
<body>
<center><h1>404 Not Found</h1></center>
```

That response came from the **default backend** because no Ingress rule matched.

---

# Kubernetes Default Backend

You can also define a **default backend** in your own Ingress resource.

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo
spec:
  ingressClassName: nginx

  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
```

Now every unmatched request goes to:

```
default-service
```

instead of returning a 404.

# Example

Deploy a simple default application.

### Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: default-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: default-app
  template:
    metadata:
      labels:
        app: default-app
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        command:
        - sh
        - -c
        - |
          echo "This is the default backend" > /usr/share/nginx/html/index.html
          nginx -g 'daemon off;'
```

apiVersion: v1

# Difference between `/` and `defaultBackend`

Many people confuse these.

## Prefix `/`

```yaml
rules:
- host: app.example.com
  http:
    paths:
    - path: /
      pathType: Prefix
      backend:
        service:
          name: frontend
```

Only handles requests for:

```
Host: app.example.com
```

Examples:

```
app.example.com/
app.example.com/about
app.example.com/contact
```

It **does not** match a different host such as:

```
shop.example.com/
```

---

## `defaultBackend`

```yaml
defaultBackend:
  service:
    name: default-service
```

Handles **any request that doesn't match any host/path rule**.

Examples:

```
unknown.example.com/
foo.bar/
app.example.com/random
```

(if there isn't another matching rule)

---

# Comparison

| Feature                  | `path: /`          | `defaultBackend`                            |
| ------------------------ | ------------------ | ------------------------------------------- |
| Requires host match      | ✅ Yes              | ❌ No                                        |
| Requires path match      | ✅ Yes (`/` prefix) | ❌ No                                        |
| Used when no rules match | ❌ No               | ✅ Yes                                       |
| Typical use              | Frontend/home page | Fallback page, custom 404, maintenance page |

---

# Real-world uses

A custom default backend can provide:

* A branded **404 page** instead of the default NGINX 404.
* A maintenance page during upgrades.
* A landing page for unknown hosts.
* A simple diagnostic service that logs unexpected requests.

For example, instead of returning:

```text
404 Not Found
```

your default backend could display:

```text
Welcome!

The requested application or URL was not found.
Please check the hostname or path and try again.
```

This gives users a clearer experience and can make troubleshooting easier.
