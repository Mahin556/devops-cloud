While Kubernetes doesn't have a built-in `strategy: BlueGreen` or `strategy: Canary` field, you can implement both patterns using native Kubernetes resources. The approach differs significantly in complexity and capability.

---

### 🔵 Blue/Green Deployment (Native & Simple)

This is the easiest advanced strategy to implement with native Kubernetes. The core idea is to have two Deployments (Blue/Green) and a single Service that acts as a traffic switch by changing its label selector.

**The Setup:**

1.  **Blue (Current) Deployment**: Your stable, running version (e.g., `version: v1`).
2.  **Green (New) Deployment**: The new version you want to release (e.g., `version: v2`).
3.  **Service**: A single Service whose `selector` points to the active version.

**The Process:**

1.  **Deploy Green**: Create the new Deployment (v2) alongside the old one. It gets its own Pods but receives no traffic.
2.  **Validate Green**: Test the new version internally (via port-forward or a separate internal Service).
3.  **Switch Traffic**: Update the main Service's selector from `version: v1` to `version: v2`.
    ```bash
    # The switch happens in a single instant
    kubectl patch service my-service -p '{"spec":{"selector":{"app":"myapp","version":"v2"}}}'
    ```
4.  **Rollback (if needed)**: Flip the selector back to `version: v1`

**The Manifests:**

```yaml
# Blue Deployment (v1)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 5
  selector:
    matchLabels:
      app: myapp
      version: v1
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      containers:
      - name: app
        image: myapp:1.0

---
# Green Deployment (v2)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
spec:
  replicas: 5
  selector:
    matchLabels:
      app: myapp
      version: v2
  template:
    metadata:
      labels:
        app: myapp
        version: v2
    spec:
      containers:
      - name: app
        image: myapp:2.0

---
# The Traffic Switch (Service)
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
    version: v1      # <- Change this to 'v2' to cut over
  ports:
  - port: 80
    targetPort: 8080
```

| Pros | Cons |
| :--- | :--- |
| **Trivial to implement** using only Deployments and Services. | Requires **double the resources** (running both v1 and v2 simultaneously). |
| **Instant rollback** (just flip the selector back). | Database schema changes must be backward-compatible. |
| **Zero downtime** during the switch. | The switch is all-or-nothing (no gradual testing). |

### 🟡 Canary Deployment (Native but Limited)

Native canary is more challenging. A standard Kubernetes Service cannot split traffic by percentage (it only does round-robin load balancing). Therefore, you have two native options:

#### Option A: The "Poor Man's Canary" (Replica-Based)

This method relies on the fact that a Service does round-robin load balancing. By controlling the number of replicas, you can approximate a traffic split.

1.  **Deploy Canary**: Create a new Deployment (v2) with a **small number of replicas** (e.g., 1 replica).
2.  **Update Service Selector**: Update the Service's selector to include **both** v1 and v2 (e.g., `version in (v1, v2)`).
3.  **Traffic Split**: The Service now load-balances across all Pods. If you have 9 v1 Pods and 1 v2 Pod, roughly **10% of traffic** goes to the canary.
4.  **Monitor**: Observe the canary's performance.
5.  **Scale Up Canary**: Gradually increase the number of v2 replicas (e.g., 2 → 5 → 10) while scaling down v1.
6.  **Complete**: When v2 has all replicas, remove v1.

**The Manifests:**

```yaml
# v1 Deployment (Stable) - 9 replicas
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-v1
spec:
  replicas: 9
  selector:
    matchLabels:
      app: myapp
      version: v1
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      containers:
      - name: app
        image: myapp:1.0

---
# v2 Deployment (Canary) - 1 replica (~10% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-v2
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
      version: v2
  template:
    metadata:
      labels:
        app: myapp
        version: v2
    spec:
      containers:
      - name: app
        image: myapp:2.0

---
# Service selects BOTH versions
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp          # Selects both v1 and v2 pods
  ports:
  - port: 80
    targetPort: 8080
```

| Pros | Cons |
| :--- | :--- |
| **Truly native** (no extra tools required). | **Imprecise** traffic splitting (depends on replica counts). |
| Low barrier to entry. | **Manual and error-prone** (you must manually adjust replica counts). |
| | Can cause **uneven traffic distribution** if Pods have different resource requests or are scheduled unevenly. |

#### Option B: Ingress Controller Canary Annotations (Ingress-Based)

If you have an **Ingress Controller** (like Nginx Ingress), you can use its native canary annotations for more precise traffic control. This is still "native" in the sense that it uses standard Kubernetes Ingress resources without a service mesh.

1.  **Deploy Canary**: Deploy the new version (v2) with its own Service.
2.  **Create Canary Ingress**: Create a second Ingress resource with canary annotations that point to the v2 Service.
3.  **Set Weight**: Use the `nginx.ingress.kubernetes.io/canary-weight` annotation to define the traffic percentage (e.g., `"10"` for 10%).
4.  **Monitor & Adjust**: Change the weight annotation to gradually increase traffic to v2.

**Example Nginx Ingress Annotations:**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"   # 10% traffic to v2
spec:
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: myapp-v2-service   # Points to the canary Deployment
            port:
              number: 80
```

| Pros | Cons |
| :--- | :--- |
| **Precise traffic splitting** (e.g., 5%, 10%, 25%). | Requires an Ingress Controller (e.g., Nginx, Traefik). |
| Can be combined with **header-based routing** for A/B testing. | More complex than the "poor man's" approach. |

#### Option C: Gateway API (The New Native Standard)

The **Gateway API** is the new standard for Kubernetes networking. It provides **native support for traffic splitting** through weighted backends, without requiring vendor-specific annotations.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp-route
spec:
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: myapp-v1-service
      port: 80
      weight: 90
    - name: myapp-v2-service
      port: 80
      weight: 10
```

| Pros | Cons |
| :--- | :--- |
| **Standardized** (not vendor-specific). | Requires a Gateway API implementation (e.g., Contour, Istio, GKE). |
| **Native** to the Kubernetes API (CRD). | Still relatively new. |

### 🚀 The Advanced Solution: Argo Rollouts

For **production-grade** canary and blue-green deployments, the community standard is **Argo Rollouts**. It replaces the standard `Deployment` with a `Rollout` custom resource and provides:

*   **Automated, progressive traffic shifting** (e.g., 10% for 5 minutes, then 50%, then 100%).
*   **Metric-based analysis** (e.g., pause rollout if error rate spikes).
*   **Automatic rollback** on failure.
*   **Integration with Ingress controllers and service meshes**

| Pros | Cons |
| :--- | :--- |
| Fully automated, production-ready progressive delivery. | Requires installing the Argo Rollouts controller (CRD). |
| Works with multiple traffic routers (Ingress, Istio, etc.). | Adds complexity to your cluster. |
| Provides a native GitOps experience. | |

### 📊 Comparison Table

| Strategy | Native Method | Complexity | Traffic Control | Automation |
| :--- | :--- | :--- | :--- | :--- |
| **Blue/Green** | Update Service selector. | **Low** | All-or-nothing. | Manual (patch command). |
| **Canary (Poor Man's)** | Adjust replica counts. | **Low** | Imprecise (based on replica count). | Manual (scale commands). |
| **Canary (Ingress)** | Nginx canary annotations. | **Medium** | Precise (weight-based). | Manual (annotation update). |
| **Canary (Gateway API)** | Weighted backend references. | **Medium** | Precise (weight-based). | Manual (CRD update). |
| **Blue/Green & Canary** | Argo Rollouts. | **High** | Full control (weights, analysis, rollback). | **Fully Automated**. |

---

### 💎 Summary

*   **Blue/Green** is natively simple: run two Deployments and switch traffic by updating a Service's selector.
*   **Native Canary** is limited. You can use replica counts for a rough split, Ingress annotations for precise weight-based routing, or the newer Gateway API for a standardized approach.
*   For **production**, consider **Argo Rollouts** to automate the entire canary/blue-green process with analysis and automatic rollback.
