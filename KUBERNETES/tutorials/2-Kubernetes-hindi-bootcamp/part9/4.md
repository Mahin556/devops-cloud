The way Kubernetes handles ServiceAccount tokens changed significantly with version 1.24, driven by a major security improvement. Here’s a breakdown of the old and new methods, how they work, and what they mean for you.

### 📜 Before Kubernetes 1.24: The Legacy Secret-Based Tokens

Prior to v1.24, when you created a `ServiceAccount`, Kubernetes automatically generated a **long-lived, non-expiring token** and stored it in a `Secret` object of type `kubernetes.io/service-account-token`.

*   **How it worked**: This token was a static, permanent credential placed inside the `Secret`. Any Pod using that ServiceAccount would have this Secret (and its token) mounted into the Pod at `/var/run/secrets/kubernetes.io/serviceaccount/`. The token itself was a **JWT (JSON Web Token)** that the API server would validate.
*   **The Security Risk**: The problem with these tokens was their **indefinite lifetime**. If a token was ever exposed—for instance, through a log or a misconfigured application—it would remain a valid credential forever. This is a significant security concern.

### 🔐 The Big Change in Kubernetes 1.24

Starting with **Kubernetes 1.24**, the automatic creation of these long-lived Secret-based tokens was **removed**. This was done to improve the default security posture of the cluster.

While the auto-generation was turned off, it's important to know that you can still **manually create** a legacy, long-lived token Secret if you have a specific need for it. However, this is considered a legacy pattern and is **not recommended** unless absolutely necessary.

### 🚀 The Modern Way: The TokenRequest API and Projected Tokens

The recommended approach for Kubernetes 1.24+ is to use the `TokenRequest` API to generate **short-lived, bound tokens**. These tokens are designed to be much more secure.

#### 1. The TokenRequest API: The Core Mechanism
The `TokenRequest` API is a Kubernetes API endpoint that allows you to request a token for a specific ServiceAccount. The resulting token is:
*   **Short-lived**: It has a configurable expiration time, with a default of **1 hour**.
*   **Bound to an Object**: The token's validity can be tied to the lifecycle of a specific object, like a `Pod` or `Secret`. If that object is deleted, the token becomes invalid.
*   **Not Stored**: Unlike the old Secrets, the token generated by the `TokenRequest` API is **not stored anywhere** within the cluster. It's returned directly to the requester.

#### 2. Projected Tokens: The Standard for Pods
The most common way to use the `TokenRequest` API is through **projected volumes**. When you configure a Pod this way, the kubelet on the node automatically requests a token for the Pod's ServiceAccount via the `TokenRequest` API and mounts it into the container as a file.

*   **Auto-rotation**: The kubelet will **automatically rotate** the token before it expires (when it's older than 80% of its TTL, or after 24 hours). This ensures your applications always have a valid token without any manual intervention.
*   **How it's mounted**: The token is still mounted at `/var/run/secrets/kubernetes.io/serviceaccount/token`, but it's a dynamically refreshed, short-lived JWT. The `ca.crt` and `namespace` files are still provided as before.

### 💻 Practical Examples

Here are the key commands and configurations for modern token management.

#### Generating a Token with `kubectl`
You can use the `kubectl create token` command to manually generate a short-lived token from the command line.
```bash
# Generate a token with the default 1-hour lifetime for the 'myapp' ServiceAccount
kubectl create token myapp

# Generate a token with a custom 10-minute expiration
kubectl create token myapp --duration 10m
```


#### Using a Projected Token in a Pod (Recommended)
This is the most secure way to give a Pod a token for authenticating to the API server.
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  serviceAccountName: my-service-account
  automountServiceAccountToken: false  # Disable the legacy auto-mount
  containers:
  - name: my-container
    image: my-app:latest
    volumeMounts:
    - name: sa-token
      mountPath: /var/run/secrets/kubernetes.io/serviceaccount
      readOnly: true
  volumes:
  - name: sa-token
    projected:
      sources:
      - serviceAccountToken:
          path: token
          expirationSeconds: 7200        # 2-hour lifetime
          audience: "api"                # Optional: custom audience
      - configMap:
          name: kube-root-ca.crt
          items:
          - key: ca.crt
            path: ca.crt
      - downwardAPI:
          items:
          - path: namespace
            fieldRef:
              fieldPath: metadata.namespace
```


#### Creating a Legacy, Long-Lived Token (For External Systems)
If you *must* create a non-expiring token for an external CI/CD system, you can manually create the Secret.
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapp-token
  annotations:
    kubernetes.io/service-account.name: myapp
type: kubernetes.io/service-account-token
```
**However**, this is a legacy pattern and should be avoided in favor of short-lived tokens whenever possible.

### 🔍 Inspecting the Token: JWTs and jwt.io

All ServiceAccount tokens (both old and new) are **JWTs (JSON Web Tokens)**. A JWT is composed of three parts (header, payload, signature) separated by dots.

*   **Inspecting with `jwt.io`**: You can paste a ServiceAccount token into the debugger at **jwt.io** to decode and inspect its contents. This will show you the **payload** (claims) of the token, which includes:
    *   `iss` (Issuer)
    *   `sub` (Subject, usually the ServiceAccount name)
    *   `aud` (Audience)
    *   `exp` (Expiration time)
    *   `kubernetes.io/serviceaccount/namespace` (The ServiceAccount's namespace)
*   **The Signature**: The JWT's signature is generated using the cluster's private signing key. The API server verifies this signature to ensure the token has not been tampered with.

### 📊 Quick Reference: Legacy vs. Modern Tokens

| Feature | Pre-1.24 (Legacy Secrets) | 1.24+ (TokenRequest & Projected Tokens) |
| :--- | :--- | :--- |
| **Creation** | **Automatic** by Kubernetes on ServiceAccount creation. | **Manual** via `kubectl` or **Projected Volume** config. |
| **Lifetime** | **Permanent** (Non-expiring). | **Short-lived** (default 1 hour). |
| **Storage** | Stored in an etcd `Secret` object. | **Not stored in etcd**. Generated on demand. |
| **Rotation** | **Manual** (requires creating a new Secret). | **Automatic** (kubelet rotates before expiry). |
| **Security** | **High risk** if exposed. | **Low risk** as tokens are short-lived and bound to objects. |
| **Status** | Legacy, **discouraged** for new use. | **Recommended**, future-proof approach. |

In short, for any new cluster or workload, you should **always use the TokenRequest API (via `kubectl create token` or projected volumes)**. The legacy Secret-based tokens are a thing of the past, kept only for backward compatibility.
