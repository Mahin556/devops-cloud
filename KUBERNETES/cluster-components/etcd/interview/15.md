Technically, you **cannot** use a single etcd node with 3 separate master nodes and still consider it a highly available setup. A single etcd instance creates a critical single point of failure for the entire cluster. 

However, the real question you are asking is likely about the architecture of a standard 3-master-node cluster, where it might appear that etcd is "separate." Here are the two standard topologies for this:

### 1. Stacked etcd Topology (Most Common)

In this setup, **you do not use a single etcd node.** Instead, each of the 3 master nodes runs its own etcd instance, forming a 3-node etcd cluster on the same machines.

*   **How it works**: `kubeadm` configures a local etcd member on each master node. These 3 etcd instances communicate with each other to form a single, distributed database cluster. Each `kube-apiserver` only communicates with the local etcd member on the same node.
*   **Fault Tolerance**: This setup is highly available. It uses the Raft algorithm and can tolerate the failure of one master node (and its etcd instance) while keeping the cluster operational.

### 2. External etcd Topology (More Resilient)

In this setup, etcd runs on its own dedicated nodes, completely separate from the control plane nodes. **A single-node etcd is still not a production option.**

*   **How it works**: You have a dedicated cluster of (at least) 3 nodes just for etcd. The 3 master nodes run the API server and other components, but they all connect to this external etcd cluster.
*   **Fault Tolerance**: This is considered more resilient because the failure of a master node doesn't affect the etcd cluster, and vice-versa. It allows you to scale and maintain the database independently from the control plane.

The following table summarizes the differences between these two topologies.

| Topology | Configuration | Key Benefit | Main Risk |
| :--- | :--- | :--- | :--- |
| **Stacked etcd** | etcd runs on same 3 nodes as the control plane | Less infrastructure required, simpler to manage | A node failure loses both a master and an etcd member |
| **External etcd** | etcd runs on 3+ dedicated, separate nodes | Fault isolation between database and control plane | Requires twice the number of machines (min. 6) |

**In short**: A cluster with 3 master nodes and 1 separate etcd node is not a standard architecture. The standard, highly available setup requires an odd number of etcd instances (minimum 3), whether they are co-located on the master nodes or on dedicated servers. A single etcd instance is only suitable for development or testing where downtime is acceptable.
