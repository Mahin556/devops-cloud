The key trick is **not to change the kubelet configuration**. Instead, configure the Linux cgroup belonging to each `herder` Pod so that an OOM kill applies only to the individual process, reproducing the pre-Kubernetes-1.28 behavior.

The challenge's hint — **“Use the force a privileged DaemonSet, Luke”** — points directly at the solution.

### What we're going to build

```text
                    Kubernetes Cluster
                           │
              ┌────────────┴────────────┐
              │                         │
          Node 1                    Node 2
              │                         │
       ┌──────┴──────┐          ┌──────┴──────┐
       │             │          │             │
   herder Pod    helper DS   herder Pod    helper DS
       │             │          │             │
       │             └──────┐   │             │
       │                    │   │             │
       ▼                    ▼   ▼             ▼
   Pod cgroup  <──── privileged DaemonSet ────>
       │
       └── memory.oom.group = 0
```

The important part is:

```text
memory.oom.group = 0
```

This tells the Linux memory cgroup subsystem **not to kill the entire cgroup when one process hits the memory limit**.

---

# 1. Understand the problem first

Suppose your container has:

```text
PID 1
 ├── process A
 ├── process B
 └── process C
```

and the container has:

```text
memory.max = 256Mi
```

Eventually:

```text
A → consumes memory
B → consumes memory
C → consumes memory
```

and the cgroup reaches:

```text
memory.max
```

The Linux OOM killer has to kill something.

With the newer Kubernetes behavior, Kubernetes configures the container cgroup so that:

```text
memory.oom.group = 1
```

Conceptually:

```text
OOM
 │
 ├── A
 ├── B
 ├── C
 └── PID 1
      ↓
entire cgroup gets killed
      ↓
container exits
      ↓
kubelet restarts container
      ↓
Pod restart count increases
```

That's exactly what this challenge wants you to avoid.

---

# 2. The important Linux file

The relevant cgroup v2 file is:

```bash
memory.oom.group
```

Check it with:

```bash
cat memory.oom.group
```

Possible values:

```text
0
```

or:

```text
1
```

### `1`

Kill the entire cgroup when an OOM occurs.

### `0`

Don't automatically kill every process in the cgroup.

The challenge wants:

```text
memory.oom.group = 0
```

for the `herder` Pod.

---

# 3. Why a normal Kubernetes Pod can't solve this

You might initially think:

```yaml
resources:
  limits:
    memory: 256Mi
```

But that only establishes the memory limit.

For example:

```yaml
resources:
  limits:
    cpu: 250m
    memory: 256Mi
```

does **not** let you directly say:

```yaml
memory.oom.group: 0
```

because `memory.oom.group` isn't a normal Kubernetes Pod resource field.

And the challenge specifically says:

> without changing the kubelet config

So we can't simply configure:

```text
singleProcessOOMKill
```

at the kubelet.

We need to manipulate the underlying Linux cgroup.

---

# 4. Why a DaemonSet?

We need this configuration on **every node**.

A DaemonSet gives us:

```text
Node 1 → helper Pod
Node 2 → helper Pod
Node 3 → helper Pod
...
```

Therefore:

```text
DaemonSet
    │
    ├── Node 1
    │     └── privileged helper
    │
    ├── Node 2
    │     └── privileged helper
    │
    └── Node N
          └── privileged helper
```

The helper can access the host's cgroup filesystem.

That's why the challenge says:

> Use the force a privileged DaemonSet, Luke.

# 8. Ensure one Pod per node

The challenge says:

> Every Pod must run on its own node.

The clean Kubernetes way is pod anti-affinity.

Add:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: herder
        topologyKey: kubernetes.io/hostname
```

Your Deployment becomes:

```yaml
apiVersion: apps/v1

metadata:
  name: herder
  namespace: default

spec:
  replicas: 3

  selector:
    matchLabels:
      app: herder

  template:
    metadata:
      labels:
        app: herder

    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: herder
```

# 10. Now the interesting part — the privileged DaemonSet

We need a process on every node that can access:

```text
/sys/fs/cgroup
```

from the host.

Create:

```bash
cat > oom-fix-daemonset.yaml <<'EOF'
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: oom-fix
  namespace: default

spec:
  selector:
    matchLabels:
      app: oom-fix

  template:
    metadata:
      labels:
        app: oom-fix

    spec:
      hostPID: true

      containers:
        - name: oom-fix
          image: alpine:3.20

          securityContext:
            privileged: true

          command:
            - /bin/sh
            - -c
            - |
              echo "OOM helper started on $(hostname)"

              while true; do
                sleep 10
              done

          volumeMounts:
            - name: cgroup
              mountPath: /host/sys/fs/cgroup

      volumes:
        - name: cgroup
          hostPath:
            path: /sys/fs/cgroup
            type: Directory
EOF
```

Then:

```bash
kubectl apply -f oom-fix-daemonset.yaml
```

Check:

```bash
kubectl get pods -l app=oom-fix -o wide
```

You should see approximately:

```text
NAME              READY   STATUS    NODE
oom-fix-xxxxx     1/1     Running   node1
oom-fix-yyyyy     1/1     Running   node2
oom-fix-zzzzz     1/1     Running   node3
```

---

# 11. Why `privileged: true`?

Because we're crossing the container/host boundary.

Normally:

```text
Container
   │
   └── /sys/fs/cgroup
```

doesn't necessarily give us permission to modify arbitrary host cgroups.

With:

```yaml
securityContext:
  privileged: true
```

the helper gets elevated Linux capabilities.

And:

```yaml
hostPath:
  path: /sys/fs/cgroup
```

exposes the host cgroup filesystem.

So we get:

```text
oom-fix container
       │
       │ hostPath
       ▼
host /sys/fs/cgroup
       │
       ├── system.slice
       ├── kubepods.slice
       ├── kubepods-burstable.slice
       └── ...
```

# 12. But mounting `/sys/fs/cgroup` isn't enough

This is where the challenge becomes interesting.

We don't merely need to write:


to some arbitrary cgroup.

We need to identify the **cgroup belonging to the herder container**.

That's the critical part.

# 15. Linux gives us another powerful mechanism

Every process has a cgroup association.

Run:

```bash
cat /proc/<PID>/cgroup
```

For cgroup v2 you'll see something resembling:

```text
0::/kubepods.slice/kubepods-burstable.slice/...
```

For example:

```text
0::/kubepods.slice/
  kubepods-burstable.slice/
  kubepods-burstable-pod<UID>.slice/
  cri-containerd-<CONTAINER_ID>.scope
```

The exact path varies by:

* Kubernetes version
* kubelet configuration
* container runtime
* systemd
* QoS class
* distribution

**Do not hard-code the path.**

That's one of the most important lessons from this challenge.

---

# 16. The elegant solution: discover the cgroup from the process

Instead of guessing:

```text
kubepods.slice/...
```

we can ask Linux:

```bash
cat /proc/<PID>/cgroup
```

Then map that path into:

```text
/sys/fs/cgroup/<path>
```

So:

```text
PID
 │
 ▼
/proc/PID/cgroup
 │
 ▼
cgroup path
 │
 ▼
/sys/fs/cgroup/<cgroup-path>
 │
 ▼
memory.oom.group
```

Then:

```bash
echo 0 > memory.oom.group
```

# 17. An even better approach for automation

The DaemonSet can continuously inspect Kubernetes/container processes and modify the cgroup automatically.

The basic logic is:

```text
Every node
   │
   ▼
Find herder containers
   │
   ▼
Find their PIDs
   │
   ▼
Read /proc/PID/cgroup
   │
   ▼
Locate cgroup directory
   │
   ▼
Write:
memory.oom.group = 0
```

This is what makes the solution work conditionally for the workload.

# 18. A practical helper container

For the challenge, you can use a privileged container with host access and a shell script.

A more useful DaemonSet looks like:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: oom-fix
  namespace: default

spec:
  selector:
    matchLabels:
      app: oom-fix

  template:
    metadata:
      labels:
        app: oom-fix

    spec:
      hostPID: true

      containers:
        - name: oom-fix
          image: alpine:3.20

          securityContext:
            privileged: true

          command:
            - /bin/sh
            - -c
            - |
              set -eu

              echo "OOM fixer running on $(hostname)"

              while true; do

                for pid in $(pgrep -f herder || true); do

                  echo "Found herder PID: $pid"

                  cgroup_path=$(awk -F: '$1 == "0" {print $3}' \
                    /proc/"$pid"/cgroup)

                  if [ -n "$cgroup_path" ]; then

                    cgroup_dir="/host/sys/fs/cgroup${cgroup_path}"

                    if [ -f "$cgroup_dir/memory.oom.group" ]; then
                      echo 0 > "$cgroup_dir/memory.oom.group"
                      echo "Configured $cgroup_dir"
                    fi

                  fi

                done

                sleep 2

              done

          volumeMounts:
            - name: cgroup
              mountPath: /host/sys/fs/cgroup

            - name: proc
              mountPath: /host/proc

      volumes:
        - name: cgroup
          hostPath:
            path: /sys/fs/cgroup
            type: Directory

        - name: proc
          hostPath:
            path: /proc
            type: Directory
```

However, **there's a subtle problem with this exact example**.

`pgrep -f herder` depends on the process command line being visible in the helper's PID namespace and assumes the process name contains `herder`.

That's why:

```yaml
hostPID: true
```

is important.

For a robust solution, I'd identify containers using the runtime rather than relying purely on `pgrep`.

---

# 19. Why `hostPID: true` matters

Without:

```yaml
hostPID: true
```

the helper sees:

```text
PID 1
PID 2
PID 3
...
```

inside its own PID namespace.

It doesn't necessarily see:

```text
host PID 12345
host PID 12346
host PID 12347
```

With:

```yaml
hostPID: true
```

the helper can see the host process namespace.

So:

```text
Host
│
├── containerd
├── kubelet
├── herder PID 12345
├── herder PID 12346
└── oom-fix
       │
       └── sees host processes
```

# 25. Why this survives the OOM

Imagine the herder internally contains:

```text
PID 1
 │
 ├── worker 100
 ├── worker 101
 ├── worker 102
 └── worker 103
```

The cgroup reaches:

```text
memory.max = 256Mi
```

An OOM event occurs.

With:

```text
memory.oom.group = 1
```

you effectively get:

```text
OOM
 ↓
kill cgroup
 ↓
PID 1 dies
 ↓
container exits
 ↓
kubelet restarts
 ↓
RESTARTS = 1
```

But with:

```text
memory.oom.group = 0
```

you get:

```text
OOM
 ↓
select process
 ↓
process dies
 ↓
PID 1 survives
 ↓
container remains running
 ↓
Pod remains Running
```

Therefore:

```bash
kubectl get pods
```

continues showing:

```text
STATUS    RESTARTS
Running   0
```

even though processes inside the container have been killed by the OOM killer.

That's the "invisible OOM" behavior the challenge is asking you to reproduce.

# 32. Why a Deployment isn't enough

A common first attempt would be:

```yaml
apiVersion: apps/v1
kind: Deployment
...
resources:
  limits:
    memory: 256Mi
```

That satisfies:

```text
memory limit
```

but doesn't satisfy:

```text
OOM behavior
```

The important distinction is:

```text
resources.limits.memory
```

controls **how much memory the container can consume**.

While:

```text
memory.oom.group
```

controls **how the cgroup behaves when that limit is exceeded**.

They're two different mechanisms.

# 33. Why not simply make the container privileged?

You might think:

```yaml
securityContext:
  privileged: true
```

inside the `herder` Pod.

That isn't the intended solution.

It would give the workload itself excessive privileges and doesn't solve the requirement cleanly.

Instead:

```text
herder
  ↓
normal workload

oom-fix DaemonSet
  ↓
privileged infrastructure component
```

This separates:

```text
application
```

from:

```text
node-level cgroup manipulation
```

That's a much better architecture for this particular challenge.

# 36. A very important distinction

Don't confuse these three:

```text
memory.max
memory.high
memory.oom.group
```

### `memory.max`

Hard memory limit:

```text
256Mi
```

If exceeded, memory reclaim/OOM handling happens.

### `memory.high`

Throttle/reclaim threshold.

It doesn't represent the same hard limit semantics as `memory.max`.

### `memory.oom.group`

Controls whether the OOM killer treats the cgroup as a single killable unit.

So the challenge is essentially asking you to configure:

```text
memory.max       = 256Mi
memory.oom.group = 0
```

## The core idea to remember

If you remember only one thing from this challenge, remember this:

```text
Kubernetes memory limit
        ↓
Linux cgroup v2
        ↓
memory.max = 256Mi
        ↓
OOM
        ↓
memory.oom.group
        │
        ├── 1 → kill the whole cgroup
        │        → PID 1 dies
        │        → container restarts
        │
        └── 0 → kill individual process
                 → PID 1 may survive
                 → container stays running
                 → Pod doesn't restart
```

And the **privileged DaemonSet** is the mechanism that lets you apply:

```bash
echo 0 > memory.oom.group
```

to the correct workload cgroup **on every node**, without modifying the kubelet configuration.
