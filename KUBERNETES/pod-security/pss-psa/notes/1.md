# Kubernetes Pod Security: PSS and PSA

The most important sentence to remember is:

> **PSS defines the security standards; PSA enforces those standards.**

```text
Pod Security Standards (PSS)
        │
        │ defines
        ▼
┌─────────────────────────────┐
│ Privileged                  │
│ Baseline                    │
│ Restricted                  │
└─────────────────────────────┘
        │
        │ enforced by
        ▼
Pod Security Admission (PSA)
        │
        ▼
Kubernetes API Server
        │
        ▼
       Pods
```

They replaced the older **PodSecurityPolicy (PSP)** mechanism.

---

# 1. Why do we need Pod Security?

A Kubernetes Pod can request potentially dangerous privileges.

For example, a Pod could try:

```yaml
securityContext:
  privileged: true
```

A privileged container has significantly greater access to the host.

A Pod could also potentially request things such as:

```text
Host networking
Host PID namespace
Host IPC namespace
Host filesystem mounts
Linux capabilities
Running as root
Privilege escalation
```

Without appropriate controls, a compromised application could potentially gain access beyond what it actually needs.

So Kubernetes provides **Pod Security Standards** and **Pod Security Admission**.

---

# 2. PSS — Pod Security Standards

PSS defines **what a secure Pod should look like**.

There are three profiles:

```text
PSS
│
├── Privileged
├── Baseline
└── Restricted
```

Think of them as increasing levels of security:

```text
Least restrictive
       │
       ▼
  Privileged
       │
       ▼
   Baseline
       │
       ▼
  Restricted
       │
       ▼
Most restrictive
```

---

# 3. Privileged

**Privileged** is essentially unrestricted.

It allows configurations that are restricted by the other profiles.

Use cases can include:

* System-level workloads
* Infrastructure components
* Certain monitoring/security agents
* Workloads that genuinely require host-level access

Example:

```yaml
securityContext:
  privileged: true
```

A privileged workload may be acceptable for a trusted infrastructure component, but generally isn't appropriate for a normal application.

### Think:

> **"Allow almost everything."**

---

# 4. Baseline

**Baseline** prevents common privilege-escalation configurations while still allowing ordinary applications to operate.

It is a good starting point for many application namespaces.

It restricts things such as:

* Privileged containers
* Host namespaces
* Host networking
* Host ports
* Certain dangerous capabilities
* Other known privilege-escalation mechanisms

Think:

> **"Block common dangerous configurations."**

Example:

```text
Frontend
Backend
API
Worker
```

These typically don't need privileged access.

So:

```text
Baseline
   ↓
Normal application workloads
```

---

# 5. Restricted

**Restricted** is the most hardened PSS profile.

It follows strong security practices such as:

* Running as non-root
* Preventing privilege escalation
* Restricting Linux capabilities
* Using appropriate seccomp settings
* Restricting sensitive security configurations

For example, a workload might use:

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
  seccompProfile:
    type: RuntimeDefault
```

Think:

> **"Apply strong security restrictions to the workload."**

---

# 6. PSS comparison

| Profile        | Restrictiveness | Typical use                     |
| -------------- | --------------- | ------------------------------- |
| **Privileged** | Very low        | System/infrastructure workloads |
| **Baseline**   | Medium          | Normal applications             |
| **Restricted** | High            | Security-sensitive applications |

Easy memory trick:

```text
Privileged → Almost unrestricted

Baseline → Block known dangerous behavior

Restricted → Harden the workload
```

---

# 7. PSA — Pod Security Admission

Now we move to the second half.

**Pod Security Admission (PSA)** is the Kubernetes **admission controller** that enforces PSS.

When you submit a Pod:

```bash
kubectl apply -f pod.yaml
```

the request goes through the Kubernetes API server.

Conceptually:

```text
kubectl
   │
   ▼
API Server
   │
   ▼
Authentication
   │
   ▼
Authorization
   │
   ▼
Admission Controllers
   │
   ▼
Pod Security Admission
   │
   ▼
PSS check
   │
   ├── Compliant → Allow
   │
   └── Violation → Enforce/Warn/Audit
```

This is the key relationship:

```text
PSS
"What security requirements?"

PSA
"Enforce those requirements."
```

---

# 8. PSA works at namespace level

This is extremely important.

You normally configure PSA using **labels on namespaces**.

For example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: secure-app
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

Now Pods created in:

```text
secure-app
```

are checked against:

```text
Restricted
```

---

# 9. PSA modes

PSA has three modes:

```text
enforce
warn
audit
```

These modes answer:

> **What should happen when a Pod violates the selected PSS profile?**

---

# 10. `enforce`

This is the strongest mode.

If a Pod violates the selected security profile:

```text
Pod
 │
 ▼
PSA
 │
 ▼
Restricted check
 │
 ▼
Violation ❌
 │
 ▼
Pod rejected
```

Example:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

Then an insecure Pod might be rejected with a message indicating that it violates the restricted policy.

### Remember:

> **enforce = block**

---

# 11. `warn`

With `warn`, the Pod is **allowed**, but the user receives a warning.

```text
Pod
 │
 ▼
PSA
 │
 ▼
Violation
 │
 ├── Warning ⚠️
 │
 ▼
Pod allowed
```

For example:

```yaml
pod-security.kubernetes.io/warn: restricted
```

This is useful when you're migrating an existing application.

You can discover what would fail before actually enforcing it.

### Remember:

> **warn = allow + tell me**

---

# 12. `audit`

With `audit`, the Pod is also allowed, but the violation is recorded in Kubernetes **audit information/logs**.

```text
Pod
 │
 ▼
PSA
 │
 ▼
Violation
 │
 ├── Audit information
 │
 ▼
Pod allowed
```

Example:

```yaml
pod-security.kubernetes.io/audit: restricted
```

### Remember:

> **audit = allow + record**

---

# 13. The three modes together

You can use all three simultaneously.

For example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:

    pod-security.kubernetes.io/enforce: restricted

    pod-security.kubernetes.io/warn: restricted

    pod-security.kubernetes.io/audit: restricted
```

This means:

```text
                    Restricted
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       ENFORCE         WARN          AUDIT
          │             │             │
       Reject          Warn          Record
```

---

# 14. Why use different levels for different modes?

You don't have to use the same profile for all three.

For example:

```yaml
pod-security.kubernetes.io/enforce: baseline
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted
```

Meaning:

```text
ENFORCE
Baseline
   ↓
Block baseline violations

WARN
Restricted
   ↓
Tell developers what would violate Restricted

AUDIT
Restricted
   ↓
Record Restricted violations
```

This is useful when gradually hardening workloads.

---

# 15. Version pinning

PSA can also specify a PSS version.

For example:

```yaml
pod-security.kubernetes.io/enforce-version: v1.35
```

Similarly:

```yaml
pod-security.kubernetes.io/warn-version: v1.35
pod-security.kubernetes.io/audit-version: v1.35
```

This can make policy behavior more predictable as Kubernetes versions change.

A common pattern is:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.35
```

# 18. Deploy an insecure Pod

Create:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: insecure-pod
  namespace: secure-app
spec:
  containers:
  - name: nginx
    image: nginx
    securityContext:
      privileged: true
```

Apply:

```bash
kubectl apply -f insecure-pod.yaml
```

PSA should reject it because:

```yaml
privileged: true
```

is incompatible with the Restricted profile.

---

# 19. Create a more secure Pod

Try:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: secure-app
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault

  containers:
  - name: nginx
    image: nginxinc/nginx-unprivileged

    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
```

This follows the general security direction expected by the Restricted profile.

Check:

```bash
kubectl get pod -n secure-app
```

---

# 20. Why `runAsNonRoot` matters

Running applications as root increases the potential impact of a container compromise.

Instead of:

```text
Container
   │
   └── UID 0 (root)
```

we want:

```text
Container
   │
   └── Non-root UID
```

Example:

```yaml
securityContext:
  runAsNonRoot: true
```

You can also specify:

```yaml
runAsUser: 1000
```

---

# 21. Why `allowPrivilegeEscalation: false` matters

This prevents a process from gaining more privileges than its parent process.

```yaml
securityContext:
  allowPrivilegeEscalation: false
```

This is an important hardening setting for Restricted workloads.

---

# 22. Linux capabilities

Linux capabilities split traditional root privileges into individual capabilities.

For example:

```text
NET_ADMIN
SYS_ADMIN
NET_RAW
CHOWN
SETUID
SETGID
```

Instead of giving a container broad privileges, you should give it only what it actually requires.

A hardened configuration commonly starts by dropping all capabilities:

```yaml
capabilities:
  drop:
  - ALL
```

Then, if absolutely necessary, add back specific capabilities.

---

# 23. Seccomp

Seccomp restricts which Linux system calls a process can make.

For example:

```yaml
seccompProfile:
  type: RuntimeDefault
```

The idea is:

```text
Application
    │
    ▼
System calls
    │
    ▼
Seccomp filter
    │
 ┌──┴───┐
 ▼      ▼
Allow  Block
```

This reduces the kernel attack surface.

---

# 24. PSA does NOT secure everything

This is an important interview distinction.

PSA/PSS primarily deal with **Pod security configuration**.

They do not replace:

* RBAC
* NetworkPolicy
* Secrets management
* Image scanning
* Runtime security
* Admission policies beyond Pod Security
* Node security
* Supply-chain security

Think of Kubernetes security as multiple layers:

```text
                    Kubernetes Security
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
     RBAC                PSA/PSS          NetworkPolicy
       │                   │                   │
  Who can do it?     How can Pod run?    Who can talk?
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ▼
                    Container Security
                           │
                  Images / Secrets / Runtime
```

---

# 25. PSA vs RBAC

Don't confuse these.

### RBAC

Controls:

> **Who can perform an action?**

Example:

```text
Can developer create Pods?
Can user delete deployments?
Can service account read Secrets?
```

### PSA

Controls:

> **Is this Pod configuration allowed?**

Example:

```text
Can this Pod run privileged?
Can it use host networking?
Does it satisfy Restricted?
```

So:

```text
RBAC → WHO can do WHAT?

PSA  → WHICH Pod security configurations are allowed?
```

---

# 26. PSA vs NetworkPolicy

Again, different purposes.

### PSA

Controls Pod security configuration:

```text
privileged
runAsNonRoot
capabilities
host namespaces
seccomp
```

### NetworkPolicy

Controls network traffic:

```text
Pod A ───────► Pod B
       ALLOW/DENY
```

So:

```text
PSA
 ↓
Pod security

NetworkPolicy
 ↓
Network communication
```

They work together.

---

# 27. PSA vs ResourceQuota

Another common interview question.

### PSA

Security:

```text
Can this Pod run with privileged=true?
```

### ResourceQuota

Resource consumption:

```text
How much CPU/RAM can this namespace consume?
```

### LimitRange

Default/per-container limits:

```text
What CPU/RAM requests/limits should containers have?
```

Therefore:

```text
PSA
 → Security

ResourceQuota
 → Namespace-wide resource limits

LimitRange
 → Container/Pod resource defaults and limits
```

# 28. PSA vs PSP

This is a very important interview topic.

**PodSecurityPolicy (PSP)** was the older Kubernetes mechanism.

It was removed in Kubernetes **1.25**.

Modern Kubernetes uses:

```text
PSS + PSA
```

instead.

### PSP

```text
PodSecurityPolicy
       ↓
Cluster resource
       ↓
Security policy
```

### Modern approach

```text
PSS
 ↓
Security standards

PSA
 ↓
Admission enforcement
```

---

# 29. Why was PSP replaced?

PSP was powerful but relatively complicated to configure and manage.

The modern approach provides standardized profiles:

```text
Privileged
Baseline
Restricted
```

and simple namespace labels:

```yaml
pod-security.kubernetes.io/enforce: restricted
```

This makes the basic security model much easier to understand and operate.

# 30. PSA admission flow

Let's understand exactly what happens when you run:

```bash
kubectl apply -f pod.yaml
```

Conceptually:

```text
                kubectl
                   │
                   ▼
            Kubernetes API
                   │
                   ▼
          Authentication
                   │
                   ▼
           Authorization
                   │
                   ▼
       Admission Controllers
                   │
                   ▼
      Pod Security Admission
                   │
                   ▼
         Read namespace labels
                   │
                   ▼
         Select PSS profile
                   │
                   ▼
         Validate Pod security
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Enforce      Warn       Audit
        │          │          │
     Reject       Warn      Record
```

If `enforce=restricted` and the Pod violates Restricted:

```text
API request
    ↓
PSA
    ↓
Violation
    ↓
REJECT
```

The Pod never gets admitted.

# 32. Practical migration strategy

Imagine you have an existing production namespace with hundreds of Pods.

You don't want to immediately enable:

```text
enforce=restricted
```

because you could break workloads.

A safer migration approach is:

### Stage 1

```yaml
warn: restricted
audit: restricted
```

Find violations.

### Stage 2

Fix workloads:

```text
Run as non-root
Drop capabilities
Disable privilege escalation
Use seccomp
Remove host access
```

### Stage 3

Enable:

```yaml
enforce: restricted
```

So:

```text
Existing workloads
       ↓
WARN/AUDIT
       ↓
Find violations
       ↓
Fix workloads
       ↓
ENFORCE
       ↓
Restricted security
```

This is a very good **real-world interview answer**.

# 33. What happens if a Pod violates `warn` and `audit`?

Suppose:

```yaml
labels:
  pod-security.kubernetes.io/warn: restricted
  pod-security.kubernetes.io/audit: restricted
```

and a Pod violates Restricted.

The Pod can still be admitted.

But:

```text
WARN
 ↓
User sees warning

AUDIT
 ↓
Violation is recorded in audit information
```

If you additionally have:

```yaml
enforce: restricted
```

then:

```text
ENFORCE
 ↓
Pod rejected
```

# 34. Important: PSS is not a single YAML resource

This is another interview trap.

You don't create:

```yaml
kind: PodSecurityStandard
```

There isn't a normal Kubernetes resource called:

```text
PodSecurityStandard
```

Instead, PSS defines the **standard/profile**, and PSA applies it through namespace configuration.

You configure it with:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

---

# 35. Important: PSA is not a separate Deployment

You don't deploy:

```text
psa-deployment.yaml
```

PSA is a **built-in admission controller**.

You configure it through Kubernetes' Pod Security Admission mechanism, primarily using namespace labels.

# 37. Interview scenario

### Interviewer:

> You have a production namespace. Developers are deploying privileged containers. How would you prevent this?

### Strong answer:

> I would use Kubernetes Pod Security Admission with the Pod Security Standards. I would label the production namespace with an appropriate PSS profile, typically Baseline or Restricted depending on the workload requirements, and use the `enforce` mode to reject non-compliant Pods. During migration, I would first use `warn` and `audit` to identify existing violations, remediate the workloads, and then enable enforcement.

That's a strong answer because you're explaining **both security and migration strategy**.

# 39. Complete security picture

For a Kubernetes production environment, you shouldn't rely on PSA alone.

A reasonable security architecture looks like:

```text
                    Kubernetes
                        │
        ┌───────────────┼────────────────┐
        │               │                │
        ▼               ▼                ▼
      RBAC             PSA            NetworkPolicy
        │               │                │
        │               │                │
   Who can access?  Pod security?   Network access?
        │               │                │
        └───────────────┼────────────────┘
                        │
                        ▼
                 Workload Security
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Images        Secrets       Runtime
       Scanning      Security      Security
```
