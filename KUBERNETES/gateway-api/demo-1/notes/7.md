A **CORS preflight** is a special `OPTIONS` request that a browser **automatically sends** before making certain cross-origin HTTP requests. 

Think of it as the browser **asking for permission** first: *"Hey server, I'm a website from `example.com`. Am I allowed to call your API using the `DELETE` method and send an `Authorization` header?"*

If the server replies with a "Yes" (via specific response headers), the browser proceeds with the actual request. If the server says "No" or doesn't reply, the browser blocks the request and throws a CORS error.

---

### When does the browser send a preflight?

Not every cross-origin request triggers a preflight. It only happens for **"non-simple"** requests.

| Type | Condition | Does it trigger a preflight? |
| :--- | :--- | :--- |
| **Simple Request** | Method: `GET`, `HEAD`, or `POST` <br> Headers: Only standard headers like `Accept`, `Accept-Language` <br> Content-Type: `text/plain`, `application/x-www-form-urlencoded`, or `multipart/form-data` | ❌ **No**. Browser sends the actual request directly. |
| **Preflighted Request** | Method: `PUT`, `DELETE`, `PATCH`, etc. <br> Headers: Custom headers like `Authorization`, `X-API-Key` <br> Content-Type: `application/json`, `application/xml`, etc. | ✅ **Yes**. Browser sends an `OPTIONS` preflight first. |

---

### How the Preflight Works (Step-by-Step)

Here is exactly what happens when your JavaScript tries to call a cross-origin API with a custom `Authorization` header:

**Step 1: Browser sends the Preflight (`OPTIONS`)**
The browser sends an `OPTIONS` request to the server with these special headers:
```
OPTIONS /api/data HTTP/1.1
Origin: https://my-frontend.com
Access-Control-Request-Method: GET
Access-Control-Request-Headers: authorization
```

**Step 2: Server checks its CORS policy**
The server examines the request and decides whether to allow `https://my-frontend.com` to call this endpoint.

**Step 3: Server sends the Preflight Response**
The server replies with headers telling the browser what is allowed:
```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://my-frontend.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: authorization
Access-Control-Max-Age: 3600
```

**Step 4: Browser checks the response**

- If the response **matches** the original request (e.g., the Origin is allowed, and `authorization` is in the `Allow-Headers`), the browser proceeds to **Step 5**.
- If the response **does not match** (e.g., `authorization` is missing from the allowed headers), the browser **blocks** the request and shows a CORS error in the console.

**Step 5: Browser sends the Actual Request**
Finally, the browser sends your actual `GET` request with the `Authorization` header, and the server returns the real data.

---

### Why is this important for Gateway API?

In the previous Gateway API CORS configuration, you might have noticed we set `allowMethods`, `allowHeaders`, and `maxAge`. 

- The gateway uses these settings to **automatically build the correct response** to that `OPTIONS` preflight request.
- The gateway **never forwards** the `OPTIONS` request to your application pods. It intercepts it, responds with the CORS headers, and moves on. 
- This means your backend developers **do not need to write any code** to handle `OPTIONS` requests or set CORS headers. The gateway completely offloads this complexity. 

**Example**: When you set `allowCredentials: true`, the gateway knows to never reply with `Access-Control-Allow-Origin: *` in the preflight response, which strictly follows the browser security rules.
