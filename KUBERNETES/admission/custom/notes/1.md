# Building Your Own Kubernetes Admission Webhook Controller

A complete, working walkthrough — from Go server code to TLS certs to the final `kubectl apply`.

---

## 1. Architecture Overview

```
kubectl apply → API Server → [Mutating Webhooks] → [Validating Webhooks] → etcd
                                      │                       │
                                      ▼                       ▼
                              Your Webhook Server (HTTPS, in-cluster)
```

Your webhook is just an **HTTPS server** running as a pod in the cluster. The API server calls it over TLS with an `AdmissionReview` JSON payload, and expects an `AdmissionReview` JSON response back with `allowed: true/false` (and, for mutating webhooks, an optional JSON patch).

**Non-negotiable requirement:** the connection MUST be HTTPS. The API server refuses to call a plain-HTTP webhook. This is the single most common reason people get stuck, so we'll set up TLS properly from the start.

Project layout we'll build:

```
pod-policy-webhook/
├── main.go                  # webhook server
├── go.mod
├── Dockerfile
├── deploy/
│   ├── certs.sh             # generates self-signed CA + cert
│   ├── deployment.yaml
│   ├── service.yaml
│   └── webhook-config.yaml
```

## 2. The Webhook Server (Go)

```go
// main.go
package main

import (
	"crypto/tls"
	"encoding/json"
	"log"
	"net/http"

	admissionv1 "k8s.io/api/admission/v1"
	corev1 "k8s.io/api/core/v1"
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
)

func handleValidatePods(w http.ResponseWriter, r *http.Request) {
	var review admissionv1.AdmissionReview
	if err := json.NewDecoder(r.Body).Decode(&review); err != nil {
		http.Error(w, "invalid request", http.StatusBadRequest)
		return
	}

	pod := corev1.Pod{}
	if err := json.Unmarshal(review.Request.Object.Raw, &pod); err != nil {
		http.Error(w, "invalid pod spec", http.StatusBadRequest)
		return
	}

	allowed := true
	reason := ""

	// Example policy: block containers running as root
	for _, c := range pod.Spec.Containers {
		if c.SecurityContext == nil || c.SecurityContext.RunAsNonRoot == nil || !*c.SecurityContext.RunAsNonRoot {
			allowed = false
			reason = "containers must set securityContext.runAsNonRoot: true"
			break
		}
	}

	response := admissionv1.AdmissionReview{
		TypeMeta: review.TypeMeta,
		Response: &admissionv1.AdmissionResponse{
			UID:     review.Request.UID, // MUST echo the original UID
			Allowed: allowed,
		},
	}
	if !allowed {
		response.Response.Result = &metav1.Status{Message: reason}
	}

	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(response)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/validate", handleValidatePods)

	server := &http.Server{
		Addr:    ":8443",
		Handler: mux,
	}

	cert, err := tls.LoadX509KeyPair("/certs/tls.crt", "/certs/tls.key")
	if err != nil {
		log.Fatalf("failed to load TLS cert: %v", err)
	}
	server.TLSConfig = &tls.Config{Certificates: []tls.Certificate{cert}}

	log.Println("webhook server listening on :8443")
	log.Fatal(server.ListenAndServeTLS("", ""))
}
```

```go
// go.mod
module pod-policy-webhook

go 1.22

require (
	k8s.io/api v0.30.0
	k8s.io/apimachinery v0.30.0
)
```

**Key details that trip people up:**
- `review.Request.UID` **must** be echoed back exactly in `response.UID` — the API server matches responses to requests by this field and silently drops mismatched ones.
- The server must listen on **TLS**, not plain HTTP.
- Always return **200 OK** even when rejecting a pod — `Allowed: false` is how you reject, not an HTTP error code. An HTTP error just means "my webhook crashed," which (depending on `failurePolicy`) may let the request through anyway.

## 4. TLS Certificates

The API server verifies your webhook's cert against a `caBundle` you supply in the `ValidatingWebhookConfiguration`. Two ways to get this:

### Option A — cert-manager (recommended for anything beyond a demo)
Install cert-manager, then create a self-signed `Issuer` + `Certificate` for `webhook-server.default.svc`, and use the `cert-manager.io/inject-ca-from` annotation on the webhook config so the `caBundle` is injected automatically. Saves you from manually rotating certs.

### Option B — manual OpenSSL (fine for learning/testing)

```bash
# deploy/certs.sh
set -e
SERVICE=webhook-server
NAMESPACE=default

# 1. Generate CA
openssl genrsa -out ca.key 2048
openssl req -x509 -new -nodes -key ca.key -subj "/CN=webhook-ca" -days 3650 -out ca.crt

# 2. Generate server key + CSR
openssl genrsa -out tls.key 2048
openssl req -new -key tls.key -subj "/CN=${SERVICE}.${NAMESPACE}.svc" -out server.csr

# 3. Sign the server cert with our CA, with the correct SAN
cat > san.cnf <<EOF
subjectAltName = DNS:${SERVICE}.${NAMESPACE}.svc
EOF
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out tls.crt -days 3650 -extfile san.cnf

# 4. Create the k8s secret the pod will mount
kubectl create secret tls webhook-server-tls \
  --cert=tls.crt --key=tls.key -n ${NAMESPACE}

# 5. Base64 the CA — you'll paste this into webhook-config.yaml's caBundle
base64 -w0 ca.crt
```

**Critical gotcha:** the cert's `CN`/SAN must be exactly `<service-name>.<namespace>.svc` — not a public domain, not `localhost`. If the SAN doesn't match how the API server addresses the service, you'll get TLS handshake failures that look identical to plain connection-refused errors in the logs.

## 5. Kubernetes Manifests

### Deployment

```yaml
# deploy/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webhook-server
  namespace: default
spec:
  replicas: 2                     # run at least 2 — a single-replica webhook is a single point of failure for your whole cluster's admission path
  selector:
    matchLabels:
      app: webhook-server
  template:
    metadata:
      labels:
        app: webhook-server
    spec:
      containers:
        - name: webhook-server
          image: your-registry/webhook-server:v1
          ports:
            - containerPort: 8443
          volumeMounts:
            - name: tls
              mountPath: /certs
              readOnly: true
          readinessProbe:
            tcpSocket:
              port: 8443
            initialDelaySeconds: 2
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
      volumes:
        - name: tls
          secret:
            secretName: webhook-server-tls
```

### Service

```yaml
# deploy/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: webhook-server
  namespace: default
spec:
  selector:
    app: webhook-server
  ports:
    - port: 443
      targetPort: 8443
```

### ValidatingWebhookConfiguration

```yaml
# deploy/webhook-config.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: pod-policy-webhook
webhooks:
  - name: pod-policy-webhook.default.svc
    admissionReviewVersions: ["v1"]
    sideEffects: None
    timeoutSeconds: 5
    failurePolicy: Fail          # Fail-closed for security policies
    rules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
        scope: "Namespaced"
    namespaceSelector:            # exclude system namespaces so you don't lock yourself out
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: ["kube-system", "kube-public"]
    clientConfig:
      service:
        name: webhook-server
        namespace: default
        path: "/validate"
        port: 443
      caBundle: <base64-CA-cert-from-step-4>
```

**Why `namespaceSelector` matters:** if you don't exclude `kube-system`, and your webhook has a bug or goes down, you can block core cluster components from being created/restarted — this has bricked real clusters. Always exclude system namespaces while you're still testing.

## 6. Deploy Order

Order matters — deploy the webhook server *before* registering the `ValidatingWebhookConfiguration`, or every matching pod creation in the cluster will fail (with `failurePolicy: Fail`) while the API server tries to reach a service that doesn't exist yet.

```bash
kubectl apply -f deploy/deployment.yaml
kubectl apply -f deploy/service.yaml
kubectl rollout status deployment/webhook-server   # wait until it's actually ready
kubectl apply -f deploy/webhook-config.yaml
```

## 7. Testing It

```bash
# This should be BLOCKED (no runAsNonRoot)
kubectl run bad-pod --image=nginx

# Expected output:
# Error from server: admission webhook "pod-policy-webhook.default.svc" denied the request:
# containers must set securityContext.runAsNonRoot: true
```

```bash
# This should be ALLOWED
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: good-pod
spec:
  containers:
    - name: nginx
      image: nginx
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
EOF
```

You can also test the webhook in isolation without going through kubectl, by port-forwarding and posting a raw `AdmissionReview` payload:

```bash
kubectl port-forward svc/webhook-server 8443:443 -n default
curl -k -X POST https://localhost:8443/validate \
  -H "Content-Type: application/json" \
  -d @sample-admission-review.json
```

## 8. Debugging Checklist

Same order as before, since the connection layer is where most webhook problems live:

```bash
kubectl get svc webhook-server -n default
kubectl get pods -n default -l app=webhook-server
kubectl logs -l app=webhook-server -n default
kubectl describe validatingwebhookconfiguration pod-policy-webhook
```

Add these two, specific to a from-scratch build:

- **`x509: certificate signed by unknown authority`** in API server logs → the `caBundle` in your `webhook-config.yaml` doesn't match the CA that actually signed `tls.crt`. Re-check step 4.
- **`x509: certificate is valid for X, not Y`** → the cert's SAN doesn't match `<service>.<namespace>.svc`. Regenerate with the correct SAN.

## 9. Making It a Mutating Webhook Instead

If you want to auto-inject values rather than just allow/block, the response needs a JSON Patch:

```go
import "encoding/base64"

patch := []map[string]interface{}{
	{"op": "add", "path": "/metadata/labels/injected-by", "value": "pod-policy-webhook"},
}
patchBytes, _ := json.Marshal(patch)

patchType := admissionv1.PatchTypeJSONPatch
response.Response.Patch = patchBytes
response.Response.PatchType = &patchType
```

Everything else — TLS setup, Deployment, Service, deploy order — is identical. Only the `kind` (`MutatingWebhookConfiguration`) and the response body differ.

## Summary

1. Write the HTTPS server (`/validate` handler, echo the UID, return `Allowed`)
2. Containerize it
3. Generate TLS cert with SAN = `<service>.<namespace>.svc`, get the CA into a `caBundle`
4. Deploy → Service → wait for readiness → **then** register the webhook config
5. Exclude `kube-system` via `namespaceSelector` while testing
6. Test both the "should block" and "should allow" cases
7. Debug connectivity issues first, TLS trust issues second
