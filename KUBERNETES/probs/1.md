Exactly. That statement is correct, and it’s an important nuance in Kubernetes probe design.

## Why `httpGet` / `tcpSocket` fail for localhost-only containers

Kubernetes probes are executed by the **kubelet**, which runs on the node—**outside** the container’s network namespace.

For `httpGet` and `tcpSocket` probes, the kubelet connects to the Pod’s IP address (or a `host` you specify, but that host is resolved from the node, not inside the container). If your application listens only on `127.0.0.1` inside the container, that socket is only reachable from **inside the container’s network namespace**. The kubelet’s connection to the Pod IP will be refused.

So:

- `httpGet` to Pod IP → fails
- `tcpSocket` to Pod IP → fails
- `httpGet` with `host: 127.0.0.1` → kubelet connects to the **node’s** localhost, not the container’s → fails
- `exec` probe → runs the command **inside** the container, so `curl http://127.0.0.1:8080/healthz` works

That makes `exec` the only built-in probe type that can check a localhost-only endpoint.

## Example exec probe

```yaml
readinessProbe:
  exec:
    command:
    - sh
    - -c
    - curl -fsS --max-time 2 http://127.0.0.1:8080/healthz || exit 1
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
```

Notes on the command:

- `-f` makes curl fail on HTTP 4xx/5xx.
- `-sS` silences progress but still shows errors.
- `--max-time 2` bounds the request.
- `|| exit 1` ensures a non-zero exit code on failure.

You can use the same pattern for `livenessProbe` and `startupProbe`.

## Trade-offs of exec probes

Exec probes are powerful but come with downsides:

| Aspect | Impact |
|---|---|
| **Requires a binary** | The image must contain `curl`, `wget`, `nc`, or a shell. Distroless/scratch images often don’t. |
| **Process overhead** | Each probe forks a new process. Frequent probes can add CPU overhead. |
| **Security surface** | Adding `curl` or a shell increases the image’s attack surface. |
| **Timeouts** | If the command hangs, the kubelet kills it after `timeoutSeconds`, but the process may not clean up instantly. |
| **Complexity** | More moving parts than a simple `httpGet`. |

## When to prefer `httpGet`

If you control the application, the cleanest fix is to make it listen on `0.0.0.0` (or the Pod IP) instead of `127.0.0.1`. Then you can use a standard `httpGet` probe:

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

This is lighter, requires no extra binaries, and is the idiomatic Kubernetes approach.

## Workarounds if you can’t change the app

If the app must stay on localhost and the image has no shell/curl:

1. **Sidecar with shared network namespace**  
   Add a sidecar container that has `curl` and shares the Pod network namespace. Define an `exec` probe on the sidecar that curls `localhost:8080`. This works because both containers share the same network namespace, so `localhost` in the sidecar reaches the main container’s localhost. It’s heavier but avoids modifying the main image.

2. **Custom probe binary**  
   If you can add a small static binary to the image, use it instead of `curl`. But this still modifies the image.

3. **Change the bind address**  
   The best long-term fix is almost always to bind to `0.0.0.0` and use `httpGet`.

## Summary

- `httpGet` and `tcpSocket` probes are initiated by the kubelet from outside the container network namespace. They cannot reach a socket bound only to `127.0.0.1`.
- `exec` probes run inside the container, so they can reach localhost.
- For localhost-only containers, `exec` is the only built-in probe type that works.
- Use it when necessary, but prefer `httpGet` with a `0.0.0.0` bind address whenever you can.
