# Helm Chart Across Multiple Namespaces — Complete Guide

---

## Reframing the Problem

The original answer treats different configs per namespace as a "problem."
It's actually the DESIGN GOAL — prod SHOULD have more replicas than dev,
SHOULD use different resource limits, SHOULD have different ingress hostnames.

The real problems to solve are:
1. How do you MANAGE intentional differences without them becoming drift?
2. How do you DETECT unintentional differences (drift) when they happen?
3. How do you ENFORCE consistency of the things that SHOULD be the same?
4. How do you SCALE this when you have 10+ namespaces?

## Part 1 — Values Hierarchy: The Right Structure

### The pattern: base values + per-namespace overrides

```
helm-charts/
├── my-app/
│   ├── Chart.yaml
│   ├── templates/
│   │   ├── deployment.yaml
│   │   ├── service.yaml
│   │   ├── ingress.yaml
│   │   └── hpa.yaml
│   └── values.yaml              ← base defaults (safe for ALL environments)
│
└── environments/
    ├── dev/
    │   └── values-dev.yaml      ← only overrides what's different in dev
    ├── staging/
    │   └── values-staging.yaml
    └── prod/
        └── values-prod.yaml     ← only overrides what's different in prod
```

### Base values.yaml — defaults that are safe everywhere
```yaml
# values.yaml (base)
replicaCount: 1                # dev-safe default

image:
  repository: myapp
  tag: ""                      # ALWAYS set explicitly — never default to latest
  pullPolicy: IfNotPresent

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

ingress:
  enabled: false               # disabled by default, enabled per env
  host: ""

autoscaling:
  enabled: false
  minReplicas: 1
  maxReplicas: 3

env: {}                        # no env vars by default
```

### Per-namespace overrides — only what differs
```yaml
# environments/prod/values-prod.yaml
# Only specify what's DIFFERENT from base — nothing else
replicaCount: 3                # prod needs more replicas

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2"
    memory: "1Gi"

ingress:
  enabled: true
  host: "app.example.com"      # prod hostname

autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 20

env:
  LOG_LEVEL: "WARN"            # less verbose in prod
  DB_POOL_SIZE: "20"
```

### Deploy with layered values (Helm merges them, last wins)
```bash
# Helm applies values in order — later files override earlier ones
helm upgrade --install my-app ./my-app \
  --namespace production \
  -f ./my-app/values.yaml \              # base (applied first)
  -f ./environments/prod/values-prod.yaml  # prod overrides (wins on conflict)
  --set image.tag=v1.2.3               # CI sets the tag (wins over everything)
```

## Part 2 — Helmfile: Managing Multi-Namespace Deployments at Scale

The original answer shows manual `helm upgrade` commands. Helmfile is the
standard tool for declaratively managing many Helm releases across namespaces.

```yaml
# helmfile.yaml — describes ALL releases across ALL namespaces
repositories:
  - name: stable
    url: https://charts.helm.sh/stable

# environments block defines per-env variables
environments:
  dev:
    values:
      - imageTag: "latest"
      - dbHost: "dev-db.internal"
  staging:
    values:
      - imageTag: "v1.2.3-rc1"
      - dbHost: "staging-db.internal"
  production:
    values:
      - imageTag: "v1.2.3"
      - dbHost: "prod-db.internal"

releases:
  # One release per namespace, sharing the same chart
  - name: my-app
    namespace: development
    chart: ./charts/my-app
    version: "~1.2.0"           # allow patch updates only
    values:
      - ./charts/my-app/values.yaml
      - ./environments/dev/values-dev.yaml
    set:
      - name: image.tag
        value: "{{ .Environment.Values.imageTag }}"   # env-specific value

  - name: my-app
    namespace: staging
    chart: ./charts/my-app
    version: "~1.2.0"
    values:
      - ./charts/my-app/values.yaml
      - ./environments/staging/values-staging.yaml
    set:
      - name: image.tag
        value: "{{ .Environment.Values.imageTag }}"

  - name: my-app
    namespace: production
    chart: ./charts/my-app
    version: "~1.2.0"
    values:
      - ./charts/my-app/values.yaml
      - ./environments/prod/values-prod.yaml
    set:
      - name: image.tag
        value: "{{ .Environment.Values.imageTag }}"
```

```bash
# Deploy to a specific environment:
helmfile --environment production sync

# Preview what would change (dry-run diff):
helmfile --environment production diff

# Deploy ALL environments at once:
helmfile sync

# Check what's actually deployed vs what's declared:
helmfile status
```

## Part 3 — ArgoCD ApplicationSet: GitOps for Multi-Namespace Helm

The original answer mentions ArgoCD but doesn't show how to actually use it
for this specific pattern. ApplicationSet is the feature that handles
"same chart, many namespaces" natively.

```yaml
# One ApplicationSet generates one ArgoCD Application per namespace
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: my-app-all-envs
  namespace: argocd
spec:
  generators:
    # List generator: explicitly define each environment
    - list:
        elements:
          - namespace: development
            env: dev
            replicaCount: "1"
            imageTag: latest
          - namespace: staging
            env: staging
            replicaCount: "2"
            imageTag: v1.2.3-rc1
          - namespace: production
            env: prod
            replicaCount: "3"
            imageTag: v1.2.3

  template:
    metadata:
      name: "my-app-{{ namespace }}"     # one Application per environment
    spec:
      project: default
      source:
        repoURL: https://github.com/org/helm-charts
        targetRevision: HEAD
        path: charts/my-app
        helm:
          valueFiles:
            - values.yaml                          # base values
            - "../../environments/{{ env }}/values-{{ env }}.yaml"
          parameters:
            - name: replicaCount
              value: "{{ replicaCount }}"
            - name: image.tag
              value: "{{ imageTag }}"
      destination:
        server: https://kubernetes.default.svc
        namespace: "{{ namespace }}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true      # reverts kubectl edit automatically
        syncOptions:
          - CreateNamespace=true
```

### What selfHeal actually does (key point missing from original answer)
```bash
# Someone manually edits the prod deployment:
kubectl edit deployment my-app -n production
# Changes replicas from 3 to 1 to "save resources"

# ArgoCD detects drift within ~3 minutes:
# ArgoCD status: OutOfSync
# ArgoCD reverts: sets replicas back to 3 automatically
# Event logged in ArgoCD audit trail: "who changed it, when, what was reverted"
```

## Part 4 — Detecting and Diagnosing Drift

The original shows only 3 commands. Here's the complete drift detection toolkit:

### Check what values are actually deployed
```bash
# See the values currently deployed (may differ from your files if manual edits)
helm get values my-app -n production
helm get values my-app -n staging

# Compare deployed values between namespaces:
diff \
  <(helm get values my-app -n production) \
  <(helm get values my-app -n staging)

# See ALL values including defaults (not just overrides):
helm get values my-app -n production --all
```

### Diff against what you WANT to deploy (before applying)
```bash
# Install helm-diff plugin first:
helm plugin install https://github.com/databus23/helm-diff

# What would change if you applied your current values files?
helm diff upgrade my-app ./charts/my-app \
  -n production \
  -f ./charts/my-app/values.yaml \
  -f ./environments/prod/values-prod.yaml \
  --set image.tag=v1.2.3

# Compare two DEPLOYED releases across namespaces:
helm diff release my-app --namespace production \
  my-app --namespace staging
```

### Detect manual kubectl edits (live state vs Helm state)
```bash
# Check if what's RUNNING matches what Helm THINKS is deployed:
helm get manifest my-app -n production > helm-expected.yaml
kubectl get deployment my-app -n production -o yaml > live-actual.yaml
diff helm-expected.yaml live-actual.yaml
# Differences here = someone used kubectl edit or kubectl set image

# Check Helm release status:
helm status my-app -n production
# STATUS: deployed         ← Helm thinks it's fine
# But live state may differ — Helm doesn't know about kubectl edits

# Check release history to spot who changed what:
helm history my-app -n production
# REVISION  STATUS     CHART          APP VERSION  DESCRIPTION
# 1         superseded my-app-1.2.0   1.0.0        Install complete
# 2         superseded my-app-1.2.0   1.0.1        Upgrade complete
# 3         deployed   my-app-1.2.1   1.0.1        Upgrade complete
```

### Find ALL Helm releases across ALL namespaces
```bash
# See every Helm release in the cluster at once:
helm list -A
# NAME     NAMESPACE    REVISION  STATUS    CHART          APP VERSION
# my-app   development  3         deployed  my-app-1.2.0   1.0.0
# my-app   staging      3         deployed  my-app-1.2.1   1.0.1   ← different version!
# my-app   production   2         deployed  my-app-1.2.0   1.0.0

# Notice: staging is on 1.2.1 but prod is on 1.2.0
# This is intentional (staged rollout) or drift? Only the team knows.
# This is why documenting WHAT should differ matters as much as detecting drift.
```

## Part 5 — Templating Chart Values Correctly

### Using named templates for repeated logic
```yaml
# templates/_helpers.tpl
# Define which values MUST be environment-specific (never have defaults):
{{- define "myapp.requiredValues" -}}
{{- required "image.tag must be set explicitly" .Values.image.tag | quote -}}
{{- end -}}
```

### Namespace-aware templating inside the chart
```yaml
# templates/ingress.yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "myapp.fullname" . }}
  namespace: {{ .Release.Namespace }}   # uses the --namespace flag value
  annotations:
    # Use Release.Namespace to set env-specific annotations:
    {{- if eq .Release.Namespace "production" }}
    kubernetes.io/ingress.class: "nginx-prod"
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    {{- else }}
    kubernetes.io/ingress.class: "nginx-dev"
    cert-manager.io/cluster-issuer: "letsencrypt-staging"
    {{- end }}
spec:
  rules:
    - host: {{ required "ingress.host must be set" .Values.ingress.host }}
{{- end }}
```

### Validating required values at chart render time
```yaml
# values.schema.json — validates values before Helm even deploys
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["image"],
  "properties": {
    "image": {
      "type": "object",
      "required": ["repository", "tag"],
      "properties": {
        "tag": {
          "type": "string",
          "minLength": 1,
          "description": "Must be set explicitly — never empty"
        }
      }
    },
    "replicaCount": {
      "type": "integer",
      "minimum": 1,
      "maximum": 50
    }
  }
}
# Helm validates this before templating — invalid values.yaml fails fast
```

## Part 6 — CI/CD Pipeline for Multi-Namespace Deployments

```yaml
# .github/workflows/deploy.yml
name: Deploy Helm Chart

on:
  push:
    tags: ['v*.*.*']           # deploy to prod on version tag
    branches: [develop]        # deploy to dev on every push

jobs:
  deploy-dev:
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to development
        run: |
          helm upgrade --install my-app ./charts/my-app \
            --namespace development \
            --create-namespace \
            -f ./charts/my-app/values.yaml \
            -f ./environments/dev/values-dev.yaml \
            --set image.tag=${{ github.sha }} \
            --atomic \            # rolls back automatically if deploy fails
            --timeout 5m

  deploy-staging:
    needs: deploy-dev             # staging only after dev succeeds
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to staging
        run: |
          helm upgrade --install my-app ./charts/my-app \
            --namespace staging \
            -f ./charts/my-app/values.yaml \
            -f ./environments/staging/values-staging.yaml \
            --set image.tag=${{ github.sha }} \
            --atomic \
            --timeout 5m

  deploy-prod:
    needs: deploy-staging
    if: startsWith(github.ref, 'refs/tags/v')
    environment: production       # requires manual approval
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Preview changes first
        run: |
          helm diff upgrade my-app ./charts/my-app \
            --namespace production \
            -f ./charts/my-app/values.yaml \
            -f ./environments/prod/values-prod.yaml \
            --set image.tag=${{ github.ref_name }}
      - name: Deploy to production
        run: |
          helm upgrade --install my-app ./charts/my-app \
            --namespace production \
            -f ./charts/my-app/values.yaml \
            -f ./environments/prod/values-prod.yaml \
            --set image.tag=${{ github.ref_name }} \
            --atomic \
            --timeout 10m
```

## Part 7 — Rollback Procedures

```bash
# Roll back to previous release (most common need):
helm rollback my-app -n production
# Reverts to revision N-1 automatically

# Roll back to specific revision:
helm rollback my-app 2 -n production

# Roll back ALL namespaces (e.g., bad chart change affects everything):
for ns in development staging production; do
  echo "Rolling back $ns..."
  helm rollback my-app -n $ns
done

# --atomic flag in CI handles rollback automatically on failure:
helm upgrade --install my-app ./charts/my-app \
  --namespace production \
  --atomic \          # if deploy fails or pods don't become Ready in --timeout,
  --timeout 10m       # Helm automatically runs `helm rollback` and exits non-zero
```

## Part 8 — Common Root Causes of Unexpected Drift

### Root cause 1: Manual kubectl edits (most common)
```bash
# Detect manually changed resources:
kubectl diff -f <(helm get manifest my-app -n production)
# Shows: what's running vs what Helm deployed

# Prevention: ArgoCD selfHeal reverts these automatically
# Detection without ArgoCD: run this in a CronJob and alert on non-empty output
```

### Root cause 2: Different chart versions per namespace
```bash
# Check chart version per namespace:
helm list -A -o json | jq '.[] | select(.name=="my-app") | {namespace, chart}'
# {namespace: "dev", chart: "my-app-1.2.0"}
# {namespace: "prod", chart: "my-app-1.1.5"}   ← intentional? or forgotten upgrade?

# Force same version everywhere:
# In Helmfile: set version: "1.2.0" (exact, not "~1.2.0") on every release
```

### Root cause 3: values files not in version control
```bash
# If values files live on a CI server or someone's laptop, not in Git:
# → Different people deploy with different files
# → No audit trail of what values were used

# Fix: ALL values files must be in Git, deployed ONLY from Git
# Enforce: protect the Helm deploy job to only run from the repo's CI
```

### Root cause 4: --set flags in CI scripts without --values
```bash
# BAD: ad-hoc --set flags don't get recorded anywhere
helm upgrade my-app ./chart \
  -n production \
  --set someFeature=true    # where is this documented? what if you forget it?

# GOOD: put it in values-prod.yaml and commit to Git
```
