# What is Database Cleanup?

Database cleanup means **removing unnecessary, outdated, or redundant data** to keep your database healthy, fast, and cost-effective.

Think of it like cleaning your house: you remove trash, old files, and things you don't need anymore.

---

## Common Database Cleanup Tasks

### 1. **Delete Expired Data**

**Example: Session tokens that expired**
```sql
-- Users have login sessions with expiration times
SELECT * FROM sessions;
-- id | user_id | token | expires_at
-- 1  | 101     | abc.. | 2025-01-15 (EXPIRED)
-- 2  | 102     | def.. | 2026-06-20 (still valid)

-- Cleanup: Delete all expired sessions
DELETE FROM sessions WHERE expires_at < NOW();
-- Removed 15,000 old expired sessions
```

**Why?**
- Expired sessions are useless (can't be used anyway)
- Takes up database storage space
- Slows down queries (more rows to scan)
- Security risk (old tokens might be compromised)

---

### 2. **Delete Old Logs**

**Example: Application logs older than 30 days**
```sql
-- Logs table with millions of entries
SELECT COUNT(*) FROM application_logs;
-- 50,000,000 rows (50 million!)

-- Cleanup: Keep only recent logs
DELETE FROM application_logs 
WHERE created_at < DATE_SUB(NOW(), INTERVAL 30 DAY);
-- Removed 30,000,000 old logs
```

**Why?**
- Old logs are rarely needed (you debug recent issues, not year-old ones)
- Saves massive storage costs
- Database queries run faster (less data to search)
- Regulatory compliance (some laws require log deletion after X days)

---

### 3. **Delete Temporary/Test Data**

**Example: Failed transactions that need cleanup**
```sql
-- Abandoned shopping carts (never checked out)
SELECT * FROM shopping_carts;
-- id | user_id | created_at | status
-- 1  | 101     | 2025-01-01 | abandoned (user left)
-- 2  | 102     | 2025-01-15 | completed (user bought)

-- Cleanup: Delete carts older than 7 days that weren't completed
DELETE FROM shopping_carts 
WHERE status = 'abandoned' AND created_at < DATE_SUB(NOW(), INTERVAL 7 DAY);
```

**Why?**
- Abandoned carts clutter the database
- Might send reminder emails (but after 7 days, not worth it)
- Frees up storage space

---

### 4. **Delete Soft-Deleted Records**

**Example: Users marked as "deleted" but still in database**
```sql
-- User deleted their account, but record still exists
SELECT * FROM users WHERE deleted_at IS NOT NULL;
-- id | name | deleted_at
-- 1  | John | 2024-01-15
-- 2  | Jane | 2024-06-20

-- Cleanup: Permanently delete users who were soft-deleted >1 year ago
DELETE FROM users 
WHERE deleted_at IS NOT NULL 
AND deleted_at < DATE_SUB(NOW(), INTERVAL 1 YEAR);
```

**Why?**
- GDPR compliance ("right to be forgotten")
- User requested account deletion, finally remove their data
- Free up storage

---

### 5. **Remove Duplicate Entries**

**Example: Duplicate records from failed transactions**
```sql
-- Payment processed twice due to network glitch
SELECT * FROM payments;
-- id | user_id | amount | timestamp
-- 1  | 101     | $50    | 2025-01-15 10:00:00
-- 2  | 101     | $50    | 2025-01-15 10:00:05 (duplicate!)

-- Cleanup: Keep only the first one
DELETE FROM payments 
WHERE id NOT IN (
  SELECT MIN(id) FROM payments GROUP BY user_id, amount, DATE(timestamp)
);
```

**Why?**
- Duplicate transactions cause incorrect financial records
- Customer double-charged
- Accounting gets confused

---

### 6. **Archive Old Data (Move, not delete)**

**Example: Keep sales data for 2 years, then archive**
```sql
-- Archive old orders to separate table
INSERT INTO orders_archive 
SELECT * FROM orders 
WHERE order_date < DATE_SUB(NOW(), INTERVAL 2 YEAR);

-- Then delete from main table
DELETE FROM orders 
WHERE order_date < DATE_SUB(NOW(), INTERVAL 2 YEAR);
```

**Why?**
- Keep data for compliance (legal requirement)
- But remove from fast main database
- Query main DB faster (less data)
- Still have archived data if needed

---

### 7. **Remove Unused Indexes Data**

**Example: Delete orphaned comments from deleted posts**
```sql
-- Post was deleted, but comments still exist (orphaned)
DELETE FROM comments 
WHERE post_id NOT IN (SELECT id FROM posts);
```

**Why?**
- Orphaned data wastes space
- Can cause referential integrity issues
- Should never exist, but bugs happen

## Why Only in Staging, Not Production?

### ⚠️ Risks of database cleanup:

```
1. Accidental data loss
   - DELETE without WHERE clause deletes EVERYTHING
   - One typo = disaster

2. Performance impact
   - Deleting 10 million rows = database locks
   - All users' queries slow down
   - Might cause timeouts

3. Can't undo mistakes
   - Once deleted, data is gone
   - Backups take time to restore
```

### Why staging first?

```
STAGING (safe to practice):
└─ Test the cleanup job
   ├─ Does it delete the right data?
   ├─ Is performance acceptable?
   ├─ Can we run it at 3 AM without impact?
   └─ Does rollback work?
   
PRODUCTION (after testing):
└─ Only run after confirming in staging
   └─ You know exactly what will happen
```

### Example: Cleanup job fails in production

```
3:00 AM Production Cleanup Starts
    ↓
3:15 AM Deleting old logs...
    ↓
3:30 AM ❌ BUG: Deletes ALL logs, not just old ones
    ↓
3:31 AM Database has no logs (audit trail gone!)
    ↓
4:00 AM Developers discover the problem
    ↓
4:30 AM Still trying to recover from backup
    ↓
5:00 AM Production database restored
    ↓
6:00 AM Lost 3 hours of operations data
    ↓
7:00 AM Compliance team angry (audit trail missing)
```

**If you tested in staging first:**
```
Staging Test Run:
└─ Same bug discovered in staging
   └─ No customers affected
   └─ Fix the code
   └─ Test again
   └─ THEN run in production with confidence
```

## Kubernetes Implementation Example

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-cleanup
spec:
  # Run every night at 2 AM
  schedule: "0 2 * * *"
  
  # ONLY runs in staging, not dev or production
  jobTemplate:
    spec:
      template:
        spec:
          nodeSelector:
            environment: staging  # Key: only staging nodes
            
          containers:
          - name: cleanup-job
            image: myapp:latest
            command:
            - /bin/sh
            - -c
            - |
              # Cleanup tasks
              python cleanup_expired_sessions.py
              python cleanup_old_logs.py
              python cleanup_abandoned_carts.py
              python cleanup_soft_deleted_users.py
            
            env:
            - name: ENVIRONMENT
              value: "staging"
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: staging-db
                  key: connection-string
          
          restartPolicy: OnFailure
```

## Complete Cleanup Script Example

```python
# cleanup.py
import mysql.connector
from datetime import datetime, timedelta

def cleanup_expired_sessions(cursor):
    """Delete login sessions older than 7 days"""
    query = """
    DELETE FROM sessions 
    WHERE created_at < DATE_SUB(NOW(), INTERVAL 7 DAY)
    """
    cursor.execute(query)
    print(f"Deleted {cursor.rowcount} expired sessions")

def cleanup_old_logs(cursor):
    """Delete application logs older than 30 days"""
    query = """
    DELETE FROM application_logs 
    WHERE created_at < DATE_SUB(NOW(), INTERVAL 30 DAY)
    """
    cursor.execute(query)
    print(f"Deleted {cursor.rowcount} old log entries")

def cleanup_abandoned_carts(cursor):
    """Delete shopping carts abandoned >7 days"""
    query = """
    DELETE FROM shopping_carts 
    WHERE status = 'abandoned' 
    AND created_at < DATE_SUB(NOW(), INTERVAL 7 DAY)
    """
    cursor.execute(query)
    print(f"Deleted {cursor.rowcount} abandoned carts")

def cleanup_soft_deleted_users(cursor):
    """Permanently delete users soft-deleted >1 year ago (GDPR)"""
    query = """
    DELETE FROM users 
    WHERE deleted_at IS NOT NULL 
    AND deleted_at < DATE_SUB(NOW(), INTERVAL 1 YEAR)
    """
    cursor.execute(query)
    print(f"Permanently deleted {cursor.rowcount} user records")

def main():
    conn = mysql.connector.connect(
        host="staging-db.example.com",
        user="admin",
        password="secret",
        database="myapp"
    )
    cursor = conn.cursor()
    
    try:
        print(f"Starting cleanup at {datetime.now()}")
        cleanup_expired_sessions(cursor)
        cleanup_old_logs(cursor)
        cleanup_abandoned_carts(cursor)
        cleanup_soft_deleted_users(cursor)
        conn.commit()
        print(f"Cleanup completed successfully at {datetime.now()}")
    except Exception as e:
        conn.rollback()
        print(f"Cleanup failed: {e}")
        raise
    finally:
        cursor.close()
        conn.close()

if __name__ == "__main__":
    main()
```

## Summary

| Term | Meaning | Example |
|------|---------|---------|
| **Database Cleanup** | Remove old/unnecessary data | Delete sessions older than 7 days |
| **Why needed** | Keep database fast & small | 500 GB → 150 GB |
| **Staging only** | Test safely before production | Find bugs without affecting users |
| **CronJob** | Runs automatically on schedule | Every night at 2 AM |
| **No dev/prod** | Too risky in production | Could delete wrong data |

**Bottom line**: Cleanup jobs keep databases healthy by removing junk data, but they're risky, so you test them in staging first!
