# NodePort Service - Complete Explanation

This is a **good approach for local testing**, but let me clarify the concepts and show you all the options.

---

## Understanding the Flow

### Traffic Path Visualization

```
Your Laptop Browser
       ↓
  http://192.168.1.100:30007
       ↓
Kubernetes Node (192.168.1.100)
       ↓
NodePort Service (listening on port 30007)
       ↓
Load balances to one of the Pods
       ↓
Pod Container (nginx on port 80)
       ↓
Response sent back to browser
```

---

## Port Explanation

### Three Different Ports (Confusing but Important!)

```yaml
ports:
- port: 80                    # Service internal port
  targetPort: 80              # Pod container port
  nodePort: 30007             # Node external port (what you type in browser)
```

| Port | Name | Used By | Purpose |
|------|------|---------|---------|
| **80** | `port` | Pod-to-pod communication inside cluster | Pods talk to service on :80 |
| **80** | `targetPort` | Service → Pod forwarding | Service forwards to container :80 |
| **30007** | `nodePort` | External access from laptop | You access `http://node-ip:30007` |

### Simple Example

```
Inside Kubernetes:
└─ Pod A wants to reach Pod B (nginx)
   └─ Talks to service on port 80
   └─ Service forwards to pod on port 80

From your laptop:
└─ Browser requests http://192.168.1.100:30007
   └─ Node listens on port 30007
   └─ Forwards to service port 80
   └─ Service forwards to pod port 80
```

## Complete Working Example

Here's the **full, production-ready setup**:

```yaml
---
# Namespace for organization
apiVersion: v1
kind: Namespace
metadata:
  name: web-app

---
# Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
  namespace: web-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.24          # ✅ Use specific version, not 'latest'
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"
            cpu: "100m"
          limits:
            memory: "128Mi"
            cpu: "200m"
        livenessProbe:             # ✅ Health check
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10
          periodSeconds: 10

---
# Service (NodePort)
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: web-app
spec:
  type: NodePort
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 80
    nodePort: 30007               # ✅ Must be 30000-32767
    protocol: TCP
```

## Different Ways to Access the App

### Method 1: NodePort (Your Scenario)

```bash
# Get node IP
kubectl get nodes -o wide
# NAME            STATUS   IP
# minikube        Ready    192.168.1.100
# worker-node-1   Ready    192.168.1.101

# Access in browser
http://192.168.1.100:30007
http://192.168.1.101:30007  # Works too! (even if pod not on this node)
```

**Why works on both nodes:**
- NodePort listens on **every node**
- If pod not on this node, traffic gets routed to the right node
- Called "kube-proxy routing"

---

### Method 2: Port-Forward (For Single Pod Testing)

```bash
# Forward local port to pod port
kubectl port-forward -n web-app pod/web-deployment-xyz 8080:80

# Now access locally
http://localhost:8080
```

**Use when:**
- Testing single pod
- Don't want to expose service yet
- Quick debugging

---

### Method 3: Minikube Service Command

```bash
# Automatically opens browser with correct URL
minikube service web-service -n web-app

# Or just get the URL
minikube service web-service -n web-app --url
# Output: http://192.168.99.100:30007
```

**Best for minikube development.**

---

### Method 4: LoadBalancer Service (Better for Testing)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: web-app
spec:
  type: LoadBalancer        # ✅ Better than NodePort
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
    protocol: TCP
```

**Access:**
```bash
# Get LoadBalancer IP
kubectl get svc -n web-app
# NAME          TYPE           IP
# web-service   LoadBalancer   192.168.1.200

# Access
http://192.168.1.200:80
```

**Difference from NodePort:**
- NodePort: Uses node's actual IP, high port (30007)
- LoadBalancer: Creates virtual IP, standard port (80)
- LoadBalancer only works on cloud (AWS, GCP, Azure)
- Local testing: Use NodePort instead

---

### Method 5: Ingress (Best for Real Development)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  namespace: web-app
spec:
  rules:
  - host: webapp.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
```

**Setup:**
```bash
# Add to /etc/hosts
192.168.1.100 webapp.local

# Access in browser
http://webapp.local
```

**Best for:**
- Multiple apps on same IP
- Path-based routing
- Production-like testing

## Complete Testing Setup

Here's what I'd recommend for **local testing**:

```bash
# 1. Create namespace
kubectl create namespace web-app

# 2. Apply all manifests
kubectl apply -f deployment.yaml -n web-app
kubectl apply -f service.yaml -n web-app

# 3. Verify deployment
kubectl get pods -n web-app
kubectl get svc -n web-app

# 4. Get node IP
NODE_IP=$(kubectl get nodes -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
echo "Access at: http://$NODE_IP:30007"

# 5. Test from laptop
curl http://$NODE_IP:30007

# 6. View logs if issues
kubectl logs -n web-app deployment/web-deployment

# 7. Describe service for debugging
kubectl describe svc web-service -n web-app
```

## Troubleshooting: Can't Access Service?

### Check 1: Service exists and has endpoints

```bash
kubectl get svc -n web-app
# Should show web-service with NodePort 30007

kubectl get endpoints -n web-app
# Should show web-service with pod IPs
```

### Check 2: Pod is running

```bash
kubectl get pods -n web-app
# STATUS should be Running

kubectl logs -n web-app deployment/web-deployment
# Check for errors
```

### Check 3: Port is actually open

```bash
# From node itself
kubectl run -it --rm debug --image=busybox --restart=Never -- \
  sh -c 'wget -O- http://web-service:80'

# From laptop (check firewall)
telnet 192.168.1.100 30007
```

### Check 4: Verify node IP is correct

```bash
kubectl get nodes -o wide
# Copy the correct IP address
```

## NodePort vs Other Services

| Type | Port Range | Access | Use Case |
|------|-----------|--------|----------|
| **ClusterIP** | None (internal) | Pods only | Pod-to-pod communication |
| **NodePort** | 30000-32767 | External via node IP | Local testing, dev |
| **LoadBalancer** | Any | External via LB IP | Cloud environments |
| **Ingress** | 80/443 | External via domain | Multiple apps, routing |

```bash
# Step 1: Deploy nginx with custom HTML
cat > deployment.yaml <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment

for i in {1..5}; do
  curl "http://$NODE_IP:$NODE_PORT" | grep -o 'Pod: [^<]*'
```

## Security Warning ⚠️

```yaml
nodePort: 30007  # Exposed to your local network!
```

**For local testing only:**
- ✅ Fine for development machines
- ✅ Fine for testing on your laptop
- ❌ NOT for production
- ❌ Anyone on your network can access

**If you need external access:**
```bash
# Secure it with authentication
- Use VPN to your development machine
- Use port forwarding instead of NodePort
- Use LoadBalancer with network policies
```
