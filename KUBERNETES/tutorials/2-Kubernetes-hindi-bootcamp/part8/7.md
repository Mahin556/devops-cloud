### 1. "There are veth pairs created or depending on CNI maybe different"

- **Standard Behavior**: The majority of CNI plugins (Calico, Flannel, Cilium, Weave) use **veth pairs** (Virtual Ethernet pairs) to connect a Pod's network namespace to the host's network stack. 
- **What a veth pair is**: It is a virtual network cable with **two ends**. One end is placed *inside* the Pod's network namespace (this becomes `eth0` inside the container). The other end is attached to a bridge (e.g., `cni0`) or a routing interface *inside the host's root network namespace*.
- **"Depending on CNI maybe different"**: This is absolutely correct! While 99% of setups use veth pairs, some advanced CNIs (like Cilium with eBPF) can use **direct routing** or **vxlan** tunnels that don't strictly rely on a traditional bridge-based veth setup, but *they still almost always use a veth pair* to connect to the Pod's namespace. The "different" part refers to what happens to the **host-side** of that pair (attached to a bridge, a routing table, or a virtual device).

---

### 2. "Contained" (Container Runtime)
This is a typo for **`containerd`** (or your container runtime). 
- The runtime (containerd, CRI-O) is responsible for interacting with the Linux kernel and the CNI plugin to actually *execute* the network setup. 
- When the kubelet tells containerd to start a Pod, containerd calls the CNI plugin to set up the network **before** the application containers (like Nginx) start.

---

### 3. "Pause container" → "Create the network namespace holds the network namespace"
This is the **most critical detail** in your notes. The `pause` container is the secret sauce of Kubernetes networking.

**Here is exactly what happens**:

1. **Sandbox Creation**: When you run a Pod, the kubelet tells containerd to create a **Pod Sandbox**.
2. **Pause starts first**: The runtime pulls the `pause` image (a tiny ~700KB image written in C) and starts it.
3. **Namespace Created**: The `pause` container process creates a brand new **Network Namespace** (and often the UTS and IPC namespaces).
4. **CNI Attachment**: The CNI plugin assigns an IP address to this namespace and creates the `veth` pair (attaching the Pod's `eth0` to the host).
5. **The Anchor**: The `pause` container **holds** (or "anchors") this network namespace. 
6. **Application containers join**: When your `nginx` or `busybox` containers start, they are configured to **join** the *existing* network namespace of the `pause` container. They do not create their own.

**Why this matters**: If the `pause` container didn't exist, and your Nginx container crashed and restarted, the network namespace would be destroyed and recreated, causing the Pod to lose its IP address. Because the `pause` container never crashes (it literally does nothing except wait), it **keeps the network namespace alive** for the entire lifecycle of the Pod, even if your application restarts 100 times.

---

### 4. "Sleep"
The `pause` container's source code is incredibly simple—just a few lines of C. It calls the `pause()` system call, which puts the process into an **indefinite sleep** (waiting for a signal). In your notes, you simply call this **"Sleep"**. 

- It consumes zero CPU and less than 1MB of memory.
- You can see it on your node by running `docker ps | grep pause` or `crictl ps | grep pause`.

---

### 5. "List of namespaces created → `ls -lt /var/run/netns`"

You correctly noted that you can list these network namespaces on the host.

- **`/var/run/netns`** is the standard directory where network namespace references are stored (as files).
- **`ls -lt`** lists them sorted by time. (Note: Your note says `Is -It`, which is likely a typo for `ls -lt` / `ls -la`).

**How to explore this practically on a Linux host (as root)**:

**Step 1:** Find a running Pod and get its container ID:
```bash
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].containerID}'
# Output: containerd://abc123...
```

**Step 2:** Find the network namespace path on the host (using `nsenter` or checking the `/proc` of the process):
```bash
# Find the PID of the pause container (or any container in the Pod)
docker inspect -f '{{.State.Pid}}' <container-id>
# Output: 12345

# Check the network namespace symlink
ls -l /proc/12345/ns/net
# Output: net -> net:[4026532890]
```

**Step 3:** You can execute a command directly *inside* that Pod's network namespace from the host:
```bash
nsenter -t 12345 -n ip addr
```
This will show you the exact same `eth0` and `lo` interfaces that `kubectl exec` would show you, proving that the namespace is isolated but accessible from the host via kernel mechanisms.

| Step | Actor | Action |
| :--- | :--- | :--- |
| **1** | **kubelet** | "Start Pod `my-nginx`." |
| **2** | **containerd** | Creates a "Pod Sandbox". |
| **3** | **Pause Container** | Starts first. Creates a **new Network Namespace**. |

| **5** | **Pause Container** | Runs `pause()` (infinite sleep). **Holds** the netns open. |
| **6** | **App Container (Nginx)** | Starts. It is configured to **join** the pause container's network namespace (not create its own). |
| **7** | **Result** | Nginx shares `eth0` and the IP with the pause container. They are effectively the same network stack. |

### 💡 The Golden Rule (Why the Pause Container is a Genius Design)

- **Without pause**: If Nginx crashes, the kernel destroys the network namespace. The IP is lost. When the container restarts, it gets a new IP. Any Service referencing the old IP breaks.
- **With pause**: If Nginx crashes, the **pause container is still running**. It holds the network namespace open. The IP stays assigned. When the container runtime restarts Nginx, the new container joins the *existing* namespace and gets the *exact same IP*.

Your notes describe exactly this architecture: The Runtime (`containerd`) starts the `Pause` container, which creates/holds the network namespace (doing a `sleep`), resulting in a list of namespaces you can check in `/var/run/netns`!
