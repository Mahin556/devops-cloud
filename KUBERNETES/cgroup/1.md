# Make a Kubernetes Pod Survive an OOM Event Without Restarting — Notes & Solution

## 1. Challenge Summary

You must deploy a multi-process container (`herder`) that aggressively consumes CPU and RAM, and make it survive OOM kills without the whole container restarting.

### Requirements
- Deploy a **Deployment** called `herder` in the `default` namespace.
- Replicas ≥ number of nodes in the cluster.
- Each Pod must run on its own node.
- No Pod may consume more than **250m CPU** and **256Mi RAM**.
- The Deployment must run for at least **60 seconds** without any Pod restart.

### Image
```text
ghcr.io/iximiuz/labs/resource-hog/herder:v1.0.0
```

---

## 2. Background: OOM Killer Behavior in Kubernetes

### Pre-Kubernetes 1.28
- When a container with multiple processes hit its memory limit, the Linux OOM killer often killed only **one** process.
- If that process was not PID 1, the container stayed alive.
- This led to “invisible” OOM kills and zombie Pods.

### Kubernetes 1.28+
- Kubernetes changed behavior to terminate the **entire container** if any process runs out of memory.
- This broke some workloads.
- Kubernetes 1.32 added `singleProcessOOMKill` kubelet flag, but it is **node-level only** — not per-workload.

### The Trick: `memory.oom.group`
- In cgroups v2, the file `memory.oom.group` controls OOM behavior.
- `1` = kill the entire cgroup (whole container).
- `0` = kill only the offending process.
- Kubernetes 1.28+ sets this to `1` by default for containers.
- To restore pre-1.28 behavior for specific workloads, write `0` to their `memory.oom.group` file.

---

## 3. Solution Strategy

1. **Deploy `herder`** with resource limits and anti-affinity so each Pod lands on its own node.
2. **Deploy a privileged DaemonSet** that runs on every node.
3. The DaemonSet mounts the host’s `/sys/fs/cgroup` and periodically writes `0` to the `memory.oom.group` file of each `herder` container’s cgroup.
4. As a result, when a subprocess in `herder` hits OOM, only that subprocess is killed. PID 1 survives, so the container and Pod do not restart.

## 4. Step 1 — Deploy the `herder` Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: herder
  namespace: default
spec:
  replicas: 3   # Replace with number of nodes in your cluster
  selector:
    matchLabels:
      app: herder
  template:
    metadata:
      labels:
        app: herder
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: herder
            topologyKey: kubernetes.io/hostname
      containers:
      - name: herder
        image: ghcr.io/iximiuz/labs/resource-hog/herder:v1.0.0
        resources:
          limits:
            cpu: 250m
            memory: 256Mi
          requests:
            cpu: 250m
            memory: 256Mi
```

Apply:
```bash
kubectl apply -f herder-deployment.yaml
```

Check:
```bash
kubectl get pods -o wide
```
Each Pod should be on a different node.

## 5. Step 2 — Deploy the Privileged DaemonSet

The DaemonSet writes `0` to `memory.oom.group` for `herder` containers.

### Option A — Simple (writes to all cgroups)
This is the quickest for a test cluster. It sets `memory.oom.group=0` for every cgroup it finds.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: oom-group-tweaker
  namespace: kube-system
spec:
  selector:
    matchLabels:
      name: oom-group-tweaker
  template:
    metadata:
      labels:
        name: oom-group-tweaker
    spec:
      hostPID: true
      containers:
      - name: tweaker
        image: alpine:3.20
        securityContext:
          privileged: true
        volumeMounts:
        - name: cgroup
          mountPath: /sys/fs/cgroup
          mountPropagation: HostToContainer
        command:
        - /bin/sh
        - -c
        - |
          while true; do
            find /sys/fs/cgroup -name memory.oom.group 2>/dev/null | while read f; do
              echo 0 > "$f" 2>/dev/null
            done
            sleep 1
          done
      volumes:
      - name: cgroup
        hostPath:
          path: /sys/fs/cgroup
          type: Directory
```

Apply:
```bash
kubectl apply -f oom-group-tweaker.yaml
```

### Option B — Targeted (only `herder` containers)
For production, you should target only `herder` cgroups. You can do this by:
- Mounting the container runtime socket (e.g., `/run/containerd/containerd.sock`).
- Using `crictl` or `ctr` to list containers and filter by name `herder`.
- Getting each container’s cgroup path from `crictl inspect <id>`.
- Writing `0` to that specific `memory.oom.group`.

Example script logic:
```bash
#!/bin/sh
while true; do
  for cid in $(crictl ps --name herder -q); do
    cgroup_path=$(crictl inspect "$cid" | jq -r '.info.runtimeSpec.linux.cgroupsPath')
    echo 0 > "/sys/fs/cgroup/${cgroup_path}/memory.oom.group"
  done
  sleep 1
done
```

You would need to install `crictl` and `jq` in the DaemonSet image, or use a custom image.

---

## 6. How It Works

- The DaemonSet runs on every node with `privileged: true` and `hostPID: true`.
- It mounts the host’s cgroup v2 filesystem at `/sys/fs/cgroup`.
- It finds the `memory.oom.group` file for the `herder` container’s cgroup.
- Writing `0` changes the OOM behavior for that cgroup:
  - When memory limit is hit, the kernel kills only the process that triggered OOM.
  - PID 1 of the container remains alive.
  - The container does not restart.
  - The Pod stays `Running`.

## 7. Verification

Watch Pods:
```bash
kubectl get pods -w
```

Check restarts:
```bash
kubectl get pods -o wide
```
Look at the `RESTARTS` column. It should stay `0`.

Check cgroup value inside the DaemonSet Pod:
```bash
kubectl exec -n kube-system <tweaker-pod> -- cat /sys/fs/cgroup/.../memory.oom.group
```
It should be `0`.

Run for at least 60 seconds. If no restarts occur, the challenge is passed.

---

## 8. Key Takeaways

- Kubernetes 1.28+ kills the whole container on OOM by default.
- `memory.oom.group=1` causes this behavior in cgroups v2.
- Writing `0` restores the old behavior: only the offending process is killed.
- A privileged DaemonSet can modify this per-workload without changing kubelet config.
- Use `podAntiAffinity` to spread `herder` Pods across nodes.
- Set resource limits to satisfy the challenge constraints.
- This technique works on Kubernetes 1.28–1.31 and beyond.
