Here is the complete English explanation of how to grant other users access to an Amazon EKS cluster, generate their `kubeconfig`, and the underlying authentication mechanism.

---

### 1. The Core Principle: AWS IAM + Kubernetes RBAC

Amazon EKS does not use standard Kubernetes static password files or simple ServiceAccount tokens for human users. Instead, it integrates deeply with **AWS IAM**. 

The process strictly follows two distinct steps:

1.  **Authentication (AWS IAM)**: Verifies *who* you are using your AWS credentials (Access Key / Secret Key / STS tokens).
2.  **Authorization (Kubernetes RBAC)**: Maps the authenticated AWS IAM entity (User/Role) to a Kubernetes `User` or `Group`, and then checks RBAC rules (`Roles`, `ClusterRoles`, `Bindings`) to decide *what* you are allowed to do.

---

### 2. How Authentication Actually Works (Step-by-Step)

When you run `kubectl get pods` against an EKS cluster, here is exactly what happens under the hood:

| Step | Actor | Action |
| :--- | :--- | :--- |
| **1** | **`kubectl` / AWS CLI** | The AWS SDK signs the API request using **AWS Signature Version 4** (via your credentials in `~/.aws/credentials` or IAM instance profile). |
| **2** | **EKS API Server** | The API server receives the request and calls the AWS IAM service to validate the signature and extract the caller's identity (e.g., `arn:aws:iam::1234567890:user/dev-user`). |
| **3** | **Authentication Plugin** | The API server uses the IAM Authenticator to map this IAM ARN to a Kubernetes username and groups. |
| **4** | **Kubernetes RBAC** | The API server checks the RBAC policies. If the mapped user/group is bound to a `ClusterRole` with `get` permissions on `pods`, the request succeeds. Otherwise, it returns a `403 Forbidden`. |

---

### 3. How to Grant Access to Other IAM Users

AWS officially recommends the new **Access Entries** API over the older `aws-auth` ConfigMap.

#### Option A: Using EKS Access Entries (Recommended)

Access Entries are the modern, AWS-native way to grant cluster access. They completely replace the `aws-auth` ConfigMap.

**Step 1: Ensure the IAM user has the `eks:DescribeCluster` permission.**
**Step 2: Create an Access Entry for the IAM principal:**

```bash
aws eks create-access-entry \
    --cluster-name my-cluster \
    --principal-arn arn:aws:iam::111122223333:user/dev-user
```

**Step 3: Attach a pre-defined EKS Access Policy to grant admin permissions:**

```bash
aws eks associate-access-policy \
    --cluster-name my-cluster \
    --principal-arn arn:aws:iam::111122223333:user/dev-user \
    --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
    --access-scope type=cluster
```

*(Note: You can also use granular Kubernetes RBAC instead of these pre-defined policies if you prefer standard `RoleBindings`.)*

---

#### Option B: Using the Legacy `aws-auth` ConfigMap (Deprecated)

If you are using an older cluster, you must map IAM ARNs to Kubernetes groups via a ConfigMap.

**Step 1: Edit the `aws-auth` ConfigMap in the `kube-system` namespace:**

```bash
kubectl edit -n kube-system configmap/aws-auth
```

**Step 2: Add the IAM User ARN to the `mapUsers` section:**

```yaml
data:
  mapUsers: |
    - userarn: arn:aws:iam::111122223333:user/dev-user
      username: dev-user
      groups:
        - view-only-group
```

**Step 3: Bind that group to a Kubernetes ClusterRole** (e.g., the `view` ClusterRole):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: dev-view-binding
subjects:
- kind: Group
  name: view-only-group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io
```

### 4. How to Generate the `kubeconfig` for the New User

Once the user is authorized in the cluster, they need a `kubeconfig` to use `kubectl`. They **do not** receive a static client certificate or token.

Instead, they generate a config file that uses the **AWS CLI plugin** to fetch temporary tokens dynamically.

**Step 1: The user must configure their AWS CLI credentials:**
```bash
aws configure
# (Enter their Access Key, Secret Key, and Region)
```

**Step 2: Generate the kubeconfig using the EKS CLI:**
```bash
aws eks update-kubeconfig --region us-east-1 --name my-cluster
```

**How this works internally**:
- This command calls the EKS API to retrieve the cluster's certificate authority (CA) and endpoint.
- It writes a `kubeconfig` file (usually to `~/.kube/config`) that contains an **`exec` plugin**.
- The `exec` plugin does not store a static token. Instead, every time `kubectl` runs, it executes the AWS CLI (`aws eks get-token`) to generate a fresh, short-lived authentication token valid for 15 minutes.

**Example `kubeconfig` snippet generated by this command:**
```yaml
users:
- name: arn:aws:eks:us-east-1:1234567890:cluster/my-cluster
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: aws
      args:
      - eks
      - get-token
      - --cluster-name
      - my-cluster
      # This generates a fresh token every time.
```

### 5. Quick Summary Table

| Aspect | Details |
| :--- | :--- |
| **Authentication Method** | AWS Signature V4 (no static passwords or long-lived client certs for users). |
| **Mapping IAM to K8s** | **Recommended**: EKS Access Entries.<br>**Legacy**: `aws-auth` ConfigMap. |
| **Kubernetes Auth** | RBAC (Roles, ClusterRoles, Bindings) applied to mapped usernames/groups. |
| **User's Kubeconfig** | `aws eks update-kubeconfig` generates a config with an `exec` plugin. |
| **Token Lifespan** | 15 minutes (auto-refreshed by the `aws` executable plugin). |
| **IAM Minimum Permissions** | The user needs `eks:DescribeCluster` to run `update-kubeconfig`. |

---

### 💡 The Golden Rule

- You **cannot** simply edit a user's `kubeconfig` and give them a token for EKS. **The user must have AWS IAM credentials configured locally.**
- The EKS API Server **never** stores user passwords. It relies entirely on IAM for authentication, and on Kubernetes RBAC (via Access Entries or the `aws-auth` ConfigMap) for authorization.
