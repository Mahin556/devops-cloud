### 2. The Exact Request Flow (From Your Second Image)

Here is the exact, non-negotiable order that every `kubectl apply` request goes through:

**1. Authentication & Authorization (The "A A" in your notes)**
- **Authentication**: Verifies the client's credentials (X509 cert, token, OIDC). Maps to a `username`.
- **Authorization**: Checks RBAC. Does this user have `create` permissions on `pods` in this namespace?

**2. Mutating Admission Phase**
- This is the **first opportunity** to modify the incoming JSON/YAML object.
- **Built-in controllers** (like `LimitRanger`, `DefaultStorageClass`, `TaintNodesByCondition`) run first. This is where `LimitRanges` are applied. If your Pod lacks CPU/Memory limits, `LimitRanger` **injects** them here.
- **MutatingAdmissionWebhooks** run next (e.g., Service Mesh injectors like Istio or Linkerd that add a sidecar container to your Pod).

**3. Schema Validation**
- **Crucial note from your snippet**: *"Schema Validation"* happens **after** Mutation but **before** Validation.
- The API Server checks if the now-mutated object strictly adheres to the OpenAPI v3 schema for that resource. For example: "Does the Pod spec have a required `containers` field? Are the resource fields properly formatted?"
- *Why after Mutation?* Because the mutating webhook might have fixed a missing field. Schema validation runs on the **final** version of the object.

**4. Validating Admission Phase**
- This checks the **final, mutated, schema-validated** object against cluster policies.
- **Built-in controllers** (like `ResourceQuota`, `PodSecurity`, `PodNodeSelector`) run. This is where `ResourceQuota` checks the namespace's total usage. If the new Pod pushes the total CPU/RAM over the quota, the request is **rejected** here.
- **ValidatingAdmissionWebhooks** run next (e.g., checking that your container image doesn't come from an untrusted registry).

**5. Persistent Storage (etcd)**
- If all the above pass, the object is written to `etcd`. The API returns a `201 Created` or `200 OK` response to the client.

### 4. The Critical Takeaway (Why the Order Matters)

| If the order were different... | Why the current order is correct |
| :--- | :--- |
| Schema Validation before Mutation | The API server would reject a Pod because it lacks a `sidecar` container, but the Mutating Webhook was supposed to inject it. |
| Validation before Schema Validation | `ResourceQuota` might check the un-mutated Pod (missing limits) and reject it, even though `LimitRanger` was going to add the limits automatically. |

**The Golden Rule**: **Mutation fixes the object first**, then **Schema validates the fixed object**, and finally **Validation checks the fixed object's compliance**. This ensures that default-injection (like `LimitRanger`) works seamlessly with enforcement policies (like `ResourceQuota`) without false rejections.
