## PART 1 — The Application

### What Was Built
A full-stack Python Flask application connected to a PostgreSQL database, deployed on Kubernetes with:
- HTTPS via cert-manager + Let's Encrypt
- NGINX Ingress Controller
- CloudNative PostgreSQL Operator
- GitHub Actions CI pipeline
- ArgoCD CD pipeline
- Horizontal Pod Autoscaler
- Load testing with k6

### Application Structure
```
app/
├── app.py              ← Flask application (main logic)
└── templates/
    └── index.html      ← HTML template (frontend)
```

### What app.py Does
```python
# Connects to PostgreSQL using environment variables:
DB_USERNAME = os.getenv("DB_USERNAME")
DB_PASSWORD = os.getenv("DB_PASSWORD")
DB_HOST     = os.getenv("DB_HOST")
DB_PORT     = os.getenv("DB_PORT")
DB_NAME     = os.getenv("DB_NAME")

# Three routes:
# GET  /         → SELECT * FROM goals → render index.html with goals list
# POST /add-goal → INSERT INTO goals (name) VALUES (...)
# POST /remove-goal → DELETE FROM goals WHERE id = ...
# GET  /health   → returns "OK" (used for readiness probe)
```

### index.html Features
- List goals from database
- Add goal form (on submit)
- Remove goal (delete button)
- Simple HTML + CSS + JavaScript

## PART 2 — Dockerfile

```dockerfile
# Slim Python base image (distroless/chainguard also preferred in prod)
FROM python:3.11-slim

WORKDIR /app

# Copy requirements first (layer caching optimization)
COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

EXPOSE 8080

# Gunicorn WSGI server (not Flask dev server) on port 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "app:app"]
```

### Build Command (Mac M1/M2 — arm64)
```bash
# --platform forces amd64 build on Mac (for cloud deployment)
docker build --platform linux/amd64 -t kubesimplify/my-app:latest .
docker push kubesimplify/my-app:latest
```

### Why requirements.txt is copied first:
If you copy all source first then install, every code change invalidates the pip install layer.
Copying requirements.txt first means pip install is cached unless dependencies change.

## PART 3 — Kubernetes Secret (DB Credentials)

```bash
# Create a generic secret with username and password
kubectl create secret generic my-postgres-credentials \
  --from-literal=password=newpassword \
  --from-literal=username=goalsuser
```

**Why secrets and not hardcoding:**
- Secrets are not visible in deployment YAML
- Can be rotated without redeploying the application
- Different values per environment (dev/staging/prod)

**Important:** Kubernetes secrets are only base64 encoded, NOT encrypted at rest by default.
To see the actual value:
```bash
kubectl get secret my-postgres-credentials -o yaml
# Decode:
echo "base64value" | base64 -d
```

## PART 4 — Deployment YAML (Complete)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: kubesimplify/my-app:latest
          imagePullPolicy: Always

          # Environment variables from Secret and ConfigMap:
          env:
            - name: DB_USERNAME
              valueFrom:
                secretKeyRef:
                  name: my-postgres-credentials
                  key: username

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: my-postgres-credentials
                  key: password

            - name: DB_HOST
              value: "my-postgres-rw.default.svc.cluster.local"
              # ↑ this comes from the Service created by CloudNative PG

            - name: DB_PORT
              value: "5432"

            - name: DB_NAME
              value: "goals"

          # Readiness probe — uses /health endpoint from the app
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5

          # Liveness probe — restart pod if app becomes unhealthy
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10

          ports:
            - containerPort: 8080
```

### Why readiness probe is important:
Without readiness probe: pod is added to Service endpoints the moment it starts
even if the app isn't ready → requests fail during startup.
With readiness probe: 0/1 READY shown until /health returns 200,
only then added to Service endpoints → zero downtime.

### DB_HOST explanation:
```
my-postgres-rw.default.svc.cluster.local
    ↑ service name   ↑ namespace   ↑ k8s DNS suffix
```
CNPG creates two services automatically:
- `my-postgres-rw` → read-write (primary only) ← use this for app writes
- `my-postgres-r`  → read-only (replicas)      ← use for read-heavy queries

## PART 5 — CloudNative PostgreSQL (CNPG) Operator

### Why NOT use plain StatefulSet for PostgreSQL:
- StatefulSet is the "old school" approach
- Kubernetes is almost 10 years old — the ecosystem has evolved
- CNPG handles HA, failover, backups, TLS, monitoring automatically
- StatefulSet requires you to implement all this yourself

### What is the Operator Pattern:
```
Normal Kubernetes objects:
  kind: Deployment    → built-in controller manages this
  kind: StatefulSet   → built-in controller manages this

CRD + Operator:
  kind: Cluster       → CNPG's custom controller manages this
  (apiVersion: postgresql.cnpg.io/v1)

The operator:
  - Watches for Cluster resources
  - Creates/manages Pods for PostgreSQL
  - Handles primary election
  - Handles failover
  - Creates PVCs automatically
  - Monitors health
  - Manages backups
```

### Install CNPG Operator:
```bash
# From CNPG documentation (installs CRDs + controller)
kubectl apply -f https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.22/releases/cnpg-1.22.0.yaml
```

### Check CRDs installed:
```bash
kubectl get crd | grep cluster
# Now you can create: clusters.postgresql.cnpg.io
# Also: backups, imagecatalogs, scheduledbackups, etc.
```

### Create PostgreSQL Cluster:
```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: my-postgres
  namespace: default
spec:
  instances: 3             # primary + 2 replicas
  storage:
    size: 1Gi

  bootstrap:
    initdb:
      database: goals       # database name
      owner: goalsuser      # user
      secret:
        name: my-postgres-credentials  # references our secret
```

```bash
kubectl apply -f postgres-cluster.yaml

# Watch pods start (StatefulSet-like behavior but custom controller):
kubectl get pods -w
# my-postgres-1   Running  ← primary
# my-postgres-2   Running  ← replica
# my-postgres-3   Running  ← replica
```

### Check which is primary:
```bash
kubectl get cluster my-postgres
# Shows: INSTANCES=3, PRIMARY=my-postgres-1
```

### Access PostgreSQL and create table:
```bash
# Port forward to primary pod:
kubectl port-forward pod/my-postgres-1 5432:5432

# Connect (in another terminal):
PGPASSWORD=newpassword psql -h localhost -U goalsuser -d goals

# Create the table:
CREATE TABLE goals (
  id   SERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL
);
```

### CNPG auto-created PVCs:
```bash
kubectl get pvc
# data-my-postgres-1   Bound
# data-my-postgres-2   Bound
# data-my-postgres-3   Bound
# PVC per pod — operator creates these automatically
```

## PART 6 — ClusterIP Service for the Application

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  type: ClusterIP       # internal only — Ingress will handle external access
  selector:
    app: my-app
  ports:
    - port: 80          # service port
      targetPort: 8080  # container port (our gunicorn port)
```

**Why ClusterIP and not LoadBalancer?**
- LoadBalancer creates a cloud LB per service = expensive
- Ingress handles all external routing from ONE load balancer
- ClusterIP is for service-to-service communication inside the cluster

## PART 8 — cert-manager (Automatic TLS Certificates)

### Install:
```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.14.3/cert-manager.yaml
```

### What cert-manager installs (as CRDs):
```bash
kubectl get crd | grep cert-manager
# certificates.cert-manager.io
# clusterissuers.cert-manager.io
# challenges.acme.cert-manager.io
# etc.
```

### Step 1: Create ClusterIssuer (Let's Encrypt):
```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx   # uses NGINX Ingress to solve challenge
```

```bash
kubectl apply -f cluster-issuer.yaml
kubectl get clusterissuer
# letsencrypt-prod   True   ← Ready
```

### Step 2: Request Certificate:
```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-app-cert
spec:
  secretName: my-app-tls         # where the cert will be stored as a Secret
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  commonName: demo.kubesimplify.com
  dnsNames:
    - demo.kubesimplify.com
```

```bash
kubectl apply -f certificate.yaml

# Watch certificate status:
kubectl get certificate
# NAME          READY   AGE
# my-app-cert   True    2m    ← True = certificate issued successfully

# If False, debug:
kubectl describe certificate my-app-cert   # check Events
kubectl get challenges                     # ACME challenge status
kubectl get clusterissuer letsencrypt-prod -o yaml  # issuer status
```

### How ACME HTTP-01 Challenge Works:
```
cert-manager → requests cert from Let's Encrypt
Let's Encrypt → "prove you own the domain"
cert-manager → creates a temporary Ingress path:
  /.well-known/acme-challenge/TOKEN → returns proof
Let's Encrypt → verifies → issues certificate
cert-manager → stores cert in Secret: my-app-tls
```

## PART 9 — DNS Setup (A Record)

### Why DNS is needed for Ingress:
```
# Ingress routes by HOSTNAME, not IP
# So http://51.x.x.x won't match — you need a domain name

# Options:
1. Own domain (prod): buy domain → set A record
2. No domain (dev/demo): use nip.io wildcard
   example: 51.8.xx.xx.nip.io → resolves to 51.8.xx.xx
   nip.io ping works ~50% of time depending on demand
```

### Set A Record:
```
Domain: demo.kubesimplify.com
Type: A
Value: <Ingress Controller External IP>  ← from kubectl get svc -n ingress-nginx

# Verify DNS propagated:
ping demo.kubesimplify.com
# Should resolve to your Ingress IP
```

## PART 11 — Horizontal Pod Autoscaler (HPA)

### Three types of autoscalers in Kubernetes:
```
1. HPA  (Horizontal Pod Autoscaler)  → scales pod COUNT up/down
2. VPA  (Vertical Pod Autoscaler)    → scales pod CPU/memory up/down (same pod count)
3. CA   (Cluster Autoscaler)         → scales NODE count (cloud-provider specific)
```

### HPA requires Metrics Server:
```bash
# Metrics server may come pre-installed (AKS/EKS) or needs manual install:
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Verify:
kubectl top pods
kubectl top nodes
# If these work, metrics server is running
```

### Create HPA:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 20   # scale up when avg CPU > 20%
```

```bash
kubectl apply -f hpa.yaml
kubectl get hpa
```

### How HPA scaling works:
```
Monitor: every 15 seconds checks average CPU across all pods
If avg CPU > 20%:  → increase replicas (scale OUT)
If avg CPU < 20%:  → decrease replicas (scale IN, slowly)
Never goes below minReplicas (1)
Never goes above maxReplicas (10)
```

## PART 14 — GitOps Concept

### Traditional CI/CD problem:
```
Developer → pushes code → Jenkins/GitHub Actions runs
→ kubectl apply → deploys to cluster

Problems:
1. kubectl credentials must be stored in CI
2. If admin manually runs `kubectl edit` → nobody knows
3. Cluster state drifts from what's in Git
4. No automatic rollback if cluster is manually changed
```

### GitOps solution:
```
Git = Single Source of Truth

No one kubectl applies directly to cluster
Instead:
  Developer → pushes to Git → PR reviewed → merged
  ArgoCD watches the Git repo
  ArgoCD automatically syncs cluster to match Git
  If someone manually changes cluster → ArgoCD reverts it back
```

### GitOps principles:
```
1. Declarative: all desired state in Git (YAML files)
2. Versioned: Git history = audit trail of every change
3. Pulled: ArgoCD PULLS from Git (not pushed to)
4. Continuous: ArgoCD continuously reconciles actual vs desired
```

## PART 15 — GitHub Actions CI Pipeline

### Directory structure:
```
repo/
├── .github/
│   └── workflows/
│       └── build-push.yml   ← GitHub Actions workflow file
├── app/
│   └── app.py
│   └── requirements.txt
│   └── Dockerfile
├── k8s/
│   └── deployment/
│       └── deployment.yaml  ← auto-updated by CI with new image tag
└── tmpl/
    └── deployment.j2        ← Jinja2 template for deployment.yaml
```

### Complete CI Workflow File:
```yaml
# .github/workflows/build-push.yml
name: Build and Push Docker Image

on:
  push:
    # Skip CI commits made by this workflow itself (prevent infinite loop)
    # Uses "if" condition with [skip ci] in commit message

jobs:
  release-docker:
    runs-on: ubuntu-24.04
    # Skip if commit message contains [skip ci] (our own auto-commits)
    if: "!contains(github.event.head_commit.message, '[skip ci]')"

    steps:
      # Step 1: Checkout code
      - name: Checkout
        uses: actions/checkout@v4

      # Step 2: Login to Docker Hub
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      # Step 3: Get short SHA (7 characters)
      - name: Generate short SHA
        id: vars
        run: |
          echo "sha_short=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT

      # Step 4: Build and push image tagged with short SHA
      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: ./app           # where Dockerfile is
          push: true
          tags: kubesimplify/my-app:${{ steps.vars.outputs.sha_short }}

      # Step 5: Render Jinja2 template to deployment.yaml with new image tag
      - name: Render deployment manifest
        uses: cuchi/jinja2-action@v1.2.2
        with:
          template: tmpl/deployment.j2
          output_file: k8s/deployment/deployment.yaml
          variables: |
            image_deploy_tag=${{ steps.vars.outputs.sha_short }}

      # Step 6: Commit and push updated deployment.yaml to repo
      - name: Commit and push deployment manifest
        uses: stefanzweifel/git-auto-commit-action@v4
        with:
          commit_message: "[skip ci] update deployment image to ${{ steps.vars.outputs.sha_short }}"
          file_pattern: k8s/deployment/deployment.yaml
```

### GitHub Secrets needed:
```
Settings → Secrets and variables → Actions → New repository secret:
  DOCKER_USERNAME = your-dockerhub-username
  DOCKER_PASSWORD = your-dockerhub-password
```

### Jinja2 Template (deployment.j2):
```yaml
# tmpl/deployment.j2 — same as deployment.yaml but with template variable
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    spec:
      containers:
        - name: my-app
          image: kubesimplify/my-app:{{ image_deploy_tag }}  # ← TEMPLATE VARIABLE
          # ... rest of deployment spec
```

### Why Jinja2 template:
```
deployment.yaml contains the actual running spec
deployment.j2 is the template that generates it

CI pipeline:
1. Builds image → gets SHA: abc123
2. Renders j2 template with image_deploy_tag=abc123
3. Outputs deployment.yaml with image: kubesimplify/my-app:abc123
4. Commits that file to Git
5. ArgoCD sees the Git change → deploys new image
```

### The [skip ci] trick:
```
When CI pipeline commits the updated deployment.yaml → that commit triggers CI again
→ infinite loop!

Fix: add "[skip ci]" to commit message
GitHub Actions condition: if: "!contains(github.event.head_commit.message, '[skip ci]')"
→ skips the workflow for auto-generated commits
```

### Create ArgoCD Application (via UI):
```
+ New App:
  Application Name: kubesimplify
  Project: default
  Sync Policy:
    ✅ Automated
    ✅ Prune Resources   (delete resources removed from Git)
    ✅ Self Heal         (revert manual kubectl changes)
    ✅ Auto-create Namespace

Repository URL: https://github.com/your-org/your-repo
Revision: main (branch)
Path: k8s/deployment  (folder ArgoCD watches)

Cluster URL: https://kubernetes.default.svc  (same cluster)
Namespace: default
```

### ArgoCD Application via YAML:
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: kubesimplify
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/your-repo
    targetRevision: HEAD
    path: k8s/deployment
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

### How ArgoCD works:
```
ArgoCD polls Git repo every 3 minutes (or webhook triggers immediate sync)
                    │
                    ↓
         Compares Git state vs Cluster state
                    │
          ┌─────────┴─────────┐
          │                   │
       In Sync            Out of Sync
          │                   │
       Do nothing         Auto-sync:
                          apply changes from Git
                          delete resources not in Git (prune)
                          revert manual changes (selfHeal)
```

### ArgoCD Sync Actions:
```bash
# Sync manually:
argocd app sync kubesimplify

# Rollback to previous version:
argocd app rollback kubesimplify

# Force sync (force replace):
argocd app sync kubesimplify --force

# From UI: click Sync button → shows diff before applying
```

### Self-Heal Demo:
```bash
# Delete deployment manually:
kubectl delete deployment my-app

# ArgoCD detects: cluster no longer matches Git
# ArgoCD auto-recreates the deployment within ~3 minutes
# This proves Git is the source of truth
```

## PART 17 — Complete End-to-End Flow (GitOps)

```
Developer makes code change
         │
         ▼
git commit + git push (to main branch)
         │
         ▼
GitHub Actions triggered:
  1. Checkout code
  2. docker build → docker push with :sha123 tag
  3. Render deployment.j2 → deployment.yaml with image:sha123
  4. git commit deployment.yaml with "[skip ci]"
  5. git push → deployment.yaml updated in repo
         │
         ▼
ArgoCD detects change in k8s/deployment folder
         │
         ▼
ArgoCD applies new deployment.yaml to cluster
         │
         ▼
Kubernetes rolling update:
  - New pod starts with image:sha123
  - Readiness probe checked
  - Old pod terminated after new pod is Ready
         │
         ▼
Application live with new code
Total time: ~2-3 minutes from git push to live
```

## PART 18 — Operator Pattern (Deeper Explanation)

### What is a Custom Resource Definition (CRD):
```yaml
# Normal Kubernetes lets you create:
kind: Deployment
kind: Service
kind: Pod

# CRDs let you add NEW resource types:
kind: Cluster          (CNPG added this)
kind: Certificate      (cert-manager added this)
kind: ClusterIssuer    (cert-manager added this)
kind: Application      (ArgoCD added this)

# You can even do:
kind: MySQLCluster
kind: KafkaCluster
kind: YourCustomThing
```

### CRD check commands:
```bash
# Before installing CNPG:
kubectl get crd | grep cluster
# (nothing)

# After installing CNPG:
kubectl get crd | grep cluster
# clusters.postgresql.cnpg.io   ← now exists
```

### The Controller Pattern:
```
Every Kubernetes resource has a controller:
  Deployment → Deployment Controller
  StatefulSet → StatefulSet Controller
  ReplicaSet → ReplicaSet Controller

Custom resources also have controllers (called Operators):
  Cluster (CNPG) → CNPG Controller
  Application (ArgoCD) → ArgoCD Application Controller
  Certificate → cert-manager Controller

Controllers watch for their resource type
and continuously reconcile actual state → desired state
```

## PART 19 — ApplicationSet (Multi-Cluster Deployment)

### What is ApplicationSet:
Instead of creating one ArgoCD Application manually,
ApplicationSet automatically creates Applications for:
- Multiple clusters
- Multiple environments (dev/staging/prod)
- Multiple namespaces

### Use case: deploy to all connected clusters:
```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook
  namespace: argocd
spec:
  generators:
    - clusters: {}  # generate for all clusters connected to ArgoCD
  template:
    metadata:
      name: '{{name}}-guestbook'   # one App per cluster
    spec:
      project: default
      source:
        repoURL: https://github.com/org/repo
        targetRevision: HEAD
        path: k8s/
      destination:
        server: '{{server}}'   # each cluster's URL
        namespace: guestbook
```

## PART 20 — ArgoCD Image Updater

### Problem with our approach:
Our approach: CI updates deployment.yaml in Git → ArgoCD picks it up.
This works but:
- Requires Jinja2 template
- Requires git-auto-commit action
- More complex CI pipeline

### ArgoCD Image Updater approach:
```
ArgoCD Image Updater:
  - Watches Docker registry
  - When new image is pushed, automatically updates the Application
  - No need to touch Git / Jinja2 / auto-commit
  - More native, less moving parts
```

### Install (from ArgoCD Labs):
```bash
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj-labs/argocd-image-updater/stable/manifests/install.yaml
```

This is part of the ArgoCD ecosystem (argoproj-labs), not core ArgoCD.
Also from the same ecosystem:
- argocd-vault-plugin — pull secrets from HashiCorp Vault
- argocd-rollouts — canary/blue-green deployments

## PART 23 — Key Learnings and Best Practices from Session

```
1. Always use readiness probe → zero traffic to unready pods
2. Always use gunicorn (not Flask dev server) in production
3. Use imagePullPolicy: Always for latest/sha tags
4. Never hardcode DB credentials → use Secrets
5. Use CloudNative PostgreSQL over bare StatefulSet
6. One Ingress Controller → many services (not one LB per service)
7. cert-manager automates TLS → never manually manage certificates
8. GitOps: Git is single source of truth, not kubectl
9. [skip ci] in commit message prevents CI infinite loops
10. ArgoCD selfHeal: cluster always matches Git, manual changes reverted
11. HPA minReplicas=1, maxReplicas=10, watch it scale under k6 load
12. Port forwarding is for local testing only, never production
13. CRDs extend Kubernetes — operators handle complex stateful apps
14. ApplicationSet = deploy to multiple clusters from one ArgoCD config
```
