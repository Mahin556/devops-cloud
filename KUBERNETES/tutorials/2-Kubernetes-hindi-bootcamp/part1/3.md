Let's get **hands-on**! The best way to understand container layering is to stop reading theory and actually break it with your terminal. 

Below is a **step-by-step lab** you can run on any machine with Docker installed (Linux, Mac, or WSL2). 

---

### 🛠 Prerequisite
Make sure Docker is installed. Open your terminal and run these commands in order.

---

### Lab 1: Visualize the Layer Stack (`docker history`)
Every image is a stack of layers. Let's see the exact blueprint of a simple Nginx image.

```bash
docker pull nginx:alpine
docker history nginx:alpine
```
**Observe**: You'll see a list of lines. Each line is a **read-only layer** (e.g., `RUN apk update`, `COPY default.conf`). Notice the "CREATED BY" column—these are the exact Dockerfile commands that created each layer. The top layer is the smallest (usually the entrypoint), and the bottom base layer is the largest.

---

### Lab 2: Run Two Containers from the Same Shared Store
Let's prove that the "shared store" saves disk space.

```bash
# Run two containers in the background
docker run -d --name web1 nginx:alpine
docker run -d --name web2 nginx:alpine

# Check how much space they use together
docker system df
```
**Observe**: Look at the "IMAGES" and "CONTAINERS" rows. Even though you have 2 containers running, they both reuse the *exact same* read-only image layers. Only the tiny "white layers" (writable layers) are unique to each container.

---

### Lab 3: Trigger the Copy-on-Write (CoW) Mechanism
Now, let's modify a file inside `web1` to force a **copy-up** into its private "white layer".

First, check the current difference (should be empty):
```bash
docker diff web1
```
*(No output means the container is purely reading from the shared image layers.)*

Now, create a new file inside `web1`:
```bash
docker exec web1 touch /tmp/my-new-file.txt
docker exec web1 bash -c "echo 'Hello Layering' > /tmp/my-new-file.txt"
```

Now, check the differences again:
```bash
docker diff web1
```
**Observe**: You should see an `A` (Added) next to `/tmp/my-new-file.txt`. This file **only exists** in `web1`'s private writable layer (the "white layer"). If you run `docker diff web2`, it will still be empty because `web2` hasn't modified anything.

---

### Lab 4: Understand "Whiteout" Files (Deleting from base)
This is the trickiest part. Let's delete a file that exists in the **read-only base image**.

```bash
# Try to delete the default nginx index.html that came with the base layer
docker exec web1 rm -f /usr/share/nginx/html/index.html

# Check the differences
docker diff web1
```
**Observe**: You will see a `D` (Deleted) next to `/usr/share/nginx/html/index.html`. But physically, the file *still exists* in the read-only shared store! The "white layer" of `web1` now holds a special **"whiteout marker"** (named `index.html.wh.`) that tells the Union File System: *"Hide this file from the lower layers when rendering the unified view."*

---

### Lab 5: Prove Containers Are Completely Isolated
Let's check if `web2` was affected by `web1`'s deletions.

```bash
# List the files inside web2's html folder
docker exec web2 ls /usr/share/nginx/html/
```
**Observe**: You will see the `index.html` file is perfectly intact! Because `web2` has its *own* private white layer, it completely ignores the whiteout markers and modifications happening inside `web1`.

---

### Lab 6 (Bonus): Peek Inside the Physical "White Layer"
Let's actually locate where Docker stores the writable "white layer" for `web1` on your hard drive.

```bash
# Get the full path to web1's writable layer (UpperDir)
docker inspect web1 | grep UpperDir
```
It will output a path like: `/var/lib/docker/overlay2/abcd1234/diff`.
Now, navigate there (you might need `sudo` on Linux):
```bash
# Replace the path with the one from your inspect output
sudo ls -la /var/lib/docker/overlay2/abcd1234/diff/
```
**Observe**: 
1. You will see your `my-new-file.txt` sitting there physically.
2. If you go into the `usr/share/nginx/html/` folder inside this path, you will NOT see the original `index.html`. But you *might* see a hidden file starting with `.wh.` (whiteout) that hides it.

---

### Summary of What You Just Proved

| Your Action | What happened technically |
| :--- | :--- |
| Ran `web1` & `web2` | Both used the **same shared store** of read-only layers. |
| Created `/tmp/my-new-file.txt` in `web1` | Triggered **Copy-on-Write**? No! Creating a completely new file writes *directly* to the **white layer**. |
| Deleted `index.html` in `web1` | Created a **Whiteout marker** (`.wh.index.html`) in `web1`'s white layer. |
| Checked `web2` | Proved that each container's **white layer** is private and isolated. |
| Disk usage | Saved massive space because 99% of the OS is shared, not duplicated. |

### 🧪 Challenge Practice for You
To fully cement this, try these on your own:

1. Run `docker exec web1 apt-get update` (if it's Debian-based) or `apk add vim` (for Alpine). Run `docker diff web1` afterward. You'll see hundreds of `A` (added) lines—these are all the new packages written *exclusively* to `web1`'s white layer. 
2. Stop and delete `web1` (`docker rm -f web1`). Docker will delete its white layer from disk. Notice how the `nginx:alpine` image remains untouched in the shared store, ready for the next container instantly.
