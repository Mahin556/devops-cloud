## What's Correct

The Ingress-Nginx Controller does not use Services to route traffic to the pods. Instead it uses the Endpoints API in order to bypass kube-proxy to allow NGINX features like session affinity and custom load balancing algorithms.

ingress-nginx refers to the Service resource to find backends, but in the actual routing configuration, it writes the raw Pod IPs obtained from EndpointSlice, not the Service ClusterIP. This avoids iptables DNAT overhead and allows it to control L7 features like Session Affinity itself.

So the original answer is right for NGINX, Traefik, HAProxy, and Envoy-based controllers — all of which run as a proxy inside the cluster and route directly to pod IPs.

## What's Wrong — AWS ALB Controller is the opposite

AWS ALB Ingress Controller (now called AWS Load Balancer Controller) provisions and manages Application Load Balancers directly from Ingress resources. Instead of running a proxy inside your cluster, the controller makes AWS API calls to create an ALB in your VPC. The controller operates in two modes: instance mode and IP mode. Instance mode registers EKS worker nodes as ALB targets and relies on kube-proxy to forward traffic from NodePort to Pods, adding an extra network hop.

So the correct picture split by controller type:

## Corrected Architecture

**NGINX / Traefik / HAProxy / Envoy (in-cluster proxy):**
```
Client → LB → Ingress Controller pod
                    │
                    │ reads EndpointSlice API → gets pod IPs directly
                    │ builds its own upstream pool
                    ▼
                  Pod IP   ← kube-proxy NOT involved in data path
```

**AWS ALB Controller, instance mode (external LB):**
```
Client → ALB (outside cluster) → Node:NodePort
                                        │
                                   kube-proxy iptables DNAT
                                        │
                                      Pod   ← kube-proxy IS involved
```

**AWS ALB Controller, IP mode (external LB, target group = pod IPs):**
```
Client → ALB → Pod IP directly   ← kube-proxy also NOT involved
               (ALB knows pod IPs from ENI/VPC networking)
```

## The Precise Accurate Statement for an Interview

> For in-cluster proxy-based Ingress controllers (NGINX, Traefik, HAProxy, Envoy): the controller watches the **EndpointSlice API** to get pod IPs directly, writes those IPs into its own proxy config, and forwards traffic to pods without going through kube-proxy or the Service ClusterIP. The Service is used only for **discovery** (which pods belong to which backend) — not for actual traffic routing.
>
> For external cloud-native controllers like the AWS ALB Controller in **instance mode**, kube-proxy IS still in the path because the ALB targets nodes at a NodePort, and kube-proxy then routes to the pod.
>
> The Service resource is **never unnecessary** — even when bypassing kube-proxy, the controller uses the Service's label selector to trace which EndpointSlice to watch.

## The One Additional Nuance Worth Knowing

Q: If bypassing ClusterIP, is the Service resource unnecessary? A: No, it is absolutely necessary. When Ingress sends packets, it doesn't pass through the ClusterIP itself, but the Service is used for Target Discovery (identifying which Pods to send to). The Ingress controller looks at the Service resource to check the label selector, and from there traces the EndpointSlice to find Pod IPs.

So the interview answer your original had — "Service IP is used only for pod discovery, not for traffic routing" — is almost right, but even more precisely: **the Service object is used for discovery, not even the Service IP** — the controller reads the label selector from the Service spec, then independently queries EndpointSlice for the matching pod IPs.
