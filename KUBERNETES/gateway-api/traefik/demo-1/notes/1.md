# Complete Guide to Kubernetes Gateway API

## Introduction to Gateway API

Gateway API is a **family of APIs** for Kubernetes that makes network services available through **extensible, role-oriented, protocol-aware configuration mechanisms**. It represents the next evolution from Ingress, offering more advanced traffic routing capabilities with a modular, role-based approach.

### Why Gateway API Exists

Gateway API was created to solve several challenges that the traditional Ingress API faced:

| Challenge | How Gateway API Solves It |
|-----------|---------------------------|
| **Single-point definition** | Ingress defines everything in one rule; Gateway API uses modular, separate objects |
| **Vendor lock-in** | Portable specification works across different controllers |
| **Limited expressiveness** | More expressive traffic routing rules |
| **Poor role separation** | Role-oriented resource model separates concerns |
| **Limited extensibility** | Extensible design supports future features |

## Core Architecture and Resource Model

Gateway API introduces a **three-tier resource model** that aligns with organizational roles:

```
┌─────────────────────────────────────────────────────────────┐
│                    GatewayClass                             │
│         (Cluster-scoped, defined by Infra Providers)        │
│         - Defines controller implementation                 │
│         - Specifies which gateway controller to use         │
└─────────────────────┬───────────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────────┐
│                       Gateway                               │
│          (Namespaced, managed by Cluster Operators)        │
│          - Defines listeners (ports, protocols)            │
│          - Configures TLS certificates                     │
│          - Specifies routing attachment rules              │
└─────────────────────┬───────────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────────┐
│                       Routes                                │
│        (Namespaced, managed by Application Developers)     │
│        - HTTPRoute, GRPCRoute, TCPRoute, UDPRoute, etc.   │
│        - Defines traffic routing rules                     │
│        - Maps to backend services                          │
└─────────────────────────────────────────────────────────────┘
```

### Detailed Resource Breakdown

#### 1. GatewayClass (Cluster-scoped)

The **GatewayClass** defines a set of gateways with common configuration managed by a controller.

**Key Characteristics:**
- **Cluster-scoped** - exists at cluster level, not in a namespace
- **Defines implementation** - points to the controller (e.g., Traefik, Envoy, Istio)
- **Similar to IngressClass** in the Ingress world
- **Managed by infrastructure providers** (cloud/platform teams)

**Example YAML:**
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: traefik-gateway
spec:
  controllerName: traefik.io/gateway-controller
```

#### 2. Gateway (Namespaced)

The **Gateway** defines an instance of traffic handling infrastructure (like a cloud load balancer).

**Key Characteristics:**
- **Namespaced** - lives within a specific namespace
- **Attaches to GatewayClass** - uses the `gatewayClassName` field
- **Defines listeners** - ports, protocols, TLS configuration
- **Controls route attachment** - which routes can bind to it
- **Managed by cluster operators** - networking team

**Listener Configuration:**
```yaml
listeners:
- name: http
  protocol: HTTP
  port: 80
  allowedRoutes:
    namespaces:
      from: Same  # or All, Selector
- name: https
  protocol: HTTPS
  port: 443
  tls:
    mode: Terminate  # or Passthrough
    certificateRefs:
    - name: my-tls-secret
      namespace: default
```

#### 3. Routes (Namespaced)

**Routes** define how traffic maps from gateway listeners to backend endpoints.

**Types of Routes:**
- **HTTPRoute** - HTTP/HTTPS routing (most common)
- **GRPCRoute** - gRPC routing
- **TCPRoute** - TCP traffic routing
- **UDPRoute** - UDP traffic routing
- **TLSRoute** - TLS passthrough routing
- **More being added** (experimental channel)

## Role-Based Access Model

Gateway API's role-oriented design creates clear separation of responsibilities:

### Infrastructure Providers (Platform Team)
- Manage GatewayClass resources
- Define available controller implementations
- Handle underlying cloud infrastructure (AWS ALB, Azure LB, etc.)
- **Should NOT be concerned with**: In-cluster network policies, application routing details

### Cluster Operators (Networking/Platform Team)
- Manage Gateway resources
- Configure listeners (ports, TLS certificates)
- Handle security policies
- **Should NOT be concerned with**: Cloud infrastructure details, application-specific routing

### Application Developers
- Manage HTTPRoute/GRPCRoute resources
- Define routing rules (hostnames, paths)
- Map traffic to their services
- **Should NOT be concerned with**: TLS certificates rotation, load balancer configuration, network ports

## Traffic Routing Features

### 1. Host-Based Routing

Route traffic based on the `Host` header of incoming requests.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: python-route
spec:
  parentRefs:
  - name: my-gateway
    sectionName: http  # Bind to specific listener
  hostnames:
  - "example-app-python.com"
  rules:
  - backendRefs:
    - name: python-svc
      port: 5000
      weight: 1
```

### 2. Path-Based Routing

Route based on URL path patterns with different matching strategies:

| Matching Type | Behavior | Use Case |
|---------------|----------|----------|
| **Exact** | Matches exact path only | Single endpoint services |
| **PathPrefix** | Matches path prefix | Services with multiple endpoints |
| **Regular Expression** | Matches regex pattern | Complex routing rules |

**Example:**
```yaml
rules:
- matches:
  - path:
      type: PathPrefix
      value: /api/python
  backendRefs:
  - name: python-svc
    port: 5000
```

### 3. URL Rewrite (Path Rewriting)

Rewrite URLs before forwarding to upstream services - essential for API gateways.

```yaml
rules:
- matches:
  - path:
      type: PathPrefix
      value: /api/go
  filters:
  - type: URLRewrite
    urlRewrite:
      path:
        type: ReplacePrefixMatch
        replacePrefixMatch: /
  backendRefs:
  - name: go-svc
    port: 5000
```

This allows:
- **Multiple APIs under one domain**: `example.com/api/go/*` and `example.com/api/python/*`
- **Clean upstream URLs**: Backend services see only path after the prefix
- **Better separation**: Different teams can manage their own path segments

### 4. Header Manipulation

Modify request or response headers using filters:

```yaml
rules:
- filters:
  - type: ResponseHeaderModifier
    responseHeaderModifier:
      add:
      - name: Access-Control-Allow-Origin
        value: "http://localhost:8000"
      - name: Access-Control-Allow-Methods
        value: "GET, POST, OPTIONS"
      remove:
      - name: Server  # Remove internal server info
```

**Available operations:**
- **Add** - Inject new headers
- **Set** - Override existing headers
- **Remove** - Delete headers

### 5. Traffic Splitting (Weighted Routing)

Distribute traffic across multiple backends using weights:

```yaml
backendRefs:
- name: go-svc-v1
  port: 5000
  weight: 80
- name: go-svc-v2
  port: 5001
  weight: 20
```

## TLS/HTTPS Configuration

### Two TLS Modes

| Mode | Description | Use Case |
|------|-------------|----------|
| **Terminate** | TLS terminated at gateway, HTTP to backend | Simplify backend TLS management |
| **Passthrough** | TLS passed through to backend | End-to-end encryption, client certificates |

### Termination Setup

**1. Create TLS Secret:**
```bash
kubectl create secret tls my-tls-secret \
  --cert=path/to/tls.crt \
  --key=path/to/tls.key \
  --namespace=default
```

**2. Configure Gateway Listener:**
```yaml
listeners:
- name: https
  protocol: HTTPS
  port: 443
  tls:
    mode: Terminate
    certificateRefs:
    - name: my-tls-secret
      namespace: default
  allowedRoutes:
    namespaces:
      from: All
```

**3. Update HTTPRoute to use HTTPS listener:**
```yaml
parentRefs:
- name: my-gateway
  sectionName: https  # Reference HTTPS listener
hostnames:
- "example-app-go.com"
rules: # Same rules as HTTP
```

### Certificate Management Benefits

- **Centralized certificates** - Store in one namespace
- **RBAC protection** - Control who can access/rotate certificates
- **Single rotation point** - Update certificates in one place
- **No per-service TLS** - Services don't need their own certificates

## Installation and Setup

### 1. Install Gateway API CRDs

```bash
# Standard channel (stable features)
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.4.0/standard-install.yaml

# Experimental channel (bleeding edge features)
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.4.0/experimental-install.yaml
```

**Stable Channel includes:**
- GatewayClass
- Gateway
- HTTPRoute

**Experimental Channel includes:**
- All stable features
- TCPRoute
- UDPRoute
- TLSRoute
- GRPCRoute
- Header manipulation
- And more

### 2. Install Gateway Controller

**Using Traefik (example):**
```bash
helm repo add traefik https://traefik.github.io/charts
helm install traefik traefik/traefik \
  --version 30.0.0 \
  --values custom-values.yaml
```

### 3. Deploy GatewayClass

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: my-gateway-class
spec:
  controllerName: traefik.io/gateway-controller
```

### 4. Deploy Gateway

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: default
spec:
  gatewayClassName: my-gateway-class
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: All
```

### 5. Deploy HTTPRoutes

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app-route
spec:
  parentRefs:
  - name: my-gateway
  hostnames:
  - "myapp.example.com"
  rules:
  - backendRefs:
    - name: app-service
      port: 8080
```

Customize underlying infrastructure (like cloud load balancers) using labels:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  labels:
    cloud-provider: aws
    load-balancer-type: internal
spec:
  infrastructure:
    labels:
      service.beta.kubernetes.io/aws-load-balancer-internal: "true"
```

## Comparison: Ingress vs Gateway API

| Feature | Ingress | Gateway API |
|---------|---------|-------------|
| **Resource Model** | Single object | Multiple objects (GatewayClass, Gateway, Routes) |
| **Role Separation** | Limited | Clear role-based design |
| **TLS Configuration** | Inline in rules | Separate listener configuration |
| **Routing Rules** | Basic host/path | Advanced with filters and rewrites |
| **Header Manipulation** | Controller-specific annotations | Native support |
| **Traffic Splitting** | Limited | Weighted routing |
| **Cross-namespace** | Limited | Flexible attachment rules |
| **Extensibility** | Annotations | Standardized API extensions |
| **Portability** | Controller-specific | Vendor-neutral specification |

## Common Challenges and Debugging

### 1. 404 Errors
- **Gateway 404**: Path doesn't match any route - check routing rules
- **Backend 404**: Path reaches service but doesn't exist - check service endpoints

### 2. TLS Issues
```bash
kubectl describe gateway my-gateway
# Check status for certificate errors
# Ensure secret exists in correct namespace
```

### 3. Route Attachment
```bash
kubectl describe httproute my-route
# Check parentRefs status
# Verify namespace restrictions
```

### 4. Controller Status
```bash
kubectl describe gatewayclass my-class
# Check if accepted
# Look for error messages in status
```

## Best Practices

### 1. Namespace Strategy
- **Centralized gateways** in a platform namespace (e.g., `gateway-system`)
- **Application routes** in application namespaces
- Use `allowedRoutes` to control access

### 2. Certificate Management
- Store certificates in a single, secure namespace
- Use cert-manager for automatic renewal
- Rotate certificates at gateway level, not per-service

### 3. Security
- Use RBAC to restrict access to Gateway resources
- Limit which namespaces can attach routes
- Use TLS for all external traffic

### 4. Monitoring
- Monitor Gateway status conditions
- Check route attachment status
- Watch controller logs for errors

### 5. Migration from Ingress
- Start with simple HTTPRoutes
- Gradually migrate complex rules
- Test thoroughly before production deployment

## Summary

Kubernetes Gateway API represents a **significant advancement** in Kubernetes networking:

1. **Role-Oriented Design** - Clear separation of infrastructure, operations, and development concerns
2. **Modular Architecture** - GatewayClass, Gateway, and Routes work together
3. **Advanced Routing** - Host-based, path-based, URL rewriting, header manipulation
4. **Portability** - Works across different controllers and cloud providers
5. **Extensibility** - Supports future features like CORS, external auth, and more
6. **Better TLS Management** - Centralized certificate handling
7. **Namespace Flexibility** - Cross-namespace routing capabilities

The Gateway API is rapidly evolving with new features being added regularly, making it the future of Kubernetes traffic management.
