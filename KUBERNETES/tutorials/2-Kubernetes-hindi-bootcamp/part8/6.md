### 1. The Node's Perspective (The Host)

> *"Node → eth0 → Root Ns → ip addr"*

- **Root Ns (Root Network Namespace)**: This is the host's primary network stack. It has its own routing table, firewall rules, and network interfaces.
- **eth0 (Node)**: This is the physical (or virtual) network interface of the host machine. It has a real IP address (e.g., `192.168.1.10/24`) that connects to your data center or cloud VPC.
- **`ip addr` (on the host)**: If you run `ip addr` on the host machine, you see the host's `eth0` and the bridge interfaces (like `cni0` or `docker0`).

**Corresponding command on the host**:
```bash
ip addr
# You will see:
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> ... inet 192.168.1.10/24 ...
# 3: cni0: <BROADCAST,MULTICAST,UP,LOWER_UP> ... inet 10.244.0.1/24 ...
```

### 2. The Pod's Perspective (The Container)

> *"pod/shared-ws-message create" → "eth0 (Pod) → ip addr → busyloop → pinginx"*

- **`pod/shared-ws-message create`**: This is your shorthand for **creating a shared network namespace for the Pod**. In Kubernetes, all containers inside a Pod share the **same network namespace**. This is why they can talk to each other on `localhost`.
- **eth0 (Pod)**: The Pod has its own virtual `eth0` interface. This is **one end of a veth pair** (Virtual Ethernet) created by the CNI plugin.
- **`ip addr` (inside Pod)**: When you run `kubectl exec -it <pod> -- ip addr`, you see the Pod's `eth0` with its own IP (e.g., `10.244.1.5/24`).
- **`busyloop` and `pinginx`**: You likely mean **`busybox`** and **`nginx`**. These are the containers inside the Pod. They both share the same `eth0` interface and IP address.

**Corresponding commands**:
```bash
# Inside the Pod
kubectl exec -it my-pod -- ip addr
# 1: lo: <LOOPBACK,UP,LOWER_UP> ...
# 2: eth0@if10: <BROADCAST,MULTICAST,UP,LOWER_UP> ... inet 10.244.1.5/24 ...
```

### 3. The Connection: How the Pod Connects to the Outside World

> *"busyloop - pinginx"*

When `busybox` (or `nginx`) in the Pod tries to ping an external IP, the packet flows like this:

| Step | Description |
| :--- | :--- |
| **1. Application** | `busybox` generates a packet destined for `8.8.8.8`. |
| **2. Pod's Netns** | The packet goes out via the Pod's `eth0` (which is actually a veth pair). |
| **3. veth Pair** | The packet crosses to the **host side** of the veth pair (linked to a bridge). |
| **4. Bridge (CNI)** | The packet hits the host's bridge (e.g., `cni0`) and looks up the routing table. |
| **5. Host's Root Netns** | The host does SNAT (Source NAT) via `iptables` or `eBPF`. It changes the source IP from the Pod's IP to the Node's `eth0` IP. |
| **6. Node's eth0** | The packet goes out to the physical network (via `eth0`). |

### 4. `ip netns list` (The Host's View of Pod Namespaces)

> *"ip netns list → List of network namespaces"*

Kubernetes (via `containerd` and the CNI) creates a network namespace for each Pod. On the host, you can list them using the `ip netns` command.

**Step-by-step exploration**:

1. **Find the Pod's container ID**:
   ```bash
   kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[0].containerID}'
   # Output: containerd://abc123...
   ```

2. **Find the network namespace on the host**:
   ```bash
   ls -l /var/run/netns/
   # Or use ip netns list (may require symbolic links)
   ```

3. **Execute a command inside the Pod's network namespace** (from the host, as root):
   ```bash
   # Get the PID of the container
   docker inspect -f '{{.State.Pid}}' <container-id>
   # nsenter the network namespace
   nsenter -t <PID> -n ip addr
   ```
   This shows you the exact same `eth0` and `lo` interfaces that the Pod sees—proving the Pod uses a separate namespace.

### 💡 Key Takeaway

Your notes perfectly capture the **before** and **after** of a Pod creation:

- **Before**: Only the Node's `Root Ns` and `eth0` exist.
- **During**: The `pod/shared-ws-message create` creates a fresh network namespace, attaches a virtual `eth0`, gives it an IP, and places all containers (`busybox`, `nginx`) inside it.
- **After**: `ip netns list` confirms the new namespace exists on the host, isolated from the `Root Ns` but connected via a virtual cable (veth pair) and a bridge.

This isolation is the foundation of Kubernetes networking: every Pod gets its own clean network stack (IP, routes, ports), avoiding port conflicts and providing a secure default environment for your containers.
