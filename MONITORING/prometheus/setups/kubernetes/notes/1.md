---

## What is kube-state-metrics?

**kube-state-metrics (KSM)** is a critical add-on for Kubernetes that acts as a bridge between the Kubernetes API server and Prometheus.

Its primary job is to **listen to the Kubernetes API server and generate metrics about the *state* of various cluster objects** (such as Pods, Deployments, Services, and Nodes).

> **Crucial Distinction:** KSM focuses on **"what the object *is*"** (its current state), whereas `metrics-server` focuses on **"how much resource the object *uses*"** (CPU/Memory consumption).

---

## How Does It Work?

`kube-state-metrics` is a stateless Go service that runs inside your cluster (usually in the `kube-system` namespace). It operates through a straightforward workflow:

1.  **Connect & Watch**: It establishes a connection to the Kubernetes API server and continuously **watches** for changes to various resource types (Pods, Deployments, Nodes, etc.).
2.  **Generate Snapshots**: It takes periodic snapshots of the current state of all objects in the cluster.
3.  **Expose Metrics**: KSM **does not modify** any raw API data. It translates the object states into Prometheus-compatible metrics and exposes them via an HTTP endpoint (default: `/metrics`).
4.  **Scrape**: Prometheus uses its service discovery (via a `ServiceMonitor` or `PodMonitor`) to locate the KSM pod and pull these metrics at regular intervals.

---

## KSM vs. metrics-server: The Key Difference

This is one of the most common points of confusion. They serve entirely different purposes:

| Feature | **kube-state-metrics** | **metrics-server** |
| :--- | :--- | :--- |
| **Primary Focus** | **Object State** ("What is happening?") | **Resource Usage** ("How much is being used?") |
| **Data Source** | Watches the API server for object statuses. | Reads from the Kubelet's cAdvisor API. |
| **Example Metrics** | `kube_pod_status_phase`, `kube_deployment_status_replicas_available` | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes` |
| **Used For** | Alerting on broken states, scaling logic, cluster health dashboards. | Horizontal Pod Autoscaler (HPA), `kubectl top` commands, node scaling. |

**In short:**
- `metrics-server` answers: *"How much CPU is my Pod using?"*
- `kube-state-metrics` answers: *"Is my Pod running or pending? Do I have enough replicas available?"*

## What Metrics Does KSM Expose?

`kube-state-metrics` generates metrics for almost all native Kubernetes resources. Here are the most commonly used ones:

### ✅ Pod Metrics
- `kube_pod_status_phase` – Current phase of the Pod (`Pending`, `Running`, `Succeeded`, `Failed`, `Unknown`).
- `kube_pod_status_ready` – Whether the Pod is ready (1) or not (0).
- `kube_pod_container_status_running` – Indicates if a container is currently running.
- `kube_pod_restart_policy` – The restart policy of the Pod.
- `kube_pod_created` – Unix timestamp of when the pod was created.

### ✅ Deployment & ReplicaSet Metrics
- `kube_deployment_spec_replicas` – Desired number of replicas.
- `kube_deployment_status_replicas_available` – Number of available replicas (ready).
- `kube_deployment_status_replicas_unavailable` – Number of unavailable replicas.
- `kube_replicaset_owner` – Which Deployment owns the ReplicaSet.

### ✅ Node Metrics
- `kube_node_status_condition` – Node conditions (Ready, MemoryPressure, DiskPressure, NetworkUnavailable).
- `kube_node_spec_unschedulable` – Whether the node is cordoned (1) or not (0).
- `kube_node_status_capacity` – Total capacity of the node (CPU, Memory, Ephemeral storage).

### ✅ Other Resources
- **Services**: `kube_service_spec_type` (ClusterIP, NodePort, LoadBalancer).
- **ConfigMaps/Secrets**: `kube_configmap_info`, `kube_secret_type`.
- **Ingress**: `kube_ingress_info`, `kube_ingress_path`.
- **CronJobs**: `kube_cronjob_status_active`, `kube_cronjob_metadata_next_schedule_time`.

## How to Install kube-state-metrics

KSM is not a default Kubernetes component. You must install it manually. Here are the two most common methods:

### Method 1: Using Helm (Recommended)

```bash
# Add the Prometheus community Helm repo
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# Install kube-state-metrics
helm install kube-state-metrics prometheus-community/kube-state-metrics
```

### Method 2: Using Standard Manifests (from GitHub)

```bash
# Clone the official repository
git clone https://github.com/kubernetes/kube-state-metrics.git

# Apply the standard deployment (creates ServiceAccount, ClusterRole, Deployment, Service)
kubectl apply -k kube-state-metrics/examples/standard
```

**Verification:**
```bash
kubectl get pods -n kube-system | grep kube-state-metrics
kubectl get service -n kube-system | grep kube-state-metrics
```

> **Note:** KSM requires a ServiceAccount with specific RBAC (ClusterRole) permissions to `get`, `list`, and `watch` cluster-wide resources. The standard manifests handle this automatically.

## Accessing the Exposed Metrics

Once installed, the KSM service exposes metrics at `http://<service-ip>:8080/metrics`.

To test it locally:
```bash
kubectl port-forward -n kube-system service/kube-state-metrics 8080:8080
```
Then visit `http://localhost:8080/metrics`. You'll see a massive list of metrics, all starting with `kube_`.

## Querying KSM Metrics with PromQL (Real Examples)

Once Prometheus is scraping KSM, you can query these metrics to gain deep insights.

### Example 1: Alert for Pods stuck in `Pending` state for > 5 minutes
```promql
kube_pod_status_phase{phase="Pending"} > 0
```
*Why this matters:* This usually indicates the scheduler cannot find a node (e.g., insufficient CPU/memory resources).

### Example 2: Find unhealthy Pods (Not Ready)
```promql
count(kube_pod_status_ready{condition="false", namespace="production"}) by (pod)
```
*Why this matters:* This shows which pods have failed their readiness probes and are not receiving traffic.

### Example 3: Check if desired replicas match available replicas
```promql
kube_deployment_status_replicas_available{namespace="default"} != kube_deployment_spec_replicas{namespace="default"}
```
*Why this matters:* This alerts you when a deployment rollout is stuck (e.g., due to CrashLoopBackOff or ImagePullBackOff).

### Example 4: Detect if a node is cordoned (unschedulable)
```promql
kube_node_spec_unschedulable == 1
```
*Why this matters:* This alerts you if a node was manually cordoned and forgotten to be uncordoned.

## Exploring the kube-state-metrics Pod Internals

If you describe the KSM pod (`kubectl describe pod -n kube-system kube-state-metrics-xxx`), you'll notice:

1. **Security Context**: It runs with a specific non-root user for security.
2. **Startup Arguments**: You can pass flags to customize its behavior, such as:
   - `--metric-labels-allowlist`: Limits which labels are exposed to prevent high cardinality.
   - `--resources`: Defines which Kubernetes resources to monitor (e.g., `pods,deployments,nodes`).
3. **Liveness/Readiness Probes**: It has endpoints like `/healthz` to ensure the service is running properly.

## Best Practices & Important Tips

1. **RBAC Permissions**: Ensure the ServiceAccount has the minimum required permissions (principle of least privilege). Usually, `get`, `list`, `watch` on `pods`, `deployments`, `nodes`, etc., are sufficient.
2. **Resource Limits (Memory/CPU)**: In large clusters (100+ nodes), KSM can consume significant memory. Monitor its usage and set appropriate requests/limits.
3. **High Availability**: For production clusters, deploy KSM with multiple replicas (though it is stateless, so multiple pods can run without conflict).
4. **Cardinality Control**: KSM generates a lot of metrics. Use `--metric-labels-allowlist` to drop unnecessary labels (e.g., labels that change frequently like `pod-template-hash`) to reduce storage costs in Prometheus.
5. **Version Compatibility**: Always ensure your KSM version matches your Kubernetes server version. Refer to the official compatibility matrix on GitHub.
6. **Opt-in scraping**: If you are using the Prometheus Operator, create a `ServiceMonitor` targeting the KSM service with the label `release: prometheus` to ensure Prometheus discovers and scrapes it automatically.

## Summary

- **kube-state-metrics** is the source of truth for object *states* in Kubernetes.
- It provides critical metrics for **cluster health dashboards** and **alerting rules**.
- It works by watching the API server and exposing data as Prometheus metrics.
- It is **NOT** a replacement for `metrics-server`; they complement each other. Use KSM for state (readiness, phases) and metrics-server for resources (CPU/Memory).

By leveraging KSM effectively, you can detect issues like stuck rollouts, pending pods, node failures, and misconfigured resources long before they impact your end users.
