# 1. What is Trivy?

**Trivy** is an open-source security scanner from Aqua Security.

It can detect things such as:

* Vulnerabilities/CVEs
* Misconfigurations
* Secrets
* License issues
* Software dependencies
* Container image vulnerabilities
* IaC misconfigurations
* Kubernetes configuration issues

A useful mental model:

```text
Trivy
 │
 ├── Vulnerability Scanner
 │
 ├── Misconfiguration Scanner
 │
 ├── Secret Scanner
 │
 ├── SBOM Generator
 │
 └── License Scanner
```

# 3. Stage 1 — Secret Scanning

One of the earliest places to use Trivy is against the source repository.

You don't want developers accidentally committing:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
GitHub tokens
Private keys
Passwords
API keys
Database credentials
```

Example:

```bash
trivy fs --scanners secret .
```

This scans the filesystem/repository for secrets.

You can use it in:

```text
Developer
   ↓
Git commit
   ↓
CI
   ↓
Trivy secret scan
   ↓
Build
```

### Why scan early?

Because finding:

```text
AWS_SECRET_ACCESS_KEY
```

after deploying to production is much worse than detecting it during CI.

# 5. Stage 3 — IaC Scanning

This is particularly useful for your **Terraform/DevOps** profile.

Trivy can scan Infrastructure as Code.

For example:

```text
Terraform
Kubernetes YAML
Helm
CloudFormation
Dockerfile
```

Suppose your Terraform contains:

```hcl
resource "aws_s3_bucket" "data" {
  bucket = "my-data"
}
```

You may have security configuration problems.

Trivy can detect certain IaC misconfigurations.

Run:

```bash
trivy config .
```

You might find issues such as:

```text
S3 bucket publicly accessible
Security group allows 0.0.0.0/0
Encryption not enabled
IAM policy too permissive
```

This is **shift-left security**.

Instead of:

```text
Terraform
 ↓
AWS
 ↓
Security problem
```

you do:

```text
Terraform
 ↓
Trivy
 ↓
Fix
 ↓
AWS
```

# 6. Stage 4 — Dockerfile scanning

You can scan your Dockerfile:

```bash
trivy config Dockerfile
```

For example:

```dockerfile
FROM ubuntu:latest

USER root

RUN apt-get update
```

Trivy can identify certain configuration problems.

Typical Docker security practices include:

```dockerfile
FROM a-minimal-image

RUN ...
    
USER 1000
```

You want to avoid unnecessary:

```text
root
privileged behavior
unnecessary packages
```

# 8. Stage 6 — Container Image Vulnerability Scanning

Scan the built image:

```bash
trivy image myapp:1.0
```

Trivy examines packages inside the image.

For example:

```text
myapp:1.0
 │
 ├── Ubuntu packages
 ├── OpenSSL
 ├── libc
 ├── Python packages
 ├── Node packages
 └── Application dependencies
```

Trivy compares these against vulnerability databases.

You may see:

```text
Library        Vulnerability    Severity
-----------------------------------------
openssl        CVE-XXXX         HIGH
libssl         CVE-YYYY         CRITICAL
```

---

# 9. Fail the pipeline based on severity

This is extremely useful.

Suppose your organization says:

> Don't deploy images containing CRITICAL vulnerabilities.

You can use:

```bash
trivy image \
  --severity CRITICAL \
  --exit-code 1 \
  myapp:1.0
```

The important part:

```text
--exit-code 1
```

If a matching vulnerability is found:

```text
Trivy
 ↓
CRITICAL found
 ↓
Exit code 1
 ↓
CI job fails
 ↓
Deployment doesn't happen
```

Without a failure threshold, Trivy may simply report findings without stopping the pipeline.

---

# 10. HIGH + CRITICAL policy

A common CI policy is:

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  myapp:1.0
```

Pipeline:

```text
Build
 ↓
Trivy
 ↓
HIGH/CRITICAL?
 ┌─────────────┐
 │             │
NO            YES
 │             │
 ▼             ▼
Continue      FAIL
```

This is one of the best Trivy examples to mention in interviews.

---

# 11. Should we fail on every vulnerability?

**Usually no.**

Imagine:

```text
100 vulnerabilities
```

but most are:

```text
LOW
```

If you fail every build:

```text
Developer
 ↓
LOW CVE
 ↓
Pipeline fails
```

you can create excessive noise.

A better approach is usually something like:

```text
LOW       → Report
MEDIUM    → Report / Review
HIGH      → Investigate
CRITICAL  → Fail
```

The exact policy should be determined by the organization's risk tolerance.

---

# 12. Stage 7 — Generate an SBOM

Trivy can generate an **SBOM — Software Bill of Materials**.

Example:

```bash
trivy image \
  --format cyclonedx \
  --output sbom.json \
  myapp:1.0
```

Conceptually:

```text
Container Image
      ↓
    Trivy
      ↓
     SBOM
      ↓
Packages + Versions + Dependencies
```

SBOM helps answer:

> **What software components are inside this image?**

For example:

```text
Image
 ├── nginx
 ├── openssl
 ├── libc
 ├── curl
 └── application dependencies
```

---

# 13. Why is SBOM important?

Suppose a new vulnerability is announced:

```text
CVE-XXXX
```

You can determine:

```text
Which applications contain the vulnerable package?
```

Without an SBOM:

```text
Search manually
   ↓
Many images
   ↓
Slow
```

With an SBOM:

```text
SBOM
 ↓
Package inventory
 ↓
Find affected applications
```

SBOM is becoming increasingly important for software supply-chain security.

# 19. Trivy in a Jenkins pipeline

Since Jenkins is on your resume, you should be able to explain something like:

```groovy
pipeline {
    stages {

        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Secret Scan') {
            steps {
                sh 'trivy fs --scanners secret .'
            }
        }

        stage('IaC Scan') {
            steps {
                sh 'trivy config .'
            }
        }

        stage('Build Image') {
            steps {
                sh 'docker build -t myapp:${BUILD_NUMBER} .'
            }
        }

        stage('Image Scan') {
            steps {
                sh '''
                    trivy image \
                    --severity HIGH,CRITICAL \
                    --exit-code 1 \
                    myapp:${BUILD_NUMBER}
                '''
            }
        }

        stage('Push Image') {
            steps {
                sh 'docker push ...'
            }
        }
    }
}
```

The important flow is:

```text
Checkout
   ↓
Secret Scan
   ↓
IaC Scan
   ↓
Build
   ↓
Image Scan
   ↓
Push
```

# 22. Trivy as a quality gate

This is one of the most important concepts.

Trivy doesn't have to merely produce a report.

You can make it a **quality gate**.

```text
                    Trivy
                      │
               Vulnerability?
                      │
             ┌────────┴────────┐
             │                 │
            NO                YES
             │                 │
             ▼                 ▼
          Continue          Fail CI
```

Example:

```bash
trivy image \
  --severity CRITICAL \
  --exit-code 1 \
  myapp:1.0
```

Interview wording:

> "I use Trivy as a security quality gate in CI. The pipeline scans the built image and fails when vulnerabilities above the organization's severity threshold are detected."

# 27. What should block the pipeline?

Don't necessarily make every finding a hard failure.

A practical policy might be:

```text
Secrets
   ↓
FAIL ❌

CRITICAL vulnerabilities
   ↓
FAIL ❌

HIGH vulnerabilities
   ↓
FAIL or approval depending on policy

MEDIUM
   ↓
Report / track

LOW
   ↓
Report
```

For example:

```bash
trivy image \
  --severity CRITICAL,HIGH \
  --exit-code 1 \
  myapp:${BUILD_NUMBER}
```

But in a real organization, you may also introduce exceptions, ignore lists, or severity policies for false positives/accepted risks, with appropriate security review.

# 29. Best interview answer

If the interviewer asks:

### "How have you used Trivy in CI/CD?"

You can say:

> **I use Trivy as a security gate at multiple stages of the CI/CD pipeline. During the source stage, I can use it for secret and filesystem/dependency scanning. Before deployment, I scan Terraform, Kubernetes manifests, Helm charts, and Dockerfiles for misconfigurations. After building the container image, I run a Trivy image vulnerability scan and configure severity thresholds, such as HIGH and CRITICAL, with a non-zero exit code so that the pipeline fails when the policy is violated. I can also generate SBOMs using formats such as CycloneDX or SPDX and store them as build artifacts. After deployment, Trivy can be used for periodic Kubernetes/registry assessments to identify newly discovered vulnerabilities or configuration issues.**

That's a **strong DevOps/DevSecOps interview answer** because you're showing that you understand Trivy as a complete security workflow rather than simply:

> "I run `trivy image`."
