These two slides are explaining one of the most important ideas in how containers actually work under the hood: **containers are not virtual machines — they're just regular processes that share the host's kernel**, and everything they do ultimately goes through **system calls**.

Let's break both slides down.

## Slide 1: Containers and System Calls

You have two Docker containers, each running an app (App1, App2). Each container process makes **system calls** — and both containers hit the **same Kernel**, which sits on top of the **same Hardware**.

This is the key insight: unlike a VM (which has its own guest OS and kernel), a container has **no kernel of its own**. It's just a process, isolated using Linux features (namespaces, cgroups), but when App1 needs to read a file, open a socket, or allocate memory, it asks the **one shared host kernel** to do it — the same kernel App2 is also asking.

That's why containers are lightweight — you're not booting a new OS per container, you're just isolating a process's *view* of the one kernel that's already running.

## Slide 2: Kernel Space vs User Space

This slide zooms into *how* that request from app to kernel actually happens.

**User Space** (top, green boxes):
- **Applications** — Firefox, curl, your Dockerized app, etc. These are the programs you and users interact with.
- **Libraries** — like `glibc` — most apps don't call the kernel directly; they call a library function (e.g., `printf`, `fopen`), and the library internally makes the raw system call for you.

**Kernel Space** (bottom, dark green/gray boxes):
- **Syscall Interface** — the strict, well-defined boundary/gate between user space and kernel space. Examples: `getpid()` (ask "what's my process ID?"), `reboot()` (ask the kernel to restart the machine).
- **Linux Kernel** — the core code that manages processes, memory, filesystems, networking, devices.
- **Hardware** — CPU, disk, RAM, network card — actually physical resources.

**Why does this separation exist?** Security and stability. User space apps run with restricted privileges and can't touch hardware directly or corrupt other processes' memory. If an app wants something privileged (read a file, send a network packet, create a process), it *must* ask the kernel through a system call — the kernel checks permissions and does it on the app's behalf. This is why a `curl` command and a Docker container in the diagram both point to the same syscall interface — doesn't matter if you're in a container or not, everyone goes through the same gate.

## Practical demo: seeing system calls happen

The best way to *see* this rather than just read about it is with `strace`, a Linux tool that logs every system call a program makes.

```bash
# Trace a simple command
strace ls

# Trace and count syscalls (a nice summary)
strace -c curl https://example.com

# Watch a container process from the host and see it's just... a process
docker run -d --name test nginx
ps aux | grep nginx      # you'll see nginx PIDs directly on the HOST
```

If you run `strace ls`, you'll see a flood of lines like:

```
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
read(3, "...", 832)
write(1, "file1.txt\nfile2.txt\n", 21)
```

Every single one of those (`openat`, `read`, `write`) is a **system call** — `ls` asking the kernel to open a file, read data, and print output to your terminal. This is exactly the "Syscall Interface" arrow in slide 2, happening in real time.

## Tying it together

- Slide 2 explains the *general* Linux mechanism: any app → library → syscall → kernel → hardware.
- Slide 1 shows *why this matters for containers*: two containers look isolated from each other, but they're both just user-space processes funneling every syscall into **one shared kernel**. There's no "Container Kernel" — containers borrow the host's.

This is also exactly why containers can't run a different OS kernel (you can't run a Windows container on a Linux host without a VM layer) — and why a kernel exploit or vulnerability can potentially let one container affect another, since they all trust the same underlying kernel.
