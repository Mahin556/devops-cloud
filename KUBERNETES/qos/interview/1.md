# Kubernetes QoS — Complete Guide

---

## Part 1 — What QoS Class Actually Is

QoS class is NOT something you set directly. Kubernetes derives it
automatically from how you configure requests and limits. Getting this
wrong is the most common reason production pods die unexpectedly.

---

## The Three Classes — Exact Rules

### Guaranteed — every container, requests == limits, both CPU and memory

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "500m"      # MUST equal request
    memory: "512Mi"  # MUST equal request
# QoS: Guaranteed
```

The trap people miss: **every container** in the pod must qualify, not just
the main one. If your app container is Guaranteed but the sidecar has no
limits, the whole pod drops to Burstable.

```yaml
# Pod with two containers — QoS is Burstable, NOT Guaranteed
containers:
  - name: app
    resources:
      requests: {cpu: "500m", memory: "512Mi"}
      limits:   {cpu: "500m", memory: "512Mi"}  # ← Guaranteed spec
  - name: sidecar
    resources:
      requests: {cpu: "50m", memory: "64Mi"}
      # NO LIMITS ← this single omission drops the entire pod to Burstable
```

### Burstable — at least one container has requests OR limits, but not equal

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"         # higher than request
    memory: "512Mi"  # higher than request
# QoS: Burstable

# Also Burstable — requests set, no limits:
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  # no limits — defaults to node capacity
# QoS: Burstable
```

### BestEffort — no requests or limits on ANY container

```yaml
containers:
  - name: worker
    image: worker:latest
    # No resources block at all
    # QoS: BestEffort
    # Will be first evicted under any node pressure
```

## Part 2 — Two Separate Kill Systems (Most Docs Confuse These)

This is the part the original answer completely skips. There are TWO
independent mechanisms that can kill pods, with different triggers and
different behavior:

```
                        Node Memory Pressure
                               │
                    ┌──────────┴──────────┐
                    ▼                     ▼
            KUBELET EVICTION         LINUX OOM KILLER
            (graceful, ordered)      (violent, immediate)

Trigger:    memory drops below       kernel can't satisfy
            eviction threshold       a memory allocation request

Order:      respects QoS class       doesn't know/care about K8s
            follows ranking algo     picks highest oom_score

Result:     pod.status = Failed      container SIGKILL'd immediately
            pod deleted from node    container restarts per restartPolicy

PDB         ignored (node pressure   not applicable — kernel-level
respected:  eviction bypasses PDB)

Grace       terminationGracePeriod   0 seconds — no warning
period:     respected for soft       ignored entirely
            eviction, 0s for hard
            eviction threshold

Status:     reason: Evicted          reason: OOMKilled, Exit Code: 137
shown as:
```

### Why OOMKilled can hit Guaranteed pods too

This surprises everyone: Guaranteed QoS protects from kubelet eviction,
but NOT from the OOM killer. If a Guaranteed pod's container exceeds its
own memory LIMIT, the kernel kills it immediately — this is not eviction,
it's the container hitting its own ceiling.

```bash
# What you see after an OOM kill:
kubectl describe pod my-pod
# Containers:
#   app:
#     State: Terminated
#       Reason: OOMKilled
#       Exit Code: 137     ← signal 9 (SIGKILL)
#     Last State: Terminated
#       Reason: OOMKilled
```

Exit code 137 = killed by SIGKILL (128 + 9). This does NOT mean eviction —
OOMKilled is the kernel acting on that specific container's memory limit.
The pod is NOT deleted from the node; the container restarts per restartPolicy.

## Part 3 — How oom_score_adj Connects QoS to the OOM Killer

Kubernetes sets the oom_score_adj value for each container's PID based on
its QoS class. This is how Kubernetes "hints" to the kernel which processes
it prefers the kernel NOT to kill:

| QoS Class | oom_score_adj | Effect |
|---|---|---|
| Guaranteed | -997 | Almost never killed by OOM killer |
| Burstable | 2 to 999 | Proportional to memory above request |
| BestEffort | 1000 (maximum) | First target for OOM killer |
| system-node-critical pods | -997 | Never evicted by kubelet |

```bash
# See the actual oom_score_adj for any container's process:
# Find the PID of a running container
cat /proc/<PID>/oom_score_adj
# Guaranteed pod: -997
# BestEffort pod: 1000
```

The kernel's OOM killer looks at oom_score_adj + actual memory % used
= effective oom_score. Highest score gets killed first. This is why a
BestEffort pod using 1% of node memory gets killed before a Burstable
pod using 40% — the 1000 oom_score_adj dominates the calculation.

## Part 4 — The Full Eviction Ranking Algorithm

The original answer shows a simple 3-row table. The actual algorithm
the kubelet uses is more nuanced. From official Kubernetes docs:

### Step 1 — QoS tier (primary sort)
<cite index="10-1">BestEffort or Burstable pods where the usage exceeds requests are
evicted first, based on their Priority and then by how much their usage
level exceeds the request. Guaranteed pods and Burstable pods where the
usage is less than requests are evicted last, based on their Priority.</cite>

The full ranking order:

```
1. BestEffort pods
   └─ sorted by: total actual memory usage (descending)

2. Burstable pods where usage > request
   └─ sorted by: (actual_usage - request) / request  ← overage ratio
   A pod using 300% of its request is evicted before one at 110%

3. Guaranteed pods AND Burstable pods where usage ≤ request
   └─ sorted by: PriorityClass value (lower priority evicted first)
   └─ Kubernetes will not evict these unless absolutely no other option
```

### Within-tier tiebreaker: PriorityClass

Within the same QoS tier, PriorityClass value breaks ties. BUT:
<cite index="8-1">A PriorityClass does not override QoS class in the eviction ranking —
a high-priority BestEffort Pod is still evicted before a low-priority
Guaranteed Pod.</cite>

Priority is a tiebreaker WITHIN a tier, not a tier-override.

## Part 5 — What Actually Triggers Eviction

The kubelet monitors specific eviction signals, not just "is the node low on memory":

```
Eviction Signal          Threshold (default)    Meaning
───────────────────────────────────────────────────────
memory.available         < 100Mi (hard)         Physical memory remaining
                         < 200Mi (soft)         (configurable via kubelet)
nodefs.available         < 10% (hard)           Root disk space
nodefs.inodesFree        < 5% (hard)            Filesystem inodes
imagefs.available        < 15% (hard)           Container image storage
pid.available            < 1000 (hard)          Available process IDs
```

**Soft vs Hard eviction thresholds:**
- **Soft**: kubelet waits for `eviction-max-pod-grace-period` before killing
  (respects terminationGracePeriodSeconds, allows graceful shutdown)
- **Hard**: kubelet terminates immediately with 0-second grace period
  (no graceful shutdown — same outcome as being SIGKILLed)

When thresholds are breached, the kubelet also taints the node with
`node.kubernetes.io/memory-pressure=:NoSchedule` — preventing NEW pods
from being scheduled onto the already-stressed node.

```bash
# Check current node conditions and eviction status:
kubectl describe node <node-name> | grep -A5 "Conditions:"
# Look for:
#   MemoryPressure     True   ← soft threshold breached
#   DiskPressure       False
#   PIDPressure        False
#   Ready              True
```

## Part 6 — QoS Class Practice (Interview-style questions)

**Q: What QoS class is this pod?**

```yaml
containers:
  - name: app
    resources:
      requests: {memory: "256Mi", cpu: "500m"}
      limits:   {memory: "256Mi", cpu: "500m"}
  - name: log-agent
    resources:
      requests: {memory: "64Mi"}
      # cpu: not set, limits: not set
```
**A: Burstable** — log-agent has no limits. For Guaranteed, every container
must have requests == limits for BOTH cpu and memory. One container fails
= entire pod is Burstable.

**Q: You have a Guaranteed pod whose memory usage is climbing. At what
point does it get evicted vs OOMKilled?**

**A:** Two distinct scenarios:
- If the pod's usage climbs but stays under its memory LIMIT, and the
  node starts running low on memory overall — the kubelet will evict
  BestEffort and Burstable pods first. Guaranteed pod is protected
  until no other pods remain to evict.
- If the pod's usage exceeds its own memory LIMIT (requests == limits
  for Guaranteed), the kernel's OOM killer kills the container
  immediately, regardless of what other pods are doing. This is NOT
  eviction — it's the container hitting its own ceiling.

**Q: Can a PriorityClass prevent a BestEffort pod from being evicted
before a Guaranteed pod?**

**A:** No. PriorityClass value is a tiebreaker within the same QoS tier.
A BestEffort pod with PriorityClass 1,000,000 is still evicted before
a Guaranteed pod with default PriorityClass (0). QoS tier always
takes precedence over PriorityClass in eviction ordering.

**Q: Your Burstable pod (requests: 256Mi, limits: 1Gi) is using 300Mi
— is it an eviction candidate before a Burstable pod using 900Mi
with requests of 512Mi?**

**A:** Your pod (300Mi / 256Mi = 117% of request) is a higher-priority
eviction candidate than the 900Mi pod (900Mi / 512Mi = 175% of request)
— wait, 175% > 117%, so the second pod gets evicted first. The ranking
is by **ratio of actual usage to request**, not absolute usage.

## Part 7 — Production Recommendations

```yaml
# Critical workloads (databases, payment processing):
# Use Guaranteed — protected from eviction, predictable performance
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
  limits:
    cpu: "2"          # deliberately same as request
    memory: "4Gi"     # deliberately same as request

# Stateless web services:
# Use Burstable — can handle eviction (replaced by deployment),
# bursts to handle traffic spikes without over-provisioning cluster
resources:
  requests:
    cpu: "250m"       # steady-state baseline
    memory: "256Mi"
  limits:
    cpu: "1"          # 4x headroom for spikes
    memory: "512Mi"   # 2x headroom

# Batch jobs / background workers:
# Burstable or even BestEffort is acceptable
# They're designed to be restarted and don't hold critical state
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  # limits: intentionally omitted for batch jobs
  # that need variable memory based on input size

# NEVER in production:
# - No resources block at all (BestEffort, first to die)
# - CPU limits == CPU requests (causes throttling during bursts —
#   CPU is compressible so throttling is silent but hurts latency)
```
