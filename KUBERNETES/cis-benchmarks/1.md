## CIS Benchmarks — what this chapter is actually teaching

### 1. What is CIS?

**CIS = Center for Internet Security.**

CIS provides security configuration best practices for different technology products. The course explains that CIS Benchmarks are developed through a consensus-based process involving cybersecurity professionals and subject-matter experts. 

So think:

```text
CIS
 │
 └── Security configuration recommendations
       │
       ├── Kubernetes
       ├── Linux
       ├── Docker
       ├── Cloud platforms
       └── Other technologies
```

For Kubernetes, CIS gives you a **security baseline** that you can use when configuring your cluster. 

---

# 2. Why CIS is useful for Kubernetes

Suppose you create a Kubernetes cluster with `kubeadm`.

You now have many security-sensitive components:

```text
Control Plane
├── kube-apiserver
├── etcd
├── kube-controller-manager
└── kube-scheduler

Worker Node
├── kubelet
├── container runtime
└── kube-proxy
```

You could manually decide:

> "What permissions should these files have?"

> "Should this endpoint be enabled?"

> "Should this process use TLS?"

> "Who should own this directory?"

Instead, CIS gives you security recommendations.

The course describes this as using CIS rules to establish a **good security base** for a cluster. 

---

# 3. CIS doesn't mean you blindly follow everything

This is an important concept.

An organization can take the CIS recommendations and customize them.

The course specifically explains that cloud providers such as Google Cloud and AWS can use CIS as a base and then customize the recommendations for their managed Kubernetes offerings. 

So:

```text
CIS Benchmark
       │
       ▼
Organization / Cloud Provider
       │
       ├── Apply as-is
       ├── Make stricter
       └── Make less strict
```

Therefore, **CIS is a baseline, not necessarily an immutable rulebook**.

---

# 4. Very important: CIS version ≠ Kubernetes version

This is something the course specifically highlights.

For example, you might see a CIS document with a version number.

That version number is the **version of the CIS Benchmark document**, not the Kubernetes version. 

You need to determine:

```text
CIS Benchmark version
        ≠
Kubernetes version
```

Instead, the benchmark itself tells you which Kubernetes versions it applies to.

The course's example benchmark covered Kubernetes 1.16 and 1.18, while the course environment was using 1.19. 

### Modern real-world lesson

Don't blindly use an old CIS PDF against a modern cluster.

Always check:

```text
Kubernetes version
       ↓
Applicable CIS Benchmark version
       ↓
Run assessment
```

# 6. Why kubeadm matters

This part is **very relevant for your CKS preparation**.

The course explains that the benchmark being used is based on the default configuration generated by **kubeadm**. 

Why does that matter?

Because kubeadm places Kubernetes configuration files in predictable locations.

For example, you commonly encounter:

```text
/etc/kubernetes/
/etc/kubernetes/manifests/
/var/lib/kubelet/
```

So when a CIS recommendation tells you to inspect a particular configuration file, you need to understand **where kubeadm placed that configuration**.

# 7. The most important part: anatomy of a CIS rule

The course demonstrates a CIS rule such as:

> Ensure that the API server pod specification file permissions are set to `644` or more restrictive. 

A CIS rule generally gives you:

```text
Recommendation
      │
      ├── Description
      │
      ├── Audit
      │
      └── Remediation
```

This is the key concept you should remember.

---

# 8. Audit vs Remediation

Suppose CIS says:

```text
Ensure file permissions are correct
```

There are two separate things.

### Audit

> How do I check the current configuration?

For example:

```bash
ls -l /some/file
```

You inspect the result.

```text
Current:
-rw-r--r--
```

Then determine whether it satisfies the CIS requirement.

### Remediation

> How do I fix it if it doesn't?

For example:

```bash
chmod 644 /some/file
```

So:

```text
CIS Rule
   │
   ├── AUDIT
   │     └── Check current state
   │
   └── REMEDIATION
         └── Change current state
```

The course explicitly emphasizes that the PDF provides both the command to check the configuration and instructions for fixing it.

# 9. Example: API server file permissions

The course's first example is essentially:

```text
Rule 1.1.1

Ensure API server pod specification
file permissions are 644 or more restrictive.
```

The workflow is:

```text
1. Read CIS rule
       ↓
2. Find the specified file
       ↓
3. Audit permissions
       ↓
4. Compare against requirement
       ↓
5. If incorrect → remediate
       ↓
6. Audit again
```

That's the **CIS mindset**.

Don't memorize:

```text
"1.1.1 = 644"
```

Instead understand:

> "CIS gives me a desired security state, an audit procedure, and a remediation procedure."

That is much more valuable.

# 17. The complete CIS workflow

You should memorize this **workflow**, not individual rules:

```text
                 CIS Benchmark
                       │
                       ▼
                Identify Rule
                       │
                       ▼
                    AUDIT
                       │
             ┌─────────┴─────────┐
             │                   │
           PASS                 FAIL
             │                   │
             ▼                   ▼
           Done              REMEDIATE
                                 │
                                 ▼
                               AUDIT
                                 │
                                 ▼
                              PASS
```

And kube-bench automates much of the audit process:

```text
             kube-bench
                 │
                 ▼
        ┌────────────────┐
        │ CIS checks     │
        └───────┬────────┘
                │
        ┌───────┼────────┐
        ▼       ▼        ▼
      PASS    FAIL     WARN
                │
                ▼
           Manual fix
                │
                ▼
          kube-bench again
```

# 19. Kubernetes CIS vs Docker CIS

This chapter makes another very important point.

Your Kubernetes cluster is **only as secure as the container runtime underneath it**.

For example:

```text
Kubernetes
     │
     ▼
containerd
     │
     ▼
Linux
```

Even if Kubernetes is hardened:

```text
Kubernetes CIS
     ↓
PASS
```

but your container runtime is badly configured:

```text
container runtime
     ↓
INSECURE
```

then your overall environment isn't secure.

The course mentions **Docker Bench** as a tool for checking Docker configuration and emphasizes that the container runtime itself also needs to be secure. 

For your setup, since you've been learning **containerd**, keep this architecture in mind:

```text
                 Security
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    Kubernetes   containerd    Linux
      CIS          hardening    hardening
```

# 20. GCP / AWS managed Kubernetes

The chapter finishes by showing that cloud providers can publish how their managed Kubernetes service aligns with CIS.

The instructor demonstrates GCP/GKE CIS information and points out that you can see which benchmarks/rules they apply and their status. 

This leads to an important concept:

### Self-managed Kubernetes

You are responsible for hardening:

```text
API Server
etcd
Controller Manager
Scheduler
Kubelet
OS
Container runtime
```

### Managed Kubernetes

The cloud provider takes responsibility for parts of the control plane.

For example:

```text
EKS/GKE
│
├── Cloud provider
│     └── Control plane
│
└── You
      ├── Workloads
      ├── RBAC
      ├── Nodes
      ├── Network
      └── Applications
```

Therefore, use the appropriate benchmark and understand the **shared responsibility model**.

## 22. The one thing I want you to remember

Don't study CIS like this:

```text
❌ Rule 1.1.1 = 644
❌ Rule 1.1.2 = something
❌ Rule 4.2.10 = something
❌ Memorize 100+ rules
```

Study it like this:

```text
                    CIS
                     │
                     ▼
             Security requirement
                     │
                     ▼
                  AUDIT
                     │
              Is it compliant?
                /          \
              YES           NO
               │             │
               ▼             ▼
             PASS        REMEDIATION
                             │
                             ▼
                          VERIFY
                             │
                             ▼
                           PASS
```

**That is the real lesson of this chapter.**

And for your CKS preparation, the most valuable hands-on exercise is to take **10–15 common CIS Kubernetes checks and practice the complete audit → understand → fix → verify cycle** on your kubeadm cluster, rather than just reading the benchmark PDF.
