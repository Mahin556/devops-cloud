This is a **multi‑target Dockerfile** (often confused with multi‑stage). Instead of using different stages to *reduce* the final image size, it uses a common `base` image and builds two different **variants** (targets) on top of it: one for **debugging** and one for **production**. 

Let’s break it down line by line.

---

### Stage 1: The Base Image
```dockerfile
FROM python:3.14-alpine as base
```
- **Image**: Uses the official Python 3.14 image built on **Alpine Linux**.
- **Why Alpine?** It’s extremely lightweight (~5MB), which keeps the final image small.
- **`as base`**: Names this stage `base`, allowing later stages to reference it.

```dockerfile
RUN mkdir /work/
WORKDIR /work/
```
- Creates the `/work/` directory and sets it as the current working directory for all subsequent commands.

```dockerfile
COPY ./src/requirements.txt /work/requirements.txt
RUN pip install -r requirements.txt
```
- Copies **only** the `requirements.txt` file first, then runs `pip install`.
- **Why copy only the requirements file first?**  
  This is a **Docker layer caching optimisation**. Docker caches the result of each `RUN` step. If `requirements.txt` hasn’t changed, Docker reuses the cached installed packages. This massively speeds up subsequent builds, as it skips reinstalling all dependencies when you only change your application source code.

```dockerfile
COPY ./src/ /work/
```
- Copies the **entire** `./src/` folder (your application code) into the `/work/` directory inside the container.

```dockerfile
ENV FLASK_APP=server.py
```
- Sets the environment variable `FLASK_APP` so that the `flask run` command knows which file to execute.

---

### Stage 2: Debug Target
```dockerfile
FROM base as debug
RUN pip install ptvsd
```
- Inherits everything from `base`.
- Installs **`ptvsd`** (Python Tools for Visual Studio Debugger).  
  **Note**: `ptvsd` is now legacy; Microsoft has replaced it with `debugpy`. However, if you have an older IDE setup, this might still be used.

```dockerfile
WORKDIR /work/
```
- Explicitly sets the working directory (redundant but safe).

```dockerfile
CMD python -m ptvsd --host 0.0.0.0 --port 5678 --wait --multiprocess -m flask run -h 0.0.0.0 -p 5000
```
This is the debugging command. Let's break down each argument:

| Argument | Meaning |
| :--- | :--- |
| `python -m ptvsd` | Runs the debugger module. |
| `--host 0.0.0.0` | The debugger listens on **all network interfaces** (so your IDE on your host machine can connect). |
| `--port 5678` | The debugger listens on port `5678`. |
| `--wait` | The application **pauses** and waits for the debugger client (e.g., VS Code) to attach before executing any code. This is crucial so you don't miss breakpoints at startup. |
| `--multiprocess` | Enables debugging for child processes (if your Flask app spawns workers). |
| `-m flask run` | Runs Flask as a module. |
| `-h 0.0.0.0 -p 5000` | Makes the Flask server itself listen on all interfaces on port `5000`. |

---

### Stage 3: Production Target
```dockerfile
FROM base as prod
CMD flask run -h 0.0.0 -p 5000
```
- Inherits everything from `base`.
- Runs the Flask development server with `flask run`, binding to all interfaces (`0.0.0` is shorthand for `0.0.0.0`) on port `5000`.

---

### How to Build and Run

Since this is a **multi-target** Dockerfile, you specify which target to build using the `--target` flag:

**For the debugging version:**
```bash
docker build --target debug -t myapp:debug .
docker run -p 5000:5000 -p 5678:5678 myapp:debug
```
- You need to expose **both** port `5000` (for HTTP traffic) and `5678` (for the debugger to connect).

**For the production version:**
```bash
docker build --target prod -t myapp:prod .
docker run -p 5000:5000 myapp:prod
```

---

### ⚠️ Major Pitfall in the Production Target

Using `flask run` (the built-in Flask development server) in a production container is **highly discouraged and insecure**. 

The Flask dev server:
- Is **single-threaded** (can only handle one request at a time).
- Is **not secure** (does not handle malicious payloads, timeouts, or scale properly).
- Is known to crash under moderate load.

#### ❌ What you *should* do instead:
Replace the `CMD` in the `prod` stage with a production-grade WSGI server, such as **Gunicorn** or **Waitress**.

**Example fix for the Dockerfile:**
```dockerfile
FROM base as prod
RUN pip install gunicorn
CMD gunicorn --bind 0.0.0.0:5000 server:app
```
*(Note: You would also need to ensure `server.py` contains a Flask instance named `app`)*

### Summary of the Structure

| Target | Inherits From | Installs | Command | Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **`base`** | None | App dependencies | (none) | Shared layer, not run directly. |
| **`debug`** | `base` | `ptvsd` | Waits for debugger attach, then runs Flask. | Local development / remote debugging. |
| **`prod`** | `base` | None | Runs Flask directly. | **⚠️ Not safe for production** – you must swap the CMD to use Gunicorn. |
