Your notes capture some important nuances about how ConfigMap and Secret updates work in Kubernetes. Let me explain each point in detail and clarify a few things.

---

### 1. Updates to Mounted Volumes (Not `subPath`)

> *"Only Mounted Volumes (not subPath) — here CM changes are reflected in mounted filesystem"*

**This is correct.** When a ConfigMap or Secret is mounted as a **volume** (a directory), updates to the ConfigMap/Secret are eventually reflected in the Pod's filesystem.

**How it works under the hood:**
- When you update a ConfigMap or Secret, the kubelet detects the change on its periodic sync cycle.
- The kubelet creates a **new timestamped directory** for the updated content, then **atomically renames** the `..data` symlink to point to the new directory.
- Your application sees the new files because the symlink now points to the updated content.

**The Delay:**
The update is **not instantaneous**. The total delay can be up to:
```
kubelet sync period (default 1 minute) + ConfigMap cache TTL (default 1 minute) = up to 2 minutes
```

**Example of a volume mount that updates automatically:**
```yaml
volumes:
- name: config-volume
  configMap:
    name: app-config
volumeMounts:
- name: config-volume
  mountPath: /etc/config    # Mounts the entire directory
```
With this setup, when `app-config` is updated, the files under `/etc/config` will eventually reflect the changes.

---

### 2. `subPath` Mounts Do NOT Update

> *"Only Mounted Volumes (not subPath)"*

**This is also correct, and it's a critical limitation.** When you use `subPath` to mount a **single file** from a ConfigMap or Secret, updates are **never** reflected—the Pod must be restarted.

**Why?**
- The `subPath` mount binds the file directly to the inode at mount time, rather than using the symlink mechanism that volume mounts use.
- The kubelet does not update these bind-mounted files when the underlying ConfigMap/Secret changes.

**Example of a subPath mount that does NOT update:**
```yaml
volumes:
- name: config-volume
  configMap:
    name: app-config
volumeMounts:
- name: config-volume
  mountPath: /etc/config/app.properties
  subPath: app.properties    # ❌ This file will NEVER update automatically
```

**Best practice:** If you need dynamic updates, mount the **entire volume** (directory) rather than using `subPath`. If you must use `subPath` for some files, separate them into different ConfigMaps—one for files that need live updates (mounted as a volume) and one for static files (using `subPath`).

---

### 3. Configuring Mounted Secret Change Detection Strategy

> *"Configuring Mounted Secret Change Detection Strategy — no Kubelet setti"*

Your note is pointing out that **there is no kubelet setting** to control the change detection strategy for mounted Secrets (or ConfigMaps). 

**What this means:**
- The behavior is hardcoded: the kubelet checks for updates on its **periodic sync cycle** (default 1 minute).
- You **cannot** configure the kubelet to detect changes more frequently or via a different mechanism (like watch events) for volume mounts.
- The sync period is a global kubelet configuration, not something you can tune per Secret or ConfigMap.

**The only "strategy" options you have:**
| Approach | How it works |
| :--- | :--- |
| **Volume mount (default)** | Updates eventually propagate (up to ~2 min delay). |
| **Environment variables** | **Never update**—Pod must be restarted. |
| **`subPath` mount** | **Never update**—Pod must be restarted. |
| **Kubernetes API watch** | Your application watches the API for changes and reloads dynamically. |
| **Sidecar reloader** | A sidecar container watches for file changes and triggers a reload of the main app. |

---

### 4. `immutable: true` → No Updates

> *"Immutable = true → no update — Only delete or update"*

**This is correct.** Setting `immutable: true` on a ConfigMap or Secret ensures that the data stored in it **cannot be updated**—only the object metadata can be modified.

**What happens when `immutable: true` is set:**
- **You cannot modify** the `data` field of the ConfigMap/Secret.
- Any attempt to `kubectl edit` or `kubectl patch` the data will be **rejected** by the API server.
- The **only way** to change the data is to:
  1. **Delete** the existing immutable ConfigMap/Secret.
  2. **Create** a new one with the updated data (and optionally set `immutable: true` again).

**Why use `immutable: true`?**
- **Performance**: The kubelet caches immutable ConfigMaps/Secrets more aggressively, reducing API server load.
- **Safety**: Prevents accidental changes to critical configuration.
- **Auditability**: Forces a deliberate "delete and recreate" workflow for configuration changes.

**Example:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: critical-config
immutable: true    # ❌ Cannot update the data field
data:
  setting: "value"
```

If you try to update this ConfigMap:
```bash
kubectl edit configmap critical-config
# The API server will reject the change with an error.
```

The correct workflow:
```bash
# 1. Delete the old one
kubectl delete configmap critical-config

# 2. Create a new one with updated data
kubectl create configmap critical-config --from-literal=setting=new-value
# Optionally set immutable: true again
```

---

### 💡 Best Practices

1. **Use volume mounts (not `subPath`)** if you need live configuration updates.
2. **Design your application** to watch for file changes and reload configuration automatically (e.g., using `inotify` or a file watcher).
3. **Set `immutable: true`** for production-critical ConfigMaps/Secrets that rarely change—it improves performance and prevents accidents.
4. **Accept the ~2 minute delay** for volume-mounted updates, or use the Kubernetes API watch mechanism for real-time updates.
5. **If you must use `subPath`**, treat those files as static and plan for Pod restarts when they change.
