### 1. The Three Probe Types (What they do)

Your notes correctly identify the three probes:

| Probe | Purpose | What happens on failure |
| :--- | :--- | :--- |
| **Startup Probe** | **"First this executes, until it's a success other probes are not executed"** (Your note). For slow-starting apps (e.g., Java Spring Boot). | **Failure**: Kubelet restarts the container (same as Liveness). **Success**: Liveness and Readiness probes take over. |
| **Readiness Probe** | Determines if the Pod is **ready to accept traffic**. Checks dependencies (database, services). | **Failure**: Pod is **removed from Service endpoints** (receives NO traffic). Container **does NOT restart**. |
| **Liveness Probe** | Checks if the container is **alive** or deadlocked. | **Failure**: **Kubelet restarts the container** (to try and fix it). |

**Your note** *"First this executes, until it's a success other probes are not executed"* specifically refers to the **Startup Probe**—it runs first and blocks the other two until it passes.

### 2. The Four Handler Types (HTTP, TCP, Exec, gRPC)

These are the mechanisms Kubernetes uses to *perform* the check. Here is exactly how each works, with YAML examples.

#### 🔹 HTTP GET (REST API Check)
- **How it works**: The kubelet sends an HTTP GET request to a specific endpoint (e.g., `/health`). 
- **Success**: Response code is `200` to `399`. 
- **Failure**: Any other response code (e.g., `404`, `500`) or a timeout.

**YAML Example (Liveness)**:
```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
    httpHeaders:
    - name: Custom-Header
      value: "Auth"
  initialDelaySeconds: 3
  periodSeconds: 10
```
**Best for**: REST APIs, web servers, microservices.

---

#### 🔹 TCP Socket (Port Check)
- **How it works**: The kubelet tries to open a TCP connection to the specified port.
- **Success**: The connection succeeds (the port is open).
- **Failure**: The connection is refused or times out.

**YAML Example (Readiness)**:
```yaml
readinessProbe:
  tcpSocket:
    port: 3306
  initialDelaySeconds: 5
  periodSeconds: 10
```
**Best for**: Databases (MySQL, Redis), message queues (Kafka), or any app that just needs to accept TCP connections.

---

#### 🔹 Exec (Custom Command)
- **How it works**: The kubelet runs a command **inside the container**. 
- **Success**: The command exits with **`0`** (success).
- **Failure**: The command exits with any **non-zero** code (e.g., `1`).

**YAML Example (Startup Probe)**:
```yaml
startupProbe:
  exec:
    command:
    - cat
    - /tmp/ready   # Check if a specific file exists
  initialDelaySeconds: 0
  periodSeconds: 5
```
**Best for**: Custom logic, like checking for a specific file (`/tmp/healthy`), running an internal script, or verifying database connectivity with a custom tool (e.g., `mysqladmin ping`).

---

#### 🔹 gRPC (Health Check for gRPC Services) - *Newer (v1.24+)*
- **How it works**: It uses the standard `grpc.health.v1.Health` service (built into most gRPC servers). The kubelet calls the `Check` method.
- **Success**: The service returns `SERVING` status.
- **Failure**: Returns `NOT_SERVING` or `UNKNOWN`.

**YAML Example (Liveness)**:
```yaml
livenessProbe:
  grpc:
    port: 9090
    service: "my-service"  # Optional: specific service name
  initialDelaySeconds: 5
  periodSeconds: 10
```
**Best for**: Microservices that use gRPC for internal communication (where HTTP isn't used).

### 3. Decoding Your Probe Configuration Parameters

Your note shows exactly how to configure a probe:
> `http-get http://:80/ delay=0s timeout=1s period=10s #success=1 #failure=3`

| Parameter | Your Value | Explanation |
| :--- | :--- | :--- |
| **`initialDelaySeconds`** (delay) | `0s` | Wait 0 seconds before first check. *Often set to 15-30s for apps that need to warm up.* |
| **`timeoutSeconds`** | `1s` | The probe must complete within 1 second, or it's considered a failure. |
| **`periodSeconds`** | `10s` | Run the probe every 10 seconds. |
| **`successThreshold`** | `1` | Needs 1 successful probe to be considered "healthy" after a failure. |
| **`failureThreshold`** | `3` | If the probe fails 3 times **consecutively**, Kubernetes marks it as failed. |

### 4. The Golden Rule of Probe Order (Startup → Readiness → Liveness)

1. **If Startup Probe is defined**: It runs first. Liveness and Readiness are **disabled** until Startup succeeds.
2. **Readiness Probe**: Runs periodically. If it fails, the Pod stops receiving traffic, but the container keeps running.
3. **Liveness Probe**: Runs periodically. If it fails, **Kubelet restarts the container**.

Your note *"Kubelet restarts container when liveness fails"* is exactly right.

| **TCP Socket** | Opens TCP connection to port. | Connection establishes. | Databases, Redis, TCP servers. |
| **Exec** | Runs custom command inside container. | Command exits with `0`. | Custom logic, file checks, internal scripts. |
| **gRPC** | Calls gRPC health service. | Returns `SERVING`. | gRPC microservices. |

### 💡 Why Probes Exist (Your Notes Explained)

> *"Kubernetes sends traffic even if pod is not ready to handle it"*
- **Solution**: Readiness probe removes the Pod from the Service's endpoint list until it is ready.

> *"Any deadlock situation still k8s sends traffic"*
- **Solution**: Liveness probe detects the deadlock and **restarts** the container, breaking the deadlock.

> *"Check dependencies for the pod in terms of availability of service or latency issue"*
- **Solution**: Readiness probe can check if the database or external API is available before marking the Pod ready to receive traffic.
