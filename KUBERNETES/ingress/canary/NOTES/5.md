Header-based canary deployments are useful when you want **only specific users** (such as QA engineers, developers, or beta testers) to access the new version. Unlike **weight-based canary**, no random traffic splitting occurs. Requests are routed based on the presence and value of an HTTP header.

---

# Architecture

```text
                    Client
                       |
        +--------------+--------------+
        |                             |
No Header                      Header: X-Canary=always
        |                             |
        v                             v
   Stable Ingress              Canary Ingress
        |                             |
 canary-test-v1                canary-test-v2
```

---

# Stable Deployment (v1)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: canary-test-v1
spec:
  replicas: 2
  selector:
    matchLabels:
      app: canary-test-v1
  template:
    metadata:
      labels:
        app: canary-test-v1
    spec:
      containers:
      - name: app
        image: hashicorp/http-echo:1.0
        args:
        - "-text=VERSION 1"
        ports:
        - containerPort: 5678
```

---

# Stable Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: canary-test-v1
spec:
  selector:
    app: canary-test-v1
  ports:
  - port: 80
    targetPort: 5678
```

---

# Stable Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: canary-test-v1
spec:
  ingressClassName: nginx
  rules:
  - host: canary-app.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: canary-test-v1
            port:
              number: 80
```

# Header-Based Canary Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: canary-test-v2
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"

    nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"

    nginx.ingress.kubernetes.io/canary-by-header-value: "always"

spec:
  ingressClassName: nginx

  rules:
  - host: canary-app.com

    http:
      paths:
      - path: /

        pathType: Prefix

        backend:
          service:
            name: canary-test-v2
            port:
              number: 80
```

# Test Without Header

```bash
curl -H "Host: canary-app.com" http://<INGRESS-IP>
```

Output:

```text
VERSION 1
```

Traffic flow:

```text
Client
   |
No X-Canary header
   |
Stable Ingress
   |
VERSION 1
```

---

# Test With Header

```bash
curl \
  -H "Host: canary-app.com" \
  -H "X-Canary: always" \
  http://<INGRESS-IP>
```

Output:

```text
VERSION 2
```

Traffic flow:

```text
Client
   |
X-Canary: always
   |
Canary Ingress
   |
VERSION 2
```

---

# Test With a Different Header Value

```bash
curl \
  -H "Host: canary-app.com" \
  -H "X-Canary: no" \
  http://<INGRESS-IP>
```

Output:

```text
VERSION 1
```

because the value does not match `"always"`.

# Verify Multiple Requests

Without the header:

```bash
for i in {1..5}
do
  curl -s -H "Host: canary-app.com" http://<INGRESS-IP>
  echo
done
```

Output:

```text
VERSION 1
VERSION 1
VERSION 1
VERSION 1
VERSION 1
```

With the header:

```bash
for i in {1..5}
do
  curl -s \
    -H "Host: canary-app.com" \
    -H "X-Canary: always" \
    http://<INGRESS-IP>
  echo
done
```

Output:

```text
VERSION 2
VERSION 2
VERSION 2
VERSION 2
VERSION 2
```

# How NGINX Decides

| Request Header       | Routed To |
| -------------------- | --------- |
| No `X-Canary` header | Version 1 |
| `X-Canary: always`   | Version 2 |
| `X-Canary: no`       | Version 1 |
| `X-Canary: test`     | Version 1 |

---

## Other Header-Based Options

NGINX also supports these related annotations:

```yaml
nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
```

Routes based on the existence of a header.

```yaml
nginx.ingress.kubernetes.io/canary-by-header-value: "always"
```

Routes to the canary only if the header has the specified value.

```yaml
nginx.ingress.kubernetes.io/canary-by-header-pattern: "^beta-.*"
```

Routes to the canary if the header value matches the given regular expression (for example, `beta-user1` or `beta-team`).

This approach is ideal for exposing a new version only to specific users, automated tests, or QA teams without affecting regular users.
