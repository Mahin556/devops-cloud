# Main Idea

You can run **multiple Ingress Controllers** in one cluster when you need **different routing behaviors or requirements**.

Each Ingress Controller handles only the Ingress resources assigned to it (using an *IngressClass*).

---

# Scenario 1: Protocol-Specific Routing

Different controllers can handle different **protocols**.

Example:

* One controller handles **HTTP/HTTPS (L7)**
* Another handles **TCP/UDP (L4)**

Example setup:

* AWS Load Balancer Controller → HTTP/HTTPS apps
* HAProxy → TCP/UDP traffic

Flow example:

```
HTTP  → ALB Ingress
TCP   → HAProxy Ingress
```

Why?
Some apps need special protocol handling that one controller alone can't handle well.

---

# Scenario 2: Multi-Tenant Isolation

Different teams use different Ingress Controllers.

Example:

* Team A → NGINX Ingress Controller
* Team B → AWS ALB

Why?

* Teams want independence
* Different configs
* Different features
* No conflicts

Example:

```
teamA.example.com → NGINX
teamB.example.com → ALB
```

---

# Scenario 3: Environment Separation

Different environments use different controllers.

Example:

* Staging → NGINX
* Production → ALB

Why?

* Production might need strict rules
* Staging might need flexibility

Example:

```
staging.example.com → NGINX
prod.example.com    → ALB
```

---

# Key Concept

Multiple Ingress Controllers work because of **IngressClass**:

Example:

```yaml
ingressClassName: nginx
```

```yaml
ingressClassName: alb
```

Each controller only watches its own class.

---

# Simple Summary

You run multiple Ingress Controllers when you need:

1. Different protocols
2. Different teams
3. Different environments
