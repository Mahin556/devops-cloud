## Interview Answer — "How have you used Trivy in CI/CD?"

> **I have used Trivy as part of the DevSecOps stage of a CI/CD pipeline to identify vulnerabilities, exposed secrets, and infrastructure misconfigurations before workloads are deployed.**
>
> I generally use Trivy at multiple points in the pipeline depending on what I'm scanning.
>
> **First, at the source-code stage**, I use `trivy fs` to scan the application repository. For example:
>
> ```bash
> trivy fs --scanners vuln,secret .
> ```
>
> This can identify vulnerabilities in application dependencies and potential exposed secrets in the source repository.
>
> **For Infrastructure as Code and configuration**, I use:
>
> ```bash
> trivy config .
> ```
>
> This is specifically intended for misconfiguration scanning of supported configuration/IaC such as Terraform, Kubernetes manifests, Helm charts, Dockerfiles, and other supported formats.
>
> Alternatively, if I want to combine misconfiguration scanning with other filesystem scanners, I can use:
>
> ```bash
> trivy fs --scanners vuln,secret,misconfig .
> ```
>
> The important distinction is that when I explicitly specify:
>
> ```bash
> --scanners misconfig
> ```
>
> Trivy runs the **misconfiguration scanner**, rather than automatically running the vulnerability and secret scanners as well.
>
> **After the application is built into a container image**, I use:
>
> ```bash
> trivy image myapp:$TAG
> ```
>
> This scans the final image for vulnerabilities in the OS packages and application dependencies. I prefer scanning the final image because it represents the actual artifact that will be deployed.
>
> I can also make Trivy a **quality gate**. For example:
>
> ```bash
> trivy image \
>   --severity HIGH,CRITICAL \
>   --exit-code 1 \
>   myapp:$TAG
> ```
>
> If HIGH or CRITICAL vulnerabilities are detected, Trivy returns a non-zero exit code and the CI pipeline fails, preventing the vulnerable image from being pushed or deployed.
>
> **I can also generate an SBOM** from the image:
>
> ```bash
> trivy image \
>   --format cyclonedx \
>   --output sbom.json \
>   myapp:$TAG
> ```
>
> This gives us an inventory of the software components and dependencies inside the image, which is useful for software supply-chain security and identifying affected applications when new CVEs are disclosed.
>
> **For Kubernetes and GitOps**, I can scan Kubernetes manifests or Helm charts before Argo CD deploys them:
>
> ```bash
> trivy config k8s/
> ```
>
> This provides a shift-left security check so that insecure Kubernetes configurations can be caught in CI rather than after deployment.
>
> So a typical pipeline for me would look like:
>
> ```text
> Developer
>     ↓
> Git Push
>     ↓
> Source / Secret Scan
> trivy fs --scanners vuln,secret
>     ↓
> IaC / Kubernetes / Helm Scan
> trivy config
>     ↓
> Tests
>     ↓
> Docker Build
>     ↓
> Container Image Scan
> trivy image
>     ↓
> SBOM Generation
>     ↓
> Security Quality Gate
>     ↓
> Push Image to ECR
>     ↓
> Update GitOps Repository
>     ↓
> Argo CD
>     ↓
> Kubernetes / EKS
> ```
>
> **I would not rely on Trivy as the only security mechanism.** It complements other controls such as RBAC, Pod Security Admission/Pod Security Standards, NetworkPolicies, IAM, image signing, and runtime security.
>
> The main goal is to **shift security left**, catch vulnerabilities and misconfigurations before deployment, and prevent artifacts that violate our security policy from reaching production.

## If the interviewer asks: "What's the difference between `trivy fs` and `trivy config`?"

Give this concise answer:

> **`trivy fs` is a filesystem/project scan, while `trivy config` is the dedicated command for configuration and IaC misconfiguration scanning. With `trivy fs`, I can select scanners such as `vuln`, `secret`, and `misconfig`. For example, `trivy fs --scanners vuln,secret,misconfig .` performs all three types of scanning. If I specifically want to analyze Terraform, Kubernetes, Helm, Dockerfile, or other supported configuration for misconfigurations, I would normally use `trivy config`.**

### Easy example

```bash
# Vulnerabilities + secrets
trivy fs --scanners vuln,secret .

# Only misconfiguration
trivy fs --scanners misconfig .

# Dedicated IaC/configuration scan
trivy config .

# Container image vulnerabilities
trivy image myapp:1.0
```

## If asked: "Why scan both the filesystem and the image?"

> **They serve different purposes. `trivy fs` scans the project before the image exists, while `trivy image` scans the actual container artifact that will be deployed. The final image can contain packages introduced by the base image or build process, so scanning the final image provides an additional security checkpoint.**

Think:

```text
Source code
    ↓
trivy fs
    ↓
Docker build
    ↓
Final image
    ↓
trivy image
```

## If asked: "How do you prevent a vulnerable image from being deployed?"

> **I use Trivy as a CI quality gate. After building the image, I scan it and configure a severity threshold. For example, I can fail the pipeline when HIGH or CRITICAL vulnerabilities are found using `--exit-code 1`. Only images that pass the security gate are pushed to ECR and made available for deployment.**

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  myapp:$TAG
```
