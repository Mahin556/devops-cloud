This is a good overview, but there are a few **important technical points I would correct before you use it for Kubernetes 1.31 interview preparation**.

## 1. The core concept

The most important relationship is:

```text
PSS = Pod Security Standards
      ↓
Defines WHAT is allowed

PSA = Pod Security Admission
      ↓
Enforces PSS

Kubernetes API Server
      ↓
Pod creation/update
```

So:

> **PSS defines the security profiles; PSA is the admission controller that evaluates Pods against those profiles.**

---

# 2. PSS — Pod Security Standards

PSS provides three profiles:

```text
                    PSS
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   Privileged      Baseline    Restricted
        │            │            │
   Least secure    Medium      Most secure
```

### Privileged

Very permissive.

Used for trusted workloads that require elevated privileges.

Examples can include certain:

* Infrastructure agents
* System-level workloads
* Monitoring/security components

---

### Baseline

Designed to prevent **known privilege-escalation configurations** while still allowing normal applications to run.

Think:

> **"Block the obvious dangerous configurations."**

---

### Restricted

The strongest profile.

Designed for workloads requiring stronger hardening.

It includes restrictions around things such as:

* Running as root
* Privilege escalation
* Linux capabilities
* Seccomp
* Host namespaces
* Host filesystem access
* Volume types

Think:

> **"Apply strong security hardening."**

---

# 3. PSA — Pod Security Admission

PSA is an **admission controller**.

When you do:

```bash
kubectl apply -f pod.yaml
```

the request eventually reaches the API server's admission phase.

Conceptually:

```text
kubectl
   │
   ▼
API Server
   │
   ▼
Admission
   │
   ▼
PSA
   │
   ▼
PSS evaluation
   │
   ├── Compliant → Allow
   │
   └── Violation
          │
          ├── enforce → Reject
          ├── warn    → Warning
          └── audit   → Audit information
```

---

# 4. PSA's three modes

This is something you should memorize.

| Mode      | What happens?                                         |
| --------- | ----------------------------------------------------- |
| `enforce` | Rejects violating Pods                                |
| `warn`    | Allows Pod but gives warning                          |
| `audit`   | Allows Pod but records violation in audit information |

Easy memory:

```text
ENFORCE → BLOCK
WARN    → ALLOW + WARN
AUDIT   → ALLOW + RECORD
```

---

# 5. How do we configure PSA?

For normal namespace-specific policies, use namespace labels.

For example:

```bash
kubectl label namespace namespace-prod \
  pod-security.kubernetes.io/enforce=restricted
```

You can also specify the version:

```bash
kubectl label namespace namespace-prod \
  pod-security.kubernetes.io/enforce-version=v1.31
```

Or YAML:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: namespace-prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.31
```

Then:

```bash
kubectl apply -f namespace.yaml
```

# 6. Very important correction about your `runAsUser` example

Your source says:

> A Pod with `runAsUser: 1000` is allowed under Baseline.

That's fine, but **Baseline doesn't mean "root is allowed as a security recommendation."**

Baseline primarily prevents specific known privilege-escalation mechanisms. It does **not** impose the same non-root requirements as Restricted.

So don't memorize:

```text
Baseline = allows root
```

as the definition.

Instead remember:

```text
Baseline
   ↓
Prevents known dangerous configurations

Restricted
   ↓
Adds stronger workload hardening,
including non-root requirements
```

# 7. Your Restricted example needs an important correction

This:

```yaml
securityContext:
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
  capabilities:
    drop:
      - ALL
```

is heading in the right direction, but don't say:

> "These three fields alone guarantee the Pod complies with Restricted."

Restricted has **multiple controls**, and compliance depends on the complete Pod specification and the Kubernetes/PSS version.

For example, Restricted also has requirements around areas such as:

* Privilege escalation
* Host namespaces
* Capabilities
* Seccomp
* User/group configuration
* Volume types

For a hardened container, you'd commonly see:

```yaml
securityContext:
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault

containers:
- name: app
  image: nginxinc/nginx-unprivileged
  securityContext:
    allowPrivilegeEscalation: false
    capabilities:
      drop:
      - ALL
```

# 8. Why `seccompProfile` is important

You were just studying seccomp, so connect the two concepts.

```yaml
seccompProfile:
  type: RuntimeDefault
```

means:

> Use the container runtime's default seccomp profile.

Seccomp filters Linux **system calls**.

```text
Application
     │
     ▼
 System Call
     │
     ▼
  Seccomp
     │
 ┌───┴────┐
 ▼        ▼
Allow    Block
```

Restricted PSS requires secure seccomp configuration and does not allow an explicitly configured:

```yaml
type: Unconfined
```

---

# 9. Why `capabilities.drop: ALL`?

Linux capabilities divide traditional root privileges into smaller privileges.

For example:

```text
NET_ADMIN
NET_RAW
SYS_ADMIN
SETUID
SETGID
```

Instead of allowing unnecessary capabilities:

```yaml
capabilities:
  drop:
  - ALL
```

you remove them.

If the application genuinely needs one, you can add only the required capability.

This follows the **principle of least privilege**.

---

# 10. Why `allowPrivilegeEscalation: false`?

This prevents a process from gaining more privileges than its parent process.

```yaml
securityContext:
  allowPrivilegeEscalation: false
```

So a hardened workload often combines:

```text
runAsNonRoot
      +
allowPrivilegeEscalation=false
      +
drop ALL capabilities
      +
RuntimeDefault seccomp
```

Each provides a different security layer.

# 11. Namespace-specific PSA

This is one of the biggest advantages of PSA.

You can have:

```text
namespace-dev
    │
    └── Baseline

namespace-prod
    │
    └── Restricted
```

For example:

```bash
kubectl label namespace namespace-dev \
  pod-security.kubernetes.io/enforce=baseline
```

and:

```bash
kubectl label namespace namespace-prod \
  pod-security.kubernetes.io/enforce=restricted
```

So:

```text
             Kubernetes Cluster
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
    namespace-dev       namespace-prod
          │                   │
       Baseline            Restricted
          │                   │
      Applications       Sensitive apps
```

# 12. `warn` + `audit` before `enforce`

This is a **very good production practice**.

Don't immediately do:

```text
enforce=restricted
```

on an existing production namespace.

You could break workloads.

Instead:

### Phase 1

```yaml
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted
```

Discover violations.

### Phase 2

Fix workloads:

```text
Run as non-root
Drop capabilities
Disable privilege escalation
Configure seccomp
Remove host access
```

### Phase 3

Enable:

```yaml
pod-security.kubernetes.io/enforce: restricted
```

So:

```text
Existing workloads
       │
       ▼
WARN + AUDIT
       │
       ▼
Find violations
       │
       ▼
Fix workloads
       │
       ▼
ENFORCE
       │
       ▼
Restricted production
```

This is a **strong interview answer**.

# 13. What about cluster-level configuration?

Your source discusses:

```yaml
kind: AdmissionConfiguration
```

with:

```yaml
plugins:
- name: PodSecurity
```

This is a different layer from simply labeling namespaces.

There are two concepts to keep separate:

### Namespace labels

Used to specify the policy for individual namespaces:

```yaml
pod-security.kubernetes.io/enforce: restricted
```

### AdmissionConfiguration

Used to configure **cluster-level PSA defaults and exemptions**.

For example, conceptually:

```yaml
defaults:
  enforce: baseline
  audit: restricted
  warn: restricted
```

and exemptions:

```yaml
exemptions:
  namespaces:
  - kube-system
```

The important distinction:

```text
Namespace labels
       ↓
Per-namespace policy

AdmissionConfiguration
       ↓
Cluster-level defaults/exemptions
```

# 14. Be careful with `kube-system`

Your source recommends:

```yaml
exemptions:
  namespaces:
  - kube-system
```

Don't interpret that as:

> "`kube-system` should always be exempt."

Exemptions should be carefully considered.

System components may legitimately require privileges, but blindly exempting namespaces weakens your security boundary.

In an interview, say:

> "I would minimize exemptions and only exempt workloads that genuinely require behavior incompatible with the selected policy."

That's a much stronger answer.

# 16. PSA vs RBAC

Very common interview question.

### RBAC

Answers:

> **Who is allowed to perform an action?**

Example:

```text
Can Alice create Pods?
Can ServiceAccount X read Secrets?
Can developer Y delete Deployments?
```

### PSA

Answers:

> **Does this Pod configuration meet the required security standard?**

Example:

```text
Is privileged=true allowed?
Is hostNetwork allowed?
Is the seccomp configuration acceptable?
```

Therefore:

```text
RBAC → WHO can do WHAT?

PSA → WHICH Pod configurations are allowed?
```

---

# 17. PSA vs NetworkPolicy

Another common question.

```text
PSA
 ↓
Pod security configuration

NetworkPolicy
 ↓
Pod network traffic
```

For example:

PSA:

```text
Can this Pod use hostNetwork?
Can it run privileged?
```

NetworkPolicy:

```text
Can frontend talk to backend?
Can backend talk to database?
```

You need both in a secure cluster.

---

# 18. PSA vs seccomp

Don't confuse them.

```text
PSA
 ↓
Admission control
 ↓
Checks Pod security configuration

seccomp
 ↓
Linux kernel security mechanism
 ↓
Filters system calls
```

PSA can **require/configure acceptable seccomp settings through PSS**, but PSA itself isn't the seccomp mechanism.

# 20. Interview scenario

### Question:

> You have 100 existing applications in production. Management wants Restricted PSS enabled. How would you implement it without causing outages?

### Answer:

> I wouldn't immediately enforce Restricted. First, I would use `warn` and `audit` at the namespace level to identify non-compliant workloads. I would analyze the violations and work with application teams to remediate issues such as privileged containers, root execution, unnecessary capabilities, privilege escalation, host namespace usage, and missing or inappropriate seccomp configuration. After validating the workloads in staging, I would gradually enable `enforce=restricted` in production. I would keep exemptions minimal and only for workloads that have a documented requirement.

That's the type of answer that demonstrates **production thinking**, not just memorization.

## ⭐ What you should be able to explain in an interview

If the interviewer asks **"Explain PSA and PSS"**, give this answer:

> **Pod Security Standards define three security profiles in Kubernetes: Privileged, Baseline, and Restricted. Privileged is essentially unrestricted, Baseline prevents common privilege-escalation configurations, and Restricted provides stronger workload hardening. Pod Security Admission is the built-in admission controller that evaluates Pods against these standards. PSA is configured primarily through namespace labels and supports three modes: `enforce`, which rejects non-compliant Pods; `warn`, which allows them but produces warnings; and `audit`, which allows them but records the violations. In production, I would normally start with warn and audit, remediate existing workloads, and then gradually enable enforcement.**

That is the **core answer** worth memorizing.
