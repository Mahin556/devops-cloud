# Kubernetes Ingress Limitations — Deep Dive

---

## 1. Namespace Scope (from before)
```
Ingress can only route to services in its OWN namespace
→ conflicts with namespace-level segregation best practices
→ some controllers solve this via annotations (not native K8s)
```

---

## 2. Protocol Support — HTTP/HTTPS Only

```
Ingress SUPPORTS:          Ingress DOES NOT Support:
────────────────           ──────────────────────────
✅ HTTP                    ❌ TCP
✅ HTTPS                   ❌ UDP
                           ❌ gRPC (natively)
```

### What is gRPC?

```
gRPC = Google Remote Procedure Call

Made by Google → open-sourced to the world

Purpose:
Different systems can talk to each other even if:
├── Written in different languages (Go, Python, Java...)
└── Running on different platforms

Under the hood → uses HTTP/2
```

### Why does this matter?
```
Modern microservices often use gRPC because:
├── Much faster than REST
├── Strongly typed contracts
└── Works across languages

But Ingress can't natively route gRPC traffic ❌
→ need special controller configuration
```

## 3. First-Class Features Not Natively Supported

These features exist — but only through **annotations**, not native Ingress spec.

### a) Canary Deployments

```
Normal deployment:
100% users → v1 of app

Canary deployment:
70% users → v1 (stable)
30% users → v2 (new/testing)
```

**Why do this?**
```
You built a new feature but you're not 100% confident yet
→ Roll it out to only 20% of users first
→ Collect feedback
→ If it works well → increase to 50% → 100%
→ If it breaks → only 20% were affected, easy rollback
```

**Common terms — all mean the same thing:**
```
Canary deployment
Traffic splitting       } → sending % of users
Weighted routing        }    to different versions
A/B testing
```

**Visual:**
```
Incoming traffic (100 users)
        │
        ▼
   Ingress/Router
        │
        ├──→ 80 users → Deployment v1 (stable) ✅
        │
        └──→ 20 users → Deployment v2 (new feature) 🧪
```

---

### b) SSL Redirect

```
User types:   http://myapp.com      (insecure)
                    │
                    ▼
             Ingress detects HTTP
                    │
                    ▼
         Automatically redirects to
                    │
                    ▼
              https://myapp.com     (secure) ✅
```

Saw this in the Ingress demo — HTTP → HTTPS redirect automatically.

---

### c) Rewrites

```
User requests:   myapp.com/app1
                       │
                       ▼
              Ingress rewrites path
                       │
                       ▼
     Internally routes to:  myapp.com/app1/mypage
```

Useful when your internal service path is different from the public-facing URL.

---

### d) Rate Limiting

```
Rule: max 100 requests per minute per user

User sends 150 requests in 1 minute:
├── First 100 → ✅ allowed
└── Next 50   → ❌ blocked (429 Too Many Requests)
```

Protects your services from abuse or DDoS attacks.

---

### The Problem With All of These

```
None of these are part of the native Ingress spec.
They are implemented via ANNOTATIONS.
```

```yaml
# Example — these are annotations (controller-specific)
annotations:
  nginx.ingress.kubernetes.io/rewrite-target: /
  nginx.ingress.kubernetes.io/limit-rps: "100"
  nginx.ingress.kubernetes.io/canary: "true"
  nginx.ingress.kubernetes.io/canary-weight: "30"
```

The issue? These only work if your controller supports them.

## 4. Portability Problem

### Annotations are Vendor-Specific

```
AWS Load Balancer Controller uses:
  alb.ingress.kubernetes.io/scheme: internet-facing

NGINX Ingress Controller uses:
  nginx.ingress.kubernetes.io/rewrite-target: /

Traefik uses:
  traefik.ingress.kubernetes.io/router.entrypoints: web
```

### The Migration Nightmare:

```
Today:   Using AWS Load Balancer Controller
         → 50 Ingress files
         → hundreds of AWS-specific annotations

Tomorrow: Want to switch to NGINX Controller
         │
         ▼
    Must rewrite ALL annotations ❌
    in ALL 50 files
    because they are vendor-specific
```

### Not Spec Validated:

```
Kubernetes validates native spec fields:
├── Wrong apiVersion → ❌ immediate error
├── Wrong kind       → ❌ immediate error
└── Wrong spec field → ❌ immediate error

Annotations are NOT validated:
├── Typo in annotation key   → silently ignored 😶
├── Wrong annotation value   → silently ignored 😶
└── Feature just doesn't work, no error message
```

```

──────────────────────────────────────────────────────────────
Namespace scope    Can't route cross-namespace  Gateway API /
                                                Service Mesh

TCP/UDP/gRPC       Only HTTP/HTTPS supported    Custom controllers

Portability        Annotations are              Standardized tools

```

---

## The Root Cause of ALL These Problems

```
Ingress was designed as a SIMPLE spec
→ just basic HTTP routing
→ everything advanced = pushed to annotations
→ annotations = no standard = vendor lock-in
→ this is exactly why Gateway API was created
   to replace Ingress with a proper, extensible spec
```
