# Kubernetes 1.31 — Pod Security Admission (PSA) and Pod Security Standards (PSS)

In Kubernetes version **1.31**, managing Pod security is achieved through the implementation of **Pod Security Admission (PSA)** and adherence to **Pod Security Standards (PSS)**. These mechanisms ensure that Pods comply with security best practices, enhancing the overall security posture of the cluster.

---

## Understanding Pod Security Standards (PSS)

Kubernetes defines three primary security profiles:

### 1. Privileged

**Unrestricted** policy allowing all Pod configurations.

Suitable for trusted workloads that require elevated privileges.

### 2. Baseline

**Minimally restrictive** policy that prevents known privilege escalations.

Ideal for general-purpose applications that follow standard security practices.

### 3. Restricted

**Highly restrictive** policy enforcing current Pod hardening practices.

Intended for security-critical applications and untrusted workloads.

Each profile specifies controls for various security settings, such as:

* Privilege escalation
* Root user enforcement
* Linux capabilities
* Host namespaces
* Seccomp profiles
* Volume types
* Other Pod security configurations

---

# Implementing Pod Security Admission (PSA)

**PSA is an admission controller that enforces PSS** by validating Pod specifications during creation and updates.

It operates in three modes:

### Enforce

Blocks the creation of Pods that don't comply with the specified security standards.

```text
Pod
 ↓
PSA
 ↓
Violation
 ↓
REJECT ❌
```

### Warn

Allows the creation of non-compliant Pods but issues warnings.

```text
Pod
 ↓
PSA
 ↓
Violation
 ↓
WARNING ⚠️
 ↓
Pod created
```

### Audit

Records non-compliance information for auditing purposes without blocking the Pod.

```text
Pod
 ↓
PSA
 ↓
Violation
 ↓
Audit information
 ↓
Pod created
```

### Easy way to remember

```text
Enforce → BLOCK
Warn    → ALLOW + WARNING
Audit   → ALLOW + RECORD
```

# Configuring PSA at the Cluster Level

To apply PSS across the cluster, PSA can be configured with default settings and exemptions.

This involves creating an `AdmissionConfiguration` file and specifying the desired defaults and exemptions.

## Example Configuration

Create a configuration file named:

```text
psa-config.yaml
```

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration

plugins:
  - name: PodSecurity

    configuration:
      apiVersion: pod-security.admission.config.k8s.io/v1
      kind: PodSecurityConfiguration

      defaults:
        enforce: "baseline"
        enforce-version: "latest"

        audit: "restricted"
        audit-version: "latest"

        warn: "restricted"
        warn-version: "latest"

      exemptions:
        usernames: []
        runtimeClasses: []
        namespaces:
          - kube-system
```

---

## Explanation

### Defaults

The configuration above sets:

```text
Enforce → Baseline
Audit   → Restricted
Warn    → Restricted
```

This means:

```text
Baseline
   ↓
Actual enforcement

Restricted
   ↓
Audit violations

Restricted
   ↓
Warn about violations
```

### Exemptions

```yaml
exemptions:
  usernames: []
  runtimeClasses: []
  namespaces:
    - kube-system
```

This excludes the `kube-system` namespace from the configured PSA policy.

> Exemptions should be used carefully and kept as limited as possible.

---

# Applying the Configuration

## Step 1 — Prepare the configuration directory

```bash
mkdir -p /etc/kubernetes/psa
cp psa-config.yaml /etc/kubernetes/psa/
```

---

## Step 2 — Modify the API Server Configuration

The API server must be able to access the PSA configuration file.

For a kubeadm-managed cluster, the API server configuration can be configured with the appropriate argument and volume mount:

```yaml
apiServer:
  extraArgs:
    admission-control-config-file: /etc/kubernetes/psa/psa-config.yaml

  extraVolumes:
    - name: psa-config
      hostPath: /etc/kubernetes/psa
      mountPath: /etc/kubernetes/psa
      readOnly: true
```

The important part is:

```text
API Server
    │
    └── /etc/kubernetes/psa/psa-config.yaml
```

---

## Step 3 — Restart the API Server

After modifying the API server configuration, restart/redeploy the API server so that the new PSA configuration is loaded.

# Implementing PSA in Production

When implementing PSA in production, several practices should be followed.

## 1. Gradual Enforcement

Start with:

```text
warn
audit
```

to identify existing security violations.

After workloads have been remediated, move to:

```text
enforce
```

This reduces the risk of unexpectedly breaking existing applications.

---

## 2. Namespace-Specific Policies

Different namespaces can use different security levels.

For example:

```text
namespace-dev
      ↓
   Baseline

namespace-prod
      ↓
  Restricted
```

This allows security requirements to match workload sensitivity.

---

## 3. Regular Auditing

Continuously monitor audit information to identify and address non-compliant Pod configurations.

---

## 4. Exemptions Management

Keep exemptions limited to essential workloads, namespaces, usernames, or runtime classes.

Avoid creating broad exemptions that unnecessarily weaken the security boundary.

# Real-World Example

Consider two namespaces:

```text
namespace-dev
    ↓
Baseline

namespace-prod
    ↓
Restricted
```

Development workloads can use the less restrictive Baseline profile, while sensitive production workloads can use the more restrictive Restricted profile.

---

# Step 1 — Create Namespaces with PSA Labels

PSA can be configured for namespaces using labels.

## Development Namespace

Create the namespace:

```bash
kubectl create namespace namespace-dev
```

Apply Baseline:

```bash
kubectl label namespace namespace-dev \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/enforce-version=latest
```

---

## Production Namespace

Create the namespace:

```bash
kubectl create namespace namespace-prod
```

Apply Restricted:

```bash
kubectl label namespace namespace-prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest
```

Verify:

```bash
kubectl get namespaces --show-labels
```

You should see the PSA labels associated with the namespaces.

---

# Step 2 — Deploy Example Pods

Now we can test Pods against the two different security profiles.

---

## Deployment in `namespace-dev`

The Baseline profile is designed to allow general-purpose application workloads while preventing known privilege-escalation configurations.

Example:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: baseline-pod
  namespace: namespace-dev

spec:
  containers:
    - name: nginx
      image: nginx

      securityContext:
        runAsUser: 1000
```

Apply:

```bash
kubectl apply -f baseline-pod.yaml
```

The Pod can be created under the Baseline profile because this configuration does not violate the relevant Baseline restrictions.

---

# Deployment in `namespace-prod`

Now create a Pod that attempts to run as root:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: restricted-pod
  namespace: namespace-prod

spec:
  containers:
    - name: nginx
      image: nginx

      securityContext:
        runAsUser: 0
```

Apply:

```bash
kubectl apply -f restricted-pod.yaml
```

Under the Restricted profile, this configuration violates the non-root requirement and the Pod will be rejected.

Conceptually:

```text
Pod
 ↓
namespace-prod
 ↓
PSA
 ↓
Restricted
 ↓
runAsUser: 0
 ↓
Violation ❌
 ↓
Pod rejected
```

---

# Step 3 — Fixing Security Issues in `namespace-prod`

Modify the Pod's `securityContext` to follow the Restricted security requirements:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: restricted-pod
  namespace: namespace-prod

spec:
  containers:
    - name: nginx
      image: nginx

      securityContext:
        runAsNonRoot: true

        seccompProfile:
          type: RuntimeDefault

        capabilities:
          drop:
            - ALL
```

Apply:

```bash
kubectl apply -f restricted-pod.yaml
```

This configuration follows important Restricted security practices:

```text
runAsNonRoot
      ↓
Don't run as root

seccompProfile
      ↓
Use RuntimeDefault seccomp profile

capabilities.drop: ALL
      ↓
Remove unnecessary Linux capabilities
```

For a real Restricted-compliant workload, the complete Pod specification must satisfy **all applicable Restricted requirements**, not just these three settings.

# Important Security Controls

Restricted workloads commonly involve settings such as:

### Non-root

```yaml
runAsNonRoot: true
```

### Seccomp

```yaml
seccompProfile:
  type: RuntimeDefault
```

### Drop capabilities

```yaml
capabilities:
  drop:
    - ALL
```

### Prevent privilege escalation

```yaml
allowPrivilegeEscalation: false
```

These controls address different parts of container security:

```text
runAsNonRoot
    ↓
Process identity

allowPrivilegeEscalation
    ↓
Privilege escalation

Capabilities
    ↓
Linux privileged operations

Seccomp
    ↓
Linux system calls
```

# Conclusion

Implementing **Pod Security Admission (PSA)** and **Pod Security Standards (PSS)** in Kubernetes 1.31 provides a built-in, standardized approach to securing workloads.

The key concepts are:

```text
PSS
 ↓
Defines security profiles

Privileged
Baseline
Restricted
```

and:

```text
PSA
 ↓
Enforces PSS

Enforce → Reject
Warn    → Warning
Audit   → Record
```

Policies can be applied at the namespace level:

```text
namespace-dev
      ↓
   Baseline

namespace-prod
      ↓
  Restricted
```

For production environments, a good approach is:

```text
Existing workloads
       ↓
Warn + Audit
       ↓
Identify violations
       ↓
Remediate workloads
       ↓
Test
       ↓
Enforce
       ↓
Restricted production workloads
```

**Final takeaway:**

> **PSS defines what secure Pod configurations look like, while PSA evaluates and enforces those standards when Pods are admitted to the cluster.** Together, they help prevent insecure configurations and privilege escalation while allowing security policies to be applied according to the requirements of different workloads and namespaces.
