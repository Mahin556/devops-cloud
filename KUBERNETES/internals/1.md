```text
Client  ───────── Request ─────────>  Server
Client  <──────── Response ─────────  Server
```


# 2. HTTP

**HTTP = HyperText Transfer Protocol**

It is an application-layer protocol used for communication between clients and servers.

Basic model:

```text
Client
   |
   | HTTP Request
   v
Server
   |
   | HTTP Response
   v
Client
```

Example:

```http
GET /api/v1/pods HTTP/1.1
Host: kubernetes.example.com
```

Response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "items": [...]
}
```

HTTP has evolved through several major versions:

```text
HTTP/1.1
   ↓
HTTP/2
   ↓
HTTP/3
```

---

# 3. HTTP/1.1

HTTP/1.1 was standardized in **1997** and is still widely supported.

It uses a **text-based HTTP protocol**.

Example:

```http
GET /users/123 HTTP/1.1
Host: example.com
Accept: application/json
```

The server might return:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "name": "Mahin"
}
```

## HTTP/1.1 connection model

Historically, requests on a connection were processed sequentially.

Simplified:

```text
Request 1 ───────────────>
             Response 1
             <────────────

Request 2 ───────────────>
             Response 2
             <────────────
```

This creates limitations when many requests need to happen concurrently.

HTTP/1.1 introduced/uses **persistent connections**, so the TCP connection can be reused:

```text
TCP connection
      |
      +--- Request 1
      +--- Response 1
      +--- Request 2
      +--- Response 2
      +--- Request 3
      +--- Response 3
```

It also has **HTTP pipelining**, but practical browser/server support was limited and it suffered from head-of-line blocking.

```text
   ↓

   ↓

   ↓
```


REST generally uses HTTP methods:

| HTTP Method | Purpose        |
| ----------- | -------------- |
| GET         | Read           |
| POST        | Create         |
| PUT         | Replace/update |

Example:


REST itself is **not a protocol**.

It is an **architectural style**.

HTTP is the protocol commonly used to implement REST APIs.

# 6. HTTP/2

HTTP/2 was standardized in **2015**.

Its major goal was to improve HTTP performance while maintaining the HTTP semantics developers already know.

The important features are:

```text
HTTP/2
 ├── Binary framing
 ├── Multiplexing
 ├── Stream-based communication
 ├── Header compression
 └── Multiple concurrent requests
```

---

# 7. HTTP/2 Binary Framing

HTTP/1.1 is primarily text-based.

HTTP/2 introduces a **binary framing layer**.

Conceptually:

```text
HTTP/1.1

GET /users HTTP/1.1
Host: example.com
...
```

HTTP/2:

```text
HTTP Messages
      ↓
Binary Frames
      ↓
TCP
```

The application still thinks in terms of HTTP requests/responses, but the underlying HTTP/2 implementation represents them as binary frames.

---

# 8. HTTP/2 Multiplexing

This is one of the most important HTTP/2 concepts.

Suppose a client needs:

```text
Request A
Request B
Request C
```

HTTP/1.1 can suffer from request/response ordering limitations.

HTTP/2 can multiplex multiple streams over **one TCP connection**:

```text
                 One TCP Connection
                        |
       +----------------+----------------+
       |                |                |
     Stream 1         Stream 3         Stream 5
       |                |                |
   Request A        Request B        Request C
```

Frames from different streams can be interleaved:

```text
A1 → B1 → C1 → A2 → C2 → B2 → A3
```

This is **multiplexing**.

### Simple definition

> Multiplexing means carrying multiple independent streams over a single connection.

---

# 9. HTTP/2 Header Compression

HTTP requests often repeat headers:

```http
Host:
Authorization:
Content-Type:
User-Agent:
Cookie:
```

HTTP/2 uses **HPACK** to compress HTTP headers.

So:

```text
HTTP/1.1
Repeated large headers
        ↓
More overhead
```

HTTP/2:

```text
Headers
   ↓
HPACK compression
   ↓
Less overhead
```

---

# 10. HTTP/3

HTTP/3 is the newer HTTP version and uses **QUIC**.

The major difference is:

```text
HTTP/1.1
    ↓
   TCP
    ↓
   IP
```

```text
HTTP/2
    ↓
   TCP
    ↓
   IP
```

But:

```text
HTTP/3
    ↓
   QUIC
    ↓
   UDP
    ↓
   IP
```

So:

> **HTTP/3 runs over QUIC, and QUIC runs over UDP.**

---

# 11. Why HTTP/3 Uses QUIC

TCP has a connection-level head-of-line blocking problem.

Imagine:

```text
TCP connection

Packet 1 ✓
Packet 2 ✗
Packet 3 ✓
Packet 4 ✓
```

Because TCP guarantees ordered delivery, later data may have to wait for packet 2.

QUIC provides independent streams:

```text
QUIC Connection
 ├── Stream 1
 ├── Stream 2
 ├── Stream 3
 └── Stream 4
```

Loss in one stream does not necessarily block progress of other streams.

QUIC also provides:

* Connection migration
* Encryption
* Multiplexed streams
* Faster connection establishment

# 12. HTTP Version Comparison

| Feature                 | HTTP/1.1      | HTTP/2       | HTTP/3          |
| ----------------------- | ------------- | ------------ | --------------- |
| Standardized            | 1997          | 2015         | 2022            |
| Transport               | TCP           | TCP          | QUIC            |
| Underlying IP transport | TCP           | TCP          | UDP             |
| Framing                 | Text-oriented | Binary       | Binary          |
| Multiplexing            | Limited       | Yes          | Yes             |
| Header compression      | No HPACK      | HPACK        | QPACK           |
| Connection migration    | No            | No           | Yes             |
| TLS integration         | Separate      | Commonly TLS | Built into QUIC |

A very important interview answer:

> **HTTP/1.1 and HTTP/2 use TCP, whereas HTTP/3 uses QUIC over UDP. HTTP/2 introduced multiplexing and binary framing, while HTTP/3 uses QUIC to provide multiplexed streams without TCP's connection-level head-of-line blocking.**

# 13. What is RPC?

RPC means:

> **Remote Procedure Call**

The idea is simple.

Instead of thinking:

```text
Send HTTP request
Receive HTTP response
Parse response
```

you think:

```text
Call a function
       ↓
Remote server executes it
       ↓
Return result
```

For example, locally:

```python
result = getUser(10)
```

With RPC, `getUser()` can actually execute on another machine:

```text
Application A
     |
     | getUser(10)
     v
Network
     |
     v
Application B
     |
     | executes getUser()
     v
Result
```

So RPC makes remote communication look somewhat like calling a local function.

---

# 14. RPC vs REST

### REST

You generally think in terms of **resources**:

```text
GET /users/10
```

### RPC

You generally think in terms of **operations/functions**:

```text
GetUser(10)
```

Conceptually:

```text
REST:

GET /users/10
        ↓
"Give me resource 10"


RPC:

GetUser(10)
        ↓
"Execute this operation"
```

Neither is universally better.

They solve communication problems differently.

# 15. What is gRPC?

Typical gRPC architecture:

gRPC commonly uses:

```text
gRPC
 ↓

HTTP/2
 ↓
```

# 16. Protocol Buffers

Protocol Buffers, or **Protobuf**, are used to define the data structures and RPC services.

Example:

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}

message GetUserRequest {
  int32 id = 1;
}

message User {
  int32 id = 1;
  string name = 2;
}
```

This defines:

```text
UserService
     |
     └── GetUser()
```

The request:

```text
GetUserRequest
     |
     └── id = 10
```

The response:

```text
User
 ├── id
 └── name
```

---

# 17. Why gRPC Is Fast

One reason is that gRPC commonly uses **Protobuf**, which is a compact binary serialization format.

Compare conceptually:

### JSON

```json
{
  "id": 10,
  "name": "Mahin"
}
```

### Protobuf

```text
Binary encoded representation
```

The binary representation is generally smaller and faster to serialize/deserialize than verbose JSON, although actual performance depends on the workload and implementation.

Then gRPC uses HTTP/2 features such as:

```text
HTTP/2
 ├── Multiplexing
 ├── Binary framing
 └── Header compression
```

# 18. gRPC Communication Types

gRPC supports four major communication patterns.

## 1. Unary RPC

One request → one response.

```text
Client                    Server
  |                         |
  |---- Request ----------->|
  |<---- Response -----------|
```

Example:

```text
GetUser()
```

---

## 2. Server Streaming

One request → multiple responses.

```text
Client                    Server
  |                         |
  |---- Request ----------->|
  |<---- Response 1 ---------|
  |<---- Response 2 ---------|
  |<---- Response 3 ---------|
```

Example:

```text
GetLogs()
```

Server can continuously send log records.

---

## 3. Client Streaming

Multiple requests → one response.

```text
Client                    Server
  |                         |
  |---- Data 1 ------------>|
  |---- Data 2 ------------>|
  |---- Data 3 ------------>|
  |---- Data 4 ------------>|
  |                         |
  |<---- Final Response -----|
```

---

## 4. Bidirectional Streaming

Both sides can continuously send messages.

```text
Client                    Server
  |                         |
  |---- Message 1 ---------->|
  |<---- Message 1 ----------|
  |---- Message 2 ---------->|
  |<---- Message 2 ----------|
  |---- Message 3 ---------->|
  |<---- Message 3 ----------|
```

This is possible because of HTTP/2's stream-based communication.

# 33. HTTP/1.1 vs HTTP/2 in One Example

Suppose your application needs:

```text
GET /users
GET /orders
GET /products
GET /payments
```

HTTP/1.1:

```text
TCP Connection

Request users
Response users

Request orders
Response orders

Request products
Response products

Request payments
Response payments
```

HTTP/2:

```text
One TCP Connection

Stream 1 → users
Stream 3 → orders
Stream 5 → products
Stream 7 → payments

Frames can be interleaved.
```

So HTTP/2 improves concurrency.

# 34. HTTP/2 vs HTTP/3

The key issue:

```text
HTTP/2
   ↓
HTTP/2 multiplexing
   ↓
TCP
   ↓
TCP ordering / retransmission
```

HTTP/3:

```text
HTTP/3
   ↓
QUIC
   ↓
Independent streams
   ↓
UDP
```

Therefore HTTP/3 can avoid **TCP's connection-level head-of-line blocking**.

But don't say:

> HTTP/3 has no packet loss.

It absolutely can have packet loss.

The difference is **how loss affects independent streams**.

# 35. Interview Answer: What is HTTP/1.1?

You can say:

> HTTP/1.1 is a widely used HTTP version standardized in 1997. It uses TCP and a text-oriented request/response model. It supports persistent connections, but its concurrency model is limited compared with HTTP/2 because HTTP/2 introduced native multiplexing and binary framing.

---

# 36. Interview Answer: What is HTTP/2?

> HTTP/2 is an HTTP version standardized in 2015 that uses TCP but introduces binary framing, multiplexing, streams, and HPACK header compression. Multiple HTTP requests and responses can be multiplexed over a single TCP connection.

---

# 37. Interview Answer: What is HTTP/3?

> HTTP/3 is the latest major HTTP version and uses QUIC over UDP instead of TCP. QUIC provides multiplexed streams, integrated TLS, connection migration, and avoids TCP's connection-level head-of-line blocking.

---

# 38. Interview Answer: What is RPC?

> RPC stands for Remote Procedure Call. It is a communication model where a client invokes an operation on a remote server as if it were calling a local procedure. RPC abstracts the underlying network communication.

---

# 39. Interview Answer: What is gRPC?

> gRPC is an RPC framework originally developed by Google. It commonly uses Protocol Buffers for serialization and HTTP/2 as the transport. It supports unary, server-streaming, client-streaming, and bidirectional-streaming RPCs and is commonly used for internal microservice communication.

---

# 40. Interview Answer: How is gRPC used in Kubernetes?

A strong answer:

> Kubernetes uses gRPC in several important internal interfaces. For example, kubelet communicates with container runtimes through the Container Runtime Interface, which uses gRPC. Kubernetes also communicates with etcd through its gRPC API, and CSI uses gRPC between Kubernetes components and CSI drivers. The Kubernetes API exposed by kube-apiserver, however, is an HTTP-based API rather than saying that all Kubernetes communication is gRPC.
