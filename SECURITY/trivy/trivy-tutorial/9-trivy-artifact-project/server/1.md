# Trivy Server Mode — Centralized Enterprise Scanning

## The Problem with Local Trivy at Scale

When every developer and CI pipeline runs Trivy locally:

| Problem | Impact |
|---------|--------|
| Each machine downloads the vulnerability DB | High network usage across org |
| Each pipeline updates the DB separately | Redundant downloads on every job |
| Scan results vary based on timing | Team A scans with Monday's DB, Team B with Friday's |
| DB download adds time to every CI job | Slower feedback loops |
| No central control over scan policy | Different teams use different severity thresholds |

> Local scanning works great for individuals — but it doesn't scale for enterprises.

---

## What Is Trivy Server Mode?

Instead of each client downloading the DB and scanning independently, you run **one central Trivy server** that:

- Holds the vulnerability DB (updated once, centrally)
- Accepts scan requests from multiple clients
- Performs the vulnerability matching
- Returns results to the client

```
Trivy Clients (CLI / CI pipelines)
        │
        │  Scan Request (component list)
        ▼
   Trivy Server  ──────► Central Vulnerability DB
        │                 (updated once, shared)
        │  Scan Results
        ▼
   Client gets findings
```

---

## Architecture — How It Works

```
Developer Laptop          CI/CD Pipeline           Another Pipeline
trivy image               trivy image              trivy fs
  --server                  --server                 --server
  http://trivy:4954          http://trivy:4954         http://trivy:4954
        │                        │                        │
        └────────────────────────┴────────────────────────┘
                                 │
                                 ▼
                         ┌──────────────┐
                         │ Trivy Server │  ◄── DB updates once here
                         │  :4954       │
                         └──────┬───────┘
                                │
                                ▼
                     Central Vulnerability DB
                       (~/.cache/trivy)
```

**What the client sends:** the list of extracted components (OS packages, library names + versions)
**What the server does:** vulnerability matching against its local DB
**What the client receives:** the final vulnerability report

The client still does artifact analysis (layer unpacking, package extraction) — only the DB lookup and matching happens on the server.

## Setting Up Trivy Server

### Step 1 — Start the server

```bash
# Start Trivy server on default port 4954
trivy server

# Start on a custom port
trivy server --listen 0.0.0.0:4954

# Start with a custom cache directory
trivy server --cache-dir /var/trivy/cache --listen 0.0.0.0:4954

# Start with token-based authentication
trivy server --listen 0.0.0.0:4954 --token mysecrettoken

# Start in background (production use)
nohup trivy server --listen 0.0.0.0:4954 &
```

### Step 2 — Use from any client

```bash
# Scan an image via remote server
trivy image --server http://trivy-server:4954 nginx:latest

# Scan filesystem via remote server
trivy fs --server http://trivy-server:4954 .

# Scan a repo via remote server
trivy repo --server http://trivy-server:4954 https://github.com/user/repo

# With token auth (if server uses --token)
trivy image \
  --server http://trivy-server:4954 \
  --token mysecrettoken \
  nginx:latest
```

## Server Configuration Options

```bash
# Full server start with all options
trivy server \
  --listen 0.0.0.0:4954 \          # bind address
  --cache-dir /var/trivy/cache \    # where DB is stored
  --token mysecrettoken \           # auth token (optional)
  --token-header X-Trivy-Token \    # custom header name (optional)
  --db-repository ghcr.io/aquasecurity/trivy-db  # custom DB source
```

### Server flags reference

| Flag | Default | Description |
|------|---------|-------------|
| `--listen` | `localhost:4954` | Bind address for the server |
| `--cache-dir` | `~/.cache/trivy` | Location of the vulnerability DB |
| `--token` | (none) | Auth token clients must provide |
| `--token-header` | `Trivy-Token` | HTTP header name for the token |
| `--db-repository` | Aqua's ghcr.io | Source for DB updates |

---

## Client Flags Reference

| Flag | Description |
|------|-------------|
| `--server <url>` | Trivy server URL |
| `--token <token>` | Auth token (must match server) |
| `--token-header <header>` | Custom auth header name |
| `--server-custom-headers` | Extra HTTP headers to send |

## Keeping the DB Updated on the Server

The server's DB needs to be kept fresh. Options:

### Option 1 — Restart server (simplest)

```bash
# Stop, update DB, restart
trivy image --download-db-only   # pre-download before starting
trivy server --listen 0.0.0.0:4954
```

### Option 2 — Cron job

```bash
# Update DB every 6 hours via cron
0 */6 * * * trivy image --download-db-only --cache-dir /var/trivy/cache
```

### Option 3 — Kubernetes CronJob (production)

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: trivy-db-updater
spec:
  schedule: "0 */6 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: trivy-updater
            image: aquasec/trivy:latest
            command:
            - trivy
            - image
            - --download-db-only
            - --cache-dir
            - /var/trivy/cache
            volumeMounts:
            - name: trivy-cache
              mountPath: /var/trivy/cache
          volumes:
          - name: trivy-cache
            persistentVolumeClaim:
              claimName: trivy-cache-pvc
          restartPolicy: OnFailure
```

  --name trivy-server \

## Kubernetes — Deploying Trivy Server

```yaml
# trivy-server-deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: trivy-server
  namespace: security
spec:
  replicas: 1
  selector:
    matchLabels:
      app: trivy-server
  template:
    metadata:
      labels:
        app: trivy-server
    spec:
      containers:
      - name: trivy
        image: aquasec/trivy:latest
        args:
        - server
        - --listen
        - 0.0.0.0:4954
        - --token
        - $(TRIVY_TOKEN)
        env:
        - name: TRIVY_TOKEN
          valueFrom:
            secretKeyRef:
              name: trivy-secret
              key: token
        ports:
        - containerPort: 4954
        volumeMounts:
        - name: cache
          mountPath: /root/.cache/trivy
      volumes:
      - name: cache
        persistentVolumeClaim:
          claimName: trivy-cache-pvc

---
apiVersion: v1
kind: Service
metadata:
  name: trivy-server
  namespace: security
spec:
  selector:
    app: trivy-server
  ports:
  - port: 4954
    targetPort: 4954
  type: ClusterIP
```

```bash
# Create the secret
kubectl create secret generic trivy-secret \
  --from-literal=token=mysecrettoken \
  -n security

# Deploy
kubectl apply -f trivy-server-deployment.yaml

# Clients inside the cluster use:
# --server http://trivy-server.security.svc.cluster.local:4954
```

## GitHub Actions — Using Trivy Server in CI/CD

```yaml
# .github/workflows/trivy-client.yml

name: Trivy scan via server

on:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Scan image via Trivy server
        run: |
          trivy image \
            --server ${{ secrets.TRIVY_SERVER_URL }} \
            --token ${{ secrets.TRIVY_TOKEN }} \
            --severity HIGH,CRITICAL \
            --exit-code 1 \
            --format sarif \
            --output trivy-results.sarif \
            ${{ env.IMAGE_NAME }}

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: trivy-results.sarif
```

> Store `TRIVY_SERVER_URL` and `TRIVY_TOKEN` as GitHub repository secrets.

## Local Mode vs Server Mode — Full Comparison

| | Local mode | Server mode |
|--|------------|-------------|
| **DB location** | Each machine downloads its own | One central server, shared |
| **DB updates** | Every pipeline re-downloads | Updated once on the server |
| **Consistency** | Varies by timing | Same DB for everyone |
| **CI speed** | Slower (DB download each run) | Faster (no DB download) |
| **Network usage** | High — N pipelines × DB size | Low — one download |
| **Scan policy** | Per-team, may differ | Centrally enforced |
| **Setup complexity** | Zero — just install Trivy | Requires server deployment |
| **Best for** | Solo devs, small teams, learning | Enterprises, many pipelines |

---

## When to Use Server Mode

**You SHOULD use server mode when:**
- You have many CI/CD pipelines (5+)
- You need consistent scan results across teams
- You operate in regulated environments (SOC2, PCI-DSS, ISO 27001)
- You care about auditability and centralized policy
- You want faster builds by eliminating DB downloads

**You DON'T need server mode when:**
- Solo developer or small team
- Local experiments and learning
- One-off scans
- You're just getting started with Trivy
