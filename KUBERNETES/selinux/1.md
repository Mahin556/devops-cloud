Yes. **SELinux is similar in purpose to AppArmor, but the way you configure it is different.** For CKS, the key thing is to understand that with SELinux you generally work with **labels + SELinux policies**, rather than creating an AppArmor-style profile with `apparmor_parser`.

Kubernetes supports SELinux through `securityContext.seLinuxOptions`. The SELinux module must be enabled on the Linux node for this to have an effect. ([Kubernetes][1])

# 1. AppArmor vs SELinux

Think of them like this:

```text
AppArmor
   ↓
Profile
   ↓
"deny writing to files"

SELinux
   ↓
Labels + Policy
   ↓
"this process/domain can access
this type of resource"
```

Both are **Mandatory Access Control (MAC)** mechanisms. ([Kubernetes][2])

A major conceptual difference:

| AppArmor                                    | SELinux                                           |
| ------------------------------------------- | ------------------------------------------------- |
| Profile-based                               | Label/policy-based                                |
| Profiles describe allowed/denied operations | Labels identify subjects/resources                |
| `apparmor_parser` loads profiles            | SELinux policy is managed by SELinux tools/policy |
| Kubernetes references an AppArmor profile   | Kubernetes assigns an SELinux context             |
| Example: `deny-write`                       | Example: `container_t`                            |

---

# 2. First Check SELinux on the Node

On the Kubernetes node:

```bash
getenforce
```

Typical output:

```text
Enforcing
```

Possible states:

```text
Enforcing
Permissive
Disabled
```

### Meaning

```text
Enforcing
   ↓
SELinux actively blocks violations

Permissive
   ↓
SELinux logs violations but doesn't enforce them

Disabled
   ↓
SELinux is not active
```

For actual enforcement, you want:

```text
Enforcing
```

You can also inspect:

```bash
sestatus
```

---

# 3. Understand SELinux Labels

SELinux works with **security contexts/labels**.

For example, you might see:

```text
system_u:system_r:container_t:s0
```

The important parts are:

```text
user : role : type : level
```

For example:

```text
system_u : system_r : container_t : s0
    |         |            |          |
   user      role         type       level
```

The **type** is especially important for access control.

---

# 4. Check SELinux Contexts

On a Linux node, you can use:

```bash
ls -Z
```

Example:

```text
-rw-r--r--. root root system_u:object_r:container_file_t:s0 test.txt
```

The `-Z` tells tools to show SELinux security contexts.

For processes:

```bash
ps -eZ
```

You might see:

```text
system_u:system_r:container_t:s0
```

So:

```text
ls -Z
   ↓
File SELinux label

ps -eZ
   ↓
Process SELinux label
```

# 5. Kubernetes Configuration

This is the important CKS part.

Kubernetes lets you assign an SELinux context using:

```yaml
securityContext:
  seLinuxOptions:
```

For example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: selinux-demo

spec:
  securityContext:
    seLinuxOptions:
      level: "s0:c123,c456"

  containers:
  - name: demo
    image: busybox
    command:
    - sleep
    - "3600"
```

Kubernetes documents `seLinuxOptions` as the field used to assign SELinux labels to containers/Pods. ([Kubernetes][1])

---

# 6. What is `level`?

This part:

```yaml
level: "s0:c123,c456"
```

is an SELinux **MCS (Multi-Category Security) level**.

Think:

```text
s0:c123,c456
     │     │
     └─────┴── categories
```

Categories can help isolate workloads.

For example:

```text
Pod A
s0:c100,c200

Pod B
s0:c300,c400
```

Different categories can provide separation between workloads.

Kubernetes notes that Pods with the same MCS label can access volumes under that label, so unique labels are important when you need inter-Pod protection. ([Kubernetes][1])

---

# 7. What Does Kubernetes Actually Do?

Suppose you write:

```yaml
securityContext:
  seLinuxOptions:
    level: "s0:c123,c456"
```

Kubernetes/container runtime arranges for the container processes to have that SELinux context.

Conceptually:

```text
Pod
 |
 | seLinuxOptions
 v
SELinux label
 |
 v
Container process
 |
 v
SELinux policy
 |
 v
Kernel
 |
 +---- Allow
 |
 +---- Deny
```

The important distinction is:

> **The YAML assigns the label; the SELinux policy determines what that label is allowed to access.**

Kubernetes itself isn't defining an entire SELinux policy in the Pod YAML. ([Kubernetes][2])

# 8. AppArmor Example vs SELinux Example

### AppArmor

You created:

```text
deny-write
```

and loaded it:

```bash
apparmor_parser -q deny-write
```

Then:

```yaml
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: deny-write
```

---

### SELinux

Instead of:

```text
deny-write
```

you assign an SELinux context:

```yaml
securityContext:
  seLinuxOptions:
    level: "s0:c123,c456"
```

Then the **existing SELinux policy** determines what that context can do.

---

# 9. Container-Level SELinux

You can also put `seLinuxOptions` inside the container's `securityContext`.

For example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: selinux-demo

spec:
  containers:
  - name: demo
    image: busybox

    securityContext:
      seLinuxOptions:
        level: "s0:c123,c456"

    command:
    - sleep
    - "3600"
```

Kubernetes supports SELinux options at both Pod and container security-context levels; container-level settings take precedence when both are specified. ([Kubernetes][3])

# 11. Important: SELinux Must Exist on the Node

Just like your AppArmor example, this is a **node/kernel-level feature**.

If your node doesn't have SELinux enabled:

```yaml
seLinuxOptions:
```

won't magically install or enable SELinux.

Kubernetes explicitly notes that the SELinux security module must be loaded on the host OS. ([Kubernetes][1])

So the mental model is:

```text
Node
 |
 +-- SELinux enabled?
       |
       +-- No → seLinuxOptions won't provide SELinux enforcement
       |
       +-- Yes
             |
             v
        SELinux policy
             |
             v
           Pod
             |
             v
       SELinux context
```

# 12. SELinux Labels on Volumes

This is another important difference from your AppArmor example.

SELinux can also label **files/volumes**.

For example:

```text
Process
  |
  | process label
  v
container_t
```

and:

```text
File
  |
  | file label
  v
container_file_t
```

SELinux's policy decides whether:

```text
container_t
```

can access:

```text
container_file_t
```

This is why SELinux can provide very strong isolation around container filesystem access.

Kubernetes also handles SELinux labeling for supported volumes when `seLinuxOptions` are specified. ([Kubernetes][1])

# 14. AppArmor vs SELinux — CKS Mental Model

This is probably the most useful comparison for you:

```text
                 Linux Kernel
                     |
          +----------+----------+
          |                     |
       AppArmor              SELinux
          |                     |
      Profiles              Labels
          |                     |
   apparmor_parser        SELinux policy
          |                     |
          +----------+----------+
                     |
                  Kernel
                     |
               Allow / Deny
```

### AppArmor

```text
Create profile
      ↓
Load profile
      ↓
apparmor_parser
      ↓
Attach profile to Pod
      ↓
Enforce
```

### SELinux

```text
SELinux enabled
      ↓
SELinux policy
      ↓
Assign SELinux context
      ↓
Kubernetes securityContext
      ↓
Kernel enforces policy
```

# 15. One Important Correction to the AppArmor Analogy

Don't think:

```text
AppArmor profile = SELinux profile
```

They aren't equivalent concepts.

A better comparison is:

```text
AppArmor:
    Profile → rules → enforcement

SELinux:
    Label/context → policy → enforcement
```

Kubernetes describes SELinux as restricting access based on **security labels and policies**, while AppArmor uses loaded profiles. ([Kubernetes][2])

## ⭐ The key difference to memorize

> **AppArmor asks: "Which profile/rules should this process follow?"**

> **SELinux asks: "What security label does this process/resource have, and does the SELinux policy allow this interaction?"**

Both provide **Mandatory Access Control**, but their policy models are different. ([Kubernetes][2])
