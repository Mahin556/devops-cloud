Good question to nail precisely — there's actually a **progression of statuses** as the startup probe fails, not just one single state. Let me walk through the exact sequence.

## Status progression when startupProbe fails

### Phase 1 — while still within failureThreshold

```bash
kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
demo-pod    0/1     Running   0          15s
```

The pod shows `Running` but `0/1` READY — the container process is actually up, but the startupProbe is still checking and hasn't hit `failureThreshold` yet. During this window:
- Liveness probe: **completely disabled** — not running at all
- Readiness probe: **completely disabled** — not running at all
- Traffic: **not routed to this pod** (READY is 0/1)

### Phase 2 — startupProbe hits failureThreshold (e.g. `failureThreshold: 30` × `periodSeconds: 10` = 300s elapsed)

The kubelet **kills the container** immediately. Pod status transitions to:

```bash
NAME        READY   STATUS             RESTARTS   AGE
demo-pod    0/1     CrashLoopBackOff   1          5m
```

CrashLoopBackOff state indicates that the backoff delay mechanism is currently in effect for a given container that is in a crash loop, failing and restarting repeatedly.

### Phase 3 — kubectl describe (the detailed picture)

This is where you actually see *why* it failed, not just that it did:

```bash
kubectl describe pod demo-pod
```

```
Containers:
  http:
    State:          Waiting
      Reason:       CrashLoopBackOff     ← current state
    Last State:     Terminated
      Reason:       Error                 ← how it ended
      Exit Code:    1                     ← killed by kubelet = non-zero exit
    Ready:          False
    Restart Count:  3

Events:
  Warning  Unhealthy  2m   kubelet  Startup probe failed: Get "http://...:8080/healthz": connection refused
  Warning  BackOff    30s  kubelet  Back-off restarting failed container
```

The **Events section** is the key — this is where you see the actual startup probe failure message, not just the CrashLoopBackOff wrapper.

## The exponential backoff timing

Kubernetes will wait an increasing back-off time between restarts — exponential delay between restarts (10s, 20s, 40s…) which is capped at five minutes. When a pod state is displaying CrashLoopBackOff, it means that it's currently waiting the indicated time before restarting the pod again.

So what you'd observe over time:

| Restart # | Status during wait | Wait before next attempt |
|---|---|---|
| 0 | Running (probe checking) | — |
| 1 | CrashLoopBackOff | 10s |
| 2 | CrashLoopBackOff | 20s |
| 3 | CrashLoopBackOff | 40s |
| 4 | CrashLoopBackOff | 80s |
| 5+ | CrashLoopBackOff | capped at 300s (5 min) |

Between each CrashLoopBackOff wait, there's a brief window where the pod flips back to `Running` (startupProbe checking again) before crashing again. You may also be "lucky" enough to find the pod in the brief time it is in the Running or the Failed state.

## One important nuance — startupProbe vs livenessProbe in the Events

Both startupProbe and livenessProbe failures ultimately produce `CrashLoopBackOff`, but the Events tell them apart:

```
# startupProbe failure event:
Warning  Unhealthy  kubelet  Startup probe failed: ...

# livenessProbe failure event:
Warning  Unhealthy  kubelet  Liveness probe failed: ...
```

This matters for debugging — if you see "Startup probe failed" specifically, you know the app never successfully initialized (the startup window expired), vs "Liveness probe failed" which means the app started fine but degraded later during normal runtime.

## Backoff reset — one gotcha worth knowing

If a container runs successfully for a certain duration (e.g., 10 minutes), Kubernetes resets the backoff delay, treating any new crash as the first one. So if your app intermittently starts successfully and then later fails its liveness probe, the restart counter and backoff timer reset — the pod might not show a high restart count even if it's been failing repeatedly over a long period.
