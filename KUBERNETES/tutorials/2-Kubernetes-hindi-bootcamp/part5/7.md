**Pod Overhead** is a Kubernetes feature that accounts for the resources (CPU and memory) consumed by the **Pod's infrastructure** itself, separate from the resources used by your application containers.

In standard Linux containers (using `runc`), this overhead is practically zero (or negligible). However, when using **sandboxed runtimes** (like Kata Containers, gVisor, or Firecracker) that run each Pod inside a lightweight Virtual Machine (VM), the VM itself consumes CPU and memory just to stay alive. Pod Overhead ensures the scheduler and kubelet account for this extra cost.

---

### 🎯 Why Does It Exist? (The Problem It Solves)

**Without Pod Overhead**:
- Your Pod requests `200Mi` of memory for your app.
- The scheduler finds a node with `200Mi` free and places the Pod there.
- The runtime starts a VM for the Pod. The VM itself consumes `120Mi` just to run the guest OS kernel.
- Total usage = `200Mi` (app) + `120Mi` (VM) = `320Mi`.
- The node runs out of memory, and the VM (or your app) gets killed by the OOM Killer.

**With Pod Overhead**:
- You define the overhead (`120Mi`) in the `RuntimeClass`.
- The scheduler adds `120Mi` to your app's `200Mi` request.
- It schedules the Pod only if the node has **`320Mi`** free.
- The node stays stable.

---

### ⚙️ How It Works (The Mechanism)

1.  **Define Overhead in a `RuntimeClass`**: You create a `RuntimeClass` object that specifies the fixed overhead for any Pod using that runtime.

2.  **Pod References the `RuntimeClass`**: Your Pod spec sets `runtimeClassName` to that class.

3.  **Scheduler Adds Overhead**: The scheduler calculates the Pod's total resource usage as:
    `Total = (Sum of container requests) + (Pod Overhead)`
    It uses this total to decide if a node has enough capacity.

4.  **Kubelet Enforces Overhead**: The kubelet allocates cgroup limits that include both the containers and the overhead, ensuring the sandbox gets its reserved resources.

---

### 📝 YAML Example

**1. Define the RuntimeClass with Overhead** (for a VM-based runtime like Kata):
```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata-runtime
handler: kata   # The name of the runtime handler in containerd/CRI-O
overhead:
  podFixed:
    memory: "128Mi"
    cpu: "250m"
```

**2. Use it in a Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  runtimeClassName: kata-runtime   # This triggers the overhead
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        memory: "256Mi"    # App requests 256Mi
        cpu: "500m"
```
- **Scheduler sees**: `256Mi + 128Mi = 384Mi` memory, and `500m + 250m = 750m` CPU.
- **Result**: The Pod is only scheduled if the node has at least 384Mi of memory available.

### 🔍 Where Does Overhead Come From?

The overhead values depend entirely on the runtime and the node's OS. For example:

| Runtime | Typical Overhead (Per Pod) | Notes |
| :--- | :--- | :--- |
| **Kata Containers** | ~120-160Mi RAM, ~0.2-0.3 CPU | Runs a full lightweight VM with its own kernel. |
| **gVisor (runsc)** | ~50-100Mi RAM, ~0.1-0.2 CPU | Runs a userspace kernel (sentry). |
| **Windows Containers** | ~1-2Gi RAM, ~0.5-1 CPU | Windows OS services per Pod. |
| **Standard runc (Linux)** | **0** (No explicit overhead) | The `pause` container uses ~2-5Mi, but it's negligible and not part of Pod Overhead by default. |

---

### ⚠️ Important Caveats

1.  **Only for Scheduling and Cgroups**: Overhead affects *scheduling decisions* (via the scheduler) and *cgroup enforcement* (via kubelet). It does **not** show up in `kubectl top pod` (that only shows application container usage).
2.  **Default is Zero**: For the default `runc` runtime, the overhead is considered `0`. You do not need to define it.
3.  **Must be Defined in RuntimeClass**: You cannot set overhead directly on a Pod; it must be part of the `RuntimeClass` definition. This ensures consistency for all Pods using that sandbox technology.
4.  **GA Status**: Pod Overhead has been stable (GA) since Kubernetes **v1.24**.

---

### 💎 Summary

| Aspect | Explanation |
| :--- | :--- |
| **What it is** | Resources (CPU/Memory) consumed by the Pod's infrastructure (e.g., VM/sandbox) that your app doesn't directly use. |
| **Why it exists** | To prevent the scheduler from overcommitting nodes when using VM-based or sandboxed runtimes. |
| **Where it's defined** | Inside the `RuntimeClass` object under `overhead.podFixed`. |
| **Who enforces it** | The scheduler (for placement) and the kubelet (for cgroup allocation). |
| **Does it apply to standard Linux (runc)?** | No. By default, it is `0`. The `pause` container overhead is negligible and not explicitly modeled here. |

**In short**: Pod Overhead ensures that when you run a Pod inside a Virtual Machine (like with Kata or gVisor), Kubernetes reserves enough node resources for **both** your app and the VM itself, preventing crashes due to unaccounted system resource usage.
