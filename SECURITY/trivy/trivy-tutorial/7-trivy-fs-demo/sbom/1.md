# SBOM — Software Bill of Materials

## What Is SBOM?

SBOM = **Software Bill of Materials**

An SBOM is a **detailed inventory of everything inside a software artifact** — like an ingredients label for your application.

It answers:
- What components are used?
- Which versions?
- Where did they come from?
- What licenses do they use?

> **Analogy:** Just like a food product lists "Oats 40%, Honey 25%, Almonds 15%…", an SBOM lists every library, framework, and dependency inside your software with its version and source.

---

## Why SBOM Is Important

### The problem — modern software is complex

- Uses dozens/hundreds of open-source libraries
- Has deep, nested dependency chains (A depends on B which depends on C…)
- Pulls code from many sources (npm, pip, GitHub, internal registries)

### Without SBOM

| Problem | Impact |
|---------|--------|
| You don't know what's inside your app | Can't respond to new CVEs quickly |
| Vulnerability response is slow | Zero-day takes days/weeks to patch |
| Compliance becomes difficult | Can't prove what licenses you're using |

### With SBOM

- **Visibility** — know exactly what's in your software
- **Traceability** — trace every component back to its source
- **Faster security response** — when Log4Shell hits, you know in seconds if you're affected

---

## Two Industry-Standard SBOM Formats

Both formats are:
- Machine readable (JSON / XML / tag-value)
- Industry accepted
- Tool-agnostic (work with Trivy, Syft, FOSSA, etc.)

---

## CycloneDX

- Created by **OWASP**
- Designed specifically for **application security**
- Lightweight and modern
- Widely used in DevSecOps pipelines

**Best suited for:**
- Vulnerability management
- CI/CD pipelines
- Cloud-native applications

---

## SPDX — Software Package Data Exchange

- Maintained by the **Linux Foundation**
- Older and more formal standard
- Strong focus on **licenses and compliance**
- Used heavily in enterprise and legal audits

**Best suited for:**
- License compliance
- Legal review
- Regulatory environments

---

## CycloneDX vs SPDX — Comparison

| Feature | CycloneDX | SPDX |
|---------|-----------|------|
| **Focus** | Security | Compliance & licensing |
| **Created by** | OWASP | Linux Foundation |
| **CI/CD friendly** | Yes | Partial |
| **Vulnerability use** | Strong | Limited |
| **License depth** | Basic | Strong |
| **DevSecOps usage** | High | Medium |

> **Rule of thumb:** Use CycloneDX for DevSecOps pipelines. Use SPDX for enterprise compliance and legal audits. Trivy can generate both.

## Generating SBOM with Trivy

### From a container image

```bash
# Generate CycloneDX SBOM from image
trivy image --format cyclonedx --output sbom.json nginx:latest

# Generate SPDX SBOM from image
trivy image --format spdx-json --output sbom.spdx.json nginx:latest

# SPDX in tag-value format (human readable)
trivy image --format spdx --output sbom.spdx nginx:latest
```

### From a filesystem / source code

```bash
# CycloneDX from local project
trivy fs --format cyclonedx --output sbom.json .

# SPDX from local project
trivy fs --format spdx-json --output sbom.spdx.json .
```

### From a Git repo

```bash
# CycloneDX from remote repo
trivy repo --format cyclonedx --output sbom.json \
  https://github.com/user/repo

# SPDX from remote repo
trivy repo --format spdx-json --output sbom.spdx.json \
  https://github.com/user/repo
```

---

## Scanning an Existing SBOM for Vulnerabilities

Once you have an SBOM file, you can scan it directly — without the original image or code:

```bash
# Scan a CycloneDX SBOM for vulnerabilities
trivy sbom sbom.json

# Scan an SPDX SBOM
trivy sbom sbom.spdx.json

# Filter severity
trivy sbom --severity HIGH,CRITICAL sbom.json

# JSON output
trivy sbom --format json --output vuln-report.json sbom.json
```

> This is powerful for supply chain security — you can audit third-party SBOMs you receive from vendors.

## What's Inside an SBOM File?

### CycloneDX JSON — example snippet

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.4",
  "version": 1,
  "metadata": {
    "component": {
      "name": "my-app",
      "version": "1.0.0",
      "type": "application"
    }
  },
  "components": [
    {
      "type": "library",
      "name": "django",
      "version": "3.2.1",
      "purl": "pkg:pypi/django@3.2.1",
      "licenses": [{ "license": { "id": "BSD-3-Clause" } }]
    },
    {
      "type": "library",
      "name": "requests",
      "version": "2.27.1",
      "purl": "pkg:pypi/requests@2.27.1"
    }
  ]
}
```

Each component records: **name + version + package URL (purl) + license**.

## SBOM in a CI/CD Pipeline

```yaml
# .github/workflows/sbom.yml

name: Generate and scan SBOM

on:
  push:
    branches: [main]

jobs:
  sbom:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Generate CycloneDX SBOM
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: fs
          scan-ref: .
          format: cyclonedx
          output: sbom.json

      - name: Scan SBOM for vulnerabilities
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: sbom
          scan-ref: sbom.json
          severity: HIGH,CRITICAL
          exit-code: 1

      - name: Upload SBOM as artifact
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json
```

## SBOM Is Not a One-Time Activity

> **SBOM is a living artifact — not a checkbox.**

| Rule | Why |
|------|-----|
| Must be regenerated on every build | Dependencies change with every `npm install` or `pip install` |
| Every version needs its own SBOM | v1.0 and v1.1 may have completely different components |
| Old SBOMs become outdated | A component safe today may have a CVE tomorrow |

**Best practice:** Generate SBOM automatically in CI/CD on every merge to `main` and store it as a build artifact alongside the image.

## Key Takeaways

| Concept | Summary |
|---------|---------|
| **SBOM** | Inventory of all software components, versions, and sources |
| **Why it matters** | Supply chain security, compliance, faster vuln response |
| **CycloneDX** | Security-focused, OWASP, best for DevSecOps |
| **SPDX** | Compliance-focused, Linux Foundation, best for legal/enterprise |
| **Trivy** | Can generate both CycloneDX and SPDX, and scan existing SBOMs |
| **Lifecycle** | Living artifact — regenerate on every build |
