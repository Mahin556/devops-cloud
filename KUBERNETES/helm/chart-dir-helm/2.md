The **`charts/` directory in Helm** is mainly used for **subcharts/dependent charts**.

Think of it like this:

> **Main chart = application**
> **`charts/` = other Helm charts that your application depends on**

### 1. What is `charts/`?

Suppose you have this structure:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── templates/
│   └── deployment.yaml
└── charts/
    ├── frontend/
    │   ├── Chart.yaml
    │   ├── values.yaml
    │   └── templates/
    │       └── deployment.yaml
    └── backend/
        ├── Chart.yaml
        ├── values.yaml
        └── templates/
            └── deployment.yaml
```

Here:

```text
myapp
```

is the **parent/main chart**.

And:

```text
charts/frontend
charts/backend
```

are **subcharts**.

So when you run:

```bash
helm install myapp ./myapp
```

Helm can install the parent chart **and its dependent subcharts**.

---

## 2. When do we use `charts/`?

You use `charts/` when your application is composed of **multiple Helm charts**.

For example, imagine an application has:

```text
Frontend
Backend
Database
Redis
```

You could structure it as:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── templates/
└── charts/
    ├── frontend/
    ├── backend/
    ├── redis/
    └── database/
```

The parent chart can manage these components together.

---

## 3. Why not just put everything in `templates/`?

You could put everything directly in:

```text
templates/
```

but that becomes difficult to manage for large applications.

For example:

```text
templates/
├── frontend-deployment.yaml
├── frontend-service.yaml
├── backend-deployment.yaml
├── backend-service.yaml
├── redis-deployment.yaml
├── redis-service.yaml
├── database-deployment.yaml
└── database-service.yaml
```

Instead, you can separate reusable components into charts:

```text
charts/
├── frontend/
├── backend/
├── redis/
└── database/
```

This provides better organization and allows charts to be **reused independently**.

---

## 4. Very important: `charts/` is usually populated through dependencies

You normally don't manually create a dependency chart from scratch.

For example, your `Chart.yaml` could say:

```yaml
apiVersion: v2
name: myapp
version: 1.0.0

dependencies:
  - name: redis
    version: "20.0.0"
    repository: "https://charts.bitnami.com/bitnami"
```

Then:

```bash
helm dependency update
```

Helm downloads the Redis chart into:

```text
charts/
└── redis-20.0.0.tgz
```

Then your chart can use Redis as a dependency.

---

### Simple way to remember

```text
myapp/
│
├── templates/       ← Resources belonging to myapp
│
├── values.yaml      ← Configuration
│
├── Chart.yaml       ← Chart metadata + dependencies
│
└── charts/          ← Other Helm charts myapp depends on
```

**`charts/` = "charts inside my chart."**

A common real-world use is a **parent/application chart** that deploys several components together, where each component is maintained as a separate subchart.
