### 1. The Three-Step API Request Flow (Decoding Your Image)

Your notes perfectly describe the sequential gates a request passes through:

> *"Authentication → credential check → gets added before moving to authorization"*

- **Authentication**: *"Who are you?"* The system verifies the identity of the requester (user or ServiceAccount). It checks the provided credentials (certificates, tokens, etc.) and associates a `username` and `groups` with the request.

> *"Authorization → check if user is allowed to perform the requested operation"*

- **Authorization**: *"Are you allowed to do this?"* The system checks the authenticated user's permissions against the requested action (e.g., `GET /api/v1/pods`). It uses RBAC (Role-Based Access Control) or ABAC policies. If the user doesn't have the right permissions, the request is rejected with a `403 Forbidden`.

> *"Admission → policy check via admission controllers"*

- **Admission**: *"Does this request comply with cluster policies?"* This is a **post-authorization** step. Admission controllers intercept the request *after* authentication and authorization, but *before* the object is saved to `etcd`. They can **mutate** (modify) the object (e.g., inject a sidecar proxy) or **validate** it (e.g., ensure PodSecurity standards are met). If an admission controller rejects the request, the API returns an error.

### 2. Decoding Your "Top Section" (The External & Internal Access)

> *"external → UMS → managed by Kubernetes → used for Authentication → Request → Service account → Secret → Token"*

This maps to two distinct ways users authenticate:

| Your Note | Correct Interpretation |
| :--- | :--- |
| **"external" / "UMS"** | **User Management System** (External Identity Provider). This refers to plugins like **OIDC** (Google, Okta) or **Webhook** authentication. Users log in to the external provider, get a token, and present it to Kubernetes. |
| **"managed by Kubernetes"** | **Internal Authentication**. This refers to **ServiceAccount tokens**. These are managed entirely by Kubernetes. |
| **"Secret → Token"** | For legacy ServiceAccounts, the token is stored as a `Secret` object (e.g., `secret-type: kubernetes.io/service-account-token`). The Pod mounts this Secret, and the token is automatically sent to the API server when the application makes requests. |

**The Flow for a Human**:
`User` -> `kubectl` -> `kubeconfig` (contains certificate or token) -> `API Server` -> `Authentication Plugin` (checks against external UMS or internal certs).

**The Flow for a Pod**:
`Pod` (ServiceAccount) -> `Secret` (Token) -> Mounted to `/var/run/secrets/kubernetes.io/serviceaccount/token` -> API Server -> `ServiceAccount Token` authentication plugin validates it.

### 3. Deep Dive into the Authentication Plugins (Your List)

You listed **8 authentication plugins**. Here is exactly what each one does and when to use it.

| Plugin Name | How it works | When to use |
| :--- | :--- | :--- |
| **X509 Client Certs** (You wrote "A509") | Uses standard TLS client certificates (PEM files). `kubectl` presents `client-certificate` and `client-key` during the TLS handshake. | **The default for cluster admins**. The `admin.conf` kubeconfig uses this. Great for machine-to-machine or static identities. |
| **Static token file** | A CSV file on the control plane (`--token-auth-file`). Contains `token,user,uid,groups`. | **Legacy / Development only**. Never use in production. Requires kube-apiserver restart to update. |
| **Bootstrap tokens** | Special tokens used by `kubeadm` for joining new nodes (`bootstrap.kubernetes.io/token`). The `kubelet` presents this token to get its own client certificate. | **Node bootstrapping** (when adding a new worker node to the cluster). |
| **Service account tokens** | Legacy tokens stored in `Secret` objects (JWT format). Automatically mounted into Pods. | **Pods talking to the API server** (Default). However, this is **deprecated** (v1.22+) in favor of projected tokens. |
| **OpenID Connect (OIDC) tokens** | Uses external Identity Providers (IdP) like Google, Okta, Keycloak, or Dex. Users log in via `kubectl oidc-login` or a browser. | **Human users in production**. Enables single sign-on (SSO), MFA, and centralized user management. |
| **Webhook token authentication** | The API server calls an external webhook (HTTP endpoint) to validate a bearer token. The webhook returns the user's identity or rejects it. | **Custom authentication systems**. Used by tools like Vault or custom authorization proxies. |
| **Authenticating proxy** | The API server is configured behind a reverse proxy (e.g., nginx). The proxy sets HTTP headers (`X-Remote-User`, `X-Remote-Group`). | **Enterprise environments** where a corporate reverse proxy handles all authentication (e.g., SSO termination at the edge). |
| **Anonymous auth** | If no credential is presented, the API server treats the request as `system:anonymous`. | **Optional**. Usually disabled in production. Used for health checks or read-only public endpoints (rare). |

### 💡 The Golden Rule

- **Authentication** answers **"Who are you?"** (It consumes certs, tokens, or OIDC credentials).
- **Authorization** answers **"What are you allowed to do?"** (It checks RBAC policies).
- **Admission Control** answers **"Is this request allowed by cluster policies and does it need to be changed?"** (It enforces defaults, limits, and security standards).

Your note that Authentication checks happen *before* Authorization is exactly correct. Kubernetes processes requests through this strict, sequential pipeline every single time, ensuring security at every layer.
