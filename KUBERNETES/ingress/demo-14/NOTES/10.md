Let's examine each directive and what it does in the context of an NGINX reverse proxy forwarding HTTPS requests to your Kubernetes Ingress.

Example configuration:

```nginx
location / {
    proxy_pass https://172.18.0.120;

    proxy_ssl_server_name on;
    proxy_ssl_verify off;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
}
```

or, for certificate verification:

```nginx
location / {
    proxy_pass https://172.18.0.120;

    proxy_ssl_server_name on;
    proxy_ssl_trusted_certificate /etc/nginx/certs/ingress-ca.crt;
    proxy_ssl_verify on;
    proxy_ssl_verify_depth 2;

    proxy_set_header Host $host;
}
```

---

# 1. `proxy_pass`

```nginx
proxy_pass https://172.18.0.120;
```

This tells NGINX:

> Forward every request to this backend.

Example:

```text
Client
GET https://myapp.example.com/api
```

NGINX forwards:

```text
GET https://172.18.0.120/api
```

If you used:

```nginx
proxy_pass http://172.18.0.120;
```

then the connection from NGINX to the backend would be HTTP instead of HTTPS.

---

# 2. `proxy_ssl_server_name on`

```nginx
proxy_ssl_server_name on;
```

Enables **SNI (Server Name Indication)**.

SNI allows the client (here, NGINX acting as an HTTPS client) to tell the backend which hostname it is connecting to during the TLS handshake.

Without SNI:

```text
NGINX
   │
TLS Handshake
   │
No hostname sent
```

With SNI:

```text
NGINX
   │
TLS Handshake
   │
Server Name: myapp.example.com
```

This is important when:

* One Ingress serves multiple HTTPS hosts.
* Different certificates are used for different hostnames.

Without SNI, the backend may present the wrong certificate.

---

# 3. `proxy_ssl_verify`

```nginx
proxy_ssl_verify off;
```

Controls whether NGINX verifies the backend's certificate.

### `off`

```nginx
proxy_ssl_verify off;
```

NGINX accepts any certificate.

Good for:

* Labs
* Self-signed certificates
* Testing

Not recommended for production.

---

### `on`

```nginx
proxy_ssl_verify on;
```

NGINX verifies:

* certificate signature
* expiration
* issuing CA
* trust chain

If verification fails:

```text
502 Bad Gateway
```

---

# 4. `proxy_ssl_trusted_certificate`

```nginx
proxy_ssl_trusted_certificate /etc/nginx/certs/ingress-ca.crt;
```

This specifies **which CA certificates NGINX should trust** when verifying the backend certificate.

Example:

```text
Backend Certificate
        │
Signed by
        │
Lab CA
```

NGINX checks:

```text
/etc/nginx/certs/ingress-ca.crt
```

If the backend certificate chains back to that CA, verification succeeds.

For a self-signed certificate, this file can simply be the self-signed certificate itself.

---

# 5. `proxy_ssl_verify_depth`

```nginx
proxy_ssl_verify_depth 2;
```

Sets how many certificates deep NGINX will follow the certificate chain.

Example:

```text
Server Certificate
        │
Intermediate CA
        │
Root CA
```

Chain length:

```text
2
```

So:

```nginx
proxy_ssl_verify_depth 2;
```

is sufficient.

Typical values:

| Depth | Supports                     |
| ----- | ---------------------------- |
| 1     | Server → Root                |
| 2     | Server → Intermediate → Root |
| 3+    | Longer certificate chains    |

---

# 6. `proxy_set_header Host $host`

```nginx
proxy_set_header Host $host;
```

Passes the original `Host` header to the backend.

Client request:

```http
GET /api HTTP/1.1
Host: myapp.example.com
```

Without this directive:

```http
Host: 172.18.0.120
```

With it:

```http
Host: myapp.example.com
```

This is very important for Ingress because it routes requests based on the `Host` header.

Your Ingress rule:

```yaml
rules:
- host: myapp.example.com
```

expects:

```http
Host: myapp.example.com
```

If the host header becomes `172.18.0.120`, the rule won't match.

---

# 7. `proxy_set_header X-Real-IP`

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

Passes the client's IP address to the backend.

Client:

```text
192.168.1.50
```

Backend receives:

```http
X-Real-IP: 192.168.1.50
```

Useful for:

* Logging
* Auditing
* Rate limiting

---

# 8. `proxy_set_header X-Forwarded-For`

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

Keeps a chain of client IPs as the request passes through proxies.

Suppose:

```text
Client
  │
Reverse Proxy
  │
Ingress
  │
Application
```

The header becomes:

```text
X-Forwarded-For:
203.0.113.10, 10.0.0.5
```

where:

* `203.0.113.10` = original client
* `10.0.0.5` = reverse proxy

This lets the backend know the full path the request took.

---

# 9. `proxy_set_header X-Forwarded-Proto`

```nginx
proxy_set_header X-Forwarded-Proto https;
```

Tells the backend which protocol the **client** used.

Client:

```text
HTTPS
```

Backend receives:

```http
X-Forwarded-Proto: https
```

This is useful because many applications generate redirects or URLs based on whether the original request was HTTP or HTTPS.

Without it, an application behind a proxy may incorrectly think the request was plain HTTP.

---

# Complete request flow

```text
Browser
GET https://myapp.example.com/api

            │
            ▼

NGINX Reverse Proxy
    proxy_pass https://172.18.0.120
    Host: myapp.example.com
    X-Real-IP: 192.168.1.100
    X-Forwarded-For: 192.168.1.100
    X-Forwarded-Proto: https

            │
            ▼

Ingress Controller
Host matches:
myapp.example.com

Path:
/api

            │
            ▼

API Service
```

# Summary

| Directive                                                      | Purpose                                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `proxy_pass https://172.18.0.120;`                             | Forward requests to the backend over HTTPS.                                  |
| `proxy_ssl_server_name on;`                                    | Send the requested hostname using SNI during the TLS handshake.              |
| `proxy_ssl_verify off;`                                        | Do not verify the backend certificate (useful for labs).                     |
| `proxy_ssl_verify on;`                                         | Verify the backend's TLS certificate.                                        |
| `proxy_ssl_trusted_certificate ...`                            | Specify the CA or self-signed certificate to trust for backend verification. |
| `proxy_ssl_verify_depth 2;`                                    | Maximum certificate chain depth to verify.                                   |
| `proxy_set_header Host $host;`                                 | Preserve the original `Host` header so Ingress host-based routing works.     |
| `proxy_set_header X-Real-IP $remote_addr;`                     | Pass the client's IP address to the backend.                                 |
| `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` | Preserve the chain of client/proxy IP addresses.                             |
| `proxy_set_header X-Forwarded-Proto https;`                    | Tell the backend that the original client used HTTPS.                        |
