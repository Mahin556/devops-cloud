## 🧩 What is the `server-snippet` annotation?

The annotation `nginx.ingress.kubernetes.io/server-snippet` allows you to inject **custom NGINX configuration directives** directly into the `server` block (the virtual host configuration) generated by the Ingress controller for a specific host.

Every Ingress resource creates a corresponding `server` block in NGINX. This annotation gives you the ability to **customise that server block** with arbitrary NGINX directives, without having to modify the global NGINX configuration or rebuild the controller.

---

## 📝 Basic Syntax

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/server-snippet: |
      # place your NGINX directives here
      add_header X-Custom-Header "Hello from server snippet";
      client_max_body_size 10M;
spec:
  # ... rules etc.
```

**Important:** The value must be a **multi-line string** (use the `|` or `>` YAML block scalar). The directives you write are placed **inside** the `server { ... }` block of the generated configuration.

---

## 🛠️ Common Use Cases

| Use Case | Example |
|----------|---------|
| **Add custom response headers** | `add_header X-Frame-Options "SAMEORIGIN";` |
| **Override client body size** | `client_max_body_size 20M;` |
| **Define custom error pages** | `error_page 404 /custom-404.html;` |
| **Add basic authentication (or custom auth logic)** | `auth_basic "Restricted";` <br> `auth_basic_user_file /etc/nginx/htpasswd;` |
| **Rate limiting (global or per‑IP)** | `limit_req zone=mylimit burst=10 nodelay;` |
| **Geo‑based access rules** | `if ($geoip_country_code = "US") { return 403; }` |
| **Redirect HTTP to HTTPS (if not already handled)** | `return 301 https://$host$request_uri;` |
| **Custom logging format for this host** | `access_log /var/log/nginx/host-access.log custom_format;` |

## 📌 Full Example

Suppose you want to:
- Add a security header.
- Increase the maximum upload size for this specific host.
- Enable a custom access log format.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/server-snippet: |
      add_header X-Content-Type-Options "nosniff";
      client_max_body_size 50M;
      access_log /var/log/nginx/example-access.log main;
spec:
  ingressClassName: nginx
  rules:
  - host: example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: my-service
            port:
              number: 80
```

## ⚠️ Important Warnings & Best Practices

1. **Syntax errors break NGINX** – If you insert invalid NGINX directives, the Ingress controller will **reject the reload**, causing the entire NGINX process to fail. Always test your directives in a standalone NGINX setup first.

2. **You are responsible for the logic** – The controller does **not** validate the content of the snippet. A missing semicolon or a wrong directive can crash the ingress.

3. **Use location‑specific snippets when possible** – If your customisation only applies to a specific path, use `nginx.ingress.kubernetes.io/configuration-snippet` (which injects directives inside the `location` block) instead. This is safer because it only affects one path, not the whole host.

4. **Avoid overriding essential settings** – The controller already sets `proxy_pass`, `proxy_set_header`, etc. If you override them in the server‑snippet, you might break the routing.

5. **No access to `$` variables that are not defined** – NGINX variables like `$host`, `$request_uri` are available. But be careful with custom variables.

6. **The annotation applies to the entire host** – All paths under this host will be affected by the snippet.

---

## 🔄 `server-snippet` vs. `configuration-snippet`

| Feature | `server-snippet` | `configuration-snippet` |
|---------|------------------|--------------------------|
| Scope | **Entire `server` block** (the whole virtual host) | **Specific `location` block** (only the matched path) |
| Risk | Higher – affects all paths under the host | Lower – only affects one path |
| Use case | Headers, global limits, error pages | Rewrites, custom auth per path, CORS per path |
| Syntax | Injected at the server level | Injected inside the location block |

---

## 📋 How to Check If Your Snippet Was Applied

1. After applying the Ingress, exec into the controller pod:
   ```bash
   kubectl exec -it -n ingress-nginx deployment/ingress-nginx-controller -- cat /etc/nginx/nginx.conf
   ```
2. Search for the `server` block of your host (by `server_name`).
3. Look for the directives you added – they should appear inside the `server { ... }` block.

---

## ✅ Summary

- `server-snippet` = **powerful but dangerous** – use it when you need to customise the entire virtual host.
- Always test your NGINX directives separately.
- Prefer `configuration-snippet` (location‑level) for path‑specific changes.
- If the snippet breaks NGINX, the controller will log errors in its logs (`kubectl logs ...`), and the reload will fail, leaving the old configuration active.
