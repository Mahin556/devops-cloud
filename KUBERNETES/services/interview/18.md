# On-Premises Kubernetes External Access — Complete Guide

---

## The Real Problem Statement

On-premises Kubernetes lacks the cloud provider integration that makes
`type: LoadBalancer` work. In cloud:

```
type: LoadBalancer → cloud controller manager → creates AWS ELB automatically
                                                 assigns external IP
                                                 ready in ~30 seconds
```

On-premises with no special setup:

```
type: LoadBalancer → cloud controller manager: "what cloud? I don't know"
                   → Service stays in PENDING state forever
                   → EXTERNAL-IP: <pending>  ← stuck here permanently

kubectl get svc web-service
# NAME          TYPE           CLUSTER-IP    EXTERNAL-IP   PORT(S)
# web-service   LoadBalancer   10.96.45.23   <pending>     80:30080/TCP
#                              ↑ works        ↑ never assigned
```

You have four real options, each solving a different subset of the problem.

---

## Option 1 — NodePort (what the original answer uses)

### How it actually works under the hood

```
External client → Node IP:30080
                      │
                  iptables DNAT rule (kube-proxy installed this)
                      │
                  Pod IP:80 (any pod, any node, even if pod isn't on this node)
```

```
Node 1 (192.168.1.10)          Node 2 (192.168.1.11)
┌──────────────────┐           ┌──────────────────┐
│  :30080 open     │           │  :30080 open     │
│                  │           │                  │
│  web-pod-1 ✓    │           │  (no web pod)    │
│                  │           │                  │
│  iptables:       │           │  iptables:       │
│  30080→pod IP   │           │  30080→pod IP   │
└──────────────────┘           └──────────────────┘

Traffic to Node 2:30080 → kube-proxy forwards to web-pod-1 on Node 1
Traffic is NOT stuck on the node it arrives at
```

### Complete NodePort setup with all real constraints

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80            # ClusterIP port (internal cluster traffic)
      targetPort: 80      # port on the pod
      nodePort: 30080     # port on every node (range: 30000-32767)
  # Optional: if you want a client to only hit pods on the node
  # they connected to (avoids extra network hop, but less balanced):
  # externalTrafficPolicy: Local   # default is Cluster (forward anywhere)
```

### externalTrafficPolicy: Local vs Cluster — important trade-off

```
Cluster (default):
  Client → Node 2:30080 → kube-proxy → Pod on Node 1
  ✅ Always balanced — pods on any node handle traffic
  ❌ Source IP is NATted — pod sees Node 2's IP, not client's real IP
  ❌ Extra network hop when pod isn't on the receiving node

Local:
  Client → Node 2:30080 → only pods ON Node 2
  ✅ Preserves client source IP (no SNAT)
  ✅ No extra hop
  ❌ If no pod on Node 2, connection is DROPPED (not forwarded)
  ❌ Load balancer in front must do health checks to avoid sending
     traffic to nodes with no pod

# For HAProxy/Nginx in front with health checks: use Local
# For direct access without health-checked LB in front: use Cluster
```

### Real limitations of NodePort alone

```
❌ Port range limited to 30000-32767 (can't use standard ports 80/443)
❌ Clients must know node IPs (if node goes down, DNS must update)
❌ No SSL termination (just TCP forwarding)
❌ No host-based or path-based routing
❌ Not production-grade without something in front of it
```

## Option 2 — HAProxy in Front of NodePort (Production-Grade)

This is what "Method 2" in the original answer mentions but never explains.
Here's the complete setup:

### HAProxy config for Kubernetes NodePort backend

```
/etc/haproxy/haproxy.cfg
```

```
global
    log /dev/log local0
    maxconn 50000
    user haproxy
    group haproxy
    daemon

defaults
    log global
    mode tcp                    # L4 mode — pass through TLS to ingress
    option tcplog
    option dontlognull
    timeout connect 5s
    timeout client 50s
    timeout server 50s

#─── Frontend: what clients connect to ──────────────────────────────────────
frontend http-in
    bind *:80
    default_backend k8s-nodes-http

frontend https-in
    bind *:443
    default_backend k8s-nodes-https

#─── Backend: your Kubernetes worker nodes ───────────────────────────────────
backend k8s-nodes-http
    balance roundrobin
    option tcp-check              # health check: can we connect to this port?

    # List every worker node + NodePort
    # HAProxy marks a node DOWN if health check fails
    # Traffic only goes to nodes that respond
    server node1 192.168.1.10:30080 check inter 10s fall 3 rise 2
    server node2 192.168.1.11:30080 check inter 10s fall 3 rise 2
    server node3 192.168.1.12:30080 check inter 10s fall 3 rise 2

backend k8s-nodes-https
    balance roundrobin
    option tcp-check

    server node1 192.168.1.10:30443 check inter 10s fall 3 rise 2
    server node2 192.168.1.11:30443 check inter 10s fall 3 rise 2
    server node3 192.168.1.12:30443 check inter 10s fall 3 rise 2

#─── Stats page (optional but useful) ───────────────────────────────────────
frontend stats
    bind *:8404
    stats enable
    stats uri /stats
    stats refresh 10s
    stats auth admin:yourpassword
```

### HAProxy high availability (HAProxy itself shouldn't be a single point of failure)

```
                        DNS: webapp.example.com
                               │
                   ┌───────────┴───────────┐
                   │   Virtual IP (VIP)    │ ← Keepalived manages this
                   │   192.168.1.5:80      │
                   └───────────┬───────────┘
                               │
                   ┌───────────┴───────────┐
                   ▼                       ▼
          ┌──────────────┐       ┌──────────────┐
          │  HAProxy-1   │       │  HAProxy-2   │
          │  (MASTER)    │       │  (BACKUP)    │
          │  192.168.1.3 │       │  192.168.1.4 │
          └──────────────┘       └──────────────┘
                 │                       │
     ┌───────────┼───────────────────────┤
     ▼           ▼           ▼           ▼
  Node1       Node2       Node3       Node4
  :30080      :30080      :30080      :30080
```

```
# Keepalived config on HAProxy-1 (/etc/keepalived/keepalived.conf)
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100              # HAProxy-2 has priority 90
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass secret123
    }
    virtual_ipaddress {
        192.168.1.5/24       # VIP — floats to BACKUP if MASTER fails
    }
    # Optional: if haproxy process dies, fail over too
    track_script {
        chk_haproxy
    }
}

vrrp_script chk_haproxy {
    script "killall -0 haproxy"   # check if haproxy process is running
    interval 2
    weight -20                    # reduce priority by 20 if haproxy dies
}
```

## Option 3 — MetalLB (Makes LoadBalancer type work on bare metal)

MetalLB makes `type: LoadBalancer` work on-premises by implementing
a software load balancer using either ARP (Layer 2) or BGP (Layer 3).

### MetalLB Layer 2 mode (simpler, no router changes needed)

```yaml
# Step 1: Install MetalLB
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.3/config/manifests/metallb-native.yaml

# Step 2: Give MetalLB a pool of IPs it can assign
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: production-pool
  namespace: metallb-system
spec:
  addresses:
    - 192.168.1.100-192.168.1.120  # IPs you've reserved in your network
                                    # NOT used by nodes, routers, or other hosts

---
# Step 3: Advertise using Layer 2 (ARP)
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: production-l2
  namespace: metallb-system
spec:
  ipAddressPools:
    - production-pool
  # Optional: restrict which nodes can send ARP for these IPs
  nodeSelectors:
    - matchLabels:
        node-role.kubernetes.io/worker: ""
```

```yaml
# Step 4: Now type: LoadBalancer actually works
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: LoadBalancer          # MetalLB intercepts this
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

# Result:
kubectl get svc web-service
# NAME          TYPE           CLUSTER-IP    EXTERNAL-IP      PORT(S)
# web-service   LoadBalancer   10.96.45.23   192.168.1.100    80:30080/TCP
#                                            ↑ MetalLB assigned this
```

### How MetalLB L2 mode actually works (what the original doesn't explain)

```
Client sends ARP: "Who has 192.168.1.100?"
MetalLB speaker pod (on one node) responds: "I do! MAC: aa:bb:cc:dd:ee:ff"
All traffic to 192.168.1.100 now flows to THAT node
That node's kube-proxy routes to the correct pod

Failover: if that node goes down, MetalLB speaker on another node
          takes over ARP — typically in 10-30 seconds

Limitation of L2 mode:
❌ One node handles ALL external traffic (not truly load balanced at L3/L4)
❌ Failover is ~10-30 seconds (ARP cache expiry on clients)
❌ Doesn't scale well for very high traffic (single node bottleneck)
```

### MetalLB BGP mode (enterprise, true load balancing)

```yaml
# BGP mode: MetalLB peers with your router/switch
# Router does ECMP (Equal-Cost Multi-Path) across all nodes
# TRUE load balancing — each node gets its share directly from the router

apiVersion: metallb.io/v1beta2
kind: BGPPeer
metadata:
  name: core-switch
  namespace: metallb-system
spec:
  peerAddress: 192.168.1.1    # your router/switch IP
  peerASN: 65000              # router's BGP ASN
  myASN: 65001                # ASN for your cluster

---
apiVersion: metallb.io/v1beta1
kind: BGPAdvertisement
metadata:
  name: production-bgp
  namespace: metallb-system
spec:
  ipAddressPools:
    - production-pool
  aggregationLength: 32       # advertise /32 host routes per service
```

```
With BGP mode:
Router learns:  192.168.1.100/32 via Node1 (cost 1)
                192.168.1.100/32 via Node2 (cost 1)
                192.168.1.100/32 via Node3 (cost 1)

Router does ECMP — splits traffic evenly across all 3 nodes
True external load balancing without HAProxy
Failover: router detects BGP session drop → removes that path → ms failover

✅ True load balancing (not single-node bottleneck)
✅ Sub-second failover (BGP keepalives)
❌ Requires BGP-capable router/switch (enterprise hardware)
❌ More complex configuration
```

## Option 4 — Ingress Controller (The Production-Standard Approach)

NodePort + MetalLB/HAProxy gets traffic INTO the cluster.
Ingress handles what happens AFTER that — routing, TLS, virtual hosts.
These are two separate concerns that work together.

```
External traffic flow (complete production stack):

Client → DNS → HAProxy/MetalLB VIP → NodePort → Ingress Controller pod
                                                       │
                                              Ingress rules match:
                                              - Host: api.example.com → api-service
                                              - Host: app.example.com → web-service
                                              - Path: /admin → admin-service
                                              - TLS termination (cert-manager)
```

### NGINX Ingress Controller via NodePort (no MetalLB needed)

```yaml
# Install NGINX Ingress for bare-metal
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.9.5/deploy/static/provider/baremetal/deploy.yaml

# Bare-metal deploy uses NodePort by default:
kubectl get svc -n ingress-nginx
# NAME                       TYPE       PORT(S)
# ingress-nginx-controller   NodePort   80:30080/TCP,443:30443/TCP
```

```yaml
# Your Deployment stays unchanged — just plain ClusterIP service
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: ClusterIP              # not NodePort, not LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

---
# Ingress resource — routing rules for NGINX Ingress Controller
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    # Rate limiting
    nginx.ingress.kubernetes.io/limit-rps: "100"
    # Client body size
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - webapp.example.com
      secretName: webapp-tls        # created by cert-manager
  rules:
    - host: webapp.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
```

### cert-manager for automatic TLS (critical for production)

```yaml
# Install cert-manager
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.14.3/cert-manager.yaml

# ClusterIssuer for internal CA (on-prem without Let's Encrypt access)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: internal-ca
spec:
  ca:
    secretName: internal-ca-key-pair   # your internal CA cert/key

---
# ClusterIssuer for Let's Encrypt (if you have internet access)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx

---
# Add annotation to Ingress — cert-manager creates/renews cert automatically
metadata:
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    # or: cert-manager.io/cluster-issuer: "internal-ca"
```

## Complete Production Architecture (On-Premises)

```
Internet / Corporate Network
          │
    webapp.example.com (DNS A record → 192.168.1.5)
          │
    ┌─────▼─────────────────────────────────┐
    │        Virtual IP: 192.168.1.5        │ ← Keepalived floats VIP
    └─────┬─────────────────┬───────────────┘
          ▼                 ▼
   ┌──────────┐      ┌──────────┐
   │ HAProxy1 │      │ HAProxy2 │  ← L4 load balancer (MASTER/BACKUP)
   │ MASTER   │      │ BACKUP   │    health checks nodes
   └──┬───────┘      └──────────┘
      │  round-robin to healthy nodes
      ├──────────────┬──────────────┐
      ▼              ▼              ▼
  Node1:30080    Node2:30080    Node3:30080    ← NodePort on all workers
      │              │              │
      └──────────────┴──────────────┘
                     │
              iptables routes to:
                     │
         ┌───────────▼───────────┐
         │  ingress-nginx pod    │  ← 3 replicas, spread across nodes
         │  (any node)           │    TLS termination here
         └───────────┬───────────┘
                     │  routes based on host/path
         ┌───────────┼───────────┐
         ▼           ▼           ▼
    web-service  api-service  admin-service  ← ClusterIP services
         │           │           │
      web pods    api pods   admin pods
```

## Comparison — Which to Use When

| | NodePort alone | NodePort + HAProxy | MetalLB L2 | MetalLB BGP | Ingress |
|---|---|---|---|---|---|
| Standard ports (80/443) | ❌ | ✅ (HAProxy) | ✅ | ✅ | ✅ |
| Host/path routing | ❌ | ❌ | ❌ | ❌ | ✅ |
| TLS termination | ❌ | ❌ (passthrough) | ❌ | ❌ | ✅ |
| True load balancing | Partial | ✅ | ❌ (single node) | ✅ | ✅ |
| HA (no single point of failure) | ❌ | ✅ (Keepalived) | Partial | ✅ | ✅ |
| Setup complexity | Low | Medium | Low | High | Medium |
| Router changes required | ❌ | ❌ | ❌ | ✅ (BGP) | ❌ |
| Production-ready | Dev only | ✅ | ✅ small clusters | ✅ enterprise | ✅ |

## Quick Decision

```
Dev / testing only?
  → NodePort directly (no extra setup)

Small production, no BGP-capable switches?
  → MetalLB L2 + Ingress Controller + cert-manager

Medium production, have enterprise switches with BGP?
  → MetalLB BGP + Ingress Controller + cert-manager

No MetalLB, prefer traditional LB infrastructure?
  → HAProxy + Keepalived (VIP) + NodePort + Ingress Controller

Everything above, plus WAF / advanced traffic policies?
  → F5 BIG-IP or Citrix ADC as external LB → Ingress → services
```
