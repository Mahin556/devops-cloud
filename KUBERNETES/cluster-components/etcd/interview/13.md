The primary command used to find the leader in an etcd cluster is `etcdctl endpoint status`. When run with the `--write-out=table` flag, this command displays a clear table that includes an "IS LEADER" column, showing `true` for the current leader node and `false` for the followers.

For a quick, script-friendly check, you can filter the output using `grep` directly within the Kubernetes environment, as suggested in the search results.

### Common Commands to Find the etcd Leader

Here are the standard approaches used in most Kubernetes setups:

**1. The standard `etcdctl` command**
This is the core command-line tool for interacting with etcd. You typically need to provide the API version, endpoints, and paths to the TLS certificates for authentication.

```bash
# From within an etcd container or a master node with etcdctl installed
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint status --write-out=table
```

**2. Using `kubectl exec` into the etcd pod**
If you don't have direct access to the master node, you can execute the command remotely using `kubectl`. A common method is to first create an alias for the lengthy `etcdctl` command to make subsequent commands easier.

```bash
# First, get the name of an etcd pod
kubectl get pods -n kube-system | grep etcd

# Then, execute the command inside that pod
kubectl exec -it <etcd-pod-name> -n kube-system -- sh

# Inside the pod, you can set an alias for simplicity and then check the status
alias ec="etcdctl --endpoints=https://127.0.0.1:2379 --cacert /etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key"
ec endpoint status --cluster -w table
```

### Understanding the Output
When you run the command successfully, you will see a table similar to the one below. The key column is **"IS LEADER"**, where a value of `true` indicates the leader node for the cluster.

```
+------------------+------------------+---------+---------+-----------+------------+-----------+------------+
|    ENDPOINT      |        ID        | VERSION | DB SIZE | IS LEADER | RAFT TERM | RAFT INDEX | ...        |
+------------------+------------------+---------+---------+-----------+------------+-----------+------------+
| 10.240.0.17:2379 | 4917a7ab173fabe7 |  3.5.0  |   45 kB |      true |         4 |      16726 | ...        |
| 10.240.0.18:2379 | 59796ba9cd1bcd72 |  3.5.0  |   45 kB |     false |         4 |      16726 | ...        |
| 10.240.0.19:2379 | 94df724b66343e6c |  3.5.0  |   45 kB |     false |         4 |      16726 | ...        |
+------------------+------------------+---------+---------+-----------+------------+-----------+------------+
```
The node where `IS LEADER` is `true` is the one currently responsible for handling all write requests.

### Important Note on Command Variations

The exact path to the TLS certificates (`--cacert`, `--cert`, `--key`) and the API version can vary significantly depending on how your Kubernetes cluster was set up (e.g., using `kubeadm`, `k3s`, or a managed service).

- For **kubeadm** setups, the certificates are usually in `/etc/kubernetes/pki/etcd/`.
- For other distributions like **k3s**, the paths will be different.

Always verify the correct paths and API version (`ETCDCTL_API=3`) for your specific environment.
