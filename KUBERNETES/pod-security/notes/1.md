# Kubernetes Pod Security — Complete Guide

Kubernetes Pod Security is the set of mechanisms used to control **what a Pod/container is allowed to do** inside the cluster and on the underlying node.

A good mental model is:

> **Pod Security = Security Context + Pod Security Standards + Pod Security Admission + Linux security mechanisms + RBAC + Network/Storage controls**

The most important distinction is:

* **SecurityContext** → *How should this Pod/container run?*
* **Pod Security Standards (PSS)** → *What configurations are considered safe?*
* **Pod Security Admission (PSA)** → *Should Kubernetes allow/reject Pods violating those standards?
* **RBAC** → *Who is allowed to create/change Pods?*

Kubernetes currently defines three PSS levels: **Privileged, Baseline, and Restricted**. ([Kubernetes][1])

---

# 1. Why Pod Security Matters

Suppose you have:

```text
Kubernetes Node
│
├── Pod A → frontend
├── Pod B → backend
├── Pod C → database
└── Pod D → untrusted application
```

Containers are isolated, but they are **not equivalent to VMs**.

A badly configured container could potentially:

* run as root
* access the host filesystem
* use the host network
* access host PID namespace
* obtain powerful Linux capabilities
* mount sensitive filesystems
* use privileged mode
* access devices
* exploit kernel vulnerabilities
* escalate privileges

For example:

```yaml
securityContext:
  privileged: true
```

is extremely dangerous because the container gets broad access to the host.

Pod security attempts to reduce this attack surface.

---

# 2. The Four Layers You Should Understand

Think of Kubernetes security like this:

```text
                    Kubernetes Security
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
       WHO?              WHAT?             WHERE?
         │                 │                 │
       RBAC         Pod Security         NetworkPolicy
                         │
                ┌────────┴────────┐
                │                 │
          SecurityContext        PSA
                │
       ┌────────┼─────────┐
       │        │         │
     UID/GID  Caps     Seccomp
                │
        AppArmor / SELinux
```

There is another important layer:

```text
Image security
   ↓
Container runtime
   ↓
Linux kernel security
   ↓
Node security
```

So **Pod Security is important, but it is not the entire Kubernetes security model.**

---

# 3. SecurityContext

The `securityContext` is one of the most important concepts.

It controls security-related runtime settings for a Pod or container.

Kubernetes supports settings such as:

* UID/GID
* privileged mode
* Linux capabilities
* privilege escalation
* read-only root filesystem
* seccomp
* AppArmor
* SELinux
* filesystem groups
* supplemental groups
* namespace/user namespace behavior

([Kubernetes][2])

There are two places where you can define it:

```yaml
spec:
  securityContext:
```

and:

```yaml
spec:
  containers:
  - name: app
    securityContext:
```

---

# 4. Pod-level vs Container-level SecurityContext

## Pod level

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-demo

spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000

  containers:
  - name: app
    image: nginx
```

This applies to the Pod/container configuration where supported.

---

## Container level

```yaml
spec:
  containers:
  - name: app
    image: nginx

    securityContext:
      runAsUser: 1000
      allowPrivilegeEscalation: false
```

Container-level settings can override applicable Pod-level settings.

---

# 5. `runAsUser`

Controls the Linux UID used by the container process.

Example:

```yaml
securityContext:
  runAsUser: 1000
```

Instead of:

```text
root = UID 0
```

the application runs as:

```text
UID 1000
```

Check it:

```bash
kubectl exec pod-name -- id
```

Example:

```text
uid=1000(app) gid=1000(app)
```

---

# 6. `runAsGroup`

Controls the primary GID:

```yaml
securityContext:
  runAsUser: 1000
  runAsGroup: 1000
```

---

# 7. `runAsNonRoot`

This is extremely important.

```yaml
securityContext:
  runAsNonRoot: true
```

It tells Kubernetes that the container must not run as UID 0.

A common hardened configuration:

```yaml
securityContext:
  runAsNonRoot: true
```

If the image tries to run as root, Kubernetes/container runtime can reject the container.

---

# 8. `fsGroup`

Used primarily for filesystem ownership of supported volumes.

Example:

```yaml
securityContext:
  fsGroup: 2000
```

Suppose a volume is mounted:

```text
/mnt/data
```

The filesystem permissions may be adjusted so the application can access it using GID `2000`.

Example:

```yaml
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 2000
```

This is especially relevant with:

* PVCs
* shared volumes
* applications that don't run as root

Kubernetes applies `fsGroup` to supported volumes for ownership management. ([Kubernetes][2])

---

# 9. `privileged`

This is one of the biggest security risks.

```yaml
securityContext:
  privileged: true
```

A privileged container gets extensive access to the host.

For example:

```yaml
containers:
- name: app
  image: ubuntu
  securityContext:
    privileged: true
```

Avoid this unless there is a legitimate infrastructure requirement.

Examples where privileged workloads may sometimes be required:

* certain node-level agents
* some storage/network plugins
* container/runtime management
* specialized infrastructure workloads

But don't use it simply because:

> "My application doesn't work."

Instead determine exactly which capability/permission is needed.

---

# 10. Linux Capabilities

Linux capabilities split some root privileges into individual permissions.

Instead of:

```text
root → everything
```

Linux can grant specific capabilities.

Examples:

```text
NET_ADMIN
NET_BIND_SERVICE
SYS_ADMIN
SYS_PTRACE
CHOWN
SETUID
SETGID
```

You can drop capabilities:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL
```

This is excellent hardening.

Then add only what is actually required:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL
    add:
      - NET_BIND_SERVICE
```

For example, an application might need `NET_BIND_SERVICE` to bind to a privileged port.

---

# 11. Why `SYS_ADMIN` Is Dangerous

One capability that deserves special attention:

```text
CAP_SYS_ADMIN
```

It is extremely powerful and is often described as being close to a "new root" in terms of breadth.

Avoid:

```yaml
capabilities:
  add:
    - SYS_ADMIN
```

unless there is a strong, documented requirement.

---

# 12. `allowPrivilegeEscalation`

Example:

```yaml
securityContext:
  allowPrivilegeEscalation: false
```

This prevents a process from gaining more privileges than its parent process through mechanisms such as set-user-ID/set-group-ID binaries.

Kubernetes documents that this setting directly controls the Linux `no_new_privs` behavior. It is always effectively true for privileged containers or containers with `CAP_SYS_ADMIN`. ([Kubernetes][2])

For hardened applications:

```yaml
allowPrivilegeEscalation: false
```

is normally desirable.

---

# 13. `readOnlyRootFilesystem`

Example:

```yaml
securityContext:
  readOnlyRootFilesystem: true
```

This makes the container's root filesystem read-only.

Instead of:

```text
/
├── bin
├── etc
├── app
├── tmp        ← writable
└── var
```

you make the root filesystem:

```text
READ ONLY
```

If the application needs temporary storage:

```yaml
volumeMounts:
- name: tmp
  mountPath: /tmp

volumes:
- name: tmp
  emptyDir: {}
```

Then:

```text
Container root filesystem
        │
        ├── /app     READ ONLY
        ├── /etc     READ ONLY
        └── /tmp     writable
                     ↑
                  emptyDir
```

This is a very useful defense against attackers modifying binaries/scripts inside the container.

---

# 14. Seccomp

Seccomp = **Secure Computing**.

It restricts which Linux system calls a process can execute.

Linux applications make syscalls such as:

```text
open()
read()
write()
execve()
clone()
mount()
ptrace()
socket()
```

Seccomp can restrict them.

Kubernetes supports:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

This is a strong default for many workloads.

---

# 15. Seccomp Profiles

Common types include:

```yaml
seccompProfile:
  type: RuntimeDefault
```

or:

```yaml
seccompProfile:
  type: Localhost
  localhostProfile: my-profile.json
```

and:

```yaml
seccompProfile:
  type: Unconfined
```

`Unconfined` removes seccomp restrictions and is generally undesirable for hardened workloads.

The Baseline standard disallows explicitly setting Seccomp to `Unconfined`. ([Kubernetes][1])

---

# 16. AppArmor

AppArmor is a Linux security mechanism that restricts what applications can access.

For example, an AppArmor profile can restrict:

```text
files
directories
network operations
capabilities
```

Example:

```yaml
securityContext:
  appArmorProfile:
    type: RuntimeDefault
```

You can also use a node-local profile:

```yaml
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: my-profile
```

Kubernetes supports `RuntimeDefault`, `Localhost`, and `Unconfined` profile types. ([Kubernetes][3])

---

# 17. SELinux

SELinux provides mandatory access control.

Instead of only relying on:

```text
UID
GID
rwx
```

you can have SELinux labels controlling access.

Example:

```yaml
securityContext:
  seLinuxOptions:
    level: "s0:c123,c456"
```

SELinux is especially important on systems such as:

* RHEL
* Fedora
* CentOS Stream
* other SELinux-enabled distributions

The exact SELinux configuration depends heavily on the host/container runtime environment.

---

# 18. Host Namespaces

A normal Pod gets its own namespaces.

But Kubernetes lets you share host namespaces.

These are dangerous:

```yaml
hostNetwork: true
hostPID: true
hostIPC: true
```

---

## `hostNetwork`

```yaml
spec:
  hostNetwork: true
```

The Pod uses the node's network namespace.

Normally:

```text
Pod network namespace
       ↓
Pod IP
       ↓
CNI
       ↓
Node
```

With:

```yaml
hostNetwork: true
```

the Pod uses:

```text
Node network namespace
```

This can bypass expected network isolation.

---

# 19. `hostPID`

```yaml
hostPID: true
```

The Pod can see processes on the host.

Normally:

```text
Pod:
PID 1
PID 2
PID 3
```

With host PID:

```text
Pod
 │
 ├── node processes
 ├── kubelet
 ├── runtime processes
 └── other host processes
```

Very sensitive.

---

# 20. `hostIPC`

```yaml
hostIPC: true
```

Shares the host IPC namespace.

This can expose IPC mechanisms between the Pod and host.

---

# 21. HostPath

This is another major security concern.

Example:

```yaml
volumes:
- name: host
  hostPath:
    path: /
```

You could potentially mount:

```text
Node /
```

inside the Pod.

For example:

```yaml
volumeMounts:
- name: host
  mountPath: /host

volumes:
- name: host
  hostPath:
    path: /
```

Now:

```text
Pod
 │
 └── /host
       │
       └── Node filesystem
```

This is why the Baseline PSS forbids `hostPath` volumes. ([Kubernetes][1])

---

# 22. Pod Security Standards

Now we move from:

> "How do I configure security?"

to:

> "What configurations should Kubernetes allow?"

This is where **Pod Security Standards (PSS)** comes in.

There are three levels:

```text
Privileged
    ↓
Baseline
    ↓
Restricted
```

They are cumulative.

### Privileged

```text
Almost unrestricted
```

### Baseline

```text
Blocks known privilege-escalation mechanisms
```

### Restricted

```text
Strong hardening / best practices
```

([Kubernetes][1])

---

# 23. Privileged

The `Privileged` profile imposes essentially no restrictions.

It is intended for trusted infrastructure/system workloads.

Example:

```text
kube-system
node-level agents
special infrastructure workloads
```

You generally don't want ordinary application namespaces running under this profile.

---

# 24. Baseline

Baseline prevents many common privilege-escalation mechanisms while remaining practical for ordinary workloads.

It restricts things such as:

```text
privileged containers
host namespaces
hostPath
dangerous capabilities
unsafe AppArmor configuration
unsafe SELinux options
unsafe proc mounts
unsafe seccomp configuration
unsafe sysctls
Windows HostProcess
```

([Kubernetes][1])

---

# 25. Restricted

Restricted is the hardened profile.

It expects applications to follow modern container hardening practices.

A typical Restricted workload should look roughly like:

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true

  capabilities:
    drop:
      - ALL

  seccompProfile:
    type: RuntimeDefault
```

Depending on your Kubernetes version and workload, additional fields such as `runAsUser`, `runAsGroup`, and appropriate volume configuration may be needed.

---

# 26. Important Difference: PSS vs PSA

This is an interview favorite.

### PSS

**Pod Security Standards**

Defines:

> "What is allowed?"

### PSA

**Pod Security Admission**

Defines:

> "How do we enforce it?"

Think:

```text
PSS
 │
 │ defines policy
 ↓
PSA
 │
 │ enforces policy
 ↓
Pod
```

---

# 27. Pod Security Admission

Pod Security Admission is a **built-in Kubernetes admission controller**.

It evaluates Pods when they are admitted to the cluster.

It works at the **namespace level**. ([Kubernetes][4])

You configure it using namespace labels.

For example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production

  labels:
    pod-security.kubernetes.io/enforce: restricted
```

Now:

```text
Pod request
     ↓
API Server
     ↓
Pod Security Admission
     ↓
PSS = Restricted
     ↓
Does Pod comply?
    / \
  yes  no
   ↓    ↓
allow reject
```

---

# 28. PSA Modes

There are three important modes:

```text
enforce
audit
warn
```

---

## `enforce`

Violating Pods are rejected.

```yaml
pod-security.kubernetes.io/enforce: restricted
```

Example:

```bash
kubectl apply -f insecure-pod.yaml
```

Could result in:

```text
Error from server:
pods "..." is forbidden:
violates PodSecurity "restricted:latest"
```

---

## `audit`

The Pod is allowed, but the violation is recorded in audit information.

```yaml
pod-security.kubernetes.io/audit: restricted
```

Useful when migrating existing workloads.

---

## `warn`

The Pod is allowed but the user receives a warning.

```yaml
pod-security.kubernetes.io/warn: restricted
```

Excellent for testing migration.

---

# 29. Best Migration Strategy

Don't immediately do:

```yaml
enforce: restricted
```

on a large production cluster.

Instead:

```text
Step 1
warn = restricted

Step 2
audit = restricted

Step 3
Fix workloads

Step 4
enforce = restricted
```

Example:

```yaml
metadata:
  labels:

    pod-security.kubernetes.io/warn: restricted

    pod-security.kubernetes.io/audit: restricted

    pod-security.kubernetes.io/enforce: baseline
```

This gives you:

```text
Existing workloads
      │
      ├── Baseline enforcement
      │
      ├── Restricted warnings
      │
      └── Restricted audit
```

Then gradually move to:

```yaml
enforce: restricted
```

Kubernetes recommends evaluating namespaces and avoiding unlabeled namespaces as unexplained security gaps. ([Kubernetes][5])

```yaml
apiVersion: v1
kind: Namespace

metadata:
  name: production

  labels:
```

```bash
kubectl apply -f namespace.yaml
```

Check:

```bash
kubectl get ns production --show-labels
```

# 31. Secure Pod Example

Here's a practical hardened Pod:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: secure-app
  namespace: production

spec:

  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
    seccompProfile:
      type: RuntimeDefault

  containers:
  - name: app
    image: nginx:1.27

    securityContext:
      allowPrivilegeEscalation: false

      readOnlyRootFilesystem: true

      capabilities:
        drop:
          - ALL

    volumeMounts:
    - name: tmp
      mountPath: /tmp

  volumes:
  - name: tmp
    emptyDir: {}
```

Conceptually:

```text
                   Secure Pod
                       │
        ┌──────────────┼──────────────┐
        │              │              │
    non-root       no escalation    seccomp
        │              │              │
        ├──────────────┼──────────────┤
        │              │
   drop ALL caps   read-only /
                       │
                    /tmp
                   writable
```

# 32. What Does `Restricted` Actually Protect Against?

Imagine an attacker compromises your application.

Without hardening:

```text
Application
     ↓
Container
     ↓
root
     ↓
CAP_SYS_ADMIN
     ↓
host filesystem / kernel interfaces
     ↓
Node compromise
```

With stronger Pod security:

```text
Application
     ↓
non-root
     ↓
few/no capabilities
     ↓
no privilege escalation
     ↓
read-only filesystem
     ↓
seccomp
     ↓
AppArmor/SELinux
     ↓
much smaller attack surface
```

It doesn't make container escape impossible, but it can significantly reduce the blast radius.

---

# 33. Pod Security Is NOT RBAC

This distinction is critical.

RBAC answers:

> Who can create a Pod?

Pod Security answers:

> What kind of Pod can be created?

Example:

```text
User
 │
 │ kubectl create deployment
 ↓
API Server
 │
 ├── Authentication
 │
 ├── Authorization / RBAC
 │
 ├── Admission
 │      └── Pod Security Admission
 │
 └── Object stored
```

Suppose a user has:

```text
create pods
```

but the namespace has:

```text
enforce=restricted
```

The user can attempt to create a Pod, but a violating Pod can still be rejected.

---

# 34. RBAC + Pod Security Relationship

Consider:

```text
Developer
   │
   │ RBAC
   ↓
Can create Deployment
   │
   ↓
Deployment creates Pod
   │
   ↓
PSA checks Pod
   │
   ↓
Restricted
   │
   ├── compliant → allow
   └── violation → reject
```

This is a very important security architecture.

Kubernetes also warns that permission to create workloads can implicitly expose access to resources such as Secrets, ConfigMaps, and ServiceAccounts in the namespace. ([Kubernetes][6])

# 35. Service Account Security

A Pod may receive a ServiceAccount token.

If the application doesn't need Kubernetes API access, disable automatic mounting:

```yaml
spec:
  automountServiceAccountToken: false
```

Example:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: app

spec:
  automountServiceAccountToken: false

  containers:
  - name: app
    image: nginx
```

This reduces unnecessary credentials inside the container.

Kubernetes RBAC guidance explicitly recommends considering disabling automatic ServiceAccount token mounting when workloads don't need it. ([Kubernetes][6])

---

# 36. Secrets and Pod Security

Pod Security does **not** protect Secrets by itself.

You also need:

```text
RBAC
+
Secret management
+
Encryption at rest
+
Least privilege
```

For example:

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: database-secret
      key: password
```

But be careful who can:

```bash
kubectl get secrets
kubectl list secrets
kubectl create pods
```

Kubernetes notes that even `list`/`watch` permissions on Secrets can expose Secret contents. ([Kubernetes][6])

---

# 37. NetworkPolicy

Pod Security doesn't control network traffic.

You need:

```text
NetworkPolicy
```

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: backend-policy
  namespace: production

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
  - Ingress
  - Egress

  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend

  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
```

So:

```text
Pod Security
    ↓
"What can the container do?"

NetworkPolicy
    ↓
"Who can communicate with it?"
```

---

# 38. Resource Limits Are Also Security-Relevant

A malicious or broken Pod could consume:

```text
CPU
Memory
PIDs
ephemeral storage
```

Use:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi

  limits:
    cpu: 500m
    memory: 512Mi
```

Also consider:

```text
ResourceQuota
LimitRange
```

for namespace-level controls.

This is especially important in multi-tenant environments.

---

# 39. Pod Security and `hostPID`, `hostIPC`, `hostNetwork`

Remember:

| Setting       | Risk                             |
| ------------- | -------------------------------- |
| `hostNetwork` | Access to node network namespace |
| `hostPID`     | Visibility into host processes   |
| `hostIPC`     | Access to host IPC namespace     |
| `hostPath`    | Potential host filesystem access |
| `privileged`  | Broad host-level privileges      |

Baseline specifically disallows host namespace sharing and privileged containers, and forbids HostPath volumes. ([Kubernetes][1])

# 40. Dangerous Pod Configuration

Avoid configurations like:

```yaml
spec:
  hostNetwork: true
  hostPID: true
  hostIPC: true

  containers:
  - name: dangerous
    image: ubuntu

    securityContext:
      privileged: true

      allowPrivilegeEscalation: true

      capabilities:
        add:
        - SYS_ADMIN
        - NET_ADMIN

      seccompProfile:
        type: Unconfined
```

Combined:

```text
hostNetwork
    +
hostPID
    +
privileged
    +
SYS_ADMIN
    +
Unconfined
```

is an extremely powerful workload.

# 41. Pod Security vs Pod Security Policy

This is important for interviews.

### Old mechanism

```text
PodSecurityPolicy (PSP)
```

PSP was deprecated in Kubernetes 1.21 and removed in Kubernetes 1.25. ([Kubernetes][7])

### Current built-in mechanism

```text
Pod Security Admission
```

along with:

```text
Pod Security Standards
```

So don't say:

> "I configure PSP."

for a modern Kubernetes cluster.

Instead:

> "I use Pod Security Admission with the Baseline or Restricted Pod Security Standard."

# 42. PSS vs PSA vs SecurityContext

Memorize this table:

| Concept              | Purpose                             |
| -------------------- | ----------------------------------- |
| SecurityContext      | Configure runtime security          |
| PSS                  | Define security standards           |
| PSA                  | Enforce PSS                         |
| RBAC                 | Control who can perform API actions |
| NetworkPolicy        | Control network communication       |
| Seccomp              | Restrict syscalls                   |
| AppArmor             | Restrict application behavior       |
| SELinux              | Mandatory access control            |
| Admission Controller | Validate/mutate API requests        |

# 44. Practical Production Baseline

For normal application namespaces, a good starting point is:

```yaml
apiVersion: v1
kind: Namespace

metadata:
  name: production

  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

Then migrate toward:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

where applications support it.

# 45. Production Pod Hardening Checklist

For an application Pod, aim for:

```text
☑ Run as non-root
☑ Use a dedicated UID
☑ Use a dedicated ServiceAccount
☑ Disable ServiceAccount token if unnecessary
☑ Drop Linux capabilities
☑ Add only required capabilities
☑ allowPrivilegeEscalation=false
☑ readOnlyRootFilesystem=true where possible
☑ RuntimeDefault seccomp
☑ Appropriate AppArmor/SELinux
☑ Don't use privileged=true
☑ Don't use hostNetwork
☑ Don't use hostPID
☑ Don't use hostIPC
☑ Don't use hostPath
☑ Use NetworkPolicy
☑ Set CPU/memory requests
☑ Set CPU/memory limits where appropriate
☑ Use ResourceQuota
☑ Use LimitRange
☑ Use trusted/minimal images
☑ Scan images
☑ Don't run unnecessary root processes
☑ Don't expose unnecessary ports
☑ Keep Kubernetes/API credentials out unless needed
```

# 47. How to Troubleshoot PSA Rejection

Suppose:

```bash
kubectl apply -f pod.yaml
```

returns:

```text
Error from server:
pods "myapp" is forbidden:
violates PodSecurity "restricted:latest"
```

First inspect the namespace:

```bash
kubectl get ns production --show-labels
```

Then inspect the Pod:

```bash
kubectl apply -f pod.yaml --dry-run=server
```

Look for:

```yaml
privileged: true
```

or:

```yaml
runAsNonRoot: false
```

or:

```yaml
allowPrivilegeEscalation: true
```

or:

```yaml
capabilities:
  add:
    - SYS_ADMIN
```

or:

```yaml
hostNetwork: true
```

or:

```yaml
hostPath:
```

or:

```yaml
seccompProfile:
  type: Unconfined
```

Then fix the Pod rather than simply weakening the policy.

# 48. A Useful Interview Scenario

### Interviewer:

> A developer says their Pod doesn't work with Restricted PSS. What do you do?

Don't immediately say:

> "Change Restricted to Baseline."

Instead:

```text
1. Identify the exact PSA violation
        ↓
2. Determine why the application needs it
        ↓
3. Remove unnecessary privilege
        ↓
4. Replace broad privilege with specific capability
        ↓
5. Test with warn/audit
        ↓
6. Enforce Restricted
```

For example:

Developer says:

> "We need privileged=true."

You investigate.

Maybe they actually need:

```text
NET_BIND_SERVICE
```

Then replace:

```yaml
privileged: true
```

with:

```yaml
capabilities:
  add:
    - NET_BIND_SERVICE
```

That is the **least privilege** approach.

# 49. The Most Important Security Principle

Always follow:

> **Don't give the container more privilege than it needs.**

Bad:

```yaml
privileged: true
```

Better:

```yaml
capabilities:
  add:
    - NET_ADMIN
```

Even better:

```yaml
capabilities:
  drop:
    - ALL
```

and add nothing if possible.

The ideal:

```text
Application
    ↓
non-root
    ↓
no unnecessary capabilities
    ↓
no privilege escalation
    ↓
read-only filesystem
    ↓
seccomp
    ↓
AppArmor/SELinux
    ↓
NetworkPolicy
    ↓
minimal RBAC
```
